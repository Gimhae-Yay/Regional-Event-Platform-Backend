# 로컬스탬프 파일럿 범위 및 콘텐츠 공통 모델 메모

## 1. 결정 사항

첫 파일럿은 **행사·체험 예약과 현장 체크인**만 검증한다.

```text
행사·체험 등록 → 탐색 → 회차 예약·결제 → 운영자 QR 체크인 → 인증 후기 → 다음 예약용 쿠폰 사용
```

쿠폰은 MVP에 포함한다. 방문 인증 완료자에게 다음 행사·체험 예약에 사용할 수 있는 단일 쿠폰을 발급한다. 스탬프와 미션은 쿠폰의 재방문 효과를 확인한 뒤 도입한다.

### 첫 파일럿에 포함하지 않는 범위

- 가게·관광지의 현장 QR 방문 인증
- 일반 음식점 좌석 예약
- 스탬프북, 지역 미션, 포인트
- 매장 현장 할인, 복수 쿠폰 조합, 판매자 자동 정산

가게·관광지는 다음 단계의 인증 대상으로 미루되, 나중에 기능을 붙일 수 있도록 콘텐츠의 공통 데이터 구조는 처음부터 둔다.

## 2. 콘텐츠 모델 원칙

### 공통 `Content`를 기준으로 확장한다

행사·체험, 가게, 관광지를 각각 완전히 분리된 최상위 모델로 만들지 않는다. 모든 콘텐츠는 지역·운영자·공개 상태·기본 소개를 공유하는 `Content`를 가진다.

| 공통 필드 예시 | 설명 |
| --- | --- |
| `contentId`, `regionId`, `operatorId` | 콘텐츠 식별, 소속 지역, 운영 주체 |
| `contentType` | `EVENT_EXPERIENCE`, `STORE`, `ATTRACTION` |
| `status` | 등록 요청, 승인, 공개, 종료, 반려 상태 |
| 제목, 소개, 대표 이미지 | 공통 탐색·상세 정보 |
| 주소, 위치 정보, 연락처, 운영 시간 | 장소·운영 기본 정보 |
| 생성·수정·종료 시각 | 운영 이력과 공개 제어 |

### 유형별 필드는 별도 상세 모델로 둔다

공통 테이블에 모든 유형의 필드를 넣어 다수의 빈 컬럼을 만드는 방식은 피한다. 예약이나 인증처럼 운영 규칙에 영향을 주는 값은 자유 형식 JSON보다 명시적 필드·테이블로 관리한다.

| 콘텐츠 유형 | 상세 모델 / 추가 정보 | 파일럿 구현 여부 |
| --- | --- | --- |
| 행사·체험 | `EventExperienceDetail`, 회차, 정원, 가격, 예약 마감, 연령·준비물, 취소 기준 | **구현** |
| 가게 | `StoreDetail`, 업종, 메뉴/서비스, 상시 운영 정보, 현장 인증 설정 | 구조만 고려, 인증 기능은 보류 |
| 관광지 | `AttractionDetail`, 관람 시간, 입장 정보, 휴무일, 현장 인증 설정 | 구조만 고려, 인증 기능은 보류 |

가게·관광지용 상세 테이블을 첫 파일럿에서 실제로 모두 만들 필요는 없다. 다만 `Content`의 유형과 공통 필드는 미리 두고, 이후 상세 모델과 검증 규칙을 추가한다.

## 3. 예약·방문·쿠폰 연결 원칙

첫 파일럿에서는 예약형 행사·체험만 거래와 방문 인증의 대상이다.

| 모델 | 핵심 관계와 역할 |
| --- | --- |
| `Content` | 행사·체험을 포함한 모든 지역 콘텐츠의 공통 부모 |
| `EventSession` | 행사·체험 콘텐츠의 날짜·회차·정원·가격. `Content`에만 연결 |
| `Reservation` | 사용자와 회차의 예약 관계. 정원 홀드·예약 상태를 관리 |
| `Payment` | 예약 결제 시도·승인·취소 상태를 관리. 결제사 콜백을 멱등 처리 |
| `Visit` | 실제 체크인 기록. `contentId`를 공통으로 가지며, 파일럿에서는 `reservationId`가 반드시 존재 |
| `Coupon` | 발급 기준이 된 `visitId`와 사용자, 적용 조건, 유효 기간, 사용 상태를 관리 |
| `Review` | 인증된 `visitId`에 연결. 방문하지 않은 사용자는 생성 불가 |

권장 관계는 다음과 같다.

```text
Content(행사·체험) 1 ─ N EventSession 1 ─ N Reservation 1 ─ 1 Payment
                                             └──── 0..1 Visit ─ 0..1 Coupon
                                                            └──── 0..1 Review
```

`Visit`은 앞으로 가게·관광지 인증으로 확장할 수 있게 `contentId`와 `verificationMethod`를 공통으로 둔다. 다만 첫 파일럿의 허용 값은 `RESERVATION_QR`뿐이며, `reservationId` 없는 방문 기록은 만들지 않는다.

## 4. 구현 경계와 확장 방식

### 파일럿에서 강제할 규칙

- `contentType = EVENT_EXPERIENCE`인 콘텐츠에만 회차와 예약을 생성한다.
- 예약 확정 전에는 QR을 발급하지 않는다.
- 운영자는 자신이 소유한 콘텐츠의 예약 QR만 체크인할 수 있다.
- 동일 예약은 한 번만 체크인하며, 재시도에는 기존 결과를 반환한다.
- 쿠폰은 체크인 완료 후에만 발급하고, 다음 행사·체험 예약 결제에 한 장만 적용한다.
- 스탬프·미션 관련 테이블과 API는 구현하지 않는다.

### 다음 단계에서 추가할 변경

| 단계 | 추가 범위 | 공통 모델을 활용하는 방식 |
| --- | --- | --- |
| 2단계 | 가게·관광지 상세 정보와 현장 방문 인증 | `Content`에 유형별 상세 모델을 연결하고, `Visit.verificationMethod`에 회전 QR 또는 운영자 확인 방식을 추가 |
| 3단계 | 스탬프북·지역 미션 | 인증된 `Visit`을 스탬프·미션 달성 조건의 근거로 사용 |
| 4단계 | 매장 쿠폰·혜택 지갑·정산 | `Coupon`의 발급·사용 이력을 확장하고, 사용처와 정산 주체를 추가 |

## 5. 기획·개발 시 확인할 질문

1. 첫 파일럿에서 쿠폰은 모든 체크인에 같은 조건으로 발급할지, 행사·회차별로 다르게 발급할지 결정한다.
2. 쿠폰은 할인 금액/비율 중 하나로 고정할지, 콘텐츠별 조건을 둘지 결정한다.
3. 예약 취소·환불 시 사용 쿠폰을 복구할지와 그 기준 시각을 취소 정책에 명시한다.
4. 가게·관광지 도입 전, 정적 QR 사진 공유를 막을 회전 QR 또는 운영자 확인 절차를 선택한다.
5. 초기 공개 지역과 참여 운영자 수, 운영 가능한 회차 수를 정해 파일럿 성공 지표의 분모를 고정한다.

이 메모의 원칙은 **현재 구현 범위는 좁히되, 공통 콘텐츠·방문 데이터는 이후 유형과 리워드 기능을 안전하게 붙일 수 있게 설계한다**는 것이다.
