# 후기 삭제 원문 파기 스케줄러 구현 명세

| 항목 | 내용 |
| --- | --- |
| 대상 릴리스 | P0 |
| 관련 요구사항 | [FR-08](review.md#fr-08-인증-후기), `REV-04`, [AC-14](../p0-spec.md#9-테스트-및-출시-수용-기준) |
| 소유 도메인 | 인증 후기 |
| 기준 문서 | [인증 후기](review.md), [ADR-0012](../adr/0012-retain-author-unlinked-reviews-and-visits-after-withdrawal.md), [ADR-0035](../adr/0035-purge-deleted-review-text-daily-at-midnight.md) |

## 1. 목적과 범위

이 문서는 삭제된 인증 후기의 별점·본문 원문을 보존 기간 후 영구 파기하는 내부 배치 작업의 구현 계약이다.
HTTP API나 외부 이벤트를 제공하지 않으며, `review` 행과 방문 연결을 삭제하지 않는다.

## 2. 실행 계약

| 항목 | 계약 |
| --- | --- |
| 실행 주체 | Spring Scheduler |
| 실행 시각 | 매일 `Asia/Seoul` 자정 (`0 0 0 * * *`) |
| 시간 기준 | 대상 판정은 애플리케이션 서버 시각이 아닌 DB 현재 시각을 사용한다. |
| 처리 단위 | 최대 100건의 배치를 하나의 트랜잭션으로 처리하고, 대상이 남아 있으면 다음 배치를 실행한다. |
| 종료 조건 | 조회한 대상이 없거나 마지막 배치가 100건보다 적으면 종료한다. |
| 외부 의존성 | MySQL만 사용한다. Redis 분산 락, 외부 큐와 Outbox는 사용하지 않는다. |

스케줄러 활성화와 cron 표현식은 운영 설정으로 분리할 수 있지만, P0 기본값은 위 표의 `Asia/Seoul` 자정이다.
운영 설정을 바꿔도 대상 조건·파기 범위·조건부 갱신 계약은 바꾸지 않는다.

## 3. 대상과 파기 동작

### 대상 조건

다음 조건을 모두 만족하는 후기만 선택한다.

- `status = DELETED`
- `deleted_at + 30일 <= DB 현재 시각`
- `rating IS NOT NULL OR review_text IS NOT NULL`

`PUBLISHED` 후기, 삭제 후 30일이 지나지 않은 후기, 이미 `rating IS NULL AND review_text IS NULL`인 후기는
대상이 아니다.

### 조건부 갱신

각 대상은 동일한 조건을 `WHERE` 절에 다시 포함한 단일 갱신으로 처리한다.

```text
UPDATE review
SET rating = NULL,
    review_text = NULL
WHERE review_id = :reviewId
  AND status = 'DELETED'
  AND deleted_at + INTERVAL 30 DAY <= DB 현재 시각
  AND (rating IS NOT NULL OR review_text IS NOT NULL)
```

갱신 성공은 원문이 파기됐음을 뜻한다. 갱신 건수 `0`은 다른 실행이 먼저 파기했거나 대상 조건이 더는 성립하지
않음을 뜻하며 오류로 취급하지 않는다. `review_id`, `visit_id`, `user_id`, `content_id`, `status`, `created_at`,
`updated_at`, `deleted_at`, `author_unlinked_at`은 이 작업에서 변경하지 않는다.

## 4. 정합성·실패 처리

- 각 배치는 독립 트랜잭션이다. 배치 중 오류가 나면 해당 배치의 갱신을 모두 롤백하고 이후 배치를 실행하지 않는다.
- 다음 날 실행은 미파기 대상을 같은 조건으로 다시 조회하므로 별도 재시도 큐·실패 상태를 저장하지 않는다.
- 여러 인스턴스가 같은 시간에 실행돼도 조건부 갱신으로 한 실행만 원문을 바꾼다. 중복 조회·0건 갱신은 허용한다.
- 후기 삭제·회원 탈퇴와 경합할 수 있다. 삭제가 완료되고 보존 기간이 지나기 전에는 대상이 아니며, 탈퇴는 이미
  삭제된 후기의 `deleted_at`·원문 파기 시계를 변경하지 않는다.
- 스케줄러가 중단되거나 DB를 사용할 수 없으면 파기하지 않은 원문은 유지한다. 복구 뒤 다음 자정 실행에서 다시
  처리한다. 이미 파기한 원문은 어떤 실패 경로에서도 복구하지 않는다.

## 5. 관측과 보안

실행 시작·종료와 배치별 조회·파기·0건 갱신·실패 건수, 소요 시간만 구조화 로그와 운영 지표로 남긴다. 후기
본문·별점·회원·방문·콘텐츠 식별자는 로그와 예외 메시지에 남기지 않는다. 이 작업은 상태 전이가 아니므로
새 `audit_event`를 만들지 않는다.

## 6. 구현 경계

- 스케줄러는 실행 시각과 배치 반복만 책임지고, 대상 선택과 원문 파기는 후기 도메인 Service·Repository에 위임한다.
- 파기 Service의 공개 메서드는 배치 단위 쓰기 트랜잭션을 연다.
- Repository는 DB 현재 시각을 이용해 대상 후보를 제한 조회하고 조건부 갱신을 수행한다.
- JPA 엔티티를 스케줄러 로그·응답 모델로 직접 노출하지 않는다.

## 7. 완료 기준

- `deleted_at + 30일` 전의 후기와 `PUBLISHED` 후기는 어떤 배치에서도 원문이 유지된다.
- 정확히 30일이 지난 `DELETED` 후기는 다음 자정 실행에서 `rating`, `review_text`만 `NULL`이 된다.
- 이미 원문이 `NULL`인 후기를 반복 실행해도 다른 컬럼과 상태가 변하지 않는다.
- 두 스케줄러 실행이 경합해도 원문 외의 데이터가 변하지 않고, 결과는 한 번 파기한 것과 같다.
- 배치 오류는 해당 배치의 변경을 롤백하며 다음 날 재시도로 파기할 수 있다.
- 운영 로그·지표와 예외에 후기 원문, 별점, 회원·방문·콘텐츠 식별자가 포함되지 않는다.
