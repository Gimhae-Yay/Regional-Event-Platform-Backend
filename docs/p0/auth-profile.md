### 기능 범위

- 회원 가입과 로그인을 제공한다.
- 방문자, 운영자, 지역 관리자 역할을 구분한다.
- 서버는 신규 콘텐츠 생성에는 승인된 운영자 역할과 담당 `region_id`를 검증하고,
  기존 자원 접근에는 역할, 담당 `region_id`, 운영자-콘텐츠 소유 관계를 함께 검증한다.
- 지역 관리자는 담당 지역만, 운영자는 자신에게 연결된 콘텐츠·회차·예약만 조회·처리한다.

가입·로그인의 요청·응답, validation, status와 오류 코드는
[API 명세서](../api-specification.md)에서 별도 계약한다.

### 역할과 권한

| 역할 | 허용 범위 |
| --- | --- |
| 방문자 | 공개 지역 선택, 콘텐츠 탐색, 본인 무료 예약, 본인 QR 제시, 작성자 연결이 유지되는 본인 인증 후기 관리 |
| 운영자 | 승인된 담당 지역 콘텐츠 생성, 소유 콘텐츠·회차 등록, 수정본 제출·철회, 전체 콘텐츠 철회 요청, 회차 취소, 마스킹된 예약자 조회와 체크인 |
| 지역 관리자 | 담당 지역 운영자 승인·반려, 콘텐츠·수정본 승인·반려, 운영 중단·전체 콘텐츠 철회 승인, 상태별 공개 전 삭제, QR 예외 건의 마스킹된 예약자 단건 조회 |

모든 데이터와 권한은 지역과 소유 관계로 격리한다.
현재 MVP에는 전체 관리자 역할이나 지역 범위를 우회하는 권한을 제공하지 않는다.
김해시·동해시와 각 최초 지역 관리자 연결은 배포 전 승인된 초기화 절차로 준비하고 수행 결과를 감사 가능하게 남긴다.
일반 API에서는 지역 생성, 지역 관리자 임명·변경과 공통 운영 기준 변경을 허용하지 않는다.
일반 운영자 신청·승인은 지역 관리자의 런타임 유스케이스이며 배포 초기화에 포함하지 않는다.
초기화와 권한 경계의 기술 결정은
[ADR-0009](../adr/0009-exclude-platform-admin-from-initial-mvp.md)를 따른다.

### 권한 및 개인정보 정책

#### `AUTH-01`

서버는 신규 콘텐츠 생성에서 승인된 운영자 역할과 담당 `region_id`를 검증하고,
기존 자원 요청에서는 역할, 담당 `region_id`, 운영자-콘텐츠 소유 관계를 검증한다.
지역 관리자는 담당 지역만 조회·변경할 수 있고, 운영자는 소유 콘텐츠·회차·예약만 조회·처리할 수 있다.
지역과 소유 관계는 각 행위에 필요한 범위 조건이며 그 자체로 행위 권한을 부여하지 않는다.
실제 요청은 [역할과 권한 표](#역할과-권한)와 각 소유 정책이 허용한 행위도 함께 충족해야 한다.

#### `AUTH-04`

현재 MVP에는 전체 관리자 역할과 지역 범위를 우회하는 전역 관리 API를 두지 않는다.
김해시·동해시 지역과 최초 지역 관리자 연결은 배포 전 승인된 초기화 절차로 준비하고
수행 결과를 감사 가능하게 남긴다. 일반 API에서는 지역 생성, 지역 관리자 임명·변경과
공통 운영 기준 변경을 허용하지 않는다.

#### `PRV-01`

P0 셀프 탈퇴는 운영자·지역 관리자 역할과 콘텐츠 소유 관계가 없는 방문자 회원에게만 허용한다.
운영 역할 또는 소유 관계가 남은 계정의 셀프 탈퇴는 거부하며 역할 해제·담당 지역 변경·소유권 이전을 포함한
별도 오프보딩은 P0 범위에 포함하지 않는다.
방문자 회원 탈퇴 시 자격 증명, 프로필, 이름·연락처와 직접 사용자 식별자를 파기한다.
법령에 따라 보존해야 하는 거래기록은 운영 데이터와 분리해 법정 기간 동안 보관하며,
`PRV-02`에 따른 작성자 연결 제거 후기와 방문 사실은 회원정보와 분리된 운영 데이터로 유지한다.

#### `PRV-02`

탈퇴 유스케이스의 첫 변경은 회원 행에 대한 `ACTIVE → WITHDRAWING` 조건부 갱신이다. 영향 행이 한 건인
트랜잭션만 탈퇴 처리권을 얻으며, 이 갱신과 모든 MySQL 연결 제거·계정 파기는 하나의 MySQL 트랜잭션에서 처리한다.
MySQL 커밋 전에 Redis 원자 스크립트로 활성 Refresh Token 계열 전체를 폐기하고 사용자→활성 계열 인덱스를
제거한다. Redis 폐기가 실패하면 MySQL 트랜잭션을 롤백하고 사용자에게 재시도를 요청한다.
홀드·예약 확정·QR·후기처럼 회원이 시작하는 변경 명령도 도메인 상태를 바꾸기 전에 같은 회원 행을
`FOR UPDATE`로 읽거나 동등한 조건부 갱신으로 잠근 뒤 현재 상태를 확인한다.
탈퇴 트랜잭션이 먼저 회원 행을 갱신하면 이후 명령은 해당 행의 잠금 해제 뒤
`WITHDRAWING` 또는 계정 부재로 거부되고, 다른 명령이 먼저 커밋되면 탈퇴 트랜잭션이 그 결과를 포함해
정리한다.

탈퇴 처리권을 얻은 트랜잭션은 `ACTIVE` 홀드를 `INVALIDATED`로 전환하고, 아직 체크인하지 않은
`CONFIRMED` 예약을 `CANCELLED`로 전환하며 미사용 QR을 즉시 무효화한다. 홀드 무효화는 차감한 정원을
성공한 최초 전이에서 한 번 복구한다. 예약 취소는 회차 시작 전이면 정원을 한 번 복구하고 시작 이후에는
복구하지 않는다.
운영자 승인 신청이 있으면 `PENDING` 신청을 `CANCELLED`로 종결하고 모든 신청 상태에서 신청자 연결과
사업자 개인정보를 제거한다. 승인과 탈퇴가 경합하면 `AUTH-02`의 활성 회원·신청 상태 조건으로 둘 중 하나만 성공한다.
이후 후기·방문의 직접 사용자 연결과 예약·홀드·감사·멱등 기록을 통한 시스템 관리 간접 역참조 경로를
비가역적으로 제거한다. 기존 `PUBLISHED` 후기의 별점·텍스트·공개 상태는 유지하고 작성자를
공통 표시인 `탈퇴한 사용자`로 대체한다. 개별 방문의 콘텐츠·회차·체크인 시각과
지역·콘텐츠·회차별 집계는 유지한다. 재식별 매핑과 사용자별 안정 가명을 남기지 않으며,
재가입 계정에 과거 후기의 관리 권한을 복구하지 않는다. 이미 `DELETED`인 후기는 복구하지 않고
기존 삭제 시점부터 30일 후 원문을 파기한다.

Redis 폐기 전에 발생한 탈퇴 트랜잭션 예외는 `WITHDRAWING` 전환을 포함해 전체를 롤백하고 사용자에게 재시도
가능한 실패를 반환한다. Redis 폐기 성공 뒤 MySQL 종결이 실패하면 MySQL 변경만 롤백하고 기존 Refresh Token은
복구하지 않는다. 계정은 `ACTIVE`로 남지만 사용자는 다시 로그인해 새 계열을 발급받은 뒤 탈퇴를 재시도한다.
처리 중 재시도 키·별도 회원 매핑·영구 탈퇴 작업 레코드는 저장하지 않는다. 모든 종결·연결 제거가 성공하면
계정 행을 파기하며 사용자별 `WITHDRAWN` 레코드는 남기지 않는다. 커밋 성공 뒤 응답만 유실된 경우에는 개인별
완료 결과를 보관하지 않으므로 계정 부재와 세션 무효 상태를 최종 상태로 취급한다.

탈퇴 후 작성자 연결 제거와 보존 데이터의 불변 조건은
[ADR-0012](../adr/0012-retain-author-unlinked-reviews-and-visits-after-withdrawal.md)와
[ADR-0017](../adr/0017-serialize-withdrawal-with-conditional-user-state.md),
[ADR-0023](../adr/0023-manage-refresh-token-revocation-in-redis.md)를 따른다.

##### 탈퇴 후 관계 변환

| 데이터·관계 | 제거·치환 | 보존 | 완료 후 허용되는 연결 |
| --- | --- | --- | --- |
| 계정·프로필·자격 증명 | 계정 식별자, 이름·연락처, 인증 자격 증명 파기 | 법정 보존 대상은 분리 저장 | 운영 데이터에서 회원으로 연결하지 않음 |
| 운영 역할·소유 관계 | 운영 역할 또는 소유 관계가 있으면 셀프 탈퇴 거부 | 기존 역할·담당 지역·owner 관계 | P0 오프보딩 절차 없음 |
| 운영자 승인 신청 | `PENDING`은 `CANCELLED`로 종결하고 모든 상태의 신청자 연결·사업자 개인정보 제거 | 요청 지역, 비개인 상태·처리 사유·시각 | 회원·프로필·requestId로 이어지는 연결 금지 |
| 홀드·예약·QR | 상태 종결 뒤 회원 식별 필드와 사용자 기반 멱등 연결 제거, QR 무효화 | 비개인 상태·회차·인원과 예약-방문 중복 방지 연결 | 예약-방문 연결은 어느 쪽에서도 회원으로 이어지지 않을 때만 허용 |
| 방문 | 회원 식별 경로 제거 | content, session, checked_at, 비개인 예약 중복 방지 연결 | 콘텐츠·회차 및 작성자 연결 제거 후기와만 연결 |
| 후기 | 작성자 연결 제거, 표시를 공통 `탈퇴한 사용자`로 치환 | visit, content, rating, text, status, deleted_at | 방문 연결은 회원으로 이어지지 않아야 함 |
| 감사·로그 | actor를 공통 `WITHDRAWN_MEMBER`로 치환하고 requestId의 회원 상관관계 제거 | 비개인 entity·transition·reason·timestamp | 탈퇴 방문자별 tombstone·안정 가명 금지 |
| 멱등·탈퇴 처리 | 응답의 회원 정보와 사용자 기반 멱등 연결 제거, 탈퇴 처리용 재시도 키·회원 매핑은 저장하지 않음 | 비개인 도메인 결과와 집계 | 실패한 트랜잭션은 전체 롤백 뒤 사용자가 새 탈퇴 요청으로 재시도 |

### 기능 범위

- 지역 관리자는 신청자의 사업자 정보와 요청 지역을 수동 확인한 뒤 운영자를 승인·반려한다.
- 승인된 운영자에게 역할과 담당 지역을 부여하고, 최초 콘텐츠 생성 시 서버가 인증 운영자를 소유자로 설정한다.
- 운영자와 지역 관리자에게 노출하는 예약자 이름과 연락처는 확정 형식으로 마스킹한다.

최초 콘텐츠 소유 관계의 생성과 금지 범위는
[ADR-0011](../adr/0011-bootstrap-operator-ownership-on-content-creation.md)을 따른다.

### 운영자 승인 흐름

- **주체:** 지역 관리자
- **선행 조건:** 담당 `region_id`가 지역 관리자 계정에 부여돼 있다.

1. 인증된 신청자가 사업자 정보와 운영을 요청할 지역을 제출한다.
2. 담당 지역 관리자는 자기 지역의 요청만 검토해 승인하거나 사유와 함께 반려한다.
3. 승인 시 운영자 역할과 담당 `region_id`를 부여하며 아직 존재하지 않는 콘텐츠 소유 관계는 만들지 않는다.
4. 승인된 운영자가 첫 `PENDING` 콘텐츠를 생성하면 서버가 담당 지역을 검증하고 현재 인증 운영자를 소유자로 설정한다.
5. 이후 콘텐츠·회차·예약 작업은 저장된 `region_id`와 `operator_id`로 범위를 제한한다.
6. 임의 소유자 지정, 타 지역 콘텐츠 생성과 P0에서의 소유권 이전·재배정 요청은 거부한다.

### 운영자 승인·정보 마스킹 정책

#### `AUTH-02`

지역 관리자는 운영자 신청의 사업자 정보와 요청 지역을 수동 확인해 승인·반려하고 처리자·시각·사유를 기록한다.
활성 회원만 신청할 수 있고, 담당 지역 관리자만 `PENDING → APPROVED` 또는 `PENDING → REJECTED`로
심사 종결할 수 있다. 승인 시 신청자가 여전히 활성 상태인지 조건으로 확인하고 운영자 역할과 담당 지역을
하나의 트랜잭션에서 함께 부여하되 콘텐츠 소유 관계는 만들지 않는다.
회원 탈퇴가 먼저 시작되면 시스템이 `PENDING → CANCELLED`로 종결해 이후 심사를 거부한다.
승인이 먼저 성공해 역할이 부여되면 운영 역할 계정의 셀프 탈퇴 조건을 충족하지 못하므로 탈퇴 시작을 거부한다.
같은 결정의 반복 요청은 기존 결과를 반환하고 반대 결정으로의 재전이는 거부한다.
반려 뒤 다시 신청하려면 새 신청을 생성하며, 승인 전 신청자는 운영자 기능을 사용할 수 없다.

#### `AUTH-03`

운영자의 소유 콘텐츠 예약 목록·번호 조회와 지역 관리자의 담당 지역 QR 예외 단건 조회 응답은
예약자 이름을 `김*수`, 연락처를 `010-****-1234` 형식으로 마스킹한다.

#### `AUTH-05`

승인된 운영자가 담당 지역에 콘텐츠를 생성하면 서버가 인증 actor와 승인된 담당 지역으로
`operator_id`와 `region_id`를 설정한다. 클라이언트의 소유자 지정·변경을 신뢰하지 않으며
P0에는 콘텐츠 소유권 이전·재배정 API를 두지 않는다.
