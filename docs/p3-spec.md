# 로컬스탬프 P3 명세

| 항목 | 내용 |
| --- | --- |
| 참고 문서 | [로컬스탬프 제품 PRD](local-stamp-platform-prd.md) |

| 기준일 | 2026-07-27 |
| 대상 릴리스 | 알림 이벤트와 중요 요청의 남용 방지 |
| 문서 성격 | `FR-12`, `FR-13`을 P3 범위로 분리한 새 기능 계약 |

> `FR-12`와 `FR-13`은 P0 구현·완료 범위에 포함하지 않는다.
> 이 문서는 두 요구사항의 P3 구현 계약을 새로 정의하며, 알림 채널과 요청 제한 수치는 구현 전 별도 결정한다.

## 1. 문서 사용 원칙

- `FR-12`와 `FR-13`은 이 문서와 `p3/`의 기능 소유 문서를 기준으로 구현한다.
- 알림 이벤트의 저장은 핵심 거래 상태 변경과 원자적으로 처리하고, 외부 전달 실패가 거래를 롤백시키지 않게 한다.
- 알림의 실제 전달 채널과 수신 동의는 구현 전 정책·ADR·API 계약으로 확정한다.
  Outbox 재시도·점유·보관의 기본값과 변경 원칙은 ADR-0007을 적용한다.
- 요청 제한은 로그인, 예약 확정, QR 스캔에만 적용한다. 다른 API로 임의 확대하지 않는다.
- 요청 제한 임계값, 키 산정, Redis 장애 시 동작과 `429` 응답 형식은 구현 전 API·운영 계약으로 확정한다.

## 3. P3 제품 목표

P3는 거래 완료 후 필요한 알림·분석 소비자가 신뢰할 수 있는 이벤트를 받도록 하고,
로그인·예약 확정·QR 스캔처럼 남용 시 서비스 신뢰성에 영향을 주는 경로를 제한하는 단계다.

핵심 흐름은 다음과 같다.

```text
예약 상태 변경 또는 체크인 성공
→ 거래와 함께 알림 이벤트 저장
→ 재시도 가능한 비동기 전달

로그인·예약 확정·QR 스캔 요청
→ 사용자·IP 기준 허용량 확인
→ 허용 또는 429 응답
```

### 3.1 핵심 목표

1. **이벤트 유실 방지:**
   거래가 성공했는데 알림 이벤트가 사라지는 구간을 없앤다.
2. **중복 전달 안전성:**
   최소 한 번 전달과 재시도를 전제로 소비자 효과가 중복되지 않게 한다.
3. **중요 경로 보호:**
   동일 사용자 또는 IP의 과도한 로그인·예약 확정·QR 스캔을 통제한다.
4. **운영 가능성:**
   이벤트 지연·실패와 제한 발생을 관찰하고, 정상 현장 운영을 해치지 않도록 기준을 조정한다.

## 4. P3 범위

### 4.1 포함 범위

- `FR-12` 예약 확정, 행사 전 리마인드, 취소·변경, 체크인 성공에 대한 알림 이벤트 발행
- `FR-13` 로그인, 예약 확정, QR 스캔의 사용자·IP 기준 요청 제한과 `429` 정책

### 4.2 비목표

- 이메일·문자·푸시 등 특정 알림 전달 채널의 선택·구축
- 광고·마케팅·추천 알림
- 로그인·예약 확정·QR 스캔 이외 API의 요청 제한
- Redis 분산 락을 통한 예약 정원 동시성 제어
- P1 거래·혜택 정책 또는 P2 웹·대시보드 정책 변경

## 6. 공통 기술·운영 규칙

### 6.1 이벤트 전달

- 거래 상태 변경과 Outbox 이벤트 저장은 같은 MySQL 트랜잭션에서 성공하거나 함께 롤백한다.
- 전달은 최소 한 번을 보장하며, 소비자는 불변 `event_id`로 중복 효과를 차단한다.
- 전달 실패는 원래 거래를 되돌리지 않고 재시도·격리·수동 처리 이력으로 관리한다.
- Outbox의 점유, 재시도, 실패 격리, 보관·정리의 기반 원칙은 [ADR-0007](adr/0007-use-transactional-outbox-with-spring-scheduler.md)을 따른다.

### 6.2 요청 제한

- 제한 키는 사용자 식별자와 IP 기준을 함께 고려하며, 인증 전·후 경로의 키 구성을 API 계약으로 명시한다.
- 허용량 초과 요청은 핵심 동작을 실행하지 않고 `429` 응답을 반환한다.
- 제한 결정에 쓰는 Redis 키·카운터에는 토큰·비밀번호·QR 원문을 저장하지 않는다.
- 임계값은 부하·현장 운영 검증 결과를 근거로 설정하며, 제한 발생과 우회 시도를 관찰한다.

## 7. 구현 전 확정 항목

| 항목 | 구현 전 확정할 내용 | 결정 필요 이유 |
| --- | --- | --- |
| 알림 계약 | 이벤트 유형별 payload 최소 정보, 수신자, 전달 채널과 동의·보관 정책 | 거래 데이터와 개인정보를 안전하게 분리해야 한다. |
| 이벤트 운영 기준 | ADR-0007의 재시도·점유·보관 기본값의 적용, 측정에 따른 변경과 실패 격리·수동 재처리 권한 | 이미 채택된 Outbox 계약을 유지하면서 운영 조정 절차를 명확히 해야 한다. |
| 제한 알고리즘 | 고정 창·슬라이딩 창 등 알고리즘, 사용자·IP 조합, IPv6·프록시 처리 | 정상 사용자와 남용 요청을 구분하는 기준이다. |
| 장애 처리 | Redis 장애·지연 시 허용/거부·축소 동작과 관측·복구 절차 | 보안과 가용성의 균형이 필요하다. |
| API 응답 | `429` 오류 코드, 재시도 안내, 헤더·본문·로그 공개 범위 | 클라이언트 재시도와 보안 노출을 일관되게 처리한다. |

## 8. 테스트 및 출시 수용 기준

| ID | 연결 정책 | 합격 기준 |
| --- | --- | --- |
| `P3-AC-01` | `NTF-01`, `NTF-02` | 예약 확정·취소·변경·체크인 성공과 해당 알림 이벤트 저장은 함께 커밋되거나 함께 롤백되고, 전달 실패가 이미 성공한 거래를 되돌리지 않는다. |
| `P3-AC-02` | `NTF-03`, `NTF-04` | 같은 이벤트가 재전달돼도 소비자 효과는 한 번만 발생하며, 반복 실패 이벤트는 뒤의 이벤트를 막지 않고 추적·재처리할 수 있다. |
| `P3-AC-03` | `RLT-01`, `RLT-02` | 로그인·예약 확정·QR 스캔은 사용자·IP 기준 허용량을 넘으면 핵심 동작 없이 `429`를 반환하고, 허용량 안의 정상 요청은 처리한다. |
| `P3-AC-04` | `RLT-03`, `RLT-04` | 동시 요청, 인증 전후 전환, 제한 저장소 지연·장애와 프록시 환경에서 확정된 제한 정책대로 동작하며 민감 정보를 키·로그·응답에 노출하지 않는다. |
