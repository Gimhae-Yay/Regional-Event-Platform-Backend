## 문서 사용 원칙

이 문서는 로컬스탬프의 장기 제품 방향과 현재 구현할 무료 예약 MVP를 함께 정의한다.

- 현재 무료 예약 MVP의 목표, 범위, 요구사항, 정책과 출시 수용 기준은 현재 릴리스의 구현 계약이다.
- 장기 제품 비전, 확장 로드맵과 성과 프레임은 제품이 지향하는 전체 방향이며 현재 MVP의 구현 요구사항이나 출시 수용 기준이 아니다.
- 후속 기능은 진입 조건을 충족한 뒤 정책, 기술 결정, API·DB 계약과 이슈가 승인돼야 구현 범위가 된다.
- 유저 시나리오는 주체별 이용 흐름, 기능 요구사항은 구현할 능력, 정책 카탈로그는 상태·수치·예외·처리 주체, 출시 수용 기준은 검증 결과를 정의한다.
- 같은 정책의 상세 정의는 정책 카탈로그 한 곳에 두고, 다른 영역에서는 정책 ID로 연결한다.

## 1. 요약

장기적으로 로컬스탬프는 지역의 행사·체험·가게·관광지를 한곳에서 탐색하고, 예약·결제·방문 인증·후기·쿠폰·
스탬프·지역 미션을 신뢰할 수 있는 방문 기록으로 연결하는 지역 참여 플랫폼을 지향한다.
방문자에게는 발견과 재방문 동기를, 운영자에게는 콘텐츠·예약·현장 운영 도구를,
지역 운영 주체에게는 지역별 운영과 성과 판단 근거를 제공한다.

현재 MVP는 **김해시와 동해시**의 예약형 행사·체험을 대상으로
**지역 콘텐츠 탐색 → 무료 예약 → 현장 체크인 → 인증 후기** 흐름을 제공한다.
사용자가 회차 정원을 10분간 홀드해 무료 예약을 확정하면 일회성 서명 QR을 발급하고,
권한 있는 운영자의 현장 체크인으로 방문 기록이 생성된 경우에만 후기를 작성할 수 있다.
콘텐츠는 운영자 등록, 지역 관리자 승인, 예약된 시각의 자동 공개 과정을 거치며 모든 데이터와 권한은 지역과 소유 관계로 격리한다.

초기 MVP는 콘텐츠 수나 사업 KPI보다 초과 예약·중복 처리 방지, QR과 방문 기록의 신뢰성,
인증 후기 자격, 지역 권한 격리와 최소 운영 가능성을 기술적으로 검증한다.
유료 예약·결제, 쿠폰, Redis 분산 락, 가게·관광지 현장 인증, 스탬프북, 지역 미션,
AI 추천과 고도화된 관리자 대시보드는 검증된 데이터와 운영 역량을 진입 조건으로 삼아 후속 제품 단계에서 확장한다.

## 2. 배경과 문제 정의

### 2.1 사용자 문제

- 지역 행사와 체험 정보가 SNS, 지도, 커뮤니티 등 여러 채널에 흩어져 있어 한 지역 안에서 비교하기 어렵다.
- 예약 가능 여부, 잔여 정원, 신청, 현장 참여 확인이 서로 다른 도구에서 처리되어 사용자 경험이 단절된다.
- 실제 방문 여부와 무관하게 작성된 후기는 신뢰도가 낮다.
- 예약과 실제 참여를 연결해 운영 품질을 검증할 일관된 기준이 부족하다.

### 2.2 운영자 문제

- 행사·체험 운영자는 SNS·전화·메신저·스프레드시트로 홍보, 신청, 명단, 현장 입장을 따로 관리한다.
- 회차별 초과 예약, 중복 신청, 중복 체크인, 노쇼 등 예약·현장 예외를 일관되게 처리하기 어렵다.
- 예약자와 실제 참여자를 구분하고 인증 후기를 연결하기 어렵다.

### 2.3 지역 운영 주체의 문제

- 지역 콘텐츠의 등록·승인·종료 상태가 기관과 담당자별로 흩어진다.
- 어떤 콘텐츠가 조회·예약되고 실제 방문까지 이어졌는지 비교할 공통 기준이 부족하다.
- 지역 단위 권한과 데이터 경계를 강제할 최소 운영 도구가 필요하다.

## 3. 현재 무료 예약 MVP 목표

### 3.1 핵심 목표

1. **핵심 전환 검증**  
   김해시와 동해시에서 사용자가 행사·체험을 발견하고 무료 예약한 뒤 실제 QR 체크인까지 완료할 수 있는지 검증한다.

2. **예약 및 방문 데이터의 신뢰성 확보**
   10분 정원 홀드, 예약 상태, 일회성 QR, 방문 기록을 일관되게 연결하고 중복·초과 처리를 방지한다.

3. **인증 후기 체계 검증**  
   체크인 완료 방문에만 후기 작성 권한을 부여하고 수정·삭제 정책이 정확히 동작하는지 검증한다.

4. **최소 운영 가능성 검증**
   운영자의 콘텐츠·회차 등록과 QR 체크인, 지역 관리자의 승인·반려 및 예외 조회가 최소 도구로 수행 가능한지 확인한다.

5. **다지역 격리 기반 확보**
   사용자 권한, 콘텐츠, 회차, 예약, 방문, 후기를 `region_id`와 연결해 김해시와 동해시의 데이터와 권한을 분리한다.

### 3.2 성공 판단 원칙

MVP는 사업 KPI 달성이 아니라 다음 기술 검증 질문을 자동화 테스트와 운영 시나리오로 통과할 때 성공한 것으로 본다.

- 마지막 잔여 정원에 동시 요청이 발생해도 초과 예약이 없는가?
- 홀드 만료와 예약 확정이 정원을 정확히 반영하고 재시도에도 결과가 중복 생성되지 않는가?
- 취소·만료·다른 회차·위변조 QR을 거부하고 동일 QR로 방문 기록을 중복 생성하지 않는가?
- 김해시와 동해시의 지역 권한 및 운영자 소유권이 교차 접근을 차단하는가?
- 체크인한 사용자만 후기를 작성하고 수정·삭제 수명주기를 지키는가?
- 예약자 개인정보 마스킹과 회원 탈퇴 후 파기·분리 보관 정책이 모든 경로에서 적용되는가?
- 콘텐츠의 승인, 자동 공개, 수정 심사, 운영 중단, 철회, 종료와 삭제 정책을 추적할 수 있는가?

탐색 전환율, 체크인율, 후기 작성률 등 사업 KPI는 초기 MVP의 출시·중단 판단 기준으로 사용하지 않는다.

## 4. 현재 무료 예약 MVP 범위

### 4.1 포함 범위

- 회원 가입·로그인과 방문자/운영자/지역 관리자/전체 관리자 역할 구분
- 지역 관리자의 사업자 정보·담당 지역·콘텐츠 소유 관계 확인과 운영자 수동 승인
- 김해시·동해시 공개 지역 선택과 지역별 홈
- 행사·체험 콘텐츠 목록, 필터, 상세 조회
- 운영자의 콘텐츠·회차·공개 예정 시각 등록 및 승인 요청
- 지역 관리자의 콘텐츠와 공개 예정 시각 승인·반려
- 승인된 공개 예정 시각에 시스템이 콘텐츠를 자동 공개하는 흐름
- 공개 콘텐츠 수정 요청 중 기존 공개본 유지와 승인된 수정본만 반영하는 흐름
- 지역 관리자의 공개 콘텐츠 운영 중단과 방문자 대상 중단 사유 표시
- `DRAFT` 하드 삭제, 공개 전 `PENDING`·`APPROVED` 소프트 삭제와 공개 후 삭제 금지
- 콘텐츠의 정상 종료와 운영자 철회 요청 관리
- 회차·정원 기반 무료 예약
- 10분 정원 홀드 생성, 예약 확인 시 확정, 미확정·만료 시 홀드 해제
- 사용자·예약·회차·만료 시각에 연결된 일회성 예약 QR
- 운영자 QR 스캔, 중복 방지, 예약 정보 보조 조회와 예외 사유 기록
- 방문 기록에 연결된 별점·텍스트 후기
- 예약·홀드·체크인·권한·후기 상태 전이와 실패 원인을 검증하기 위한 이벤트·로그
- 콘텐츠 승인·반려·수정 심사·운영 중단, 예약자 조회, QR 예외 처리를 위한 내부용 최소 화면 또는 보호된 운영 API

### 4.2 비목표(Non-goals)

다음 항목은 현재 MVP 범위에 포함하지 않는다.

- 가게·관광지의 비예약형 현장 QR 방문 인증
- 일반 음식점 좌석 예약
- 유료 예약, 결제 승인·웹훅·취소·환불과 결제 정합성 검증
- 쿠폰 발급·사용·복구
- Redis 분산 락을 이용한 예약 동시성 제어
- 스탬프북, 지역 미션, 포인트, 현금성 보상
- 매장 현장 할인, 다중 쿠폰 조합, 복잡한 혜택 지갑
- 여러 판매자 간 자동 정산
- 지도 기반 탐색, 추천 코스, 개인화·AI 추천
- 위치 기반 자동 인증
- 실시간 채팅, SSE 기반 대화형 탐색, RAG
- 전국 단위 공공데이터 자동 수집·정제
- 고도화된 운영자·지역 관리자 통계 대시보드
- 후기 사진, 운영자 답글, 별도 신고 화면, 지역별 후기 피드

가게·관광지는 장기 확장을 위해 공통 콘텐츠 모델에 수용하되 현재 MVP의 현장 인증 대상으로 삼지 않는다.

## 5. 사용자와 권한

| 사용자           | MVP 역할                               | 핵심 니즈                        |
|---------------|--------------------------------------|------------------------------|
| 주말 나들이 방문자    | 지역 선택, 탐색, 무료 예약, QR 제시, 인증 후기 작성    | 믿을 만한 체험을 한곳에서 찾고 예약·방문까지 완료 |
| 지역 주민·재방문 사용자 | 방문자와 동일한 무료 예약·체크인 흐름                | 익숙한 지역의 새 콘텐츠 발견과 참여         |
| 행사·체험 운영자     | 콘텐츠·회차 등록 요청, 예약자 조회, QR 체크인, 예외 기록  | 신청·명단·현장 참가를 하나의 흐름으로 관리     |
| 지역 관리자        | 담당 지역 운영자 수동 승인, 콘텐츠 승인·반려, QR 예외 조회 | 지역별 권한·공개 품질과 운영 이슈 통제       |
| 전체 관리자        | 지역 생성, 역할 부여, 공통 운영 기준 관리            | 지역 경계와 초기 운영 체계 설정           |

MVP의 최우선 고객은 **주말 나들이 방문자**, 최우선 공급자는 **예약형 행사·체험 운영자**다.
지역 관리자는 구매 고객보다 서비스 운영을 가능하게 하는 필수 주체로 본다.

## 6. 유저 시나리오(User Scenario)

시나리오는 정책을 다시 정의하지 않고 각 주체의 이용 흐름과 정책이 적용되는 지점을 설명한다.

### US-01. 방문자가 행사·체험을 탐색하고 예약한다

**주체:** 주말 나들이 방문자  
**목표:** 선택한 지역에서 원하는 행사·체험을 찾고 무료 예약을 완료한다.
**선행 조건:** 사용자가 로그인했으며 공개 지역이 1개 이상 존재한다.

**기본 흐름**

1. 사용자가 공개 지역 중 하나를 선택한다.
2. 지역 홈에서 진행 중이거나 임박한 행사·체험을 확인한다.
3. 유형과 예약 가능 여부로 콘텐츠를 필터링한다.
4. 상세 화면에서 위치, 운영 시간, 소개, 유의사항, 날짜·회차, 잔여 정원, 취소 기준, 인증 후기를 확인한다.
5. 날짜·회차·인원을 선택한다.
6. 시스템이 잔여 정원을 확인하고 정원 홀드를 생성한다.
7. 사용자가 홀드 유효 시간 안에 예약 내용을 확인하고 무료 예약 확정을 요청한다.
8. 시스템은 활성 홀드를 예약으로 전환하고 일회성 예약 QR을 발급한다.
9. 사용자는 확정된 예약 내역과 QR을 확인한다.

**예외 흐름**

- 잔여 정원이 부족하면 홀드를 만들지 않고 다른 회차 선택을 안내한다.
- 예약을 확정하지 않은 홀드는 만료시키고 정원을 복구한다.
- 만료된 홀드는 연장하거나 재사용하지 않으며 사용자는 새 홀드를 요청해야 한다.
- 동일 예약 확정 요청이 반복돼도 예약은 한 번만 생성한다.

**적용 정책:** `RSV-01`~`RSV-06`, `QR-01`

### US-02. 운영자가 행사·체험을 등록하고 지역 관리자가 승인한다

**주체:** 행사·체험 운영자, 지역 관리자  
**목표:** 예약 가능한 콘텐츠를 표준 정보와 함께 안전하게 공개한다.  
**선행 조건:** 지역 관리자가 사업자 정보·담당 지역·콘텐츠 소유 관계를 수동 확인해 운영자 계정을 승인했고 담당 권한이 부여돼 있다.

**기본 흐름**

1. 운영자가 대표 이미지, 소개, 위치, 운영 시간, 연락처, 유의사항을 입력한다.
2. 날짜·회차별 정원, 연령·준비물, 취소 기준과 공개 예정 시각을 입력한다.
3. 필수 항목 검증을 통과하면 승인 요청을 제출하고 콘텐츠를 `PENDING`으로 전환한다.
4. 담당 지역 관리자가 콘텐츠와 공개 예정 시각을 함께 검토해 승인 또는 반려한다.
5. 승인된 콘텐츠는 `APPROVED` 상태로 유지되며 공개 예정 시각 전에는 일반 사용자에게 노출되지 않는다.
6. 승인된 공개 예정 시각이 되면 시스템이 콘텐츠를 한 번만 `PUBLISHED`로 전환하고 지역 홈과 목록에 노출한다.
7. 종료일이 지나거나 정상 종료 처리되면 예약 접수와 노출을 종료한다.

**예외 흐름**

- 필수 정보가 누락되면 승인 요청을 제출할 수 없다.
- 반려 시 사유를 기록하고 운영자가 보완 후 다시 제출한다.
- 승인 후 공개 예정 시각을 변경하려면 운영자가 변경 요청을 제출하고 지역 관리자의 승인을 다시 받아야 한다.
- 운영자와 지역 관리자는 담당하지 않은 지역·콘텐츠를 조회하거나 변경할 수 없다.

**적용 정책:** `AUTH-01`, `AUTH-02`, `CON-01`~`CON-09`

### US-03. 운영자가 현장에서 예약 QR을 체크인한다

**주체:** 행사·체험 운영자, 예약 방문자
**목표:** 예약자의 해당 회차 실제 참여를 빠르고 신뢰성 있게 확인한다.  
**선행 조건:** 예약 상태가 `CONFIRMED`이고 현재 시각이 허용된 체크인 시간 범위에 있다.

**기본 흐름**

1. 방문자가 예약 QR을 제시한다.
2. 운영자가 QR을 스캔한다.
3. 시스템이 서명, 만료 시각, 예약 상태, 행사·회차, 운영자 권한, 기존 체크인 여부를 검증한다.
4. 검증에 성공하면 방문 기록을 한 건 생성하고 예약 상태를 `CHECKED_IN`으로 변경한다.
5. 방문자와 운영자에게 체크인 성공 결과를 표시한다.
6. 시스템은 방문자에게 인증 후기 작성 권한을 부여한다.

**예외 흐름**

- 이미 체크인한 QR은 새 방문 기록을 만들지 않고 이전 성공 결과를 반환한다.
- 만료, 위·변조, 취소, 다른 회차, 권한 없는 운영자 스캔은 실패 사유를 구분해 반환한다.
- QR을 표시할 수 없거나 스캔에 실패하면 운영자가 예약 번호로 보조 조회하고,
  확인 사유·처리자·시각을 기록한 뒤 권한 범위 안에서 처리한다.

**적용 정책:** `QR-01`~`QR-05`, `AUTH-01`, `AUTH-03`

### US-04. 방문자가 인증 후기를 작성·수정·삭제한다

**주체:** 체크인 완료 방문자  
**목표:** 실제 경험을 후기 형태로 공유하고 확정된 기간과 삭제 정책에 따라 관리한다.
**선행 조건:** 방문 기록이 생성됐으며 같은 방문 기록에 연결된 후기가 아직 없다.

**기본 흐름**

1. 사용자가 체크인 완료 화면 또는 예약 내역에서 후기 작성으로 이동한다.
2. 별점과 텍스트를 입력해 후기를 등록한다.
3. 시스템은 후기를 방문 기록과 콘텐츠에 연결한다.
4. 등록된 후기는 해당 콘텐츠 상세에 노출된다.
5. 작성자는 허용된 기간 안에 후기를 수정할 수 있다.
6. 작성자는 기간 제한 없이 후기를 삭제할 수 있다.
7. 삭제한 후기는 즉시 비노출 상태가 되고 보존 기간 후 영구 삭제된다.

**예외 흐름**

- 체크인하지 않은 사용자는 후기를 작성할 수 없다.
- 동일 방문 기록에 대한 중복 후기는 차단하거나 기존 후기 수정 흐름으로 안내한다.
- 수정 허용 기간이 지난 후기는 수정할 수 없다.
- 삭제한 후기는 사용자 또는 관리자가 복구할 수 없다.

**적용 정책:** `REV-01`~`REV-04`, `PRV-02`

### US-05. 지역 관리자가 운영 예외를 처리한다

**주체:** 지역 관리자  
**목표:** 담당 지역의 콘텐츠 공개 품질과 QR 운영 문제를 최소 도구로 통제한다.  
**선행 조건:** 담당 `region_id`가 계정에 부여돼 있다.

**기본 흐름**

1. 관리자가 운영자 승인 요청의 사업자 정보·담당 지역·콘텐츠 소유 관계를 확인한다.
2. 검증을 통과한 운영자에게 담당 지역과 콘텐츠 권한을 부여한다.
3. 관리자가 승인 대기 콘텐츠와 반려 이력을 확인한다.
4. 필수 정보와 운영 기준을 검토해 승인·반려한다.
5. QR 실패 또는 보조 조회가 발생한 건을 사유별로 확인한다.
6. 필요한 경우 운영자에게 보완을 요청하거나 전체 관리자에게 에스컬레이션한다.

고도화된 대시보드가 없어도 지역 관리자는 파일럿 운영의 핵심 예외를 처리할 수 있어야 하며,
다른 지역의 데이터는 조회·처리할 수 없고 모든 예외 처리는 감사 가능한 이력을 남겨야 한다.

**적용 정책:** `AUTH-01`, `AUTH-02`, `CON-09`, `QR-05`

### 8.1 권한·개인정보 정책

| ID      | 정책 |
|---------|------|
| AUTH-01 | 서버는 모든 요청에서 역할, 담당 `region_id`, 운영자-콘텐츠 소유 관계를 검증한다. 지역 관리자는 담당 지역만 조회·변경할 수 있고, 운영자는 자신에게 연결된 콘텐츠·회차·예약만 조회·처리할 수 있다. |
| AUTH-02 | 지역 관리자는 운영자 승인 전에 사업자 정보, 담당 지역, 콘텐츠 소유 관계를 수동 확인하고 검증을 통과한 운영자에게 담당 지역과 콘텐츠 권한을 부여한다. |
| AUTH-03 | 운영자에게 노출되는 모든 예약 목록과 예약 번호 보조 조회 응답은 예약자 이름을 `김*수`, 연락처를 `010-****-1234` 형식으로 마스킹한다. |
| PRV-01  | 회원 탈퇴 시 회원정보를 파기하고, 법령에 따라 보존해야 하는 거래기록만 운영 데이터와 분리해 법정 기간 동안 보관한다. |
| PRV-02  | 회원 탈퇴 시 후기·방문 데이터의 개인 연결을 제거하고 지역·콘텐츠·회차별 비식별 집계만 남긴다. |

### 8.2 콘텐츠 정책

| ID     | 정책                                                                                                                                                                                                                               |
|--------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| CON-01 | 콘텐츠 기본 상태는 `DRAFT → PENDING → APPROVED → PUBLISHED → ENDED`로 전이한다. 반려 시 `PENDING → REJECTED → DRAFT`로 전이하며 반려 사유를 기록하고 운영자가 보완 후 다시 제출한다.                                                                                        |
| CON-02 | 운영자는 대표 이미지, 소개, 위치, 운영 시간, 연락처, 유의사항, 날짜·회차별 정원, 연령·준비물, 취소 기준과 공개 예정 시각의 필수 검증을 통과해야 승인 요청할 수 있다.                                                                                                                              |
| CON-03 | 운영자가 지정한 공개 예정 시각과 콘텐츠를 지역 관리자가 함께 승인한다. `APPROVED`는 일반 사용자에게 노출하지 않으며 시스템은 승인된 `publish_at`에 콘텐츠를 한 번만 `PUBLISHED`로 전환한다.                                                                                                        |
| CON-04 | 승인된 공개 예정 시각을 변경하려면 운영자가 변경 요청을 제출하고 지역 관리자의 승인을 다시 받아야 한다. 종료일이 지나거나 정상 종료 처리되면 `ENDED`로 전환하고 예약 접수와 노출을 종료한다.                                                                                                                  |
| CON-05 | `PUBLISHED` 콘텐츠는 직접 수정하지 않는다. 수정본은 `EDIT_DRAFT → EDIT_REQUESTED → EDIT_APPROVED`로 전이하고, 반려 시 `EDIT_REQUESTED → EDIT_REJECTED`로 전이한다. 심사 중에는 원본의 `PUBLISHED` 상태와 기존 내용을 유지하고 승인된 수정본만 원본에 반영한다. 반려되거나 철회된 수정본만 폐기하며 원본에는 영향을 주지 않는다. |
| CON-06 | 지역 관리자는 공개 콘텐츠를 `PUBLISHED → SUSPENDED`로 전환할 수 있다. 중단 시각, 처리자와 사유를 기록하고 방문자에게 운영 중단 안내와 사유를 표시한다.                                                                                                                                |
| CON-07 | 운영자는 자신이 소유한 공개 콘텐츠만 철회 요청할 수 있다. 지역 관리자가 승인하면 `PUBLISHED → WITHDRAWN`으로 전환하고 철회 시각과 사유를 보존한다.                                                                                                                                   |
| CON-08 | `DRAFT`만 하드 삭제한다. 공개 전 `PENDING`·`APPROVED`는 `deleted_at`, `deleted_by`, `deletion_reason`을 기록해 소프트 삭제한다. `PUBLISHED`·`SUSPENDED`·`WITHDRAWN`·`ENDED`는 삭제하지 않고 상태와 사유 이력을 보존한다.                                                  |
| CON-09 | 승인·반려·자동 공개·수정 심사·운영 중단·철회·종료·삭제에는 처리자, 처리 시각과 사유를 기록한다. 자동 공개처럼 시스템이 처리한 작업도 처리 주체를 구분할 수 있어야 한다.                                                                                                                               |

### 8.3 정원 홀드·예약 정책

| ID     | 정책 |
|--------|------|
| RSV-01 | 정원 홀드는 생성 후 **10분** 동안 유효하며 `ACTIVE → CONSUMED` 또는 `ACTIVE → EXPIRED`로 전이한다. 홀드는 연장하거나 재사용하지 않고, 10분 안에 확정되지 않으면 만료시키며 차감한 정원을 복구한다. |
| RSV-02 | 잔여 정원이 부족하면 홀드를 생성하지 않는다. 활성 홀드만 예약으로 확정할 수 있고, 정원 차감과 홀드·예약 전환은 MySQL 조건부 업데이트와 하나의 트랜잭션으로 처리해 확정 인원이 회차 정원을 초과하지 않게 한다. |
| RSV-03 | 예약 확정은 멱등 키 또는 처리 이력으로 중복 요청에 같은 결과를 반환한다. 동일 사용자의 동일 확정 요청을 반복해도 예약 생성과 정원 차감은 각각 한 번만 발생한다. |
| RSV-04 | 예약 기본 상태는 `CONFIRMED → CHECKED_IN`이며 예외·종료 상태는 `CANCELLED`, `EXPIRED`다. 사용자는 회차 시작 전까지 예약 전체를 취소할 수 있고 부분 취소는 제공하지 않으므로 인원 변경은 전체 취소 후 새로 예약한다. |
| RSV-05 | 회차 시작 후 취소하지 않고 체크인하지 않은 예약은 `EXPIRED`로 처리해 노쇼로 구분한다. |
| RSV-06 | 운영자가 회차를 취소하면 해당 회차의 모든 예약을 `CANCELLED`로 전환하고 사용자에게 취소 사실을 안내한다. 현재 무료 예약 MVP에서는 금전 환불이 발생하지 않는다. |

### 8.4 QR·체크인 정책

| ID    | 정책 |
|-------|------|
| QR-01 | `CONFIRMED` 예약에만 사용자·예약·회차·만료 시각에 연결된 일회성 QR을 발급한다. QR은 HMAC-SHA256으로 서명하고 짧은 유효 기간을 두며 예약 ID, 회차와 만료 시각을 검증할 수 있어야 한다. |
| QR-02 | 체크인은 허용된 시간 범위 안에서 서명, 만료 시각, 예약 상태, 행사·회차, 운영자 권한과 기존 체크인 여부를 검증한다. 취소·만료·다른 회차·위변조 QR과 권한 없는 운영자 요청은 실패 사유를 구분해 거부한다. |
| QR-03 | 검증에 성공하면 예약당 방문 기록을 한 건만 생성하고 예약을 `CHECKED_IN`으로 전환한다. 동일 체크인 요청이나 QR 재스캔은 새 방문 기록을 만들지 않고 최초 성공 결과를 반환한다. |
| QR-04 | 예약 취소 후 체크인과 홀드 만료 후 예약 확정처럼 현재 상태와 양립할 수 없는 요청을 차단하고 실패 사유를 추적할 수 있어야 한다. |
| QR-05 | QR을 표시할 수 없거나 스캔에 실패하면 운영자가 담당 콘텐츠의 예약 번호로 보조 조회할 수 있다. 처리 전 확인 사유, 처리자와 처리 시각을 기록하고 권한 범위 안에서만 체크인한다. |

### 8.5 후기 정책

| ID     | 정책 |
|--------|------|
| REV-01 | 유효한 방문 기록 한 건에 별점·텍스트 후기 한 건만 작성할 수 있다. 체크인하지 않은 사용자는 후기를 작성할 수 없으며 후기에는 해당 방문 기록과 콘텐츠를 연결한다. |
| REV-02 | 후기 상태는 `PUBLISHED → DELETED`로 전이한다. 등록된 `PUBLISHED` 후기는 해당 콘텐츠 상세에 공개한다. |
| REV-03 | 작성자는 후기 등록 후 **30일 동안** 내용을 수정할 수 있다. 등록 후 30일이 지나면 수정 요청을 거부한다. |
| REV-04 | 작성자는 기간 제한 없이 후기를 삭제할 수 있다. 삭제 즉시 공개 조회에서 제외하고 사용자와 관리자 모두 복구할 수 없으며, 삭제 시점부터 **30일 후** 별점·텍스트 원문을 영구 삭제한다. |

### 8.6 파일럿 운영 정책

| ID       | 정책 |
|----------|------|
| PILOT-01 | 첫 파일럿은 **김해시와 동해시**에서 **6주간** 운영한다. 첫 **2주**는 안정화, 다음 **4주**는 기술 검증 기간이며, 지역별 행사·체험 운영자 **3곳 이상**, 콘텐츠 **5개 이상**, 회차 **15개 이상**을 공개 기준으로 삼는다. |
| PILOT-02 | 초기 MVP는 **무료 예약만 지원**하며 사업 KPI를 출시·중단 판단 기준으로 사용하지 않는다. 자동화 테스트와 운영 시나리오의 기술 검증 결과로 출시 여부를 판단한다. |

## 10. 기술 구성과 설계 원칙

이 절의 기술 구성은 현재 무료 예약 MVP에 필요한 범위만 자체 완결적으로 정의한다.

### 10.1 확정 구성

확정 구성 및 기술 스택은 [기술 스택 문서](local-stamp-platform-tech-stack.md)를 참조한다.

### 10.2 현재 릴리스에서 확정하지 않는 구성

초기 MVP는 백엔드 API와 보호된 최소 운영 API를 범위로 한다.
**프런트엔드 프레임워크, 사용자 채널(Web/App), 알림 전달 채널, API 문서화 도구**는
현재 MVP의 출시 기준으로 간주하지 않으며 화면 구현 착수 전에 별도 기술 결정으로 확정한다.

유료 예약·결제 어댑터, 쿠폰, Redis 분산 락도 후속 MVP 기술 범위로 분리한다.

### 10.3 설계 원칙

- Redis는 지역 홈·공개 콘텐츠 목록·상세 캐시와 로그인·예약 확정·QR 스캔 요청 제한에만 사용한다.
- 잔여 정원과 예약 가능 여부는 캐시하지 않으며 예약 정합성과 동시성 제어의 최종 책임은 MySQL이 가진다.
- 초기 MVP 예약 경로에는 Redis 분산 락을 사용하지 않는다.
- 예약 확정과 체크인은 재시도를 전제로 멱등하게 설계한다.
- 알림과 분석 이벤트 실패가 예약 확정을 롤백시키지 않도록 Transactional Outbox로 분리한다.
- AI, RAG, SSE 채팅과 Kafka는 MVP 기본 구성에서 제외한다.

## 11. 비기능 요구사항

### 11.1 보안·개인정보

- QR 토큰의 서명과 유효 기간은 `QR-01`을 적용한다.
- 개인정보, JWT 키와 QR 원문을 로그에 남기지 않는다.
- 역할·지역·소유권 검증, 예약자 마스킹과 회원 탈퇴 후 처리는 `AUTH-01`~`PRV-02`를 적용한다.

### 11.2 정합성·신뢰성

- 정원 홀드와 예약 확정은 동시 요청 테스트로 초과 예약이 발생하지 않음을 검증한다.
- 예약 확정과 체크인 요청이 반복돼도 결과 엔터티가 중복 생성되지 않아야 한다.
- 예약 취소 후 체크인, 홀드 만료 후 예약 확정 같은 불일치 상태를 차단하고 추적할 수 있어야 한다.

### 11.3 관측 가능성

- 모든 요청에 `requestId`를 부여하고 홀드·예약·방문 ID 및 상태 전이를 구조화 로그로 연결한다.
- 홀드 만료·정원 복구, 예약 확정 실패, QR 실패 사유, 권한 거부와 오류율을 관찰한다.
- 기술 검증 결과와 운영 이벤트를 김해시·동해시, 콘텐츠, 회차별로 재현할 수 있는 이벤트 명세를 유지한다.

### 11.4 성능·가용성

- 지역 홈과 공개 콘텐츠 조회는 캐시 적용 전후를 같은 조건으로 측정해 병목과 효과를 확인한다.
- 로그인·예약·QR API는 정상 현장 운영을 방해하지 않는 임계값을 부하 테스트로 정한다.
- 응답 시간·가용성 목표 수치는 예상 트래픽과 파일럿 운영 시간이 확정된 뒤 SLO로 정의한다.

## 12. 테스트 및 출시 수용 기준

MVP 출시 전 다음 자동화 테스트와 운영 검증을 모두 통과해야 한다.
이 표는 정책을 새로 정의하지 않고 정책 카탈로그의 요구사항이 관찰 가능한 결과로 충족됐는지 판정한다.

| ID    | 연결 정책 | 합격 기준 |
|-------|------|------|
| AC-01 | `RSV-01`, `RSV-02` | 마지막 1자리에 동시 요청이 발생해도 한 사용자만 확정되고 확정 인원이 회차 정원을 초과하지 않는다. |
| AC-02 | `RSV-01` | 홀드는 생성 후 10분에 만료되고 연장·재사용되지 않으며, 만료 처리 후 정원이 복구되고 만료된 홀드로 예약을 확정할 수 없다. |
| AC-03 | `RSV-03` | 동일 사용자의 동일 예약 확정 요청을 반복해도 예약과 정원 차감은 각각 한 번만 발생한다. |
| AC-04 | `QR-01`, `QR-02` | 확정된 예약에만 QR이 발급되고 취소·만료·다른 회차·위변조 QR과 권한 없는 운영자 요청은 모두 거부된다. |
| AC-05 | `QR-03` | 동일 QR을 반복 스캔해도 방문 기록은 한 건만 존재하고 최초 성공 결과를 반환한다. |
| AC-06 | `AUTH-01` | 김해시 담당자는 동해시 데이터에, 동해시 담당자는 김해시 데이터에 접근할 수 없고 운영자는 자신에게 연결된 콘텐츠·회차·예약만 조회·처리할 수 있다. |
| AC-07 | `AUTH-03` | 모든 운영자 예약 목록과 예약 번호 보조 조회 응답에서 이름과 연락처가 확정 형식으로 마스킹된다. |
| AC-08 | `CON-03` | `PENDING`과 `APPROVED` 콘텐츠는 공개 조회에 노출되지 않고, 승인된 공개 예정 시각이 도래하면 콘텐츠가 한 번만 `PUBLISHED`로 전환된다. |
| AC-09 | `CON-05` | 공개 콘텐츠 수정 심사 중 기존 공개본이 유지되고 승인된 수정본만 반영되며 반려·철회된 수정본은 원본에 영향을 주지 않는다. |
| AC-10 | `CON-08` | `DRAFT`만 하드 삭제되고 `PENDING`·`APPROVED`는 삭제 정보와 함께 소프트 삭제되며 공개 이후 상태의 콘텐츠는 삭제되지 않는다. |
| AC-11 | `CON-06` | 콘텐츠 운영 중단 시 중단 시각·처리자·사유가 기록되고 방문자에게 중단 안내와 사유가 표시된다. |
| AC-12 | `CON-09` | 승인·반려·자동 공개·수정 심사·운영 중단·철회·종료·삭제의 처리자, 처리 시각과 사유를 재현할 수 있다. |
| AC-13 | `REV-01`, `REV-03` | 체크인 완료 방문당 후기 한 건만 작성할 수 있고 체크인 없는 사용자의 작성과 등록 후 30일이 지난 후기의 수정은 거부된다. |
| AC-14 | `REV-04` | 후기 삭제 즉시 공개 조회에서 제외되고 복구되지 않으며 삭제 시점 30일 후 별점·텍스트 원문이 영구 삭제된다. |
| AC-15 | `PRV-01`, `PRV-02` | 회원 탈퇴 시 회원정보와 후기·방문 데이터의 개인 연결이 제거되고 법정 거래기록만 별도 저장소에 남으며 비식별 집계만 유지된다. |
| AC-16 | `QR-05` | QR 스캔 실패 시 담당 운영자가 예약 번호로 보조 조회할 수 있고 확인 사유·처리자·처리 시각이 기록된다. |
| AC-17 | `CON-09`, `RSV-03`, `QR-02`~`QR-05` | 핵심 상태 전이와 실패 사유를 지역·콘텐츠·회차별로 재현할 수 있다. |

## 14. 단계별 출시 계획

- 무료 예약·10분 홀드·취소·노쇼 정책 확정
- 콘텐츠 승인·자동 공개·수정 심사·운영 중단·철회·삭제 정책 확정
- 운영자 승인·연락처 마스킹·개인정보·후기 삭제 정책 확정
- 사업 KPI 대신 기술 검증 기준과 자동화 테스트 합격 조건 확정

### 단계 1. MVP 구현·검증

- 지역·콘텐츠·수정본·회차·홀드·무료 예약·방문·후기 핵심 도메인과 자동 공개 작업 구현

### 단계 2. 김해시·동해시 6주 파일럿

- `PILOT-01`의 기간과 지역별 운영자·콘텐츠·회차 기준으로 운영
- 파트너 온보딩과 현장 교육
- 기술 검증 결과와 예외 사유 수집
- 운영자 인터뷰와 사용자 피드백으로 정책·UX 보완

### 단계 3. 확장 의사결정

- 무료 예약·체크인·후기 데이터와 기술 검증 결과에 따라 지역과 콘텐츠 확대 여부 결정
- 유료 예약·결제, 쿠폰, Redis 분산 락 도입 여부 결정
- 프런트엔드 프레임워크·사용자 채널·알림 채널을 별도 기술 결정으로 확정
- 체크인 신뢰성이 확보되면 가게·관광지 인증 검토
- 콘텐츠 밀도와 재방문 효과가 확인되면 스탬프·미션 도입 검토

## 15. 유료 예약 도입 시 적용할 거래 정책

다음 정책은 방향이 확정됐지만 현재 무료 예약 MVP의 구현 요구사항은 아니다.

- 유료 예약 도입 시 사용자의 회차 시작 전 취소와 운영자 취소는 전액 환불한다.
- 운영자 취소 시 사용한 쿠폰을 복구한다.
- 결제 취소 실패와 예약·결제 불일치의 수동 처리 책임자는 **플랫폼 전체 관리자**다.
- 행사·체험 운영자는 결제 문제의 1차 확인과 고객 안내를 담당한다.
- 지역 관리자는 결제 상태를 변경할 수 없다.

현재 무료 예약 파일럿 정책의 오픈 이슈는 없다.
유료 결제·쿠폰·Redis 분산 락·프런트엔드는 후속 MVP 또는 별도 기술 결정 범위로 이관한다.

## 16. 장기 제품 비전

### 16.1 제품 정의

로컬스탬프는 지역 콘텐츠를 발견하는 순간부터 예약·방문·후기·재방문까지 연결해,
실제 방문 기록을 기반으로 지역 참여를 확장하는 플랫폼을 지향한다.

장기 제품의 핵심 흐름은 다음과 같다.

**지역 콘텐츠 등록·승인 → 탐색 → 예약·결제 또는 현장 방문 → QR 인증 → 인증 후기·쿠폰 → 스탬프·지역 미션
→ 재방문 → 운영·지역 성과 확인**

장기 제품은 다음 원칙을 따른다.

- 모든 후기, 쿠폰, 스탬프와 미션 달성은 신뢰할 수 있는 방문 기록을 근거로 삼는다.
- 예약형 행사·체험과 비예약형 가게·관광지는 서로 다른 방문 인증 규칙을 사용한다.
- 예약·결제·방문·혜택의 상태와 이력은 중복 요청과 실패 재시도에서도 일관되게 유지한다.
- 콘텐츠와 운영 데이터는 지역에 연결하고 역할·지역·소유 관계에 따라 접근 범위를 제한한다.
- 기능은 검증된 데이터와 운영 역량을 진입 조건으로 삼아 단계적으로 확장한다.

## 18. 장기 제품 성과 프레임

장기 제품 지표는 제품 확장 여부를 판단하기 위한 기준이다.
현재 무료 예약 MVP의 출시 합격 여부는 자동화 테스트와 운영 검증으로 판단하며
아래 사업·제품 지표를 현재 출시 차단 조건으로 사용하지 않는다.

| 목표     | 대표 지표                                      | 활용 시점       |
|--------|--------------------------------------------|-------------|
| 콘텐츠 발견 | 지역 홈 대비 상세 진입률, 사용자당 탐색 콘텐츠 수              | 현재 기반부터 관찰  |
| 예약 전환  | 예약 가능한 상세 방문 대비 예약 확정률, 결제 도입 후 결제 성공·실패율  | 현재 기반·거래 확장 |
| 실제 참여  | 예약 확정 대비 체크인율, QR 실패율과 실패 사유               | 현재 기반부터 관찰  |
| 재방문    | 체크인 사용자 재예약률, 쿠폰 발급 대비 사용률                 | 거래·재방문 확장   |
| 지역 참여  | 스탬프 적립률, 미션 참여·완료율, 가게·관광지 인증 방문 수         | 지역 참여 확장    |

확정한다. 개인 단위 분석은 목적에 필요한 최소 데이터만 사용하고 외부 보고에는 비식별 집계를 사용한다.
