## 1. 요약

로컬스탬프는 지역의 행사·체험 콘텐츠를 탐색하고 무료로 예약한 뒤 현장에서 일회성 QR로 실제 참여를 인증하며, 인증된 방문자만 후기를 작성할 수 있게 하는 지역 참여형 플랫폼이다. 초기 MVP는 콘텐츠를 최대한 많이 모으는 것보다 **지역 콘텐츠 탐색 → 무료 예약 → 현장 체크인 → 인증 후기** 흐름의 정합성과 운영 가능성을 기술적으로 검증하는 데 집중한다.

첫 파일럿 지역은 **김해시와 동해시**로 확정하고 예약형 행사·체험으로 범위를 한정한다. 유료 예약·결제, 쿠폰, Redis 분산 락, 가게·관광지 현장 인증, 스탬프북, 지역 미션, AI 추천, 고도화된 관리자 대시보드는 무료 예약과 현장 운영의 기술적 안정성이 검증된 뒤 후속 MVP에서 확장한다.

근거: [상세 기획서 (제안서)](local-stamp-platform-proposal.md), [로컬스탬프 기획 검토 및 보완 제안](local-stamp-platform-planning-review.md)

> 문서 간 정합성 기준: 2026-07-23 파일럿 정책 결정을 최우선 기준으로 삼는다. 상세 기획서와 기술 스택 문서에 유료 결제·쿠폰이 포함돼 있더라도 본 PRD의 초기 MVP에서는 제외하며, 무료 예약의 정원 정합성·QR 체크인·인증 후기·지역 권한을 우선 검증한다.

## 2. 배경과 문제 정의

### 2.1 사용자 문제

- 지역 행사와 체험 정보가 SNS, 지도, 커뮤니티 등 여러 채널에 흩어져 있어 한 지역 안에서 비교하기 어렵다.
- 예약 가능 여부, 잔여 정원, 신청, 현장 참여 확인이 서로 다른 도구에서 처리되어 사용자 경험이 단절된다.
- 실제 방문 여부와 무관하게 작성된 후기는 신뢰도가 낮다.
- 예약과 실제 참여를 연결해 운영 품질을 검증할 일관된 기준이 부족하다.

### 2.2 운영자 문제

- 행사·체험 운영자는 SNS·전화·메신저·스프레드시트로 홍보, 신청, 명단, 현장 입장을 따로 관리한다.
- 회차별 초과 예약, 중복 신청, 중복 체크인, 노쇼 등 예약·현장 예외를 일관되게 처리하기 어렵다.
- 예약자와 실제 참여자를 구분하고 인증 후기를 연결하기 어렵다.

### 2.3 지역 운영 주체의 문제

- 지역 콘텐츠의 등록·승인·종료 상태가 기관과 담당자별로 흩어진다.
- 어떤 콘텐츠가 조회·예약되고 실제 방문까지 이어졌는지 비교할 공통 기준이 부족하다.
- 지역 단위 권한과 데이터 경계를 강제할 최소 운영 도구가 필요하다.

## 3. 프로젝트 목표

### 3.1 핵심 목표

1. **핵심 전환 검증**  
   김해시와 동해시에서 사용자가 행사·체험을 발견하고 무료 예약한 뒤 실제 QR 체크인까지 완료할 수 있는지 검증한다.

2. **예약 및 방문 데이터의 신뢰성 확보**
   10분 정원 홀드, 예약 상태, 일회성 QR, 방문 기록을 일관되게 연결하고 중복·초과 처리를 방지한다.

3. **인증 후기 체계 검증**  
   체크인 완료 방문에만 후기 작성 권한을 부여하고 수정·삭제 정책이 정확히 동작하는지 검증한다.

4. **최소 운영 가능성 검증**
   운영자의 콘텐츠·회차 등록과 QR 체크인, 지역 관리자의 승인·반려 및 예외 조회가 최소 도구로 수행 가능한지 확인한다.

5. **다지역 격리 기반 확보**
   사용자 권한, 콘텐츠, 회차, 예약, 방문, 후기를 `region_id`와 연결해 김해시와 동해시의 데이터와 권한을 분리한다.

### 3.2 성공 판단 원칙

MVP는 사업 KPI 달성이 아니라 다음 기술 검증 질문을 자동화 테스트와 운영 시나리오로 통과할 때 성공한 것으로 본다.

- 마지막 잔여 정원에 동시 요청이 발생해도 초과 예약이 없는가?
- 10분 홀드 만료와 예약 확정이 정원을 정확히 반영하는가?
- 동일 예약·체크인 요청을 재시도해도 결과가 중복 생성되지 않는가?
- 김해시와 동해시의 지역·운영자 권한이 교차 접근을 차단하는가?
- 취소·만료·다른 회차 QR과 중복 QR을 정확히 거부하는가?
- 체크인한 사용자만 후기를 작성하고 확정된 수정·삭제 정책을 지키는가?
- 예약자 연락처 마스킹과 탈퇴·파기 정책이 전 경로에서 적용되는가?

구체적인 합격 기준은 13장의 기술 검증 기준을 따른다. 탐색 전환율, 체크인율, 후기 작성률 등 사업 KPI는 초기 MVP의 출시·중단 판단 기준으로 사용하지 않는다.

근거: [상세 기획서 (제안서)](local-stamp-platform-proposal.md), [로컬스탬프 기획 검토 및 보완 제안](local-stamp-platform-planning-review.md)

## 4. 비목표(Non-goals)

다음 항목은 MVP 범위에 포함하지 않는다.

- 가게·관광지의 비예약형 현장 QR 방문 인증
- 일반 음식점 좌석 예약
- 유료 예약, 결제 승인·웹훅·취소·환불과 결제 정합성 검증
- 쿠폰 발급·사용·복구
- Redis 분산 락을 이용한 예약 동시성 제어
- 스탬프북, 지역 미션, 포인트, 현금성 보상
- 매장 현장 할인, 다중 쿠폰 조합, 복잡한 혜택 지갑
- 여러 판매자 간 자동 정산
- 지도 기반 탐색, 추천 코스, 개인화·AI 추천
- 위치 기반 자동 인증
- 실시간 채팅, SSE 기반 대화형 탐색, RAG
- 전국 단위 공공데이터 자동 수집·정제
- 고도화된 운영자·지역 관리자 통계 대시보드
- 후기 사진, 운영자 답글, 별도 신고 화면, 지역별 후기 피드

## 5. 사용자와 권한

다음 역할과 니즈는 [페르소나](local-engagement-stamp-reward-platform-personas.md)와 [상세 기획서 (제안서)](local-stamp-platform-proposal.md)를 기준으로 정리했다.

| 사용자           | MVP 역할                                   | 핵심 니즈                        |
|---------------|------------------------------------------|------------------------------|
| 주말 나들이 방문자    | 지역 선택, 탐색, 무료 예약, QR 제시, 인증 후기 작성 | 믿을 만한 체험을 한곳에서 찾고 예약·방문까지 완료 |
| 지역 주민·재방문 사용자 | 방문자와 동일한 무료 예약·체크인 흐름              | 익숙한 지역의 새 콘텐츠 발견과 참여        |
| 행사·체험 운영자     | 콘텐츠·회차 등록 요청, 예약자 조회, QR 체크인, 예외 기록      | 신청·명단·현장 참가를 하나의 흐름으로 관리     |
| 지역 관리자        | 담당 지역 운영자 수동 승인, 콘텐츠 승인·반려, QR 예외 조회      | 지역별 권한·공개 품질과 운영 이슈 통제       |
| 전체 관리자        | 지역 생성, 역할 부여, 공통 운영 기준 관리                | 지역 경계와 초기 운영 체계 설정           |

MVP의 최우선 고객은 **주말 나들이 방문자**, 최우선 공급자는 **예약형 행사·체험 운영자**다. 지역 관리자는 구매 고객보다 서비스 운영을 가능하게 하는 필수 주체로 본다.

## 6. MVP 범위

### 6.1 포함 범위

- 회원 가입·로그인과 방문자/운영자/지역 관리자/전체 관리자 역할 구분
- 지역 관리자의 사업자 정보·담당 지역·콘텐츠 소유 관계 확인과 운영자 수동 승인
- 김해시·동해시 공개 지역 선택과 지역별 홈
- 행사·체험 콘텐츠 목록, 필터, 상세 조회
- 운영자의 콘텐츠·회차 등록 요청
- 지역 관리자의 콘텐츠 공개 여부 전환(공개 :left_right_arrow: 비공개)과 소프트 삭제
  운영자의 콘텐츠 세부 정보 수정 요청 제출과 지역 관리자 승인 반영 흐름
- 지역 관리자의 승인·반려와 공개·종료 상태 관리
- 회차·정원 기반 무료 예약
- 10분 정원 홀드 생성, 예약 확인 시 확정, 미확정·만료 시 홀드 해제
- 사용자·예약·회차·만료 시각에 연결된 일회성 예약 QR
- 운영자 QR 스캔, 중복 방지, 예약 정보 보조 조회와 예외 사유 기록
- 방문 기록에 연결된 별점·텍스트 후기
- 예약·홀드·체크인·권한·후기 상태 전이와 실패 원인을 검증하기 위한 이벤트·로그
- 콘텐츠 승인·반려, 예약자 조회, QR 예외 처리를 위한 내부용 최소 화면 또는 보호된 운영 API

### 6.2 후속 범위

- 가게·관광지는 공통 콘텐츠 모델에는 수용할 수 있게 설계하되, MVP에서 현장 인증 대상으로 삼지 않는다.
- 유료 예약·결제와 쿠폰은 무료 예약의 기술 검증이 완료된 후 후속 MVP에서 도입한다.
- 예약 동시성은 MySQL 조건부 업데이트로 보장하고 Redis 분산 락은 후속 MVP에서 검토·도입한다.
- 스탬프와 지역 미션은 체크인 데이터의 신뢰성과 콘텐츠 밀도를 확보한 후 도입한다.
- 프런트엔드 프레임워크·사용자 채널·알림 채널은 현재 백엔드 MVP 범위에 포함하지 않고 별도 기술 결정으로 확정한다.
- 고도화된 통계·성과 리포트는 데이터 품질이 안정된 후 제공한다.

## 7. 유저 시나리오(User Scenario)

시나리오는 원문의 핵심 이용 흐름에 [기획 검토 및 보완 제안](local-stamp-platform-planning-review.md)의 동시성·멱등성·권한·예외 처리 기준을 결합해 작성했다.

### US-01. 방문자가 행사·체험을 탐색하고 예약한다

**주체:** 주말 나들이 방문자  
**목표:** 선택한 지역에서 원하는 행사·체험을 찾고 무료 예약을 완료한다.
**선행 조건:** 사용자가 로그인했으며 공개 지역이 1개 이상 존재한다.

**기본 흐름**

1. 사용자가 공개 지역 중 하나를 선택한다.
2. 지역 홈에서 진행 중이거나 임박한 행사·체험을 확인한다.
3. 유형과 예약 가능 여부로 콘텐츠를 필터링한다.
4. 상세 화면에서 위치, 운영 시간, 소개, 유의사항, 날짜·회차, 잔여 정원, 취소 기준, 인증 후기를 확인한다.
5. 날짜·회차·인원을 선택한다.
6. 시스템이 MySQL 조건부 업데이트로 잔여 정원을 확인하고 10분 정원 홀드를 생성한다.
7. 사용자가 10분 안에 예약 내용을 확인하고 무료 예약 확정을 요청한다.
8. 시스템은 활성 홀드를 예약으로 전환하고 일회성 예약 QR을 발급한다.
9. 사용자는 확정된 예약 내역과 QR을 확인한다.

**예외 흐름**

- 잔여 정원이 부족하면 홀드를 만들지 않고 다른 회차 선택을 안내한다.
- 홀드 생성 후 10분 안에 예약을 확정하지 않으면 홀드를 만료시키고 정원을 복구한다.
- 만료된 홀드는 연장하거나 재사용하지 않으며 사용자는 새 홀드를 요청해야 한다.
- 동일 예약 확정 요청이 반복돼도 예약은 한 번만 생성한다.

**수용 기준**

- 마지막 1자리를 여러 사용자가 동시에 요청해도 한 예약만 확정된다.
- 홀드 만료 후 정원이 복구되고 만료된 홀드로 예약을 확정할 수 없다.
- 확정된 예약에만 QR이 발급된다.

### US-02. 운영자가 행사·체험을 등록하고 지역 관리자가 승인한다

**주체:** 행사·체험 운영자, 지역 관리자  
**목표:** 예약 가능한 콘텐츠를 표준 정보와 함께 안전하게 공개한다.  
**선행 조건:** 지역 관리자가 사업자 정보·담당 지역·콘텐츠 소유 관계를 수동 확인해 운영자 계정을 승인했고 담당 권한이 부여돼 있다.

**기본 흐름**

1. 운영자가 대표 이미지, 소개, 위치, 운영 시간, 연락처, 유의사항을 입력한다.
2. 날짜·회차별 정원, 연령·준비물, 취소 기준을 입력한다.
3. 필수 항목 검증을 통과하면 승인 요청을 제출한다.
4. 담당 지역 관리자가 내용을 검토해 승인 또는 반려한다.
5. 승인된 콘텐츠는 공개 상태가 되고 지역 홈과 목록에 노출된다.
6. 종료일이 지나거나 관리자가 종료 처리하면 예약과 노출을 종료한다.

**예외 흐름**

- 필수 정보가 누락되면 승인 요청을 제출할 수 없다.
- 반려 시 사유를 기록하고 운영자가 보완 후 다시 제출한다.
- 운영자와 지역 관리자는 담당하지 않은 지역·콘텐츠를 조회하거나 변경할 수 없다.

**수용 기준**

- 승인 전 콘텐츠는 일반 사용자에게 노출되지 않는다.
- 모든 승인·반려·종료 작업에 처리자, 시각, 사유가 남는다.
- 운영자는 자신에게 연결된 콘텐츠와 회차만 관리한다.

### US-03. 운영자가 현장에서 예약 QR을 체크인한다

**주체:** 행사 운영자, 예약 방문자  
**목표:** 예약자의 해당 회차 실제 참여를 빠르고 신뢰성 있게 확인한다.  
**선행 조건:** 예약 상태가 확정이고 현재 시각이 허용된 체크인 시간 범위에 있다.

**기본 흐름**

1. 방문자가 예약 QR을 제시한다.
2. 운영자가 QR을 스캔한다.
3. 시스템이 서명, 만료 시각, 예약 상태, 행사·회차, 운영자 권한, 기존 체크인 여부를 검증한다.
4. 검증에 성공하면 방문 기록을 한 건 생성하고 예약 상태를 체크인 완료로 변경한다.
5. 방문자와 운영자에게 체크인 성공 결과를 표시한다.
6. 시스템은 방문자에게 인증 후기 작성 권한을 부여한다.

**예외 흐름**

- 이미 체크인한 QR은 새 방문 기록을 만들지 않고 이전 성공 결과를 반환한다.
- 만료, 위·변조, 취소, 다른 회차, 권한 없는 운영자 스캔은 실패 사유를 구분해 반환한다.
- QR을 표시할 수 없거나 스캔에 실패하면 운영자가 예약 번호로 보조 조회하고, 확인 사유·처리자·시각을 기록한 뒤 권한 범위 안에서 처리한다.

**수용 기준**

- 같은 QR을 반복 스캔해도 방문 기록은 한 건만 존재한다.
- QR 원문과 개인정보는 로그에 남지 않는다.
- 운영자는 담당 콘텐츠의 예약만 조회·체크인할 수 있다.

### US-04. 방문자가 인증 후기를 작성·수정·삭제한다

**주체:** 체크인 완료 방문자  
**목표:** 실제 경험을 후기 형태로 공유하고 확정된 기간과 삭제 정책에 따라 관리한다.
**선행 조건:** 방문 기록이 생성됐으며 같은 방문 기록에 연결된 후기가 아직 없다.

**기본 흐름**

1. 사용자가 체크인 완료 화면 또는 예약 내역에서 후기 작성으로 이동한다.
2. 별점과 텍스트를 입력해 후기를 등록한다.
3. 시스템은 후기를 방문 기록과 콘텐츠에 연결한다.
4. 등록된 후기는 해당 콘텐츠 상세에 노출된다.
5. 작성자는 등록 후 30일 이내에 후기를 수정할 수 있다.
6. 작성자는 기간 제한 없이 후기를 삭제할 수 있다.
7. 삭제한 후기는 즉시 비노출 상태가 되고 30일 후 영구 삭제된다.

**예외 흐름**

- 체크인하지 않은 사용자는 후기를 작성할 수 없다.
- 동일 방문 기록에 대한 중복 후기는 차단하거나 기존 후기 수정 흐름으로 안내한다.
- 등록 후 30일이 지난 후기는 수정할 수 없다.
- 삭제한 후기는 사용자 또는 관리자가 복구할 수 없다.

**수용 기준**

- 후기에는 반드시 유효한 방문 기록과 콘텐츠가 연결된다.
- 삭제 즉시 공개 조회에서 제외되고 삭제 시점부터 30일이 지나면 원문이 영구 삭제된다.
- 탈퇴한 사용자의 후기와 방문 데이터는 개인 연결을 제거하고 비식별 집계만 남긴다.

### US-05. 지역 관리자가 운영 예외를 처리한다

**주체:** 지역 관리자  
**목표:** 담당 지역의 콘텐츠 공개 품질과 QR 운영 문제를 최소 도구로 통제한다.  
**선행 조건:** 담당 `region_id`가 계정에 부여돼 있다.

**기본 흐름**

1. 관리자가 운영자 승인 요청의 사업자 정보·담당 지역·콘텐츠 소유 관계를 확인한다.
2. 검증을 통과한 운영자에게 담당 지역과 콘텐츠 권한을 부여한다.
3. 관리자가 승인 대기 콘텐츠와 반려 이력을 확인한다.
4. 필수 정보와 운영 기준을 검토해 승인·반려한다.
5. QR 실패 또는 보조 조회가 발생한 건을 사유별로 확인한다.
6. 필요한 경우 운영자에게 보완을 요청하거나 전체 관리자에게 에스컬레이션한다.

**수용 기준**

- 다른 지역 데이터는 조회·처리할 수 없다.
- 모든 예외 처리는 감사 가능한 이력을 남긴다.
- 고도화된 대시보드 없이도 파일럿 운영의 핵심 예외를 처리할 수 있다.

## 9. 핵심 상태와 비즈니스 규칙

### 9.1 상태 모델

- 콘텐츠: `DRAFT → SUBMITTED → APPROVED/PUBLISHED → ENDED`, 반려 시 `REJECTED → DRAFT`, 이미 승인/공개된 콘텐츠를 취소 하는 경우 `APPROVED/PUBLISHED → WITHDRAWN`로 처리
- 콘텐츠 삭제 중단 및 취소/철회의 경우: `APPROVED/PUBLISHED → WITHDRAWN/SUSPENDED` 및 updated_at 기준으로 처리, `DRAFT`상태의 경우는 하드 삭제로 처리
- `APPROVED` 상태의 콘텐츠를 수정하는 경우 `APPROVED → EDIT → EDIT_REQUESTED -> APPROVED`로 처리, `EDIT_REQUESTED` 상태의 콘텐츠는 지역 관리자의 승인 필요
- 정원 홀드: `ACTIVE → CONSUMED` 또는 `EXPIRED`
- 예약: `CONFIRMED → CHECKED_IN`
- 예약 예외·종료: `CANCELLED`, `EXPIRED`
- 후기: `PUBLISHED → DELETED`; `DELETED` 전환 즉시 비노출하고 삭제 시점 30일 후 원문을 영구 삭제

### 9.2 핵심 규칙

- 정원 홀드는 생성 후 10분 동안 유효하며 연장하지 않는다.
- 활성 홀드만 예약으로 확정할 수 있고 예약 확정 요청은 멱등하게 처리한다.
- 정원 차감과 홀드·예약 전환의 최종 정합성은 MySQL 조건부 업데이트와 트랜잭션이 책임진다.
- Redis 분산 락은 초기 MVP에서 사용하지 않고 후속 MVP에서 도입한다.
- 예약 확정과 체크인 API는 멱등 키 또는 처리 이력으로 중복 요청에 같은 결과를 반환한다.
- QR에는 예약 ID, 회차, 만료 시각을 검증할 수 있는 서명을 포함한다.
- 취소됐거나 다른 회차인 예약은 체크인할 수 없다.
- 사용자는 회차 시작 전까지 예약 전체를 취소할 수 있으며 부분 취소는 제공하지 않는다.
- 회차 시작 후 취소하지 않고 체크인하지 않은 예약은 `EXPIRED`로 처리한다.
- 운영자 취소 시 해당 회차의 예약을 모두 취소하고 사용자에게 안내한다.
- 방문 기록 한 건에는 후기 한 건만 허용하는 것을 기본 정책으로 한다.
- 후기는 작성 후 30일 동안 수정할 수 있고 언제든 삭제할 수 있다. 삭제 즉시 비노출하며 복구 없이 30일 후 영구 삭제한다.
- 지역 관리자와 운영자의 조회·변경 권한은 `운영자-콘텐츠-지역` 소유 관계로 제한한다.
- 운영자는 예약 목록에서 마스킹된 이름과 연락처(`김*수`, `010-****-1234`)만 조회한다.
- 콘텐츠 `PUBLISHED` 시점은 지역 이벤트 시작 3주전을 원칙으로 하되 다음과 같은 예외사항을 가진다.
    1. 콘텐츠의 승인 시점이 지역 이벤트 시작하기 3주전 이내인 경우
        - 콘텐츠 승인 시점 기준 3일 후에 `PUBLISHED` 상태로 변경
    2. 콘텐츠의 승인 시점이 지역 이벤트 시작하기 1주전 이내가 되는 경우 (시점은 예시임)
        - 시스탬상 `REJECTED`로 처리 및 승인 거절
- `PUBLISHED`, `SUSPENDED` 상태의 콘텐츠는 하드 삭제하거나 직접 수정할 수 없다. 운영자 취소는 지역 관리자 승인 후 `WITHDRAWN`으로 전환한다.
- `EDIT_REQUESTED` 상태를 철회/반려하는 경우 `EDIT_REQUESTED → APPROVED (이전 콘텐츠 내용)`로 처리
    - 수정본은 하드삭제 원칙
- 콘텐츠 삭제 중단 및 취소/철회는 행사 운영자 및 지역 관리자의 권한으로 가능
- 행사 운영자는 본인의 콘텐츠만 취소 가능하며 취소시에는 지역 관리자의 승인 필요 (예시 목적: 지원금 먹튀 방지)
- `DRAFT`상태 의 콘텐츠 외의 모든 콘텐츠의 중단 및 취소의 경우 변경 경우 삭제 중단 및 취소/철회의 사유 명시 필수

## 11. 기술 스택

[기술 스택 정리](local-stamp-platform-tech-stack.md)를 기본으로 삼되, 2026-07-23에 확정한 무료 예약 파일럿 정책을 우선 적용해 결제·쿠폰·Redis 분산 락을 후속 범위로 분리했다.

### 11.2 미확정 스택

초기 MVP는 백엔드 API와 보호된 최소 운영 API를 범위로 한다. **프런트엔드 프레임워크, 사용자 채널(Web/App), 알림 전달 채널, API 문서화 도구**는 현재 MVP의 출시 기준으로 간주하지 않으며, 화면 구현 착수 전에 별도 기술 결정 기록(ADR)으로 확정한다.

유료 예약·결제 어댑터, 쿠폰, Redis 분산 락도 후속 MVP 기술 범위로 분리한다.

### 11.3 설계 원칙

- Redis는 캐시와 요청 제한에만 사용하고 예약 정합성과 동시성 제어의 최종 책임은 MySQL이 가진다.
- 초기 MVP 예약 경로에는 Redis 분산 락을 사용하지 않는다.
- 지역 홈, 공개 콘텐츠 목록, 상세만 캐시한다. 잔여 정원과 예약 가능 여부는 캐시하지 않는다.
- 예약 확정과 체크인은 재시도를 전제로 멱등하게 설계한다.
- 알림과 분석 이벤트 실패가 예약 확정을 롤백시키지 않도록 Outbox로 분리한다.
- AI, RAG, SSE 채팅, Kafka는 MVP 기본 스택에서 제외한다.

## 12. 비기능 요구사항

### 12.1 보안·개인정보

- 서버는 모든 요청에서 역할, 담당 지역, 콘텐츠 소유 관계를 검증한다.
- 행사·체험 운영자에게 노출되는 예약자 정보는 이름 `김*수`, 연락처 `010-****-1234` 형식으로 마스킹한다.
- QR 토큰은 HMAC-SHA256으로 서명하고 짧은 유효 기간을 둔다.
- 개인정보, JWT 키, QR 원문을 로그에 남기지 않는다.
- 회원정보는 탈퇴 시 파기하고, 법령에 따라 보존해야 하는 거래기록만 운영 데이터와 분리해 법정 기간 동안 보관한다.
- 탈퇴 시 후기·방문 데이터의 개인 연결을 제거하고 지역·콘텐츠·회차별 비식별 집계만 남긴다.

### 12.2 정합성·신뢰성

- 정원 홀드와 확정은 동시 요청 테스트로 초과 예약이 발생하지 않음을 검증한다.
- 10분이 지난 홀드는 연장 없이 만료되고 정원이 복구돼야 한다.
- 동일 예약 확정 요청과 동일 체크인 요청이 반복돼도 결과 엔터티가 중복 생성되지 않는다.
- 예약 취소 후 체크인, 홀드 만료 후 예약 확정 같은 불일치 상태를 차단하고 추적할 수 있어야 한다.

### 12.3 관측 가능성

- 모든 요청에 `requestId`를 부여하고 홀드·예약·방문 ID 및 상태 전이를 구조화 로그로 연결한다.
- 홀드 만료·복구, 예약 확정 실패, QR 실패 사유, 권한 거부와 오류율을 관찰한다.
- 기술 검증 결과를 김해시·동해시, 콘텐츠, 회차별로 재현할 수 있는 이벤트 명세를 유지한다.

### 12.4 성능·가용성

- 지역 홈과 공개 콘텐츠 조회는 캐시 적용 전후를 측정해 병목을 확인한다.
- 로그인·예약·QR API는 정상 현장 운영을 방해하지 않는 임계값을 부하 테스트로 정한다.
- 응답 시간·가용성 목표 수치는 예상 트래픽과 파일럿 운영 시간이 확정된 뒤 SLO로 정의한다.

## 14. 테스트 및 출시 수용 기준

MVP 출시 전 최소한 다음 자동화·운영 검증을 통과해야 한다.

- 마지막 1자리 동시 예약에서 한 사용자만 확정된다.
- 동일 예약 확정 요청이 반복돼도 예약은 한 건만 유지된다.
- 10분 홀드 만료 시 정원이 복구되고 만료된 홀드는 연장되지 않는다.
- 취소·다른 회차·만료 QR은 체크인되지 않는다.
- 동일 QR 재스캔 시 이전 결과를 반환하고 방문 기록은 한 건만 유지된다.
- 운영자가 다른 지역 또는 다른 운영자의 예약을 조회·체크인할 수 없다.
- 체크인 없는 사용자는 후기를 작성할 수 없다.
- 후기 수정 30일, 상시 삭제, 즉시 비노출, 30일 후 영구 삭제 정책이 자동화 테스트로 검증된다.
- 예약자 이름과 연락처가 모든 운영자 조회 응답에서 마스킹된다.
- 회원 탈퇴 시 개인정보 파기와 법정 거래기록 분리 보관이 검증된다.
- QR 스캔 실패 시 예약 번호 보조 조회와 사유 기록이 가능하다.
- 핵심 상태 전이와 실패 사유가 지역·콘텐츠·회차별로 재현된다.

### 단계 1. MVP 구현·검증

- 지역·콘텐츠·회차·홀드·무료 예약·방문·후기 핵심 도메인 구현

- 지역별 행사·체험 운영자 3곳 이상, 콘텐츠 5개 이상, 회차 15개 이상 확보

- 파트너 온보딩과 현장 교육
- 기술 검증 결과와 예외 사유 수집
- 운영자 인터뷰와 사용자 피드백으로 정책·UX 보완

### 단계 3. 확장 의사결정

- 무료 예약·체크인·후기 데이터와 기술 검증 결과에 따라 지역과 콘텐츠 확대 여부 결정
- 유료 예약·결제, 쿠폰, Redis 분산 락 도입 여부 결정
- 프런트엔드 프레임워크·사용자 채널·알림 채널을 별도 ADR로 확정
- 체크인 신뢰성이 확보되면 가게·관광지 인증 검토
- 콘텐츠 밀도와 재방문 효과가 확인되면 스탬프·미션 도입 검토

## 17. 확정된 결정 사항

2026-07-23 기준 기존 오픈 이슈는 다음과 같이 해소했다.

1. 첫 파일럿은 **김해시와 동해시**에서 6주간 운영한다. 2주는 안정화, 4주는 기술 검증 기간으로 두며 지역별 최소 행사·체험 운영자 3곳, 콘텐츠 5개, 회차 15개를 공개 기준으로 삼는다.
2. 초기 MVP는 **무료 예약만 지원**한다. 유료 예약과 결제 정합성 검증은 후속 MVP로 분리한다.
3. 정원 홀드는 **10분이며 연장하지 않는다**. MySQL 조건부 업데이트를 최종 정합성 기준으로 사용하고 Redis 분산 락은 후속 MVP에서 구현한다.
4. 사용자는 회차 시작 전까지 예약 전체를 취소할 수 있고 시작 후 취소하지 않은 미체크인 예약은 노쇼로 처리한다. 부분 취소 없이 전체 취소 후 재예약한다. 초기 MVP는 무료이므로 금전 환불은 발생하지 않으며, 유료 예약 도입 시 회차 시작 전 취소와 운영자 취소는 전액 환불하고 운영자 취소 시 쿠폰을 복구한다.
5. 유료 예약 도입 후 결제 취소 실패와 예약·결제 불일치의 수동 처리 책임자는 **플랫폼 전체 관리자**로 한다. 행사·체험 운영자는 1차 확인과 고객 안내를 담당하고 지역 관리자는 결제 상태를 변경할 수 없다.
6. 사업자 정보·담당 지역·콘텐츠 소유 관계는 **지역 관리자가 수동 승인**한다. 행사·체험 운영자의 예약 목록에는 이름 `김*수`, 연락처 `010-****-1234` 형식만 표시한다.
7. 후기는 작성 후 **30일 동안 수정**할 수 있고 언제든 삭제할 수 있다. 삭제 즉시 비노출하고 복구 없이 삭제 시점 30일 후 영구 삭제한다.
8. 쿠폰은 무료 예약 MVP에서 제외하고 유료 예약 도입 이후의 후속 MVP에서 구현한다.
9. 프런트엔드 프레임워크, 사용자 채널(Web/App), 알림 채널은 현재 백엔드 MVP 범위에서 제외하고 화면 구현 착수 전 별도 ADR로 결정한다.
10. 사업 KPI는 초기 MVP의 판단 기준에서 제거하고 13장의 **기술 검증 기준**으로 대체한다.
11. 회원정보는 탈퇴 시 파기하고 법정 거래기록만 별도 분리 보관한다. 후기·방문 데이터는 개인 연결을 제거하고 비식별 집계만 남긴다.

현재 PRD의 파일럿 정책 오픈 이슈는 없다. 유료 결제·쿠폰·Redis 분산 락·프런트엔드는 후속 MVP 또는 별도 ADR의 범위로 확정적으로 이관했다.
