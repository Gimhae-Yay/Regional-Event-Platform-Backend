# P1 ERD 정책 결정 로그

> 작성일: 2026-08-05
> 범위: 사용자가 “잠깐 잠깐 처음부터 다시하자”라고 한 시점 이후의 질의·응답만 기록한다. 그 이전의 논의는 폐기된 것으로 취급한다.
>
> 이 문서는 대화에서 확정된 제품·운영 정책의 작업 기록이다. 프로젝트 기준 문서나 채택 ADR을 대체하지 않는다.

## 1. 전체관리자와 역할

| 순서 | 질문 요지 | 사용자 결정 | ERD 반영 의미 |
| --- | --- | --- | --- |
| 1 | P1에 전체관리자 기능이 있는가 | 있다면 P1에 포함 | P1 전체관리자 모델을 포함한다. |
| 2 | 전체관리자 계정과 일반 역할을 같은 역할 테이블에 둘 것인가 | 권한은 별도 관리 | `platform_admin_assignment`를 일반 역할과 분리한다. |
| 3 | 고권한 등급 | `SUPER_ADMIN`, `PLATFORM_ADMIN` 두 등급 | 전용 등급·상태 카탈로그를 둔다. |
| 4 | 고권한 계정과 방문자·운영자·지역관리자 역할 겸임 | 양방향 모두 금지 | 계정 분류를 영구적으로 분리한다. |
| 5 | 고권한이 비활성화된 뒤 일반 역할 전환 | 전환 불가 | 비활성화 후에도 일반 역할을 부여하지 않는다. |
| 6 | 고권한 계정 삭제 | 삭제하지 않고 `INACTIVE` | 권한 배정 이력은 상태 전이로 보존한다. |
| 7 | 비활성 고권한 계정의 탈퇴 | 권한 비활성 후에만 가능 | 사용자 연결을 제거한 비식별 권한 이력을 남긴다. |
| 8 | 최초 슈퍼관리자 준비 | 최초 배포 때 내부 bootstrap으로 1개 생성 | 일반 가입·마이그레이션 비밀번호 하드코딩 경로를 두지 않는다. |
| 9 | 운영 중 고권한 계정 추가 | 허용 | 활성 슈퍼관리자가 새 슈퍼·전체관리자를 만든다. |
| 10 | 슈퍼·전체관리자의 계정 상태 변경 권한 | 슈퍼만 변경 가능 | 전체관리자는 고권한 계정 상태를 바꿀 수 없다. |
| 11 | 슈퍼관리자 보호 | 자기 상태 변경 금지, 활성 슈퍼 0명 금지 | 다른 활성 슈퍼가 있을 때만 비활성화·재활성화한다. |
| 12 | 전체관리자 업무 범위 | 지역·지역관리자·거래 예외 관리, 슈퍼는 이를 상속 | 지역 관리자·운영자의 일반 경로를 우회하지 않는 전용 유스케이스로 제한한다. |
| 13 | 지역관리자 권한 회수 이력 | 추천안 채택 | 일반 역할 배정을 이력형 `ACTIVE`/`REVOKED` 구조로 바꾼다. |

## 2. 지역

| 순서 | 질문 요지 | 사용자 결정 | ERD 반영 의미 |
| --- | --- | --- | --- |
| 14 | 새 지역 운영 상태(`SUSPENDED` 등) 추가 | 고려하지 않음 | 새 상태 열거형을 만들지 않는다. |
| 15 | 지역 공개·운영 표현 | 기존 `is_public` 사용 | `false`는 비공개·준비, `true`는 공개·운영이다. |
| 16 | 공개 지역을 비공개로 바꾸는 조건 | 콘텐츠가 없을 때만 가능 | `content.deleted_at IS NULL`인 행이 하나라도 있으면 `true → false`를 거부한다. |
| 17 | 지역 관리자 수 | 한 지역에 여러 명 허용 | 지역당 복수의 활성 `REGION_ADMIN` 배정을 허용한다. |
| 18 | 마지막 지역 관리자 회수 | 콘텐츠가 있으면 불가 | 비삭제 콘텐츠가 있는 지역에는 활성 지역관리자 1명 이상을 유지한다. |

## 3. 결제·가격·환불

| 순서 | 질문 요지 | 사용자 결정 | ERD 반영 의미 |
| --- | --- | --- | --- |
| 19 | 가격 보관 방식 | 별도 가격 스냅샷 테이블 | 가격·할인·최종 금액을 불변 스냅샷으로 보관한다. |
| 20 | 결제 재시도 가격 | 같은 예약 시도는 같은 스냅샷 | 결제 시도는 같은 `reservation_price_snapshot`을 참조한다. |
| 21 | 결제 대기 예약 상태 | P0 10분 홀드 재사용 | `PENDING_PAYMENT` 예약을 만들지 않는다. |
| 22 | 결제 성공 시 처리 | 홀드 소비와 예약 확정을 함께 처리 | 검증 승인 때만 `reservation(CONFIRMED)`을 생성한다. |
| 23 | 결제 실패 | 결제는 `DECLINED` | 가격 스냅샷은 상태를 갖지 않고 불변으로 남는다. |
| 24 | 동시 결제 시도 | 활성 홀드당 진행 중 시도 1개 | 진행 중 결제가 있으면 새 외부 결제를 시작하지 않는다. |
| 25 | 결제 생성 멱등성 | `Idempotency-Key`, 종결 후 24시간 보관 | 같은 키는 기존 결제를 반환하고 다른 키는 진행 중 오류를 반환한다. |
| 26 | 사용자 결제 취소와 늦은 승인 | 취소 뒤 성공은 자동 확정하지 않음 | `DISCREPANT`로 기록하고 수동 조사한다. |
| 27 | 결제 상태 | `PENDING`, `APPROVED`, `DECLINED`, `CANCELLED`, `EXPIRED`, `DISCREPANT` | `REFUNDED`는 결제 상태에 넣지 않고 환불로 분리한다. |
| 28 | 부분 환불 | 하지 않음 | 환불 금액은 승인 결제의 최종 금액과 같다. |
| 29 | 환불 상태 | `REQUESTED → PROCESSING → SUCCEEDED | FAILED | DISCREPANT` | 환불과 외부 시도 이력을 분리한다. 응답 미수신과 1분 뒤에도 남은 `PENDING`은 외부 결과가 불명확하므로 `DISCREPANT`로 관리한다. |
| 30 | 환불 재시도 | 자동 재시도 없음, 전체관리자만 수동 재시도 | 콘텐츠 운영자·지역 관리자는 재시도하지 못한다. |
| 31 | 환불 최대 시도 | 응답 미수신을 포함해 총 3회 | PortOne 호출은 최대 30초만 기다리고 외부 호출 직전 시도 번호를 점유한다. 1분 주기 `PENDING` 복구 조회는 기존 행만 갱신하므로 시도를 추가 소비하지 않는다. 최초 시스템 시도 1회와 수동 시도 최대 2회를 남긴다. |
| 32 | 결제 불일치 수동 처리 | 예약·결제를 강제 성공시키지 않음 | 증빙 후 문제 없음 종결 또는 전액 환불만 허용한다. |
| 33 | 수동 처리 이중 승인 | P1에서는 미적용 | 권한 있는 전체관리자 1명이 증빙·사유와 함께 처리한다. |
| 34 | PortOne 계약 | V2와 서버 재검증 | V2 거래 ID·웹훅 ID·검증 이력을 보관하고 원문·비밀값은 저장하지 않는다. |
| 35 | 0원 결제 | P0 무료 예약 재사용 | PortOne `payment` 행 없이 가격 스냅샷·쿠폰 사용·홀드 소비·예약 확정을 처리한다. |

## 4. 쿠폰

| 순서 | 질문 요지 | 사용자 결정 | ERD 반영 의미 |
| --- | --- | --- | --- |
| 36 | 쿠폰 한 예약 사용 수 | 최대 1장 | 가격 스냅샷에는 쿠폰 FK를 최대 하나만 둔다. |
| 37 | 결제 중 쿠폰 상태 | 스냅샷 생성 때 `RESERVED`, 승인 때 `USED` | 실패·취소·홀드 만료는 다시 사용 가능 상태로 복구한다. |
| 38 | 쿠폰 상태 이력 | 모든 상태 전이를 별도 이력으로 보관 | `coupon_status_history`는 추가 전용이다. |
| 39 | 만료 반영 | 배치가 `EXPIRED`로 전환하고 이력 기록 | 조회 시점의 계산만으로 처리하지 않는다. |
| 40 | 쿠폰 발급 주체 | 운영자 임의 지급 금지 | 방문·미션 보상·스탬프북 보상에 따른 시스템 발급만 허용한다. |
| 41 | 발급 근거 무결성 | 근거 테이블을 직접 FK로 연결 | `visit`, `mission_reward_claim`, `stampbook_reward_grant` 중 정확히 하나를 연결한다. 미션·스탬프북 보상 근거의 정책은 각각 원본 보상 정책과 일치한다. |
| 42 | 동일 근거 중복 지급 | 같은 근거·같은 정책은 1장 | 각 근거와 정책의 고유 제약을 둔다. |
| 43 | 쿠폰 정책 공개 | 지역 관리자 승인 필요 | `DRAFT → PENDING_REVIEW → PUBLISHED → ENDED`를 사용하며, `PUBLISHED` 정책만 새 쿠폰 발급 근거가 된다. 공개 중인 미션·스탬프북이 완료 보상으로 참조하면 정책 종료를 거부한다. |
| 44 | 할인 방식 | 정액 할인만 | 정률·최소 결제금액·할인 상한을 제외한다. |
| 45 | 적용 범위 | 한 지역의 모든 현재·신규 유료 콘텐츠 | 정책-콘텐츠 매핑 테이블을 만들지 않는다. |
| 46 | 발급 경로 | 정책당 정확히 하나 | `VISIT`, `MISSION_REWARD`, `STAMPBOOK_COMPLETION` 중 하나다. |
| 47 | 방문 보상 지급 한도 | 사용자당 정책별 1회 | 여러 방문으로 같은 정책 쿠폰을 반복 발급하지 않는다. |
| 48 | 쿠폰 유효 기간 | 정책별 발급 후 유효 일수 | 정책 종료 뒤에도 이미 발급된 쿠폰은 자체 만료 시각까지 사용한다. |
| 49 | 예약 취소 시 쿠폰 | 회차 시작 전 취소면 복구 | 원래 만료 시각은 연장하지 않는다. 기존 쿠폰 사용 이력은 삭제하지 않고 `REVERSED`로 남긴다. |
| 50 | 공개 후 정책 수정 | 핵심 값 수정 금지, 종료만 허용 | 발급된 쿠폰의 기준을 바꾸지 않는다. |

## 8. 초안 반영 전 확인이 필요한 연결 정책

다음 항목은 위 결정들을 서로 연결할 때 새로 드러난 공백이다. 사용자에게 아직 질문하지 않았으므로 ERD 초안에서 미확정으로 표시한다.

1. 미션이 종료된 뒤 이미 `COMPLETED`지만 보상 수령 요청을 하지 않은 사용자의 수령 기한
3. P1 공통 감사 기록의 90일 보관 기간을 특권·거래 감사에도 그대로 적용할지 여부
