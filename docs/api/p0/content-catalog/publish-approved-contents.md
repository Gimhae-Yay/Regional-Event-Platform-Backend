## 승인 콘텐츠 자동 공개

이 기능은 외부 클라이언트가 호출하는 HTTP API가 아닌 내부 스케줄러 작업이다.
실행 경로 식별자는 `scheduler`이며, 외부 URL·인증 헤더·JSON 요청과 응답은 제공하지 않는다.

스케줄러는 승인된 공개 예정 시각이 도래한 콘텐츠를 `PUBLISHED`로 전환한다. 공개 전 수정 심사, 소프트 삭제와
다른 상태 전이가 먼저 성공한 콘텐츠는 공개하지 않는다.

### 실행 계약

| 항목 | 계약 |
| --- | --- |
| 실행 경로 | `scheduler` |
| 실행 주체 | 애플리케이션 내부 스케줄러 |
| 외부 HTTP 경로 | 없음 |
| 인증·인가 | 없음. 외부 요청을 받지 않는다. |
| 요청 본문·응답 본문 | 없음 |
| 시간 기준 | 애플리케이션 서버 시계가 아닌 MySQL 현재 시각 |
| 실행 주기 | 운영 설정으로 관리한다. 스케줄러 지연은 실제 공개를 늦출 수 있지만 공개 예정 시각 전 전이를 허용하지 않는다. |

### 처리 대상과 상태 전이

| 구분 | 대상 조건 | 상태 전이 | 공개 처리 |
| --- | --- | --- | --- |
| 자동 공개 | `status = APPROVED`, `deleted_at IS NULL`, `publish_at <= MySQL 현재 시각` | `APPROVED → PUBLISHED` | 공개 조회의 현재 상태 검증을 통과한다. |

### 처리 규칙

1. 스케줄러는 `content(status, publish_at, deleted_at)` 인덱스를 기준으로 대상 후보를 조회한다.
2. 공개 판정은 `publish_at <= MySQL 현재 시각`, `status = APPROVED`, `deleted_at IS NULL`을 함께 조건으로 사용한다. 애플리케이션 서버 시계, 스케줄러 실행 시각 또는 캐시 값을 기준으로 판정하지 않는다.
3. 콘텐츠 상태 전이는 반드시 `APPROVED`를 조건으로 수행한다. 이미 `PUBLISHED`이거나 다른 상태가 된 콘텐츠는 변경하지 않는다.
4. 자동 공개 성공 시 콘텐츠 상태, `PUBLISHED` 콘텐츠 로그와 성공 감사 기록을 하나의 MySQL 트랜잭션에서 함께 커밋한다.
5. `content_log.status`는 `PUBLISHED`, `actor_id`와 `reason`은 `NULL`이고 `date`는 MySQL 기준 공개 처리 시각이다. 실제 공개 시각은 이 로그의 `date`이며 `content`에 별도 `published_at`을 저장하지 않는다.
6. 공개 전 수정본 생성이 먼저 원본을 `APPROVED → PENDING`으로 전환하면 기존 `publish_at`이 도래했어도 자동 공개하지 않는다. 수정본 승인으로 다시 `APPROVED`가 된 뒤 반영된 `publish_at`을 기준으로 처리한다.
7. 자동 공개가 공개 전 수정본 생성보다 먼저 성공하면 이후 수정 요청은 `PUBLISHED` 콘텐츠 수정본 계약을 따른다.
8. 소프트 삭제와 경합하면 `APPROVED`, `deleted_at IS NULL` 조건을 먼저 충족해 커밋한 처리만 성공한다. 삭제가 먼저 성공하면 공개하지 않고, 공개가 먼저 성공하면 공개 이후 콘텐츠 삭제를 허용하지 않는다.
9. 승인 트랜잭션이 과거 또는 현재의 `publish_at`으로 커밋되더라도 승인 경계가 직접 공개하지 않는다. 다음 스케줄러 실행이 현재 상태와 MySQL 시각을 다시 확인해 공개한다.
10. 공개 조회는 `publish_at`만으로 노출하지 않고 MySQL의 현재 `status = PUBLISHED`와 `deleted_at IS NULL`을 항상 검증한다. 스케줄러 지연 중인 `APPROVED` 콘텐츠는 공개하지 않는다.
11. 하나의 후보 처리에서 예외가 발생하면 해당 콘텐츠의 상태·로그·성공 감사를 함께 롤백한다. 다음 스케줄러 실행에서 같은 후보를 재시도할 수 있다.
12. 스케줄러가 중복 실행되거나 다중 인스턴스에서 동시에 실행돼도 `APPROVED` 조건부 전이에 먼저 성공한 처리만 상태 변경·콘텐츠 로그·성공 감사를 한 번 반영한다.
13. 스케줄러는 외부 API 응답을 만들지 않는다. 처리 건수, 실제 공개 시각과 `publish_at`의 차이, 실패 사유는 구조화 로그와 비개인 운영 지표로 관찰한다.

### 감사 및 정합성

- 감사 이벤트의 공통 필드와 보관 규칙은 [P0 감사 및 운영 로그](../../../p0-spec.md#88-감사-및-운영-로그)와
  [ADR-0015](../../../adr/0015-store-audit-events-in-mysql-with-withdrawn-actor-anonymization.md#결정)를 따른다.
- 성공한 자동 공개는 콘텐츠·지역 식별자, `APPROVED → PUBLISHED` 전이와 MySQL 기준 처리 시각을 재현할 수 있도록 감사 기록에 남긴다.
- 스케줄러 실행마다 고유한 `requestId`를 생성한다. 자동 공개 성공·실패 감사 이벤트의 `actor_kind`는 `SYSTEM`이며
  사용자 처리자 또는 `audit_event_actor_link`를 연결하지 않는다.
- 후보 처리 예외로 트랜잭션이 롤백되면 롤백 완료 후 `result = FAILURE`와 비개인 실패 코드를 가진 감사 이벤트를
  독립 트랜잭션으로 기록한다. 이 실패 감사 기록도 실패하면 구조화 로그로 관찰한다.
- 후보 조회 후 다른 처리가 먼저 성공해 상태 조건이 달라진 정상적인 건너뛰기는 처리 실패로 기록하지 않는다.
- 콘텐츠 상태 갱신, 콘텐츠 로그 또는 성공 감사 기록 중 하나라도 실패하면 어느 변경도 커밋하지 않는다.
- 공개 전 수정본 생성·삭제·다른 상태 전이와 경합해도 같은 콘텐츠의 `APPROVED → PUBLISHED`는 최대 한 번만 발생한다.
- Redis 캐시가 있거나 장애가 발생해도 MySQL의 현재 공개 상태 검증을 생략하지 않으며, 캐시 값만으로 `APPROVED` 콘텐츠를 공개하지 않는다.
