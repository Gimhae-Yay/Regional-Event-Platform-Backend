> 이 문서는 P1 유료 결제·환불 정책의 단일 기준이다. P1은 PortOne V2를 서버 재검증하고,
> P0 `capacity_hold`와 불변 가격 스냅샷을 재사용한다. PortOne 세부 연동은 아래 공급자 계약을 따른다.

## 1. 범위

### P1-FR-07. 유료 결제

- 활성 `capacity_hold`와 불변 가격 스냅샷에 연결된 내부 결제 요청을 생성한다. 예약은 서버 승인 뒤에만 생성한다.
- 서버가 PortOne의 거래 결과를 확인해 내부 결제 상태를 반영한다.
- 방문자는 본인 결제 상태를 조회한다.
- PortOne 웹훅을 인증·중복 처리 방지와 함께 수신한다.

### P1-FR-08. 취소·환불

- 방문자는 유료 예약 취소와 환불을 요청하고 본인 환불 상태를 조회한다.
- 담당 콘텐츠 운영자는 담당 예약의 결제·환불 상태를 조회한다.
- `FAILED` 환불은 `SUPER_ADMIN` 또는 `PLATFORM_ADMIN`만 권한 있는 운영 절차로 재요청한다.
- 결제 불일치와 환불 실패의 최종 수동 처리는 [전체관리자](platform-admin.md) 범위에서 수행한다.

## 2. 유저 시나리오

### US-P1-07. 방문자가 유료 예약 결제를 완료한다

- **주체:** 방문자
- **목표:** 예약 대상과 금액이 일치하는 결제 결과를 확인한다.
- **선행 조건:** 유료 예약 대상, 가격 기준과 결제 가능 조건이 확정돼 있다.

#### 기본 흐름

1. 방문자가 활성 정원 홀드에 대한 유료 결제 생성을 요청한다.
2. 시스템은 홀드 소유자·상태, 불변 가격 스냅샷과 기존 `PENDING` 결제 시도를 확인하고 내부 결제 요청을 만든다.
3. 클라이언트는 내부 결제 식별자와 연결된 PortOne 결제 절차를 수행한다.
4. PortOne 웹훅이 도착하면 서버가 외부 거래를 조회·검증한다.
5. 검증된 거래의 금액, 통화, 주문 식별자와 홀드·가격 스냅샷 대상이 일치하면 내부 결제 상태를 반영하고 예약과 적용 쿠폰 사용을 함께 확정한다.
6. 사용자는 본인 결제 상태를 조회한다.

#### 예외 흐름

- 클라이언트가 보낸 성공 표시만으로 내부 결제 성공을 처리하지 않는다.
- 외부 거래 식별자, 금액, 주문 식별자 또는 홀드·가격 스냅샷 대상이 다르면 성공 상태로 전이하지 않고 불일치로 기록한다.
- 웹훅이 반복되거나 서로 다른 결제 이벤트의 순서가 뒤바뀌면 최초 반영 결과를 따르고 예약·결제·쿠폰 상태를 중복 전이시키지 않는다.
- 외부 서비스 지연·실패가 발생해도 장시간 데이터베이스 잠금을 유지하지 않는다.

**적용 정책:** `PAY-01`~`PAY-04`

### US-P1-08. 방문자가 취소·환불을 요청하고 운영자가 상태를 확인한다

- **주체:** 방문자, 담당 콘텐츠 운영자, 권한 있는 환불 처리자
- **목표:** 유료 예약 취소와 환불의 진행 상태를 역할별 범위 안에서 추적한다.
- **선행 조건:** 예약과 결제가 연결돼 있으며 취소·환불 가능 조건이 확정돼 있다.

#### 기본 흐름

1. 방문자가 본인 유료 예약의 취소·환불을 요청한다.
2. 시스템은 예약·결제·쿠폰 상태와 환불 가능 조건을 검증한다.
3. 최초 요청이면 환불 요청과 처리 이력을 만들고 외부 환불 처리를 시작한다.
4. 최종 금액 0원 예약은 회차 시작 전 취소 성공 시, 양수 결제 예약은 회차 시작 전 사용자·운영자 취소의 전액 환불이 완료되면 연결된 쿠폰 사용 이력을 반전하고 쿠폰을 복구한다.
5. 방문자는 내 환불 상태를 조회한다.
6. 담당 콘텐츠 운영자는 담당 예약의 결제·환불 상태를 조회해 고객 안내에 사용한다.
7. 일시 실패한 환불은 확정된 권한과 재시도 규칙에 따라 재시도한다.
8. 처리 불일치 또는 실패가 남으면 전체관리자 수동 처리 절차로 이관한다.

#### 예외 흐름

- 다른 사용자의 예약·환불 상태는 조회하거나 취소할 수 없다.
- 이미 종결된 환불을 다시 요청해 새 환불 효과를 만들 수 없다.
- 지역 관리자는 결제·환불 상태를 직접 변경할 수 없다.
- 외부 취소 결과가 불명확하면 내부 상태를 성공으로 단정하거나 쿠폰을 복구하지 않고 불일치·재조사 대상으로 남긴다.
- 외부 환불 호출은 최대 30초 동안만 응답을 기다린다. 응답 없이 끝난 호출도 시도 이력과 최대 시도 횟수에 포함하며, 외부 재조회로 미처리가 확인되기 전에는 다시 호출하지 않는다.
- 프로세스 종료로 결과 확정 전 남은 환불 시도는 1분 고정 지연 복구 작업이 PortOne 상태를 재조회해 같은 시도 행으로 확정하며, 새 환불 호출이나 새 시도 횟수를 만들지 않는다.

**적용 정책:** `PAY-05`~`PAY-07`

## 3. 결제·환불 정책

- `PAY-01`:
  결제 생성은 활성 `capacity_hold`, 홀드당 하나의 불변 가격 스냅샷과 내부 결제 식별자를 연결한다. 홀드 하나에는 진행 중 `PENDING` 결제를 최대 하나만 허용한다.
  같은 홀드의 재시도는 같은 가격·쿠폰 스냅샷을 사용하며, 결제 생성 멱등성은 전용 `payment_idempotency`에 24시간 보관한다. 쿠폰 선택과 선점은 결제 생성이 소유하고 최종 금액이 0원이면 같은 요청에서 예약과 쿠폰 사용을 확정한다.
- `PAY-02`:
  결제 승인 확인은 서버가 PortOne V2에서 조회한 거래 정보를 기준으로 수행한다.
  외부 거래 식별자, 내부 주문 식별자, 금액, 통화와 예약 대상의 일치 여부를 검증하고,
  검증 실패는 성공 상태로 전이하지 않는다.
- `PAY-03`:
  예약 상태와 결제 상태는 분리해 관리한다. 결제 상태는 `PENDING`, `APPROVED`, `DECLINED`, `CANCELLED`, `EXPIRED`, `DISCREPANT`이고, 환불은 별도 상태로 관리한다.
  양수 결제는 서버 검증 승인 때만 홀드 소비·`reservation(CONFIRMED)` 생성·결제 `APPROVED` 전이와 적용 쿠폰 사용을 같은 트랜잭션으로 처리한다. 취소 뒤 늦은 외부 성공은 예약을 되살리지 않고 `DISCREPANT`로 기록하며, 원본 외부 응답 해시와 내부 판단 결과를 함께 추적한다.
- `PAY-04`:
  웹훅은 PortOne V2 웹훅 버전 `2024-04-25`의 Standard Webhooks HMAC-SHA256 인증·검증 절차를 통과한 요청만 처리한다.
  원문 본문과 `webhook-id`, `webhook-timestamp`, `webhook-signature`을 검증하고 `webhook-id`를 외부 이벤트 식별자로 사용한다.
  결제 수신 경로는 `Transaction.*`만 결제·예약·쿠폰 처리 대상으로 삼는다. 정상 `BillingKey.*`와 이후 추가되는 알 수 없는 `type`은 공통 JSON 검증 뒤 결제 필드를 요구하거나 결제 이력을 만들지 않고 `200 OK`로 끝낸다.
  같은 외부 이벤트의 재전송과 서로 다른 웹훅 이벤트의 순서 역전·동시 도착은 하나의 내부 처리 결과로 수렴해야 한다. 양수 결제 승인·예약·쿠폰 사용 확정의 HTTP 진입점은 웹훅 하나만 둔다.
- `PAY-05`:
  취소·환불 요청은 본인 예약과 회차 시작 전 조건을 검증한다. 환불 금액은 승인 결제의 최종 금액 전체이며 부분 환불은 지원하지 않는다.
  요청, 외부 호출 결과, 상태 변화와 쿠폰 연계 판단을 분리된 이력으로 남기며,
  같은 요청의 재시도는 새 환불 효과를 만들지 않는다. 외부 호출 직전에 시도 이력을 만들고,
  최대 30초 내 응답을 받지 못하면 실패 사유와 함께 남겨 시도 횟수에 포함한다.
  사용자의 회차 시작 전 취소와 운영자 취소는 전액 환불한다. 해당 환불이 최초 요청·재시도·수동 확정·복구 작업 중 어느 경로에서든 `SUCCEEDED`로 완료되면 쿠폰 사용 이력을 `REVERSED`로 남기고
  원래 만료 시각을 유지해 쿠폰을 복구한다. 최종 금액 0원 예약은 결제·환불 행을 만들지 않으므로 회차 시작 전 예약 취소 성공을 복구 완료 시점으로 사용한다. 원래 만료 시각이 지났으면 쿠폰은 `EXPIRED`가 되며,
  같은 취소·환불의 재처리는 새 반전 이력이나 추가 복구 효과를 만들지 않는다. 보류·실패한 환불과 회차 시작 뒤 취소에서는 쿠폰을 복구하지 않는다.
- `PAY-06`:
  방문자는 본인 결제·환불만, 콘텐츠 운영자는 담당 예약만 조회한다.
  지역 관리자는 결제·환불 상태를 변경하지 않는다. 전체관리자 전용 수동 처리 권한은 일반 경로에서 재사용하지 않는다.
- `PAY-07`:
  환불 재시도는 이전 시도와 외부 거래 상태를 확인한 뒤 수행한다.
  응답 미수신은 외부 결과가 불명확한 상태로 분류해 재조사하며, 외부 미처리가 확인된 뒤에만 남은 횟수 안에서 재시도한다.
  1분이 지난 `PENDING` 시도는 PortOne 재조회로 같은 시도 행을 확정하며, 복구 확인은 재시도 횟수를 추가로 소비하지 않는다.
  P1은 총 3회, 자동 재시도 금지, 외부 호출 최대 30초, 1분 주기 `PENDING` 복구를 적용한다.

## 4. PortOne V2 공급자 계약

| 항목 | 확정 계약 |
| --- | --- |
| 웹훅 형식 | 결제모듈 V2 웹훅 버전 `2024-04-25`, `application/json` 본문을 사용한다. 테스트와 실연동 URL·웹훅 시크릿은 PortOne 콘솔에서 서로 분리해 설정한다. |
| 웹훅 식별·본문 | 재전송 멱등 식별자는 본문의 값이 아닌 `webhook-id` 헤더다. 모든 본문은 `type`, 이벤트 발생 시각 `timestamp`, `data.storeId`를 가진다. 결제 처리 대상 `Transaction.*`은 `data.paymentId`, `data.transactionId`와 취소 이벤트의 선택 `data.cancellationId`를 가진다. `BillingKey.*`는 별도 `data.billingKey` 형식이므로 이 결제 경로에서는 공통 검증 뒤 `200 OK`로 끝낸다. |
| 서명 검증 | `webhook-id.webhook-timestamp.원문_본문`을 Standard Webhooks의 `v1` HMAC-SHA256 서명으로 검증한다. `webhook-signature`의 공백 구분 후보 중 하나가 일치해야 하고, `webhook-timestamp`는 현재 시각의 ±5분 안이어야 한다. |
| 서버 SDK | JVM 구현은 `io.portone:server-sdk:0.22.0`의 `WebhookVerifier`를 사용한다. 검증기는 PortOne API Secret이 아닌 웹훅 시크릿을 받으며 HMAC-SHA256 대칭 서명만 지원한다. |
| PortOne 거래 재조회 | V2 API의 `GET /payments/{paymentId}`를 V2 API Secret으로 조회한다. `Authorization` 헤더는 `PortOne` 접두사 뒤에 배포 환경에서 주입한 API Secret 값을 붙인다. |
| 환경별 비밀값 | 배포 환경의 비밀 저장소에서 테스트·실연동별 `PORTONE_API_SECRET`과 `PORTONE_WEBHOOK_SECRET`을 주입한다. API Secret은 거래 조회에만, 웹훅 시크릿은 서명 검증에만 사용한다. DB·문서·로그·감사 이력에는 원문이나 값을 저장하지 않는다. |
| 시크릿 교체 | PortOne 콘솔에서 환경별 두 번째 웹훅 시크릿을 발급하고 배포 환경의 `PORTONE_WEBHOOK_SECRET`을 새 값으로 교체한 뒤 기존 시크릿을 만료한다. PortOne이 회전 기간에 복수 `v1` 서명을 보내므로 검증기는 새 시크릿으로 하나라도 일치하는 값을 수용한다. |
| 재전송 | PortOne은 비-`2xx`, 타임아웃, 연결 실패를 실패로 보고 최초 전송 뒤 최대 5회 재전송한다. 재전송 기본 지연은 1분·4분·16분·64분·256분이며 Full Jitter가 적용되고, 마지막 재전송 실패 뒤 전송을 종료한다. 정상 형식·서명의 웹훅에서 일시적 PortOne 거래 조회 실패에만 `500`을 반환하고, 조회 성공 또는 조회 불필요한 경우에는 `200`을 반환한다. |

계약의 외부 기준은 [PortOne V2 웹훅 연동 가이드](https://developers.portone.io/opi/ko/integration/webhook/readme-v2?v=v2),
[PortOne V2 REST API](https://developers.portone.io/api/rest-v2?v=v2),

## 5. 구현 전 잔여 확정 항목

## 6. 데이터 요구사항

| 데이터 | 핵심 식별·연결 정보 | 용도 |
| --- | --- | --- |
| 가격 스냅샷 | `reservation_price_snapshot_id`, `hold_id`, 적용 쿠폰, 기본·할인·최종 금액, 통화 | 홀드 기준 가격·쿠폰의 불변 기준 |
| 결제 | `payment_id`, `hold_id`, 가격 스냅샷, nullable `reservation_id`, 내부·외부 거래 식별자, 상태 | 결제 생성·서버 승인·조회 |
| 결제 생성 멱등 기록 | 요청자 비-FK 식별값, 연산·키·요청 해시, 처리 상태, 결제 결과, 만료 시각 | 동일 결제 생성 요청의 수렴과 24시간 보관 |
| 결제 검증 이력 | 결제, 검증 원인, 비교 결과, 처리 시각 | 서버 검증과 불일치 추적 |
| 웹훅 처리 이력 | 외부 이벤트 식별자, 결제, 인증 결과, 처리 결과, 수신 시각 | 재전송 중복 차단과 감사 |
| 환불 | `refund_id`, 결제, 전액 환불 금액, 상태, 요청·종결 시각 | 취소·환불 수명주기 |
| 환불 시도 이력 | 환불, 시도 번호, 요청 원인, 호출 결과, 응답 미수신 사유, 외부 결과, 재시도·종결 정보 | 실패 추적과 안전한 재시도 |
| 결제 불일치 | 결제, 관측된 차이, 증빙 참조, 처리 결과 | 전체관리자 수동 처리 |

상세 엔티티, 컬럼, 관계, 고유 제약과 인덱스는 [P1 ERD](../p1-erd.md)에 확정하고, P0 재사용 테이블은 [P0 ERD](../erd.md)를 따른다.
