> 이 문서는 P1 유료 거래의 기능 계약을 정의한다. PortOne의 구체적 연동 버전과 상태 모델은
> 공급자 계약을 확인한 뒤 ADR·API·ERD에서 확정한다.

## 1. 범위

### P1-FR-07. 유료 결제

- 유료 예약에 연결된 내부 결제 요청을 생성한다.
- 서버가 PortOne의 거래 결과를 확인해 내부 결제 상태를 반영한다.
- 방문자는 본인 결제 상태를 조회한다.
- PortOne 웹훅을 인증·중복 처리 방지와 함께 수신한다.

### P1-FR-08. 취소·환불

- 방문자는 유료 예약 취소와 환불을 요청하고 본인 환불 상태를 조회한다.
- 담당 콘텐츠 운영자는 담당 예약의 결제·환불 상태를 조회한다.
- 실패 또는 재시도가 필요한 환불을 권한 있는 운영 절차로 재요청한다.
- 결제 불일치와 환불 실패의 최종 수동 처리는 [전체관리자](platform-admin.md) 범위에서 수행한다.

## 2. 유저 시나리오

### US-P1-07. 방문자가 유료 예약 결제를 완료한다

- **주체:** 방문자
- **목표:** 예약 대상과 금액이 일치하는 결제 결과를 확인한다.
- **선행 조건:** 유료 예약 대상, 가격 기준과 결제 가능 조건이 확정돼 있다.

#### 기본 흐름

1. 방문자가 유료 예약에 대한 결제 생성을 요청한다.
2. 시스템은 예약 자격, 가격 스냅샷과 기존 결제 시도를 확인하고 내부 결제 요청을 만든다.
3. 클라이언트는 내부 결제 식별자와 연결된 PortOne 결제 절차를 수행한다.
4. 결제 확인 요청 또는 PortOne 웹훅이 도착하면 서버가 외부 거래를 조회·검증한다.
5. 검증된 거래의 금액, 통화, 주문 식별자와 예약 연결이 일치하면 내부 결제 상태를 반영한다.
6. 사용자는 본인 결제 상태를 조회한다.

#### 예외 흐름

- 클라이언트가 보낸 성공 표시만으로 내부 결제 성공을 처리하지 않는다.
- 외부 거래 식별자, 금액 또는 대상 예약이 다르면 성공 상태로 전이하지 않고 불일치로 기록한다.
- 결제 확인·웹훅이 반복되면 최초 반영 결과를 반환하고 예약·결제 상태를 중복 전이시키지 않는다.
- 외부 서비스 지연·실패가 발생해도 장시간 데이터베이스 잠금을 유지하지 않는다.

**적용 정책:** `PAY-01`~`PAY-04`

### US-P1-08. 방문자가 취소·환불을 요청하고 운영자가 상태를 확인한다

- **주체:** 방문자, 담당 콘텐츠 운영자, 권한 있는 환불 처리자
- **목표:** 유료 예약 취소와 환불의 진행 상태를 역할별 범위 안에서 추적한다.
- **선행 조건:** 예약과 결제가 연결돼 있으며 취소·환불 가능 조건이 확정돼 있다.

#### 기본 흐름

1. 방문자가 본인 유료 예약의 취소·환불을 요청한다.
2. 시스템은 예약·결제·쿠폰 상태와 환불 가능 조건을 검증한다.
3. 최초 요청이면 환불 요청과 처리 이력을 만들고 외부 환불 처리를 시작한다.
4. 방문자는 내 환불 상태를 조회한다.
5. 담당 콘텐츠 운영자는 담당 예약의 결제·환불 상태를 조회해 고객 안내에 사용한다.
6. 일시 실패한 환불은 확정된 권한과 재시도 규칙에 따라 재시도한다.
7. 처리 불일치 또는 실패가 남으면 전체관리자 수동 처리 절차로 이관한다.

#### 예외 흐름

- 다른 사용자의 예약·환불 상태는 조회하거나 취소할 수 없다.
- 이미 종결된 환불을 다시 요청해 새 환불 효과를 만들 수 없다.
- 지역 관리자는 결제·환불 상태를 직접 변경할 수 없다.
- 외부 취소 결과가 불명확하면 내부 상태를 성공으로 단정하지 않고 불일치·재조사 대상으로 남긴다.

**적용 정책:** `PAY-05`~`PAY-07`

## 3. 결제·환불 정책

- `PAY-01`:
  결제 생성은 유료 예약, 가격 스냅샷과 내부 결제 식별자를 연결한다.
  새 결제 시도 생성 조건, 같은 예약의 복수 시도 허용 여부와 결제 유효 기간은 구현 전 확정한다.
- `PAY-02`:
  결제 승인 확인은 서버가 PortOne에서 조회한 거래 정보를 기준으로 수행한다.
  외부 거래 식별자, 내부 주문 식별자, 금액, 통화와 예약 대상의 일치 여부를 검증하고,
  검증 실패는 성공 상태로 전이하지 않는다.
- `PAY-03`:
  예약 상태와 결제 상태는 분리해 관리한다. 결제 결과가 예약에 미치는 전이와 불일치 판정 기준은
  구현 전 상태 전이표로 확정하며, 원본 외부 응답과 내부 판단 결과를 함께 추적한다.
- `PAY-04`:
  웹훅은 채택한 PortOne 연동 계약의 인증·검증 절차를 통과한 요청만 처리한다.
  같은 외부 이벤트의 재전송, 승인 확인과 웹훅의 순서 역전·동시 도착은 하나의 내부 처리 결과로 수렴해야 한다.
- `PAY-05`:
  취소·환불 요청은 본인 예약과 확정된 환불 가능 조건을 검증한다.
  요청, 외부 호출 결과, 상태 변화와 쿠폰 연계 판단을 분리된 이력으로 남기며,
  같은 요청의 재시도는 새 환불 효과를 만들지 않는다.
- `PAY-06`:
  방문자는 본인 결제·환불만, 콘텐츠 운영자는 담당 예약만 조회한다.
  지역 관리자는 결제·환불 상태를 변경하지 않는다. 전체관리자 전용 수동 처리 권한은 일반 경로에서 재사용하지 않는다.
- `PAY-07`:
  환불 재시도는 이전 시도와 외부 거래 상태를 확인한 뒤 수행한다.
  재시도 한도, 자동·수동 처리 구분, 지연·실패 분류와 종결 기준은 구현 전 확정한다.

## 4. 구현 전 확정 항목

| 항목 | 확정할 내용 |
| --- | --- |
| PortOne 연동 계약 | 사용하는 API·SDK 버전, 인증 정보 보관 방식, 웹훅 검증·재전송 규약 |
| 거래 상태 모델 | 결제·예약·환불의 상태 전이, 불일치·보류·종결 상태와 허용 전이 |
| 금액·가격 정책 | 가격 스냅샷 시점, 통화, 할인·쿠폰 적용 순서와 금액 비교 기준 |
| 취소·환불 조건 | 사용자·운영자 취소 조건, 전액·부분 환불 여부, 쿠폰 복구와 수수료 처리 |
| 재시도 운영 | 자동 재시도, 수동 재시도, 외부 결과 불명확 시 조사·종결 절차 |

## 5. 데이터 요구사항

| 데이터 | 핵심 식별·연결 정보 | 용도 |
| --- | --- | --- |
| 결제 | `payment_id`, `reservation_id`, `user_id`, 금액·통화, 내부·외부 거래 식별자, 상태 | 결제 생성·승인·조회 |
| 결제 검증 이력 | 결제, 검증 원인, 비교 결과, 처리 시각 | 서버 검증과 불일치 추적 |
| 웹훅 처리 이력 | 외부 이벤트 식별자, 결제, 인증 결과, 처리 결과, 수신 시각 | 재전송 중복 차단과 감사 |
| 환불 | `refund_id`, 결제, 요청자, 요청 금액, 상태, 외부 환불 식별자 | 취소·환불 수명주기 |
| 환불 시도 이력 | 환불, 시도 번호, 요청 원인, 외부 결과, 재시도·종결 정보 | 실패 추적과 안전한 재시도 |
| 결제 불일치 | 결제, 관측된 차이, 증빙 참조, 처리 결과 | 전체관리자 수동 처리 |

상세 엔티티, 컬럼, 관계, 고유 제약과 인덱스는 [ERD](../erd.md)에 확정한다.
