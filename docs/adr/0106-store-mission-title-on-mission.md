# ADR-0106: 미션이 방문자 표시 제목을 직접 소유한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-18
- 결정일: 2026-08-18
- 관련 요구사항: [P1-FR-03·P1-FR-04](../p1-spec.md#6-기능-요구사항과-소유-문서), [지역 미션 `MSN-01`·`MSN-05`](../p1/regional-mission.md#3-지역-미션-정책)
- 관련 단계: 단계 0. 정책·설계 확정
- 관련 이슈: [#910](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/910), [#912](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/912)
- 대체 대상: 없음

## 맥락

방문자는 공개 미션 목록과 본인의 미션 참여 목록·상세를 조회할 수 있지만 현재 응답에는 `missionId`만 있고
사람이 미션을 구분할 제목이 없다. 현재 `mission`은 완료 조건과 보상·상태·종료 시각만 저장하며, 생성·수정
요청에도 제목이 없다.

`CONTENT_SET`에는 여러 대상 콘텐츠가 연결될 수 있고 각 콘텐츠 제목은 미션과 별도 수명주기로 관리된다.
`VISIT_COUNT`에는 제목을 파생할 대상 콘텐츠가 없다. 따라서 두 조건 유형에서 동일하게 사용할 표시명 원천과
공개 뒤 불변성, 기존 데이터 전환을 함께 결정해야 한다.

## 결정 동인과 불변 조건

- `VISIT_COUNT`와 `CONTENT_SET` 모두 사람이 식별할 수 있는 제목을 제공한다.
- 제목은 미션의 조건·대상 콘텐츠 변경과 독립된 하나의 값이며 공개 뒤 바뀌지 않는다.
- 제목 추가가 미션 상태, 조건, 보상, 참여, 진행도와 기존 조회 정렬을 바꾸지 않는다.
- 생성·수정 요청의 제목 실패는 다른 입력 검증과 같은 공개 오류 계약을 사용한다.
- 기존 미션은 누락 없이 제목을 얻고, 전환 뒤 새 행에는 제목이 반드시 존재한다.
- 제목 값 자체를 감사·구조화 로그에 기록하지 않는다.

## 결정

`mission`이 방문자 표시 제목을 직접 소유한다. 물리 모델은 `title VARCHAR(255) NOT NULL`을 사용하며 제목에
유일 제약이나 유일 인덱스를 두지 않는다. 같은 지역·상태 또는 서로 다른 지역에서 같은 제목을 허용한다.

운영자 미션 생성과 수정 요청은 JSON 필드 `title`을 필수로 받는다. 서버는 양끝 공백을 제거하고 내부 공백은
입력 그대로 보존한다. 정규화한 제목은 Unicode code point 기준 1자 이상 255자 이하여야 한다. 별도 문자
allowlist를 두지 않는다.
조건을 위반하면 `400 INVALID_INPUT`을 반환하고 미션과 감사 성공 이벤트를 만들거나 변경하지 않는다.

제목은 조건·보상·종료 시각과 같은 미션 핵심 값이다. 생성 시 `DRAFT`에 저장하고 `DRAFT`에서만 전체 교체
수정할 수 있다. `PENDING_REVIEW`, `PUBLISHED`, `ENDED`에서는 제목을 변경하지 않는다. 기존
`DRAFT → DRAFT`, `reason_code = MISSION_UPDATED` 감사로 수정 발생만 기록하며 제목 전·후 값의 별도 변경
이력은 만들지 않는다. 감사 이벤트와 구조화 로그에는 제목 값을 넣지 않는다.

제목 입력은 `POST /api/v1/operator/missions`와 `PATCH /api/v1/operator/missions/{missionId}`에 추가한다.
제목 응답은 다음 방문자 API에만 추가한다.

- `GET /api/v1/regions/{regionId}/missions`
- `GET /api/v1/me/mission-participations`
- `GET /api/v1/me/mission-participations/{participationId}`

운영자·지역 관리자 조회 응답과 `GET /api/v1/missions/{missionId}` 공개 상세 응답은 이 결정에서 변경하지 않는다.
기존 응답 래퍼, 인증·인가, 상태 필터, 페이지네이션, 정렬과 나머지 필드도 유지한다.

## 결과와 트레이드오프

### 기대 효과

- 방문자는 조건 유형과 진행 상태가 같은 미션도 제목으로 구분할 수 있다.
- 공개 미션과 참여 이력이 대상 콘텐츠 제목의 수정 여부와 무관한 표시명을 유지한다.
- 생성·수정·조회가 하나의 `mission.title`을 사용하므로 별도 파생 규칙이 필요 없다.
- 중복 제목을 허용해 이름 선점과 지역·기간별 유일성 경합을 만들지 않는다.

### 수용한 단점과 위험

- 기존 모든 미션 행을 backfill한 뒤 `NOT NULL`로 전환해야 한다.
- 같은 제목의 미션이 여러 개일 수 있으므로 클라이언트는 식별자로 `missionId`를 계속 사용해야 한다.
- 문자 allowlist가 없으므로 제목의 표현 품질은 운영자 입력과 지역 관리자 검토에 의존한다.
- 별도 제목 변경 이력이 없어 감사만으로 이전 제목 값을 복원할 수 없다.

## 전환과 롤백

문서 계약을 먼저 반영한 뒤 별도 Fix Task에서 다음 순서로 전환한다.

1. 호환 migration에서 `mission.title`을 nullable `VARCHAR(255)`로 추가한다.
2. 기존 각 행을 `미션 {mission_id}` 형식으로 backfill하고 행 수, null·빈 문자열·길이를 검증한다.
3. 운영자 클라이언트가 생성·수정 요청에 제목을 보내도록 전환한 뒤, 제목을 필수 검증하고 새 행에 저장하는
   애플리케이션을 배포한다. 이 단계의 DB 컬럼은 구버전 writer와 롤백 호환을 위해 nullable로 유지한다.
4. 모든 writer가 새 버전이고 새 null 행이 생기지 않음을 확인한 뒤 후속 migration에서 `title`을 `NOT NULL`로
   변경한다. 영구 기본값은 두지 않는다.
5. 세 방문자 조회 응답의 제목과 기존 API 회귀 검증을 완료한다.

`NOT NULL` 전환 전 애플리케이션 배포에 실패하면 이전 애플리케이션으로 롤백하되 backfill된 nullable 컬럼은
유지한다. `NOT NULL` 전환 뒤 이전 애플리케이션으로 롤백해야 하면 먼저 제목 값을 보존한 채 컬럼을 nullable로
되돌리는 호환 migration을 적용한다. 제목 컬럼 제거는 새 계약을 철회하는 후속 ADR과 API 호환 계획을 채택한
경우에만 수행한다.

## 검증 방법

- 생성·수정에서 제목 누락, null, 공백만 입력, 정규화 후 256자 이상을 `400 INVALID_INPUT`으로 거부하는지 검증한다.
- 양끝 공백은 제거하고 내부 공백과 허용 문자 입력은 보존하는지 검증한다.
- 같은 제목의 미션을 반복·동시 생성해도 제목 유일성 충돌 없이 각 `missionId`로 저장되는지 검증한다.
- `DRAFT` 제목 수정은 저장되고 `PENDING_REVIEW`, `PUBLISHED`, `ENDED` 수정은 기존 상태 충돌로 거부되는지 검증한다.
- 기존 행 backfill 뒤 행 수, 식별자, 조건·상태·보상·시각이 유지되고 모든 제목이 `미션 {mission_id}`인지 검증한다.
- nullable 호환 단계에서 구버전 writer가 실패하지 않고, `NOT NULL` 전환 전후에 새 null 행이 없는지 검증한다.
- 생성·수정 성공 감사가 기존 원자성을 유지하고 감사·구조화 로그에 제목 전·후 값이 남지 않는지 검증한다.
- 세 방문자 조회가 저장된 제목을 반환하면서 기존 공개 필터, 본인 범위, 진행 집계, 정렬과 페이지 메타데이터를 유지하는지 검증한다.
- 운영자·지역 관리자 조회와 공개 미션 상세의 응답 필드가 변경되지 않는지 계약 회귀 검증한다.

## 대체 조건

- 다국어 제목, 제목 번역 또는 사용자 언어별 표시명이 제품 요구사항으로 채택된다.
- 제목 중복으로 운영상 오선택이 반복되고 지역·상태·기간을 포함한 유일성 범위가 별도 요구사항으로 확정된다.
- 255자를 넘는 제목이나 별도 문자 제한이 필요하다는 실제 입력·운영 근거가 확인된다.
- 감사에서 이전 제목 복원이 필요하다는 법적·운영 요구가 채택된다.
