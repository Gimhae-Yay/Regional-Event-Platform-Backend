# ADR-0026: 회원가입 역할 선택과 운영자 신청 생성

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-29
- 결정일: 2026-07-29
- 관련 요구사항: [FR-01 인증·역할·지역 권한](../p0/auth-profile.md#fr-01-인증역할지역-권한), [FR-09 운영자 승인·정보 마스킹](../p0/auth-profile.md#fr-09-운영자-승인정보-마스킹)
- 관련 단계: 단계 0. 정책·설계 확정
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

기존 회원가입 계약은 모든 신규 계정에 `VISITOR` 역할을 자동으로 부여했다. 이 방식은 클라이언트가 운영자로
가입 의사를 표현할 수 없고, 운영자 신청을 별도 흐름에서 다시 시작해야 한다.

운영자 권한은 담당 지역 관리자의 사업자 정보 심사 뒤에만 부여되어야 하며, 클라이언트가 `OPERATOR`를 선택했다는
사실만으로 운영 권한을 얻어서는 안 된다. 사용자 요청에 따라 가입 단계에서 희망 역할을 받되 운영자 선택은
`PENDING` 신청으로 처리한다.

## 결정 동인과 불변 조건

- 클라이언트는 가입 시 `VISITOR` 또는 `OPERATOR`를 선택할 수 있어야 한다.
- `OPERATOR` 선택만으로 운영자 역할, 담당 지역 또는 콘텐츠 소유 관계를 부여해서는 안 된다.
- 운영자 신청에는 요청 지역과 사업자 정보를 함께 저장하고, 지역 관리자 승인 시에만 `OPERATOR` 역할과 담당 지역을 부여해야 한다.
- 계정·역할 또는 계정·운영자 신청 생성은 하나의 트랜잭션으로 처리해 일부 상태가 남지 않아야 한다.
- 사업자 정보는 응답과 로그에 노출하지 않는다.

| 1 | 가입 시 희망 역할을 받고 방문자는 즉시 부여, 운영자는 `PENDING` 신청 생성 | 방문자 가입은 단순하게 유지하면서 운영자 권한은 기존 지역 관리자 심사 경계로 보호한다. 가입과 신청 정보가 한 흐름으로 연결된다. | 운영자 신청 반려 뒤 재신청 경로를 별도 API로 제공해야 한다. | 중간 | 채택. 사용자 요청과 기존 `operator_application` 모델에 맞는다. |

## 결정

회원가입 요청에 `requestedRole`을 필수로 둔다.

- `VISITOR`를 선택하면 새 `ACTIVE` 계정과 `VISITOR` 역할을 한 트랜잭션에서 생성한다.
- `OPERATOR`를 선택하면 새 `ACTIVE` 계정, 요청 지역 및 사업자 정보를 가진 `operator_application(PENDING)`을 한 트랜잭션에서 생성한다. 이때 `VISITOR`, `OPERATOR` 역할과 담당 지역은 부여하지 않는다.
- `REGION_ADMIN`은 가입 요청에서 선택할 수 없다. 지역 관리자 연결은 배포 초기화 절차만 사용한다.
- 운영자 신청이 승인될 때에만 기존 `AUTH-02` 정책에 따라 `OPERATOR` 역할과 담당 지역을 함께 부여한다.

운영자 신청의 `businessInformation`은 수동 심사를 위한 비어 있지 않은 텍스트로 받는다. 세부 사업자 정보 항목과
암호화·마스킹·보관 방식은 사업자 정보 정책을 확정하는 후속 결정에서 구체화한다.

## 결과와 트레이드오프

### 기대 효과

- 가입 의도에 맞게 방문자 사용 가능 상태와 운영자 심사 대기 상태를 구분한다.
- 운영 권한을 지역 관리자 심사 전까지 차단해 기존 권한 경계를 유지한다.
- 운영자 신청의 신청자·지역·사업자 정보를 가입 트랜잭션에서 일관되게 연결한다.

### 수용한 단점과 위험

- `PENDING` 운영자 신청 계정은 승인 전 방문자·운영자 권한을 모두 갖지 않는다.
- 반려 또는 취소된 신청의 재신청 API와 사업자 정보의 세부 스키마는 별도로 정의해야 한다.
- 사업자 정보는 개인정보·영업정보일 수 있으므로 응답·로그 노출을 막고 저장소 보호 정책을 추가로 확정해야 한다.

## 전환과 롤백

현재는 구현 전 문서 계약 변경이므로 데이터 이관은 없다. 구현 시 가입 요청 DTO, `app_user`,
`user_role_assignment`, `operator_application` 쓰기를 위 결정에 맞춰 같은 트랜잭션에 둔다.

가입 중 계정·역할·신청 생성 중 하나라도 실패하면 모두 롤백한다. 기존 자동 방문자 부여 방식으로 되돌리려면
신규 `PENDING` 신청 계정의 처리와 클라이언트 요청 호환성을 검토하는 후속 ADR을 작성한다.

## 검증 방법

- `VISITOR` 가입이 계정과 `VISITOR` 역할만 생성하는지 검증한다.
- `OPERATOR` 가입이 계정과 `PENDING` 운영자 신청만 생성하고 역할·담당 지역을 생성하지 않는지 검증한다.
- 존재하지 않거나 공개되지 않은 요청 지역, 누락된 사업자 정보, 중복 이메일에서 계정·역할·신청이 하나도 생성되지 않는지 검증한다.
- 지역 관리자 승인 전 운영자 API가 거부되고, 승인 시에만 `OPERATOR` 역할과 요청 지역이 함께 부여되는지 검증한다.
- 사업자 정보가 HTTP 응답과 로그에 포함되지 않는지 검증한다.

## 대체 조건

- 모든 신규 회원에게 기본 방문자 권한을 반드시 부여해야 하는 제품 요구사항이 확정된다.
- 운영자 심사가 외부 사업자 검증 서비스 또는 별도 온보딩 시스템으로 이전된다.
- 사업자 정보의 구조·암호화·보관 정책이 확정되어 현재 텍스트 기반 신청 계약을 유지할 수 없게 된다.
