# ADR-0056: 출력 Port를 소유 도메인의 port.out 패키지에 둔다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-02
- 결정일: 2026-08-02
- 관련 요구사항: [아키텍처의 기본 구조](../ARCHITECTURE.md#2-기본-구조), [유스케이스별 경계 전환](0008-evolve-clean-architecture-by-use-case.md#결정), [Service와 UseCase의 협력 규칙](0042-prohibit-direct-service-dependencies-and-use-usecase-orchestrators.md#결정)
- 관련 단계: 단계 0. 정책·설계 확정
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

Task 구현 절차는 외부 기술 의존이 필요한 단일 Service 또는 복합 UseCase가 역할 인터페이스(Port)를 정의하거나
기존 Port를 사용하도록 한다. 아키텍처와 ADR-0008·0042도 외부 기술 경계를 역할 인터페이스와 Adapter로
분리하도록 정하지만, 인터페이스의 패키지 위치는 명시하지 않는다.

위치가 없으면 같은 역할 인터페이스가 `infra`에 놓여 애플리케이션이 구체 기술 방향으로 의존하거나, 특정
도메인 계약이 `global`에 섞여 소유 책임이 흐려질 수 있다. 반대로 모든 도메인에 빈 `port` 패키지와 내부
인터페이스를 미리 만들면 ADR-0008의 점진적 전환 원칙과 충돌한다.

## 결정 동인과 불변 조건

- 패키지는 기술 계층보다 업무 도메인을 우선한다.
- 외부 기술 계약의 소유 도메인과 Adapter 구현 위치를 코드 리뷰에서 바로 추적할 수 있어야 한다.
- Service와 UseCase는 구체 외부 구현이 아니라 필요한 역할 계약에만 의존한다.
- Port는 실제 외부 기술 경계에만 만들며, 내부 Service·정책 객체·테스트 편의를 위한 인터페이스로 확대하지 않는다.
- Adapter는 Service·UseCase를 역으로 참조하지 않고, Port는 Repository·Service를 감싼 우회 경로가 되지 않는다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 필요한 출력 Port를 `domain.<도메인>.port.out`에 둔다 | 도메인 소유와 외부 Adapter 경계가 함께 드러나며, 도메인 중심 구조를 유지한다. | 도메인별 패키지 구성이 달라지고 Port 소유 도메인을 판단해야 한다. | 낮음~중간. Port와 Adapter를 함께 이동하고 import를 수정하면 된다. | 점진적 전환과 필요한 경계만 도입하는 현재 원칙에 가장 적합하다. |
| 2 | 모든 Port를 `application.port` 같은 공통 패키지에 둔다 | Port를 한곳에서 찾기 쉽고 계층 이름이 균일하다. | 업무 책임이 기술 계층에 가려지고, 관련 없는 도메인 계약이 함께 증가한다. | 중간. 공통 계약을 도메인별로 다시 분류해야 한다. | 도메인 중심 패키지 우선 원칙에 맞지 않는다. |
| 3 | Port를 `infra` Adapter와 같은 패키지에 둔다 | 구현체와 인터페이스를 가까이 둘 수 있다. | 애플리케이션이 구체 기술 패키지에 의존하거나 의존 방향을 오해하기 쉽다. | 중간. 계약을 도메인으로 옮기고 Adapter 의존성을 정리해야 한다. | 기술 경계 분리 목적에 맞지 않는다. |

## 결정

외부 기술 경계가 실제로 필요한 경우에만, 역할 인터페이스를 그 업무 책임을 소유한
`domain.<도메인>.port.out` 패키지에 둔다. 예를 들어 결제 요청·조회 계약인 `PaymentGateway`는
`domain.payment.port.out`에 두고, 결제사 구현체 `PortOnePaymentAdapter`는 `infra.payment`에 둔다.

단일 도메인 흐름에서는 해당 Service가 Port를 의존할 수 있고, 여러 Service 또는 Repository의 실행 순서·권한·
트랜잭션을 조정하는 복합 흐름에서는 UseCase가 Port를 의존할 수 있다. 어느 경우에도 Port는 외부 기술과의
역할 계약만 표현하며 Repository, Service 또는 다른 도메인 흐름을 감싸지 않는다.

`port.out` 패키지는 모든 도메인에 미리 생성하지 않는다. 실제 외부 기술 경계, 교체 가능성 또는 독립 검증이 필요한
계약이 생길 때만 생성한다. 내부 정책 객체, 단순 기술 협력자, 전달 전용 계층 또는 테스트 편의만으로 Port를
만들지 않는다. Port 이름에는 `Port` 접미사를 강제하지 않고 `PaymentGateway`, `TokenProvider`처럼 역할을
드러내는 이름을 사용한다.

이 결정은 ADR-0008의 점진적 Port·Adapter 도입과 ADR-0042의 역할 인터페이스 규칙을 대체하지 않으며, 그
출력 Port의 패키지 배치만 구체화한다.

## 결과와 트레이드오프

### 기대 효과

- 외부 기술 계약의 업무 소유자와 구현체의 기술 경계를 패키지 경로만으로 확인할 수 있다.
- 도메인 Service와 UseCase가 `infra` 구현체 대신 역할 인터페이스에 의존하도록 유지한다.
- 필요할 때만 Port를 추가해 빈 패키지와 불필요한 인터페이스를 줄인다.

### 수용한 단점과 위험

- 도메인마다 `port` 패키지의 존재 여부가 달라 패키지 모양이 완전히 균일하지 않다.
- 여러 도메인에서 쓰는 외부 기술의 계약 소유 도메인을 잘못 정하면 경계가 흔들릴 수 있다.
- Port 수가 늘면 Adapter·통합 테스트와 패키지 탐색 비용도 함께 증가한다.

## 전환과 롤백

이 결정은 문서상 패키지 배치 원칙만 추가하며, 현재 변경에서 프로덕션 클래스의 생성·이동이나 데이터 이관은
수행하지 않는다. 이후 Port를 도입하거나 기존 Port를 정리하는 Task는 역할 계약, Adapter 구현, 단위·통합
테스트를 같은 범위에서 검증한다.

Port가 잘못된 도메인에 배치된 것이 확인되면 공개 API 동작을 유지한 채 인터페이스와 Adapter의 import를
소유 도메인으로 이동하고, 의존 방향과 회귀 테스트를 확인한다. 분리 효과 없이 전달만 늘어난 Port는 ADR-0008의
롤백 기준에 따라 제거하고 기존 Service 구조로 되돌린다.

## 검증 방법

- 새 Port가 실제 외부 기술 경계에만 추가되고, 해당 업무 책임을 소유한 `domain.<도메인>.port.out`에 배치되는지 코드 리뷰로 확인한다.
- Service와 UseCase가 `infra` 구현체가 아닌 Port에 의존하고, Adapter가 Port를 구현하는지 컴파일과 통합 테스트로 확인한다.
- Port가 Repository·Service를 감싸거나 Service·UseCase를 역으로 참조하지 않는지 의존성 검토로 확인한다.
- Port 도입 전후에 해당 유스케이스의 정상·실패·권한·멱등성 결과가 유지되는지 회귀 테스트로 확인한다.

## 대체 조건

- 둘 이상의 도메인이 같은 외부 계약을 동등하게 소유해 도메인별 배치가 중복 계약이나 순환 의존을 반복해서 만든다.
- 모든 신규 기능에 Port와 Adapter 구조를 일관되게 적용하는 편이 점진적 도입보다 유지보수 비용이 낮다는 증거가 쌓인다.
- 모듈 분리나 독립 배포로 포트 계약을 별도 모듈 또는 공통 애플리케이션 계층으로 분리할 필요가 생긴다.
