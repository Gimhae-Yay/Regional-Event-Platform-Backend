# ADR-0015: MySQL 감사 이벤트를 기준 기록으로 저장하고 탈퇴 회원 연결을 제거

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-28
- 결정일: 2026-07-28
- 관련 요구사항: [PRD](../local-stamp-platform-prd.md)의 `FR-11`, `PRV-01`, `PRV-02`, `CON-09`, `AC-15`, `AC-17`
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

P0는 콘텐츠·홀드·예약·방문·후기의 상태 전이와 실패 사유를 재현할 수 있는 감사 이벤트를 요구한다. 동시에
회원 탈퇴가 완료되면 회원정보와 후기·방문 데이터의 직접·간접 개인 연결을 제거해야 한다.

구조화 JSON 로그만으로는 보관 기간 만료, 로그 순환 또는 운영 환경 변경 뒤에도 상태 전이의 기준 기록을
보장할 수 없다. 반대로 사용자 식별자를 감사 이벤트에 직접 저장하거나 사용자별 안정 가명을 남기면
ADR-0012의 탈퇴 불변 조건을 위반한다. 외부 전달용 Outbox는 현재 P0 범위에서 제외되어 있으며,
감사 이벤트 자체는 외부 전달 이벤트가 아니다.

사용자는 MySQL 감사 이벤트 테이블을 기준 기록으로 두고 구조화 로그는 관측 용도로 분리하는 안과,
비식별 감사 이벤트의 90일 보관을 선택했다.

## 결정 동인과 불변 조건

- 상태 전이의 처리자 유형, 지역, 대상, 전이 전후 상태, 사유·실패 코드, `requestId`, 시각을 재현할 수 있어야 한다.
- 개인정보, JWT 키, QR 원문, 이름·연락처, 사용자별 안정 가명은 감사 이벤트와 구조화 로그에 저장하지 않는다.
- 상태 전이가 성공하면 도메인 변경과 그 성공 감사 이벤트는 하나의 MySQL 트랜잭션으로 함께 커밋하거나 롤백한다.
- 탈퇴한 방문자를 감사 이벤트나 연결 테이블을 통해 역참조할 수 없어야 하며, 탈퇴 후 actor 표시는 공통 값
  `WITHDRAWN_MEMBER`만 사용한다.
- 감사 이벤트 본문은 애플리케이션에서 수정·개별 삭제하지 않는다. 오류 정정은 새 정정 이벤트를 추가한다.
- 감사 이벤트 보관 만료는 90일이며, 콘텐츠·예약 등 도메인별 상태·사유 보존 정책을 대신하거나 단축하지 않는다.

## 결정

`audit_event`를 MySQL의 기준 감사 기록으로 둔다. 이벤트에는 서버가 확인한 `requestId`, `region_id`,
대상 유형·식별자, 전이 전후 상태, 처리 결과, 사유 또는 실패 코드, actor 역할, 발생 시각만 저장한다.
클라이언트가 보낸 지역·처리자·대상 값은 감사 값으로 신뢰하지 않는다.

성공한 상태 전이는 도메인 변경과 감사 이벤트 삽입을 같은 트랜잭션에서 처리한다. 상태 변경이 롤백된 실패·거부는
롤백 완료 뒤 독립 트랜잭션으로 실패 코드와 비개인 문맥만 기록한다. 이 독립 기록도 실패하면 구조화 로그로
관찰하되, 로그만으로 상태 전이의 성공 여부를 확정하지 않는다.

`audit_event`에는 `user_id`나 사용자별 가명을 넣지 않는다. 사용자 식별이 필요한 활성 회원의 감사 조회는 별도
`audit_event_actor_link`에서 이벤트와 회원을 연결한다. 탈퇴 완료 시 해당 연결 행을 먼저 파기한다. 연결이 없는
방문자 actor는 모든 탈퇴 회원에 공통인 `WITHDRAWN_MEMBER`로만 표시하며, 이벤트 본문에는 동일 탈퇴 회원의
행동을 묶을 수 있는 안정 식별자를 남기지 않는다. 운영 역할 또는 콘텐츠 소유 관계가 남은 계정의 셀프 탈퇴는
ADR-0012의 범위 밖이며, 그 계정의 연결 제거 규칙을 이 ADR로 확장하지 않는다.

애플리케이션 실행 계정에는 `audit_event`의 `UPDATE`와 `DELETE` 권한을 주지 않는다. 90일이 지난 이벤트는
보관 전용 관리 작업이 일괄 파기하며, 관련 actor 연결도 함께 제거한다. 보관 기간 전 데이터의 수정·삭제가
필요한 오류는 기존 행을 바꾸지 않고 정정 또는 종결 이벤트를 추가한다.

구조화 JSON 로그는 동일한 비개인 상관관계 값과 오류 관찰에 사용하지만, 감사 이벤트의 대체물이나 외부 전달
계약으로 사용하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 상태 전이와 감사 이력의 성공 여부가 같은 MySQL 트랜잭션 경계에서 일관되게 유지된다.
- 로그 수집기 교체나 로그 순환과 무관하게 90일 동안 운영 이력을 조회할 수 있다.
- 탈퇴 후에도 사건의 종류·대상·시각은 남기면서 개인을 연결하는 경로는 제거한다.
- 감사 기록과 관측 로그, 외부 이벤트 전달의 책임이 분리된다.

### 수용한 단점과 위험

- 별도 테이블과 actor 연결의 파기 순서를 정확히 구현·검증해야 한다.
- 실패 이벤트는 성공 상태 전이와 같은 트랜잭션에 둘 수 없으므로, 독립 기록 자체의 실패는 구조화 로그로만 관찰한다.
- 90일을 넘은 감사 이벤트로는 과거 개별 상태 전이를 재현할 수 없다.
- 탈퇴 후에는 같은 회원이 과거에 수행한 여러 행동을 추적할 수 없으며, 이는 의도한 개인정보 보호 비용이다.

## 전환과 롤백

신규 구현이므로 기존 감사 데이터를 이관하지 않는다. 먼저 감사 이벤트와 actor 연결의 스키마·권한·90일 보관
작업을 마련하고, 이후 각 상태 전이에 기준 이벤트 기록을 연결한다. 감사 이벤트 작성에 실패하면 성공 상태 전이를
커밋하지 않는다.

도입 중 문제가 생기면 새 상태 전이 기능을 중지하고 기존 도메인 상태를 유지한다. 이미 파기한 actor 연결과
90일이 지나 파기한 감사 이벤트는 복구하지 않는다. 외부 감사 저장소나 더 긴 보관이 필요해지면 새 ADR로
보관·이관·운영 관측 방식을 결정한다.

## 검증 방법

- 콘텐츠 승인·반려·자동 공개·중단·철회·종료·삭제, 홀드·예약·방문·후기의 상태 전이가 도메인 변경과 감사
  이벤트를 함께 커밋하거나 함께 롤백하는지 검증한다.
- 권한 거부와 상태 조건 불일치가 실패 코드·`requestId`·비개인 문맥으로 기록되고, 개인정보와 JWT·QR 원문이
  감사 이벤트·구조화 로그에 없는지 검증한다.
- 애플리케이션 실행 계정으로 감사 이벤트를 수정·삭제할 수 없고, 정정은 새 이벤트로만 가능한지 검증한다.
- 탈퇴 후 `audit_event_actor_link`와 다른 감사 경로를 통해 회원을 역참조할 수 없으며 actor가
  `WITHDRAWN_MEMBER`로만 표시되는지 검증한다.
- 90일 경과 이벤트와 actor 연결이 함께 파기되고, 보관 기간 전 이벤트가 보존되는지 검증한다.
- 구조화 로그 수집 실패가 감사 이벤트의 성공 상태를 바꾸지 않고, 감사 이벤트 기록 실패가 성공 상태 전이를
  만들지 않는지 검증한다.

## 대체 조건

- 법률·계약이 90일보다 긴 감사 보관, 변경 불가능한 외부 보관 또는 별도 접근 통제를 요구한다.
- 감사 이벤트의 양·조회 부하가 MySQL의 합의한 운영 한계를 지속적으로 넘는다.
- 알림·분석·외부 기관에 대한 전달 보장이나 재생이 실제 릴리스 범위로 채택된다.
- 탈퇴 뒤에도 개인별 감사 추적을 보존해야 하는 법적 근거가 확인된다.
