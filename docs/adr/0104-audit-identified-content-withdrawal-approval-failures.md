# ADR-0104: 식별 완료된 전체 콘텐츠 철회 승인 실패만 감사한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-17
- 결정일: 2026-08-17
- 관련 요구사항: [지역·콘텐츠 카탈로그](../p0/content-catalog.md)의 `CON-09`, [P0 명세](../p0-spec.md)의 `8.8 감사 및 운영 로그`, [전체 콘텐츠 철회 승인 API](../api/p0/region-content/approve-content-withdrawal.md)의 `실패 감사·구조화 로그 경계`
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: [#880](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/880), [#743](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/743)
- 대체 대상: 없음. [ADR-0101](0101-store-content-withdrawal-requests-and-serialize-review.md)의 성공 감사 계약을 유지하고 미확정이던 승인 실패 감사 경계를 보완한다.

## 맥락

ADR-0101은 전체 콘텐츠 철회 승인 성공 시 요청·콘텐츠·수정본·실제로 전이된 홀드·결제·쿠폰의 성공 감사를 원
업무 트랜잭션에 포함했지만, 승인 실패의 감사 범위는 정하지 않았다. 승인 API는 입력 파싱, 인증, 역할·지역 검증,
대상·상태 확인과 원자적 상태 전이 중 서로 다른 단계에서 실패할 수 있다. 대상이나 actor가 확인되지 않은 사건을
동일한 감사 모델에 저장하면 nullable 필드가 사실 확인 실패와 실제 업무 거부를 함께 표현하고, 경로의 원문
식별자나 인증 정보를 잘못 보관할 위험이 있다.

반대로 모든 실패를 구조화 로그로만 남기면 담당 지역 관리자와 실제 철회 요청·상태를 확인한 뒤 거부된 사건을
상태 전이 감사와 같은 축으로 재현할 수 없다. 기존 `RecordFailedAuditEventUseCase.record()`는 원 업무 트랜잭션의
롤백 완료 뒤 별도 `REQUIRES_NEW` 트랜잭션으로 실패 감사를 저장하고, 감사 저장 장애가 원래 오류를 바꾸지 않는
경계를 제공한다.

## 결정 동인과 불변 조건

- 실패 감사는 실제 철회 요청, 요청 콘텐츠 지역, 확인된 요청 상태와 활성 지역 관리자 actor를 모두 연결해야 한다.
- 입력 오류, 미인증과 실재하지 않는 대상은 확인된 업무 거부와 같은 실패 감사로 만들지 않아야 한다.
- 실패 감사 때문에 원 승인 트랜잭션의 롤백, HTTP 상태 또는 공개 오류 코드가 바뀌지 않아야 한다.
- API 경로·요청·성공 응답, 기존 7개 공개 오류 코드, 상태 전이·잠금 순서와 성공 트랜잭션 범위를 바꾸지 않아야 한다.
- 이미 승인된 요청의 자연 멱등 재응답과 커밋 후 캐시 삭제 실패를 승인 실패로 재분류하지 않아야 한다.
- 로그와 감사에 경로의 원문 식별자, 인증 정보, 자유 텍스트, 토큰·비밀값과 개인정보를 추가하지 않아야 한다.

| --- | --- | --- | --- | --- | --- |
| 1 | 추천안: 대상·지역·현재 상태·활성 actor를 모두 확인한 뒤의 실패만 감사하고, 식별 전 정책 실패는 비개인 구조화 로그로 관찰 | 확인된 업무 거부만 감사해 필드 의미가 명확하고 기존 롤백 후 독립 저장 방식을 재사용한다. | 독립 감사 저장 장애 시 감사가 영구 누락될 수 있고 식별 전 실패는 감사 조회로 재현할 수 없다. | 낮음. 공통 실패 감사 명령과 저장 경계를 그대로 사용한다. | P0의 재현 요구와 비개인 관측 경계를 함께 만족한다. |

| 3 | 승인 실패를 모두 구조화 로그로만 기록 | 별도 감사 트랜잭션과 누락 처리가 필요 없다. | 확인된 요청·상태·actor 기반 거부를 성공 감사와 연결해 재현할 수 없다. | 중간. 이후 누락된 과거 실패를 감사 이벤트로 복원할 수 없다. | `CON-09`와 `AC-17`의 실패 재현 요구를 충족하지 못한다. |

## 결정

추천안인 선택지 1을 채택한다. 대상 철회 요청, 요청 콘텐츠의 지역, 현재 철회 요청 상태와 활성 `REGION_ADMIN`
actor를 모두 확인한 뒤 감지한 `FORBIDDEN`, `CONTENT_STATE_CONFLICT`, `INTERNAL_SERVER_ERROR`만 실패 감사로
기록한다. 같은 오류가 식별 완료 전에 발생하면 `requestId`, 고정된 대상 유형, 공개 오류 코드와 식별 단계만
포함한 비개인 구조화 로그로 관찰한다.

`INVALID_INPUT`, `INVALID_TYPE`, `UNAUTHENTICATED`, 실재하지 않는 철회 요청의 `NOT_FOUND`에는 전체 콘텐츠 철회
승인 전용 실패 감사나 구조화 로그를 추가하지 않는다. 공통 입력·인증·오류 처리 계약은 유지한다.

실패 감사는 다음 값을 사용한다.

| 필드 | 값 | nullable |
| --- | --- | --- |
| `target_type` | `CONTENT_WITHDRAWAL_REQUEST` | N |
| `target_id` | 확인한 철회 요청 ID | N |
| `region` | 요청 콘텐츠의 지역 | N |
| `previous_state` | 실패 전에 확인한 철회 요청 상태 | N |
| `next_state` | 실제 전이가 없으므로 `NULL` | Y, 항상 `NULL` |
| `result` | `FAILURE` | N |
| `actor` | 확인된 활성 `REGION_ADMIN` 사용자와 actor link | N |
| `reason_code` | 반환할 공개 오류 코드 | N |
| `reason`, `evidence_reference` | 저장하지 않음 | Y, 항상 `NULL` |
| `requestId` | 현재 HTTP 요청 ID | N |
| `occurred_at` | 원 승인 트랜잭션에서 실패를 감지한 시각 | N |

원 승인 트랜잭션에 실패 감사 명령을 등록하고 원래 예외를 전파한다. 원 트랜잭션의 롤백 완료 뒤에만 별도
`REQUIRES_NEW` 트랜잭션으로 실패 감사와 actor link를 한 번 저장한다. 감사 저장 자체가 실패해도 원래 롤백,
HTTP 상태와 공개 오류 코드를 유지하고 원 승인이나 감사 저장을 자동 재시도하지 않는다. 감사 누락은 기존 형식인
`requestId`, `targetType`, `targetId`, `originalErrorCode`, `auditWriteResult = FAILURE`만 포함한 비개인 `error`
구조화 로그 한 건으로 관찰한다.

이미 `APPROVED`인 요청의 저장 결과 `200 OK` 재응답은 성공이며 새 감사를 만들지 않는다. 승인 커밋 후 캐시 삭제
실패는 승인 실패 감사에서 제외하고 비개인 구조화 로그만 남기며 기존 `200 OK`를 유지한다.

## 결과와 트레이드오프

### 기대 효과

- 확인된 철회 요청·지역·상태·actor와 공개 오류 코드를 연결해 실제 승인 거부를 재현할 수 있다.
- 불완전하거나 신뢰할 수 없는 식별자를 감사 이벤트에 저장하지 않고 식별 전 실패를 비개인 로그로 관찰한다.
- 기존 실패 감사 명령과 롤백 후 독립 저장 방식을 재사용해 원 승인 트랜잭션의 원자성·응답 계약을 유지한다.
- 자연 멱등 응답과 캐시 장애를 도메인 승인 실패와 분리한다.

### 수용한 단점과 위험

- 독립 감사 저장이 실패하면 해당 승인 실패는 `audit_event`에서 영구 누락될 수 있다.
- 자동 재시도나 사후 보정 저장소를 두지 않으므로 운영자는 비개인 `error` 로그와 `requestId`로 누락을 조사해야 한다.
- 식별 전 정책 실패는 감사 조회에 나타나지 않으며 로그 보관 기간과 운영 조회 수단에 의존한다.
- 입력 오류, 미인증과 실재하지 않는 대상의 실패는 이 API 전용 감사·로그가 없어 공통 오류 관측 범위만 사용한다.

## 전환과 롤백

이 결정은 문서 계약만 확정하며 스키마·데이터 이관, API 공개 계약 변경은 없다. P0 정책과 API 명세를 먼저
정합화한 뒤 후속 프로덕션 구현 Task에서 기존 `RecordFailedAuditEventUseCase.record()`와 실패 감사 nullable 계약을
재사용한다. #880에서는 프로덕션 코드, 테스트, migration, 설정을 변경하지 않는다.

후속 구현에서 장애가 확인되면 실패 감사 등록 경로를 비활성화해 원래 승인 실패 응답과 롤백을 유지할 수 있다.
채택된 경계나 누락 허용 정책을 바꾸려면 이 ADR을 수정하지 않고 후속 ADR로 대체한다. 이미 저장된 감사 이벤트는
추가 전용 사실이므로 삭제하거나 수정하지 않는다.

## 검증 방법

- 공개 오류 코드와 식별 완료 전·후 조합별로 실패 감사, 비개인 구조화 로그 또는 추가 기록 제외 결과를 확인한다.
- 실패 감사가 필수 대상·지역·이전 상태·actor·공개 오류 코드·요청 ID·실패 감지 시각을 기록하고
  `next_state`, `reason`, `evidence_reference`는 `NULL`인지 확인한다.
- 원 승인 트랜잭션이 먼저 롤백되고 별도 트랜잭션의 실패 감사만 커밋되는지 확인한다.
- 감사 저장 예외를 주입해도 원래 HTTP 상태·공개 오류 코드·롤백 결과가 유지되고 지정된 비개인 `error` 로그만
  한 건 남으며 자동 재시도하지 않는지 확인한다.
- 이미 `APPROVED`인 요청 재응답에 새 감사·부수 효과가 없고, 커밋 뒤 캐시 삭제 실패에도 `200 OK`와 승인 결과가
  유지되며 실패 감사 대신 비개인 구조화 로그만 남는지 확인한다.
- #880 문서 변경은 관련 링크와 용어 정합성 검사 및 `git diff --check`로 검증한다.

## 대체 조건

- 감사 누락이 법률·감사 또는 운영 수용 기준을 위반하거나, 감사 저장 장애율이 합의된 운영 한도를 초과한다.
- 반복된 감사 저장 장애 때문에 수동 조사만으로 복구 목표를 충족하지 못해 Outbox·영속 재처리 저장소 또는
  중복 방지 키를 포함한 사후 보정이 필요해진다.
- 식별 전 실패도 감사 저장소에서 장기 보관·검색해야 한다는 요구가 채택된다.
- 실패 요청의 목표 상태나 원문 증빙을 별도 필드로 검색해야 한다는 요구가 채택된다.
