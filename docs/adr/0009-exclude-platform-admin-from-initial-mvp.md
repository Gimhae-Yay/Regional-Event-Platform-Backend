# ADR-0009: 초기 MVP에서 전체 관리자를 제외하고 초기 운영 데이터를 배포 절차로 준비

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-25
- 결정일: 2026-07-25
- 관련 요구사항: [P0 명세](../p0-spec.md)의 무료 예약 MVP 범위·최소 운영 도구, [인증·프로필](../p0/auth-profile.md)의 권한 정책과 [인증·프로필 API](../api/p0/auth-profile/auth-profile.md)
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0002](0002-isolate-regions-in-a-shared-schema.md)의 초기 MVP 전체 관리자, 지역 범위 우회와 전체 관리자 전용 유스케이스 결정 부분, [ADR-0005](0005-use-jwt-access-and-rotating-refresh-tokens.md)의 초기 MVP 역할 집합에 전체 관리자를 포함한 부분

## 맥락

현재 무료 예약 MVP는 김해시와 동해시에서 방문자, 행사·체험 운영자와 지역 관리자의 핵심 흐름을 검증하는 데
집중한다. 전체 관리자의 지역 생성, 지역 관리자 임명, 공통 운영 기준 변경과 지역 간 통합 조회는 첫 릴리스에
필요하지 않으며, 이를 포함하면 전역 권한과 별도 관리 API의 구현·보안·테스트 범위가 늘어난다.

ADR-0002는 공유 스키마와 `region_id` 격리를 채택하면서 초기 MVP의 전체 관리자 지역 범위 우회를 허용했고,
ADR-0005는 초기 역할 집합에 전체 관리자를 포함했다. 제품 범위가 세 역할로 축소됐으므로 공유 스키마와 JWT
결정은 유지하되 현재 MVP의 전체 관리자와 전역 우회 부분을 대체해야 한다.

전체 관리자를 제거해도 김해시·동해시 지역 기준 데이터와 각 최초 지역 관리자 연결은 출시 전에 준비돼야 한다.
이 초기 설정을 일반 업무 API로 제공하면 자기 권한 부여나 지역 경계 우회 경로가 생기므로 제품 런타임 권한과
분리된 초기화 절차가 필요하다.

## 결정 동인과 불변 조건

- 현재 MVP의 사용자 역할은 방문자, 운영자와 지역 관리자로 제한한다.
- 모든 운영자·지역 관리자 유스케이스는 담당 `region_id`와 콘텐츠 소유 관계를 검사한다.
- 현재 MVP에 지역 범위를 우회하는 사용자 권한이나 전역 조회·변경 API를 두지 않는다.
- 김해시·동해시와 각 최초 지역 관리자 연결은 서비스 공개 전에 재현 가능하고 감사 가능한 방식으로 준비한다.
- 초기화 절차는 지역 관리자 자격 증명 원문을 migration, 소스 코드나 로그에 저장하지 않는다.
- 초기화 재실행은 같은 연결을 중복 생성하지 않고, 기존 연결과 충돌하면 자동 덮어쓰기 없이 실패해야 한다.
- 권한 밖의 운영 예외는 애플리케이션 상태를 임의로 변경하지 않고 사유를 남겨 별도 운영 절차로 이관한다.

## 결정

현재 무료 예약 MVP에는 전체 관리자 역할, 계정 유형, 화면과 API를 구현하지 않는다. JWT 역할과 현재 DB의
권한 상태는 방문자, 운영자와 지역 관리자만 지원하며, 지역 범위를 우회하는 사용자 경로를 만들지 않는다.
공유 스키마와 `region_id` 격리, 짧은 JWT Access Token과 회전형 Refresh Token 결정은 그대로 유지한다.

김해시·동해시 지역 기준 데이터는 버전 관리되는 배포 migration으로 준비한다. 각 최초 지역 관리자 연결은
대상 사용자 계정이 존재한 뒤 명시적인 사용자 식별자와 지역 식별자를 받는 승인된 일회성 초기화 절차로
설정한다. 이 절차는 한 트랜잭션에서 실행하고 같은 연결의 재실행은 기존 결과를 반환하며, 다른 지역이나 역할과
충돌하면 변경 없이 실패한다.

초기화 결과에는 승인·실행 주체, 대상 사용자, 지역, 수행 시각과 성공·실패 결과를 자격 증명 없이 남긴다.
일반 API에서는 지역 생성, 지역 관리자 임명·변경과 공통 운영 기준 변경을 제공하지 않는다. 공통 운영 기준은
현재 MVP의 승인된 문서와 설정으로 고정한다.

지역 관리자가 처리할 수 없는 운영 예외는 상태를 변경하지 않고 사유를 기록해 별도 운영 절차로 이관한다.
전체 관리자는 장기 제품 역할로만 유지하며, 후속 릴리스에서 필요성이 확인되면 제품 정책, 권한 범위, API·DB
계약과 새로운 기술 결정을 확정한 뒤 도입한다.

## 결과와 트레이드오프

### 기대 효과

- 현재 MVP의 인증·인가와 보호된 운영 API가 세 역할과 지역 범위에만 집중한다.
- 일반 업무 경로에 전역 조회 메서드나 지역 우회 권한이 생기지 않는다.
- 고정된 두 지역의 초기 운영 조건을 전체 관리자 기능 없이 준비할 수 있다.
- 후속 전체 관리자 도입 여부를 실제 지역 확장과 운영 예외 증거를 바탕으로 다시 결정할 수 있다.

### 수용한 단점과 위험

- 지역 추가, 최초 지역 관리자 변경과 공통 운영 기준 변경을 제품 화면에서 처리할 수 없다.
- 초기화 절차와 승인·복구 방법을 배포 운영자가 별도로 관리해야 한다.
- 최초 지역 관리자 연결이 잘못되거나 계정을 사용할 수 없으면 승인된 복구 절차 전까지 해당 지역의 관리 업무가
  중단될 수 있다.
- 지역 간 통합 조회와 애플리케이션 내부 에스컬레이션 경로를 첫 릴리스에서 제공하지 않는다.

## 전환과 롤백

현재 소스에는 전체 관리자 역할이나 전역 권한 경로가 구현되지 않아 기존 데이터 이관과 호환 계층은 필요하지
않다. 먼저 PRD와 P0 기능 문서에서 현재 역할과 초기화 책임을 확정하고, 구현에서는 전체 관리자 역할 값과
전역 관리 엔드포인트를 만들지 않는다. 이후 지역 기준 데이터 migration과 최초 지역 관리자 초기화 절차를
추가하고, 지역 격리·초기화 검증을 통과한 뒤 배포한다.

초기화가 일부라도 실패하면 해당 트랜잭션을 롤백하고 서비스 공개를 중단한다. 잘못된 연결을 자동으로
덮어쓰거나 지역 기준 데이터를 하향 migration으로 삭제하지 않는다. 승인된 복구 절차와 전진 migration으로
수정하고 기존·수정 결과를 함께 추적한다.

출시 전에 전체 관리자가 필요해지면 이 ADR을 직접 수정하지 않는다. 필요 근거와 권한 범위를 비교한 새 ADR로
대체하고 P0/P1 범위, 내부 API·DB 계약과 테스트를 함께 갱신한다.

## 검증 방법

- 역할 모델, JWT 권한 매핑과 보호된 API에 전체 관리자 또는 지역 범위 우회 권한이 없는지 검사한다.
- 김해시 지역 관리자가 동해시 데이터에, 동해시 지역 관리자가 김해시 데이터에 접근할 수 없음을 목록 조회와
  ID 직접 지정 경로에서 검증한다.
- 일반 API로 지역이나 지역 관리자 연결을 생성·변경할 수 없고 관련 엔드포인트가 노출되지 않는지 검증한다.
- 지역 migration을 반복 적용해 기준 데이터가 중복되지 않는지 검증한다.
- 같은 최초 지역 관리자 초기화를 반복하면 기존 결과를 반환하고, 충돌하는 사용자·지역 연결은 변경 없이
  실패하는지 검증한다.
- 초기화 성공·실패 결과에 승인·실행 주체, 대상 사용자, 지역과 수행 시각이 남고 비밀번호·토큰 등 자격 증명이
  기록되지 않는지 확인한다.
- 권한 거부와 초기화 실패는 `requestId` 또는 배포 실행 식별자로 추적하며, 교차 지역 접근이 한 건이라도
  허용되거나 초기화가 부분 반영되면 출시 실패로 판정한다.

## 대체 조건

- 운영 중인 지역이 추가되어 배포 초기화만으로 지역과 관리자 수명주기를 관리하기 어렵다.
- 지역 관리자 교체·복구 요청이 반복되어 별도 운영 절차의 처리 시간이나 오류가 허용 범위를 넘는다.
- 지역 간 공통 정책 변경, 통합 감사 조회나 운영 예외 처리를 애플리케이션에서 수행해야 한다.
- 유료 결제 도입으로 지역 범위를 넘는 결제 불일치·취소 실패의 수동 처리 책임과 권한이 필요하다.
- 법률·계약·조직 운영 요구로 중앙 관리 주체와 감사 가능한 전역 권한이 필요하다.
