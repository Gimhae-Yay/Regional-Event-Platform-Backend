# ADR-0001: MySQL 조건부 갱신으로 회차 정원 정합성 보장

- 상태: 채택됨
- 기록 유형: 소급
- 기록일: 2026-07-23
- 결정일: 2026-07-23
- 관련 요구사항: [정원 홀드·무료 예약](../p0/reservation.md)의 `FR-05`·`US-01`과 [정원 홀드·무료 예약 API 명세서](../api/p0/reservation/reservation.md)의 동시성 계약
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

초기 MVP는 무료 예약을 대상으로 하며, 사용자가 예약을 확인하는 동안 정원을 10분간 홀드한다. 마지막 잔여 정원에 여러 요청이 동시에 들어와도 활성 홀드와 확정 예약의 합이 회차 정원을 넘지 않아야 한다. 홀드 생성, 만료, 예약 확정이 서로 다른 요청과 작업에서 실행되므로 단일 애플리케이션 인스턴스의 메모리 락으로는 정합성을 보장할 수 없다.

2026-07-23 PRD에서 MySQL 조건부 갱신과 트랜잭션을 최종 정합성 기준으로 확정하고 Redis 분산 락은 초기 MVP 예약 경로에서 제외했다. 당시 비교 논의의 전체 기록은 남아 있지 않으므로, 이 ADR은 확인 가능한 요구사항과 선택 결과를 소급해 기록한다.

## 결정 동인과 불변 조건

- 활성 홀드 인원과 확정 예약 인원의 합은 회차 정원을 초과하지 않는다.
- 홀드 생성과 정원 확보는 하나의 MySQL 트랜잭션에서 함께 성공하거나 함께 실패한다.
- 활성 홀드만 한 번 예약으로 전환할 수 있다.
- 만료 또는 소비된 홀드는 정원을 두 번 반환하거나 다시 소비할 수 없다.
- 애플리케이션 인스턴스 수와 무관하게 같은 정합성 규칙이 적용된다.
- Redis 장애가 예약 정합성에 영향을 주지 않는다.

## 결정

회차 정원의 최종 정합성은 MySQL이 책임진다. 홀드 생성 시 회차의 현재 활성 홀드와 확정 예약을 반영하는 조건부 `UPDATE`가 성공한 경우에만 `ACTIVE` 홀드를 같은 트랜잭션에서 생성한다.

예약 확정은 홀드를 `ACTIVE`에서 `CONSUMED`로 한 번만 전환하고 예약을 생성하는 작업을 하나의 트랜잭션에서 처리한다. 홀드 만료는 `expires_at`과 현재 상태를 조건으로 `ACTIVE`에서 `EXPIRED`로 한 번만 전환하며, 성공한 전환만 정원을 반환한다. 스케줄러는 만료 처리를 촉발할 수 있지만 만료 시각과 상태의 기준은 MySQL에 둔다.

Redis는 공개 콘텐츠 캐시와 요청 제한에만 사용한다. 초기 MVP의 홀드 생성·확정·만료 경로에는 Redis 분산 락을 사용하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 정원 상태와 트랜잭션의 장애·롤백 의미가 MySQL 하나로 수렴한다.
- 애플리케이션 다중 인스턴스 환경에서도 같은 조건부 갱신 규칙을 적용할 수 있다.
- Redis 장애나 락 유실이 초과 예약으로 이어지지 않는다.
- 조건부 갱신 결과로 정원 부족과 상태 경합을 명시적으로 판정할 수 있다.

### 수용한 단점과 위험

- 인기 회차의 쓰기 경합과 DB 부하를 수용한다.
- 조건부 갱신 실패를 정원 부족, 홀드 만료, 중복 확정, 일시 장애로 구분해야 한다.
- 만료 스케줄러가 지연되면 물리적인 정원 반환이 늦어질 수 있으므로 요청 경로에서도 만료 상태를 신뢰하지 않고 `expires_at`을 확인해야 한다.
- 처리량이 증가하면 회차 행이 쓰기 병목이 될 수 있다.

## 전환과 롤백

신규 구현이므로 기존 예약 데이터 이관은 없다. Flyway로 회차 정원, 홀드 상태, 만료 시각과 필요한 제약·인덱스를 추가하고 조건부 갱신을 저장소 계층에 구현한다.

조건부 갱신이 목표 처리량을 충족하지 못하면 우선 쿼리와 인덱스, 트랜잭션 범위를 조정한다. 그래도 해결되지 않을 때 새 ADR로 비관적 락, 낙관적 락 또는 Redis 직렬화 계층 도입을 결정한다. Redis를 추가하더라도 MySQL의 정원 불변 조건은 제거하지 않은 채 단계적으로 적용한다.

## 검증 방법

- 정원 1인 회차에 동시 홀드 요청을 보내 성공한 활성 홀드 인원이 1을 넘지 않는지 Testcontainers 기반 통합 테스트로 검증한다.
- 같은 홀드를 동시에 확정해 예약과 정원 전환이 한 번만 발생하는지 검증한다.
- 만료 처리와 예약 확정을 동시에 실행해 둘 중 하나만 성공하고 정원이 중복 반환되지 않는지 검증한다.
- 트랜잭션 중간에 예외를 발생시켜 회차 정원과 홀드가 함께 롤백되는지 검증한다.
- `session_id`, `hold_id`, 이전·다음 상태, 조건부 갱신 결과와 `requestId`를 구조화 로그로 남긴다.
- 초과 예약이 한 건이라도 발생하면 실패로 판정한다.

## 대체 조건

- 운영 부하에서 회차 행의 락 대기나 갱신 충돌이 합의한 SLO를 지속적으로 위반한다.
- 다중 리전 또는 다중 저장소 구조로 전환해 하나의 MySQL 트랜잭션을 사용할 수 없다.
- 만료 홀드 규모가 스케줄러와 요청 경로에서 감당할 수 있는 범위를 넘는다.
- 유료 결제 도입으로 장시간 홀드와 외부 결제 상태를 함께 조정해야 한다.
