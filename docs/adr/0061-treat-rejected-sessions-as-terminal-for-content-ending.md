# ADR-0061: REJECTED 회차를 콘텐츠 종료 판정에서 종결로 처리

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-04
- 결정일: 2026-08-04

- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0059](0059-automatically-end-content-after-all-sessions-terminate.md#결정)의 자동·수동 종료 대상 회차 상태와 검증 범위, [ADR-0060](0060-serialize-content-ending-and-session-creation-with-content-lock.md#결정-동인과-불변-조건)의 `REJECTED` 회차 종료 방해 조건. 조정 스케줄러와 공통 `content` 행 잠금 결정은 유지한다.

## 맥락

회차 반려 계약은 추가 회차가 `PENDING → REJECTED`로 전이하면 심사가 종결되고, 공개·홀드·예약 대상에서
제외된다고 정한다. `REJECTED` 회차를 다시 `PENDING`이나 `SCHEDULED`로 바꾸는 상태 전이도 없다.

반면 ADR-0059와 ADR-0060은 `REJECTED` 회차가 하나라도 있으면 콘텐츠를 종료하지 않도록 정했다. 이 규칙을
그대로 적용하면 실제 운영 회차가 모두 완료되거나 취소돼도 과거에 반려된 추가 회차 하나 때문에 콘텐츠가 계속
`PUBLISHED`로 남는다. 회차 반려의 종결 의미와 콘텐츠 종료 판정이 서로 맞지 않는다.

## 결정 동인과 불변 조건

- `REJECTED` 회차는 공개·홀드·예약 대상으로 다시 사용하지 않아야 한다.
- 승인 가능성이 남은 `PENDING` 회차와 운영 예정인 `SCHEDULED` 회차가 있으면 콘텐츠를 종료하지 않아야 한다.
- `REJECTED` 회차만을 이유로 공개 콘텐츠가 계속 남지 않아야 한다.
- 콘텐츠에는 하나 이상의 회차가 있어야 하며, 회차가 없는 콘텐츠는 자동·수동 종료하지 않아야 한다.
- 자동 종료, 수동 종료와 추가 회차 생성은 ADR-0060의 공통 `content` 행 잠금과 잠금 뒤 재확인 규칙을 유지해야 한다.

## 결정

콘텐츠 자동·수동 종료 판정에서 `COMPLETED`, `CANCELLED`, `REJECTED`를 종결 상태로 사용한다. 연결된 회차가
하나 이상이고 모든 회차가 이 세 상태 중 하나일 때만 소프트 삭제되지 않은 `PUBLISHED` 콘텐츠를 `ENDED`로
전환한다. `PENDING` 또는 `SCHEDULED` 회차가 하나라도 있으면 종료하지 않는다.

`REJECTED`는 회차가 실제 운영을 완료했다는 뜻이 아니라, 심사가 끝나 더 이상 공개·홀드·예약 대상으로 진행되지
않는다는 뜻으로만 종료 판정에 포함한다. 회차 반려 상태와 반려 사유는 그대로 보존한다.

종료 처리의 트랜잭션과 잠금 방식은 바꾸지 않는다. 자동 종료, 수동 종료와 추가 회차 생성은 같은 `content` 행을
먼저 잠그고, 잠금을 얻은 뒤 콘텐츠와 전체 회차 상태를 다시 확인한다.

## 결과와 트레이드오프

### 기대 효과

- 반려된 추가 회차가 정상적인 콘텐츠 종료를 영구적으로 막지 않는다.
- 회차 반려 문서의 종결 의미와 자동·수동 종료 조건이 일치한다.
- 종료를 막는 상태가 `PENDING`, `SCHEDULED`로 명확해진다.

### 수용한 단점과 위험

- `PUBLISHED` 콘텐츠의 모든 회차가 `REJECTED`인 데이터도 자동 종료될 수 있다.
- 나중에 `REJECTED → PENDING` 재심사 전이를 도입하면 종료 조건을 다시 검토해야 한다.

## 전환과 롤백

DB 스키마나 기존 데이터 이관은 필요 없다. 콘텐츠 기준 문서, ERD, 자동·수동 종료 명세와 출시 완료 기준을 먼저
같은 상태 집합으로 맞춘다. 구현할 때 종료 대상 조회의 허용 상태를 `COMPLETED`, `CANCELLED`, `REJECTED`로 바꾸고
관련 MySQL 통합 테스트를 추가한다.

예상하지 못한 자동 종료가 확인되면 자동 종료 스케줄러를 중지하고 원인을 확인한다. 이미 종료된 콘텐츠를 임의로
되돌리지 않으며, 종료 상태 집합을 다시 바꾸려면 새 ADR로 이 결정을 대체한다.

## 검증 방법

- `COMPLETED`, `CANCELLED`, `REJECTED`가 섞여 있고 `PENDING`, `SCHEDULED`가 없으면 콘텐츠가 한 번만 `ENDED`로 전환되는지 검증한다.
- `REJECTED` 회차만 남아 있어도 다른 종료 조건을 충족하면 자동·수동 종료되는지 검증한다.
- `PENDING` 또는 `SCHEDULED` 회차가 하나라도 있으면 콘텐츠·로그·감사·홀드·정원이 변경되지 않는지 검증한다.
- 스케줄러 중복 실행, 수동 종료와 추가 회차 생성의 동시 실행에서도 종료 결과와 기록이 중복되지 않는지 검증한다.
- 자동 종료 건수와 종료 시점의 회차 상태별 건수를 구조화 로그와 MySQL 운영 조회로 확인한다.

## 대체 조건

- `REJECTED` 회차를 다시 `PENDING`으로 돌리는 재심사 흐름이 도입된다.
- 반려 회차를 물리 또는 소프트 삭제해 콘텐츠 종료 조회에서 제외하는 모델로 바뀐다.
- 모든 회차가 `REJECTED`인 공개 콘텐츠를 별도 운영 상태로 처리해야 한다는 정책이 확정된다.
