# ADR-0032: 공개 전 승인 콘텐츠의 수정 심사 중 자동 공개를 차단

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-30
- 결정일: 2026-07-30
- 관련 요구사항: [P0 명세의 FR-03·FR-04·FR-14](../p0-spec.md#7-기능-요구사항과-소유-문서), [CON-04](../p0/content-catalog.md#con-04), [CON-05](../p0/content-catalog.md#con-05), [ERD의 콘텐츠·회차 정규화 규칙](../erd.md#콘텐츠회차-정규화-규칙)
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0014](0014-store-published-content-edits-in-relational-revision-tables.md)의 수정본 대상을 `PUBLISHED` 원본으로 한정한 범위, [ADR-0020](0020-merge-event-experience-details-into-content-and-revision.md)의 수정본 승인 시 원본이 `PUBLISHED`여야 한다는 범위

## 맥락

기존 P0 계약은 `PUBLISHED` 콘텐츠의 수정본만 허용한다. 그러나 이미 `APPROVED`됐지만 아직 공개되지 않은 콘텐츠가
공개 예정 시각이나 표시 정보를 바꾸려면, 원본을 직접 수정할 수도 수정본 심사를 받을 수도 없는 공백이 있었다.

승인된 공개 예정 시각만 바꾸는 경우에도 지역 관리자의 재승인이 필요하다. 원본을 계속 `APPROVED`로 두면 수정본 심사 중
기존 `publish_at`에 자동 공개되어, 심사하지 않은 변경 후보와 이미 공개된 원본의 관계가 모호해진다. 사용자는 이 경우
원본을 `PENDING`으로 되돌려 자동 공개를 차단하고, 수정본이 반려·철회돼도 `PENDING`을 유지하기로 선택했다.

## 결정 동인과 불변 조건

- 공개 여부는 `publish_at`만이 아니라 `content.status = PUBLISHED`와 `deleted_at IS NULL`로 판정한다.
- 공개 콘텐츠는 운영자가 원본을 직접 수정할 수 없고, 승인된 수정본만 원본에 원자적으로 반영한다.
- 공개 전 수정 요청이 심사 중이거나 종결된 뒤 재보완 대기 중이면, 이전 승인본이 자동 공개돼서는 안 된다.
- 공개 전 수정본의 후보 공개 예정 시각과 공개 콘텐츠 수정본의 공개 예정 시각 의미를 혼동하지 않는다.
- 수정본 승인·반려·철회와 자동 공개가 경합해도 원본·수정본·상태 로그·감사 기록이 부분 반영되지 않는다.
- 초기 생성 직후의 일반 `PENDING` 콘텐츠를 수정본 재제출 경로로 우회하지 않는다.

## 결정

`POST /operator/contents/{contentId}/revisions`는 다음 원본에 수정본을 만들 수 있다.

- `PUBLISHED` 콘텐츠: 후보 `publish_at`은 `NULL`로 저장한다. 승인 시 후보 표시 필드만 원본에 반영하고
  원본 `PUBLISHED` 상태와 기존 `content.publish_at`은 유지한다.
- `APPROVED` 콘텐츠: 후보 `publish_at`은 필수다. 수정본과 원본의 `APPROVED → PENDING` 전이, `PENDING`
  상태 로그와 성공 감사 기록을 하나의 트랜잭션에서 기록한다.
- 앞선 공개 전 수정본이 `EDIT_REJECTED` 또는 `EDIT_WITHDRAWN`으로 종결된 경우: 활성 수정본이 없고 직전 공개 전
  수정 요청에 따른 `APPROVED → PENDING` 이력이 있는 `PENDING` 콘텐츠만 새 공개 전 수정본을 만들 수 있다.
  최초 생성 후 일반 `PENDING` 콘텐츠에는 적용하지 않는다.

공개 전 수정본 승인에는 원본 `PENDING`, 수정본 `EDIT_REQUESTED`, 기준 원본 버전 일치와 후보 `publish_at` 존재가
필요하다. 성공 시 후보 필드와 후보 `publish_at`을 원본에 반영하고, 원본을 `PENDING → APPROVED`로 전이한다.
원본 버전 증가, 수정본 `EDIT_APPROVED` 전이, `APPROVED` 상태 로그와 성공 감사 기록은 같은 트랜잭션에서 커밋한다.

공개 전 수정본의 반려·철회는 수정본만 종결하고 원본을 `PENDING`으로 유지한다. 자동 공개 작업은 `APPROVED`인
원본만 조건부로 `PUBLISHED`로 전이하므로, 이 콘텐츠는 새 수정본이 승인될 때까지 자동 공개되지 않는다.

자동 공개와 공개 전 수정본 생성이 경합하면 현재 상태를 조건으로 먼저 커밋한 요청만 성공한다. 자동 공개가 먼저
`PUBLISHED`로 전이했으면 운영자는 공개 콘텐츠 수정본 흐름으로 다시 요청한다. 수정본 생성이 먼저
`APPROVED → PENDING`으로 전이했으면 자동 공개는 실패하며, 수정본 승인 뒤의 새 `publish_at`만 자동 공개 대상이 된다.

`PUT /operator/contents/{contentId}`는 계속 `REJECTED` 원본 콘텐츠의 보완에만 사용한다. 수정본의 상세 승인·반려
HTTP 경로와 요청·응답은 구현 전에 별도 API 계약으로 확정하며, 해당 계약은 수정본 식별자를 기준으로 공개 전과
공개 콘텐츠의 승인 조건을 구분해야 한다.

## 결과와 트레이드오프

### 기대 효과

- `APPROVED`지만 아직 공개되지 않은 콘텐츠도 원본 직접 수정 없이 재심사를 받을 수 있다.
- 미승인 변경이나 이전 승인본이 예정 시각에 자동 공개되는 일을 막는다.
- 공개 콘텐츠 수정과 공개 전 수정에서 `content_revision.publish_at`의 의미를 구분한다.
- 상태 조건부 갱신으로 자동 공개와 수정 요청의 경합 결과를 하나로 제한한다.

### 수용한 단점과 위험

- 공개 전 수정본이 반려·철회되면 콘텐츠는 자동 공개되지 않고 `PENDING`으로 남아 운영자의 후속 후보 제출이 필요하다.
- `PENDING`이 최초 심사 대기와 공개 전 수정 재심사 대기를 모두 표현하므로, API와 운영 화면은 활성 수정본과 상태 이력을
  함께 확인해야 한다.
- `content_revision.publish_at`의 `NULL`은 공개 콘텐츠 수정본의 일정 변경 없음이라는 의미이므로, 단순한 널 병합으로
  승인 분기를 구현하면 안 된다.
- 기존 수정본 심사 API는 원본 `PUBLISHED`만 전제하므로, 구현 전 공개 전 수정본 심사 계약을 추가·정정해야 한다.

## 전환과 롤백

신규 `content_revision.publish_at`은 nullable 컬럼으로 Flyway migration에 추가한다. 기존 공개 콘텐츠 수정본은
`publish_at = NULL`로 유지하므로 데이터 이관이 필요 없다. 이후 공개 전 수정본 생성, 원본 상태 전이, 심사와
자동 공개 작업의 조건부 갱신을 순서대로 배포한다.

배포 중 문제 발생 시 공개 전 수정본 생성 명령을 중지하고, `PENDING`으로 전이된 콘텐츠는 지역 관리자가 현재 승인 정책에
따라 수동으로 검토한다. nullable 컬럼은 보존해도 기존 공개 콘텐츠 수정본과 호환된다. 이미 생성된 수정본·상태 로그·감사
기록은 삭제하거나 원본 상태를 자동 복구하지 않으며, 새 상태 전이 또는 전진 수정으로 정정한다.

## 검증 방법

- `APPROVED` 콘텐츠의 수정본 생성이 후보 `publish_at`과 함께 원본을 한 번만 `PENDING`으로 전이하고, 자동 공개 작업이
  이전 `publish_at`으로 `PUBLISHED` 전이에 실패하는지 검증한다.
- 공개 전 수정본 승인 시 후보 필드·후보 `publish_at`, `PENDING → APPROVED`, 수정본 종결, 원본 버전 증가와 감사 기록이
  함께 커밋되고, 하나라도 실패하면 모두 롤백되는지 검증한다.
- 공개 전 수정본 반려·철회 뒤 원본이 `PENDING`으로 남고, 활성 수정본이 없을 때만 새 공개 전 수정본을 만들 수 있는지 검증한다.
- 최초 생성 직후의 일반 `PENDING` 콘텐츠는 수정본 생성으로 우회할 수 없고 기존 콘텐츠 심사 흐름만 따르는지 검증한다.
- `PUBLISHED` 원본 수정본의 후보 `publish_at`이 `NULL`이며 승인 뒤 원본 상태·기존 `publish_at`이 바뀌지 않는지 검증한다.
- 자동 공개와 수정본 생성, 수정본 승인·반려·철회가 동시에 요청돼도 최초 조건부 전이만 성공하고 상태 로그·감사 기록이
  중복되거나 부분 반영되지 않는지 검증한다.
- `content_revision.publish_at IS NULL`인 공개 전 수정본 또는 `IS NOT NULL`인 공개 콘텐츠 수정본이 0건인지,
  `PENDING`인데 활성 공개 전 수정본도 직전 `APPROVED → PENDING` 이력도 없는 재수정 시도가 0건인지 관찰한다.

## 대체 조건

- 공개 전 수정본 반려·철회 뒤 기존 승인본을 자동 공개해야 한다는 제품 정책이 확정된다.
- 공개 전 수정본의 병렬 편집, 병합 또는 여러 후보 비교가 필요해 단일 활성 수정본 제약을 유지할 수 없다.
- `PENDING`의 두 심사 의미가 운영 화면·API·감사 조회에서 지속적인 오류를 만들어 별도 수정 심사 상태가 필요해진다.
- 자동 공개 지연이나 공개 전 수정 심사 대기 시간이 합의한 운영 기준을 지속적으로 넘는다.
