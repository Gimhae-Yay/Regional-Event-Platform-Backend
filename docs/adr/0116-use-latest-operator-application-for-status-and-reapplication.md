# ADR-0116: 최신 운영자 신청을 현황 조회와 재신청 판단의 단일 기준으로 사용한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-24
- 결정일: 2026-08-24
- 관련 요구사항: [FR-09 운영자 승인·정보 마스킹](../p0/auth-profile.md#fr-09-운영자-승인정보-마스킹), [AUTH-02](../p0/auth-profile.md#auth-02)
- 관련 단계: 단계 0. 정책·설계 확정
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

인증된 회원은 운영자 신청 이력이 있어도 본인의 현재 심사 상태와 반려 사유를 조회할 수 없다. 클라이언트가
`REJECTED` 상태에서만 재신청 버튼을 제공하려면 회원에게 노출할 현재 상태와 재신청 제출 시 서버가 검증하는 상태의
기준이 같아야 한다.

기존 재신청 계약과 구현은 `PENDING` 신청의 존재 여부와 과거 `REJECTED` 신청의 존재 여부를 각각 확인한다. 현재
상태 전이에서는 이 방식도 정상 흐름을 거부하지만, 과거 반려 이력이 가장 최근의 승인·취소 상태보다 우선하는 조건을
직접 배제하지 않는다. 또한 조회 뒤 심사 또는 다른 재신청이 커밋될 수 있으므로 클라이언트가 조회한 상태만으로 제출을
허용해서는 안 된다.

## 결정 동인과 불변 조건

- 본인 신청 현황과 재신청 허용 여부는 같은 운영자 신청을 기준으로 판정해야 한다.
- 여러 신청의 생성 시각이 같아도 가장 최근 신청을 결정적으로 선택해야 한다.
- 클라이언트의 버튼 노출 여부와 무관하게 서버는 제출 트랜잭션에서 현재 상태를 다시 검증해야 한다.
- 동시 재신청은 새 `PENDING` 신청을 하나만 생성해야 한다.
- 본인 조회와 재신청 응답에 사업자 정보 원문과 심사자 정보를 노출하지 않는다.
- 회원 탈퇴가 제거한 신청자 연결을 복원하거나 별도 사용자 식별자를 추가하지 않는다.

## 결정

신청자 연결이 유지된 본인의 `operator_application`을 `created_at` 내림차순으로 정렬하고, 같은 시각이면
`operator_application_id` 내림차순으로 정렬한 첫 행을 가장 최근 신청으로 정의한다.

`GET /api/v1/me/operator-application`은 이 신청의 비민감 상태를 반환한다. 신청 이력이 없으면
`operatorApplication: null`을 반환한다. `PENDING`, `REJECTED`, `APPROVED`는 각각 심사 중, 반려, 승인 상태로
조회할 수 있다. `CANCELLED` 신청은 현재 회원 탈퇴에서 신청자 연결과 계정을 함께 제거하므로 인증된 본인 조회의
관찰 가능한 상태로 계약하지 않는다.

`POST /api/v1/operator/operator-requests`는 회원 행을 잠근 쓰기 트랜잭션에서 역할과 가장 최근 신청을 다시 조회한다.
가장 최근 신청이 `REJECTED`일 때만 새 `PENDING` 신청을 생성한다. `PENDING`이면
`OPERATOR_APPLICATION_PENDING`, 신청 이력이 없거나 가장 최근 신청이 `APPROVED` 또는 `CANCELLED`이면
`OPERATOR_APPLICATION_REAPPLICATION_NOT_ALLOWED`로 거부한다. 이미 `OPERATOR` 또는 `REGION_ADMIN` 역할이
부여된 회원을 `FORBIDDEN`으로 거부하는 기존 인가 경계는 유지하며 이 역할 검사를 최신 신청 상태 검사보다 먼저
적용한다. 따라서 승인 뒤 `OPERATOR` 역할이 유지된 정상 회원은 `APPROVED` 상태 오류가 아니라 `FORBIDDEN`을 받는다.

본인 조회는 신청 식별자, 상태, 요청 지역 식별자·이름, 신청 시각, 심사 시각과 반려 사유만 반환한다.
`businessInformation`과 심사자 정보는 반환하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 프론트엔드는 조회된 `REJECTED` 상태에만 재신청 버튼을 노출할 수 있다.
- 조회 이후 상태가 바뀌어도 POST가 잠금 획득 뒤 최신 상태를 다시 확인해 잘못된 재신청을 막는다.
- 과거 반려 이력과 현재 상태의 의미가 섞이지 않고 최신 신청 한 건으로 일관된다.
- 신청 시각이 같은 데이터에서도 식별자 역순으로 결과가 결정된다.

### 수용한 단점과 위험

- 기존 재신청 Repository·Service의 존재 여부 조회를 최신 신청 조회로 바꾸고 회귀 테스트를 보강해야 한다.
- 본인 조회만으로 재신청 성공을 보장하지 않으므로 클라이언트는 POST의 상태 오류를 정상적으로 처리해야 한다.
- 현재 탈퇴·개인정보 파기 정책에서는 `CANCELLED` 상태를 본인에게 보여 줄 수 없다.

## 전환과 롤백

스키마와 기존 데이터 이관은 필요하지 않다. 먼저 인증·프로필 정책과 GET·POST API 명세를 확정하고, 구현에서 최신
신청 조회와 POST 재검증을 적용한 뒤 클라이언트가 GET 응답으로 화면을 전환한다.

공개 전에는 문서와 구현을 함께 되돌려 기존 재신청 흐름으로 복구할 수 있다. 공개 뒤에는 GET 계약을 제거하거나 최신
신청의 정의를 바꾸지 않는다. 변경이 필요하면 새 ADR과 버전 또는 호환 계약을 먼저 확정한다.

## 검증 방법

- 신청 이력이 없으면 GET이 `operatorApplication: null`을 반환하는지 검증한다.
- 최신 신청이 `PENDING`, `REJECTED`, `APPROVED`일 때 상태별 nullable 필드와 비민감 정보만 반환하는지 검증한다.
- 생성 시각이 같은 신청은 더 큰 `operator_application_id`를 최신 신청으로 선택하는지 검증한다.
- GET 뒤 심사 상태가 변경된 경우 POST가 조회 당시 상태가 아니라 잠금 획득 뒤 최신 상태로 판정하는지 검증한다.
- 동시 재신청에서 새 `PENDING` 신청이 한 건만 생성되고 나머지는 처리 중 오류로 끝나는지 검증한다.
- 과거 `REJECTED` 신청이 있어도 가장 최근 신청이 `APPROVED` 또는 `CANCELLED`이면 재신청을 거부하는지 검증한다.
- 본인 조회와 재신청 응답·로그에 사업자 정보 원문과 심사자 정보가 포함되지 않는지 검증한다.

## 대체 조건

- 운영자 신청을 별도 온보딩 시스템으로 이전해 `operator_application`이 현재 상태의 기준이 아니게 된다.
- 활성 회원이 신청을 직접 취소하는 기능이 추가되어 `CANCELLED`를 본인 조회에 노출해야 한다.
- 운영자 신청 이력을 단일 최신 행이 아닌 별도 현재 상태 스냅샷이나 이벤트 스트림으로 관리하도록 저장 모델을 변경한다.
