# ADR-0064: 전체관리자 계정을 배포로 준비하고 안전하게 비활성화한다

- 상태: 채택됨

- 기록일: 2026-08-05
- 결정일: 2026-08-05

- 관련 이슈: 없음

## 맥락

ADR-0063은 기존 역할 연결에 `PLATFORM_ADMIN`을 저장하는 방식을 정했지만, 최초 전체관리자 계정의 준비 경로와 계정
비활성화 뒤 인증 상태를 확정하지 않았다. 최초 계정을 일반 보호 API로 만들 수 없고, 역할만 회수하면 기존 세션과
계정 상태가 남아 특권 회수의 의미가 불명확해진다.

## 결정 동인과 불변 조건

- 최초 전체관리자 계정은 공개 또는 일반 업무 API로 생성하지 않는다.
- 활성 `PLATFORM_ADMIN`만 추가 전체관리자 계정을 생성할 수 있다.
- 비활성화된 계정은 로그인과 새 특권 요청을 수행할 수 없고, 활성 Refresh Token 계열을 계속 사용할 수 없다.
- 자기 자신과 마지막 활성 전체관리자의 비활성화는 허용하지 않는다.
- 계정 생성·비활성화에는 actor, 대상, 이전·이후 상태, 사유, 시각과 `requestId`를 감사 이력으로 남긴다.
- 비밀번호·토큰·Redis 키와 값은 응답·로그·감사 이력에 남기지 않는다.

## 결정

최초 전체관리자 계정은 자격 증명을 migration·소스·로그에 저장하지 않는 승인된 배포 절차로 준비한다. 일반 API는
최초 계정을 만들 수 없으며, 이미 활성인 `PLATFORM_ADMIN`만 `POST /api/v1/platform-admin/admin-accounts`로 추가 계정을
생성할 수 있다. 생성 성공 시 새 `app_user`는 `ACTIVE`이고 `user_role_assignment`에 `PLATFORM_ADMIN`, `region_id = NULL`을
가진다.

비활성화는 `POST /api/v1/platform-admin/admin-accounts/{userId}/deactivate`에서만 수행한다. 대상은 활성 `PLATFORM_ADMIN`이어야
하며 처리자 자신과 마지막 활성 `PLATFORM_ADMIN`은 대상이 될 수 없다. 대상의 Refresh Token 활성 계열을 Redis에서 먼저 모두
폐기한 뒤, `app_user.status`를 `ACTIVE → INACTIVE`로 전이하고 성공 감사 이벤트를 같은 MySQL 트랜잭션에 기록한다.
Redis 폐기에 실패하면 상태와 감사 이벤트를 변경하지 않는다. Redis 폐기 성공 뒤 MySQL 전이가 실패하면 폐기한 계열을
복구하지 않으며 대상은 다시 로그인해야 한다. 기존 Access Token은 자연 만료 전까지 존재할 수 있지만, 보호 API는
계정 상태를 최종 확인해 `INACTIVE` 계정의 새 특권 요청을 거부한다.

`INACTIVE` 계정의 재활성화, 마지막 관리자 복구와 비상 절차는 현재 일반 API로 제공하지 않는다. 별도 운영 요구가
확정되면 후속 ADR·API·ERD에서 다룬다.

## 결과와 트레이드오프

### 기대 효과

- 최초 특권 계정 생성 경로와 추가 계정 관리 경로가 분리돼 권한 상승을 막는다.
- 비활성화가 역할 회수뿐 아니라 로그인·Refresh Token 재발급을 차단하는 계정 상태 전이가 된다.
- 마지막 활성 전체관리자 손실과 자기 자신을 비활성화하는 실수를 막는다.

### 수용한 단점과 위험

- Redis 성공 뒤 MySQL 실패 시 대상 계정은 여전히 `ACTIVE`이지만 Refresh Token으로는 재로그인해야 한다.
- `INACTIVE` 상태·비활성화 시각·감사 제약을 ERD와 인증 구현에 추가하기 전에는 API를 구현할 수 없다.

## 전환과 롤백

현재 P1 전체관리자 데이터와 구현이 없으므로 데이터 이관은 없다. 구현 전에 ERD에 `INACTIVE` 상태와 필요한
비활성화 정보·제약을 추가하고, 배포 절차·JWT 계정 상태 검증·Redis 계열 폐기·감사 기록을 이 결정에 맞춘다.

도입 중 Redis 폐기 또는 MySQL 감사 기록이 실패하면 비활성화를 성공으로 응답하지 않는다. 잘못 비활성화된 계정을
일반 API로 재활성화하지 않으며, 승인된 비상 복구 절차와 전진 migration으로만 처리한다.

## 검증 방법

- 최초 계정 생성 API가 노출되지 않고, 활성 `PLATFORM_ADMIN`만 추가 계정을 생성할 수 있는지 검증한다.
- 생성 성공 시 계정·`PLATFORM_ADMIN` 역할·성공 감사 이벤트가 함께 생성되고, 중복 로그인 식별자는 어떤 행도 추가하지 않는지 검증한다.
- 자기 자신·마지막 활성 관리자·이미 비활성화됐거나 `PLATFORM_ADMIN`이 아닌 대상은 비활성화되지 않는지 동시 요청을 포함해 검증한다.
- Redis 폐기 실패 시 MySQL 상태와 감사 이벤트가 유지되고, Redis 성공 뒤 MySQL 실패 시 폐기 계열을 복구하지 않는지 검증한다.
- 비활성화 뒤 로그인·Refresh Token 갱신·보호 API가 거부되고, 비밀번호·토큰·Redis 키가 응답·로그·감사 이력에 없는지 검증한다.

## 대체 조건

- 다중 승인, 별도 보안 운영 주체 또는 조직 단위 특권 계정이 필요해 단일 `PLATFORM_ADMIN` 역할과 배포 절차로 관리할 수 없게 된다.
- 승인된 재활성화 또는 마지막 관리자 비상 복구를 제품 API로 제공해야 하는 운영 요구가 확정된다.
