# ADR-0047: 예약 확정에서 홀드와 예약 감사 이벤트를 분리해 기록

- 대체 대상: [ADR-0015](0015-store-audit-events-in-mysql-with-withdrawn-actor-anonymization.md)의 감사 대상 모델 범위

## 맥락

예약 확정은 `capacity_hold`의 `ACTIVE → CONSUMED` 전이와 `reservation`의 `CONFIRMED` 생성을 함께 만든다.
그러나 기존 `audit_event`는 하나의 `target_type`, `target_id`만 기록하고 대상 유형에 `CAPACITY_HOLD`가 없다.
예약만 대상으로 기록하면 홀드 소비 전이를 직접 재현할 수 없고, 홀드를 예약 대상으로 표시하면 감사 대상의 의미가
틀어진다.

사용자는 홀드 소비와 예약 생성을 각각의 감사 이벤트로, 같은 MySQL 트랜잭션에서 기록하는 방식을 선택했다.

## 결정 동인과 불변 조건

- 예약 확정의 홀드·예약 식별자와 두 상태 변이를 90일 동안 재현할 수 있어야 한다.
- 성공 도메인 변경, 멱등 성공 결과, 두 감사 이벤트와 actor link는 함께 커밋하거나 함께 롤백해야 한다.
- 감사 본문과 구조화 로그에 개인정보, QR 원문, 멱등 키 원문을 저장하지 않는다.
- 이미 적용한 V1 migration은 수정하지 않고 이후 변경은 증분 migration으로 적용한다.

## 결정

`AuditEventTargetType`과 `audit_event.target_type` CHECK 제약에 `CAPACITY_HOLD`를 추가한다.
예약 확정이 성공하면 동일한 `request_id`, 지역, 처리자와 처리 시각을 가진 다음 두 성공 이벤트를 기록한다.

- `CAPACITY_HOLD`: 대상은 확정한 홀드이며 `previous_state = ACTIVE`, `next_state = CONSUMED`다.
- `RESERVATION`: 대상은 새 예약이며 `previous_state = NULL`, `next_state = CONFIRMED`다.

두 이벤트, 활성 처리자의 `audit_event_actor_link`, 멱등 키 점유·성공 결과, 홀드 소비와 예약 생성은 하나의
MySQL 트랜잭션에서 처리한다. 실패·거부 감사는 ADR-0015의 독립 트랜잭션 원칙을 유지하며, 안전하게 식별한
홀드가 있으면 `CAPACITY_HOLD`를 대상으로 사용하고 없으면 `target_id`를 비운다.

## 결과와 트레이드오프

### 기대 효과

- 예약 확정의 두 도메인 전이를 대상 의미에 맞게 재현한다.
- 예약과 홀드의 FK 관계 및 같은 `request_id`를 통해 운영 조회가 두 이벤트를 안전하게 연결한다.
- 감사 이벤트에 사용자 식별자나 QR·멱등 키 원문을 추가하지 않는다.

### 수용한 단점과 위험

- 성공 한 건당 감사 행이 두 건 생성되어 저장·조회량이 늘어난다.
- 두 이벤트 중 하나만 저장되는 오류를 막기 위해 트랜잭션과 통합 테스트가 반드시 필요하다.

## 전환과 롤백

구현 시 `V2` 이상의 Flyway migration으로 `audit_event`의 CHECK 제약을 교체하고 JPA enum을 확장한다.
V1은 변경하지 않는다. 아직 예약 확정 감사 데이터가 없으므로 backfill은 필요 없다.

배포 전 검증에서 두 이벤트 원자성이 보장되지 않으면 새 예약 확정 경로를 배포하지 않는다. 배포 뒤 문제가
발견되면 새 쓰기를 중단하고 누락된 감사 행을 임의 수정하지 않으며, 원인과 정정 사실을 새 감사 이벤트로 남긴다.

## 검증 방법

- 성공 확정 한 건에 동일 `request_id`의 `CAPACITY_HOLD`와 `RESERVATION` 이벤트가 정확히 한 건씩 생성되는지 검증한다.
- 두 이벤트·actor link·예약·멱등 결과 중 하나라도 저장에 실패하면 홀드가 `CONSUMED`로 남거나 예약이 생성되지 않는지 검증한다.
- 상태 충돌·권한 거부·존재하지 않는 홀드의 실패 이벤트가 개인정보 없이 안전한 대상 또는 빈 대상 ID로 기록되는지 검증한다.
- 이벤트 대상 유형별 생성량과 같은 요청의 두 이벤트 누락을 구조화 지표로 관찰한다.

## 대체 조건

- 하나의 업무 명령이 세 개 이상의 독립 대상을 항상 같은 감사 행으로 기록해야 한다.
- 90일 감사 보관량 또는 대상별 조회 비용이 합의한 운영 한계를 지속적으로 넘는다.
- 외부 감사 저장소나 다중 대상 감사 모델이 P0 범위로 확정된다.
