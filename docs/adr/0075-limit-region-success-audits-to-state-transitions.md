# ADR-0075: 지역 성공 감사를 실제 상태 전이로 한정

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-07
- 결정일: 2026-08-07
- 관련 요구사항: [P1 명세](../p1-spec.md)의 3.1 핵심 목표와 7.4 권한·감사·개인정보, [전체관리자](../p1/platform-admin.md)의 `P1-FR-09`, `ADM-02`, `ADM-05`
- 관련 단계: 단계 3. 확장 의사결정
- 관련 이슈: 없음
- 대체 대상: [ADR-0072](0072-use-allowlisted-reason-codes-for-region-changes.md)의 공개 여부 변경 성공 시 사유 코드·증빙 참조 저장 범위

## 맥락

[ADR-0072](0072-use-allowlisted-reason-codes-for-region-changes.md)는 지역 공개 여부 변경 요청이 성공하면 검증된 `reasonCode`와 `evidenceReference`를 성공 감사에 저장하도록 정했다. 이후 [ADR-0074](0074-treat-repeated-region-visibility-as-no-op-success.md)는 현재 공개 여부와 같은 목표 상태의 유효한 요청을 `200 OK` 무변경 성공으로 처리하되 감사 이벤트를 생성하지 않도록 정했다.

두 결정에서 사용하는 성공의 범위가 다르다. HTTP 성공 응답 전체를 ADR-0072의 감사 대상으로 해석하면 무변경 요청에도 감사를 생성해야 하고, ADR-0074를 따르면 생성하지 않아야 한다. 실제 상태 전이와 단순 재시도를 구분하는 감사 기준을 명시적으로 확정해야 한다.

## 결정 동인과 불변 조건

- 실제 지역 생성 또는 공개 여부 상태 전이는 성공 감사 이벤트와 같은 트랜잭션으로 커밋해야 한다.
- 현재 값과 같은 공개 여부 요청은 `200 OK`를 반환하더라도 상태 전이가 아니므로 성공 감사 이벤트를 생성하지 않아야 한다.
- 무변경 요청도 인증·인가, `reasonCode`, `evidenceReference` 검증을 먼저 통과해야 한다.
- 성공 감사가 존재하면 검증된 요청 사유 코드와 증빙 참조를 반드시 저장해야 한다.
- 실패 감사의 사유 코드는 클라이언트 사유가 아니라 서버 판정 코드를 사용한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 추천안: 실제 상태 전이 성공만 성공 감사로 기록 | 재시도 때문에 동일한 성공 감사가 중복되지 않고 상태 전이와 감사가 일대일로 대응한다. | HTTP 성공 요청 수와 성공 감사 수가 같지 않으므로 운영 지표에서 둘을 구분해야 한다. | 낮음 | ADR-0074의 무변경 성공과 P1 감사 일관성에 적합하다. |

## 결정

지역 공개 여부 변경의 성공 감사는 실제 `region.is_public` 값이 바뀐 경우에만 생성한다. 이때 요청의 `reasonCode`와 `evidenceReference`를 각각 `audit_event.reason_code`, `audit_event.evidence_reference`에 저장하고 지역 변경과 같은 트랜잭션으로 커밋한다.

현재 값과 요청 값이 같으면 인증·인가와 입력 검증을 완료한 뒤 `200 OK`와 현재 지역을 반환한다. 지역 행과 `updatedAt`을 변경하지 않으며 성공·실패 감사 이벤트도 만들지 않는다. 따라서 이 경우 검증된 `reasonCode`와 `evidenceReference`는 저장되지 않는다.

이 결정은 ADR-0072의 공개 여부 변경 성공 감사 범위를 실제 상태 전이 성공으로 좁힌다. 지역 생성은 항상 새 지역 상태를 만드는 실제 변경이므로 ADR-0072의 기존 성공 감사 규칙을 그대로 적용한다. 상태 조건 실패 감사의 서버 판정 코드 저장 규칙도 변경하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 실제 지역 상태 전이와 성공 감사가 일대일로 대응한다.
- 응답 유실 뒤 재시도가 성공·실패 또는 중복 성공 감사로 기록되지 않는다.
- API 요청 필드의 저장 조건을 구현과 테스트에서 명확히 구분할 수 있다.

### 수용한 단점과 위험

- `200 OK` 요청 건수와 성공 감사 이벤트 건수가 일치하지 않는다.
- 무변경 요청의 업무 사유와 증빙은 감사 테이블에 남지 않으므로 요청 로그와 감사 이력의 목적을 구분해야 한다.

## 전환과 롤백

P1 지역 공개 여부 변경 API가 구현 전이므로 데이터 이관은 없다. API 요청 필드 설명, 처리 규칙, P1 ERD와 테스트 계약을 실제 상태 전이 기준으로 함께 갱신한다.

이 결정을 되돌리려면 후속 ADR에서 무변경 요청 감사의 중복 판정 기준, 보관 비용과 기존 감사 집계의 호환 정책을 먼저 확정한다. 지역 생성의 성공 감사 계약은 이 전환의 영향을 받지 않는다.

## 검증 방법

- 실제 공개 여부 전이는 지역 변경과 사유·증빙을 포함한 성공 감사 한 건을 함께 커밋하는지 확인한다.
- 동일 상태 요청은 `200 OK`를 반환하고 `updatedAt`과 감사 이벤트 수를 바꾸지 않는지 확인한다.
- 같은 목표 상태의 동시 요청은 한 건의 실제 전이와 한 건의 성공 감사로 수렴하는지 확인한다.
- 허용하지 않은 사유 코드나 누락된 증빙은 동일 상태 요청에서도 `400`으로 거부되고 감사 이벤트를 만들지 않는지 확인한다.

## 대체 조건

- 모든 고권한 API 호출 자체를 법적 감사 대상으로 보관해야 한다는 요구가 확정된다.
- 무변경 요청의 사유·증빙을 운영 조사에서 반복적으로 복원해야 한다는 근거가 축적된다.
- 별도 멱등 요청 저장소를 도입해 논리 요청별 최초 결과와 감사를 정확히 재생하게 된다.
