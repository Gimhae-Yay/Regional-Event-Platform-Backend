# ADR-0053: 로그아웃과 토큰 갱신 경합을 활성 jti 기준으로 직렬화한다

- 상태: 채택됨

- 결정일: 2026-08-01

- 대체 대상: [ADR-0023](0023-manage-refresh-token-revocation-in-redis.md)의 소비된 Refresh Token 재제시 시 계열을 폐기하는 규칙 중 `POST /api/v1/auth/logout`에 적용하는 범위

## 맥락

로그아웃 API는 이미 소비·폐기된 Refresh Token이면 서버 상태를 바꾸지 않고 쿠키만 만료한다고 정의한다. 반면 갱신이
먼저 완료돼 제시 토큰이 소비된 경우에도 로그아웃이 같은 계열 전체를 폐기한다고 하면, 완료 후 재사용과 정상 경합을
구분할 수 없다. 둘 다 이전 `jti`를 담은 서명·만료가 유효한 JWT 요청이기 때문이다.

계열 ID만으로 폐기하면 과거에 유출되거나 재전송된 소비 토큰도 새 활성 토큰을 가진 계열을 폐기할 수 있다. P0에는
요청 식별자나 별도 동시성 상태를 전달하는 공개 계약이 없으므로, 활성 `jti` 상태를 기준으로 로그아웃의 상태 변경
대상을 판정해야 한다.

## 결정 동인과 불변 조건

- 소비·폐기·상태가 유실된 Refresh Token은 로그아웃에서 Redis 상태를 추가로 바꾸지 않는다.
- 이전 Refresh Token의 재전송만으로 새 활성 Refresh Token 계열을 종료할 수 없어야 한다.
- 로그아웃이 먼저 상태 변경을 완료하면 같은 계열의 갱신 완료는 성공할 수 없어야 한다.
- Redis 장애에서는 폐기 성공이나 Cookie 삭제 성공으로 응답하지 않는다.
- Refresh Token 원문, `jti`, `family_id`와 Redis 키·값을 응답이나 로그에 노출하지 않는다.

## 결정

`POST /api/v1/auth/logout`은 서명과 만료가 유효한 제출 Refresh Token의 `jti`가 해당 계열의 활성 `jti`와
일치하고 사용자 활성 계열 인덱스도 일치할 때만 Redis 원자 작업으로 계열을 폐기한다. 이 조건이 성립하면 폐기 표지와
사용자 활성 계열 인덱스를 함께 갱신한다.

토큰이 없거나 서명·만료가 유효하지 않고, 제출 `jti`가 활성 값과 다르거나, 활성 계열·사용자 인덱스가 없거나,
계열이 이미 폐기된 경우에는 Redis 상태를 변경하지 않는다. 이 경우 로그아웃은 만료된 Refresh Cookie와 `200 OK`를
반환한다. Redis 읽기·쓰기 실패는 `503 AUTH_SERVICE_UNAVAILABLE`로 반환하고 Cookie를 변경하지 않는다.

갱신 완료 원자 작업과 로그아웃 폐기 원자 작업의 Redis 실행 순서가 경합 결과를 정한다. 로그아웃이 먼저 활성
`jti` 일치를 확인해 폐기하면 갱신 완료는 거부된다. 갱신 완료가 먼저 활성 `jti`를 새 값으로 교체하면, 이전 토큰을
담은 로그아웃은 상태를 변경하지 않고 Cookie만 만료한다. 소비 토큰을 `POST /api/v1/auth/refresh`에 다시 제시하는
경우의 계열 폐기 규칙은 ADR-0052를 그대로 따른다.

브라우저 클라이언트는 갱신과 로그아웃을 하나의 인증 상태 전이로 직렬화한다. 로그아웃 전 진행 중인 갱신이 끝나면
브라우저의 최신 Cookie로 로그아웃을 요청하고, 로그아웃이 끝날 때까지 새 갱신을 시작하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 소비된 Refresh Token의 사후 재전송으로 활성 세션이 종료되는 것을 막는다.
- 로그아웃의 무상태 변경·Cookie 정리 계약과 Redis 활성 `jti` 검증을 일관되게 유지한다.
- 추가 요청 식별자, Redis 키, MySQL 저장소 없이 기존 회전·폐기 상태를 재사용한다.

### 수용한 단점과 위험

- 클라이언트가 갱신과 로그아웃을 직렬화하지 않으면 갱신 완료 뒤의 이전 토큰 로그아웃은 서버의 새 계열을 폐기하지
  않는다.
- 로그아웃 API와 갱신 API는 같은 소비 토큰을 서로 다른 목적으로 처리하므로, 호출 경로별 테스트가 필요하다.

## 전환과 롤백

아직 로그아웃 API 구현과 운영 Refresh Token 상태가 없으므로 데이터 이관이나 호환 계층은 필요 없다. 구현 시
로그아웃 폐기 Redis 스크립트에 제출 `jti`와 활성 상태 일치 조건을 추가하고, API·Redis 통합 테스트를 함께 반영한다.

배포 뒤 장애로 코드를 되돌려야 해도 소비 토큰으로 활성 계열을 폐기하는 이전 동작으로 되돌리지 않는다. 조건부 폐기
검사를 포함한 마지막 정상 버전을 유지하거나 로그아웃 API를 재시도 가능한 실패로만 전환한다. 기존 Redis 폐기 표지와
TTL은 변경하지 않는다.

## 검증 방법

- 현재 활성 Refresh Token으로 로그아웃하면 계열이 폐기되고 동일 속성의 Cookie가 만료되는지 검증한다.
- 토큰 없음·만료·변조·소비·폐기·활성 상태 유실에서 Redis 상태가 변하지 않고 Cookie만 만료되는지 검증한다.
- 로그아웃 폐기가 먼저 완료되면 진행 중인 갱신 완료가 거부되고, 갱신 완료가 먼저 활성 `jti`를 바꾸면 이전 토큰
  로그아웃이 상태를 바꾸지 않는지 Redis 통합 테스트로 검증한다.
- 소비 토큰을 갱신 API에 다시 제시하면 계열 전체가 폐기되는 기존 규칙이 유지되는지 검증한다.
- Redis 연결·명령 실패에서 `503 AUTH_SERVICE_UNAVAILABLE`과 Cookie 미변경을 검증하고, 토큰·식별자·Redis 키가
  로그와 응답에 노출되지 않는지 확인한다.

## 대체 조건

- 여러 탭·클라이언트의 갱신·로그아웃 직렬화를 클라이언트에서 보장할 수 없어 사용자 로그아웃 완료 보장이 필요해진다.
- 공개 요청 식별자나 세션 세대 계약을 도입해 정상 경합과 소비 토큰 재전송을 서버에서 구별해야 한다.
- 외부 IdP 또는 독립 인증 서비스가 Refresh Token 회전·폐기·로그아웃 경합을 제공한다.
