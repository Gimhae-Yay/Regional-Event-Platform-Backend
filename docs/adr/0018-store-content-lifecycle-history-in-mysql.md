# ADR-0018: 콘텐츠 생명주기 이력을 MySQL 불변 테이블로 분리한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-28
- 결정일: 2026-07-28
- 관련 요구사항: [P0 명세](../p0-spec.md)의 `FR-04`, `FR-11`, `FR-14`, `AC-11`, `AC-12`, `AC-17`, [콘텐츠 카탈로그](../p0/content-catalog.md)의 `CON-03`, `CON-06`~`CON-09`
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음. [ADR-0015](0015-store-audit-events-in-mysql-with-withdrawn-actor-anonymization.md)의 90일 감사 이벤트와 역할을 분리해 보완한다.

## 맥락

기존 `content`에 게시·중단·철회·종료·소프트 삭제 시각과 처리자·사유를 함께 저장하면 한 행의
`updated_at`은 마지막 수정 시각만 남긴다. 이후 제목 또는 다른 필드를 변경하면 각 상태 전이의 실제 시각과
사유를 일반 컬럼으로 재현할 수 없다.

P0는 자동 공개·중단·철회·종료·삭제의 처리 주체, 시각과 사유를 구분해 재현하고, 중단·철회 사유를
보존할 것을 요구한다. ADR-0015의 `audit_event`는 성공·실패를 포함하는 전 도메인 감사 기록이지만 90일 후
파기하므로 콘텐츠의 장기 업무 이력을 대신할 수 없다.

사용자는 이 업무 이력을 Redis가 아니라 MySQL의 콘텐츠 전용 테이블에 저장하기로 선택했다.

## 결정 동인과 불변 조건

- 콘텐츠 현재 상태·자동 공개 조회와 공개 전 소프트 삭제의 조건부 갱신은 단일 `content` 행에서 효율적으로
  판정할 수 있어야 한다.
- 콘텐츠 생명주기 이력은 `updated_at`에 덮어쓰지 않고 생성 순서, 전후 상태, 처리 시각, 처리자 유형과
  필요한 사유를 보존해야 한다.
- 성공한 상태 전이·소프트 삭제, 현재 상태 스냅샷 갱신과 성공 `audit_event`는 하나의 MySQL 트랜잭션에서
  함께 커밋하거나 함께 롤백해야 한다.
- 이력 본문에는 `user_id`, 이름·연락처, JWT·QR 원문 또는 사용자별 안정 가명을 저장하지 않는다.
- 회원 탈퇴 후 이력에서 해당 회원을 역참조할 수 없어야 한다.
- `audit_event`의 90일 보관·실패 기록 책임과 콘텐츠 업무 이력의 장기 보존 책임을 혼합하지 않는다.

## 결정

`content_lifecycle_event`를 MySQL의 추가 전용 콘텐츠 업무 이력으로 둔다. 이 테이블은 `content_id`와
콘텐츠별 유일한 `sequence_no`, 이벤트 유형(`INITIALIZED`, `STATUS_CHANGED`, `SOFT_DELETED`), 전후 상태,
actor 유형·역할, 사유와 `occurred_at`을 보관한다. 생성 시 `INITIALIZED(NULL → PENDING)` 이벤트를 한 건
기록한다. 상태 전이는 `STATUS_CHANGED`, 공개 전 소프트 삭제는 상태가 아니므로 `SOFT_DELETED` 이벤트로
기록한다.

활성 사용자 actor는 이력 본문에 저장하지 않고 1:0..1 `content_lifecycle_event_actor_link`로 연결한다.
`actor_kind = USER`이면 actor link와 역할이 필수이고, `SYSTEM`이면 actor link와 역할이 없다. 회원 탈퇴
완료 전에 actor link를 파기하며, 연결이 제거된 이력은 `WITHDRAWN_MEMBER`라는 공통 표시 값으로만 조회한다.

`content`는 현재 상태 스냅샷으로 `status`, `publish_at`, `created_at`, `updated_at`을 유지한다.
`published_at`, `suspended_at/by/reason`, `withdrawn_at/by/reason`, `ended_at`, `deleted_by/reason`은 생명주기
이벤트에서 조회한다. `deleted_at`만은 P0의 `deleted_at IS NULL` 조건부 갱신·목록 제외를 유지하기 위한
통제된 현재 상태 투영으로 남기며, 반드시 `SOFT_DELETED` 이벤트의 `occurred_at`과 같아야 한다.

상태 전이는 `content.status`의 기대 상태를 조건으로 갱신하고, 같은 트랜잭션에서 다음 `sequence_no` 이벤트와
성공 `audit_event`를 삽입한다. 셋 중 하나라도 실패하면 모두 롤백한다. 생명주기 이벤트 본문은 애플리케이션이
수정·개별 삭제하지 않으며, 상태 전이의 실패·권한 거부와 90일 감사 조회는 계속 `audit_event`가 담당한다.

## 결과와 트레이드오프

### 기대 효과

- 콘텐츠 상태별 시각·사유·처리자를 이후 일반 수정과 무관하게 보존한다.
- 콘텐츠 상태 이력과 전 도메인 감사·실패 이력의 보관 기간과 조회 책임을 분리한다.
- 콘텐츠 상태·소프트 삭제의 일반 조회와 조건부 갱신은 현재 `content` 행에서 계속 수행한다.
- 탈퇴 처리에서 actor link만 제거해 개인 역참조 없이 이력 사실을 유지한다.

### 수용한 단점과 위험

- 콘텐츠 상태 한 번을 바꿀 때 현재 행·이력 행·감사 이벤트를 함께 기록해야 한다.
- `sequence_no`와 `content.status`가 어긋나지 않도록 조건부 갱신, 유일 제약과 통합 테스트가 필요하다.
- `deleted_at`은 이력에서 유도 가능한 값이지만 소프트 삭제 경합과 목록 조회를 위해 중복 저장한다.
- 이력 장기 보존의 실제 기간은 콘텐츠 보존 정책을 따르며, 90일 감사 파기 작업과 혼동하면 안 된다.

## 전환과 롤백

아직 콘텐츠 migration과 구현이 없으므로 기존 데이터를 이관하거나 호환 계층을 둘 필요는 없다. 구현 시
`content`의 상태별 메타데이터 컬럼을 만들지 않고, 먼저 생명주기 이벤트·actor link의 스키마와 유일 제약을
추가한 뒤 콘텐츠 생성·전이 유스케이스를 같은 트랜잭션 경계로 구현한다.

도입 중 상태 스냅샷과 이력의 불일치가 발견되면 새 상태 전이 기능을 중지하고, 아직 배포하지 않은 migration을
되돌린다. 운영 데이터가 생긴 뒤에는 이력 행을 수정·삭제해 고치지 않으며, 불일치 원인을 새 정정 이벤트와
운영 절차로 기록한다. 이력을 단기 캐시나 외부 전달 이벤트로 바꾸려면 보관·원자성·탈퇴 처리 방식을 새 ADR로
다시 결정한다.

## 검증 방법

- 생성, 승인, 자동 공개, 반려, 중단, 철회, 종료와 소프트 삭제마다 허용된 전후 상태·순번·처리 시각·사유가
  이력에 정확히 한 건 기록되는지 검증한다.
- 같은 콘텐츠의 동시 상태 전이에서 `content.status` 기대 상태 조건과 `(content_id, sequence_no)` 유일
  제약으로 하나만 성공하며, 성공한 행의 상태와 마지막 이력이 같은지 검증한다.
- 상태 전이·이력 삽입·감사 이벤트 삽입 각각에 실패를 발생시켜 세 변경이 함께 롤백되는지 검증한다.
- 자동 공개·종료 이벤트에는 사용자 actor link가 없고, 사용자 처리 이벤트에는 정확히 한 actor link와 필요한
  사유가 있는지 검증한다.
- 탈퇴 완료 전 콘텐츠 생명주기 actor link를 제거한 뒤, 해당 회원을 직접·간접 역참조할 수 없고 이력은 공통
  `WITHDRAWN_MEMBER`로만 표시되는지 검증한다.
- `SOFT_DELETED` 이벤트와 `content.deleted_at`이 같은 시각이며, 삭제된 콘텐츠가 자동 공개·상태 전이·일반
  목록에서 제외되는지 검증한다.

## 대체 조건

- 콘텐츠 상태 이력을 법률·계약상 외부 변경 불가 저장소에 더 오래 보관해야 한다.
- 콘텐츠 상태 이력의 조회량·보관량이 MySQL의 합의한 운영 한계를 지속적으로 넘는다.
- 상태 전이를 외부 전달·재생하는 보장된 이벤트 계약이 실제 출시 범위로 채택된다.
- 콘텐츠 소프트 삭제의 `deleted_at` 현재 상태 투영이 인덱스·조회 최적화로도 불필요하다는 측정 근거가 생긴다.
