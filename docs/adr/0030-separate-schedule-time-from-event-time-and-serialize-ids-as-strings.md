# ADR-0030: 일정 시각과 사건 시각을 분리하고 API 식별자는 문자열로 직렬화한다

- 상태: 채택됨

## 맥락

회차의 `startsAt`, `endsAt`, 체크인 창은 사용자가 정한 지역 일정이며, `audit_event.occurred_at`와 취소·생성·확정 시각은 이미 발생한 사건이다. ERD도 회차와 감사 이벤트를 별도 모델로 둔다. 두 값은 모두 시각이지만, 전자는 지역 업무 시간 의미를 잃지 않아야 하고 후자는 시스템·클라이언트·감사 조회 사이에서 같은 순간을 가리켜야 한다.

기존 명세의 `+09:00` 예시는 회차 일정에는 적합하지만 모든 사건 시각을 같은 표기로 강제할 근거는 아니다. 반대로 모든 값을 UTC로 전송하면 운영자가 입력·검토하는 회차 시간에서 지역 시간 의미를 매번 복원해야 한다. 또한 Java의 `Long`은 JavaScript `Number`의 안전 정수 범위를 넘을 수 있으므로 JSON 숫자로 외부 식별자를 표현하면 값이 손상될 수 있다.

## 결정 동인과 불변 조건

- 회차 일정은 P0 운영 지역의 벽시계 시간과 순서 규칙을 보존해야 한다.
- 감사·상태 전이·생성 시각은 시간대 변환과 무관하게 같은 순간을 비교·정렬할 수 있어야 한다.
- 외부 API 식별자는 JavaScript를 포함한 일반 JSON 소비자가 정밀도 손실 없이 왕복할 수 있어야 한다.
- 내부 영속 식별자와 외부 직렬화 형식을 분리하되, 서버의 양의 `Long` 제약은 유지해야 한다.

## 결정

1. 회차 시작·종료와 체크인 창처럼 사용자가 정한 **일정 시각**은 `Asia/Seoul`의 ISO 8601 오프셋 일시 `YYYY-MM-DDTHH:mm:ss[.fraction]+09:00`으로 요청·응답한다. 일정 시각에는 `Z` 또는 다른 오프셋을 허용하지 않는다.
2. 생성·수정·확정·취소·처리·감사 발생 시각처럼 이미 발생한 **사건 시각**은 UTC ISO 8601 일시 `YYYY-MM-DDTHH:mm:ss[.fraction]Z`로 응답한다. 서버는 이 값을 UTC `Instant`로 기록·비교한다.
3. 데이터베이스의 `Long` 식별자를 외부 API에 노출할 때는 양의 10진 정수 문자열로 표현한다. URL 경로 변수도 같은 문자열 표현을 사용한다. 서버는 `^[1-9][0-9]*$`를 만족하고 signed 64비트 `Long` 범위에 들어오는 값만 허용한다.
4. 개별 API 명세는 해당 필드가 일정 시각인지 사건 시각인지, 그리고 식별 대상만 정의한다. 공통 형식은 API 공통 규칙을 단일 출처로 사용한다.

## 결과와 트레이드오프

### 기대 효과

- 운영 화면은 회차 일정을 변환 없이 `Asia/Seoul` 기준으로 입력·검토할 수 있다.
- 감사·상태 전이 시각은 UTC 기준으로 비교·정렬되어 지역 시간대 확장이나 서버 시간대 설정의 영향을 받지 않는다.
- JavaScript와 다른 JSON 소비자가 큰 식별자를 손상 없이 전달·저장할 수 있다.

### 수용하는 단점과 위험

- 클라이언트는 문자열 식별자를 숫자로 강제 변환하지 않아야 한다.
- API 문서와 DTO는 일정 시각·사건 시각을 혼동하지 않도록 필드별 의미를 명시해야 한다.
- 해외 운영 지역이 추가되면 일정 시각의 지역 시간대 선택 모델을 별도 ADR로 확장해야 한다.

## 전환과 롤백

이번 회차 API 명세와 공통 규칙을 먼저 전환하고, 다른 도메인 명세·DTO·클라이언트는 배포 전에 같은 계약으로 순차 전환한다. 기존 소비자가 숫자 식별자 또는 `+09:00` 사건 시각을 사용 중이면 호환 기간과 버전 전략을 별도 ADR로 결정하기 전에는 배포하지 않는다.

## 검증 방법

- 회차 일정 예시가 `+09:00`이고, 취소·감사 사건 예시가 `Z`인지 확인한다.
- URL·요청·응답의 리소스 식별자가 양의 10진 문자열인지 확인한다.
- 문자열 식별자가 `Long.MAX_VALUE`까지 손상 없이 파싱되고, `0`·음수·소수·범위 초과·비숫자 값이 거부되는지 검증한다.
- 사건 시각을 UTC로 비교하고 일정 시각을 `Asia/Seoul` 규칙으로 검증하는 테스트를 둔다.

## 대체 조건

- P0 운영 지역이 `Asia/Seoul` 단일 지역을 벗어나 일정별 시간대 모델이 필요해진다.
- 외부 API 소비자가 문자열 식별자보다 다른 공개 식별자 체계를 요구하거나, 내부 `Long` 식별자를 더 이상 사용하지 않는다.
