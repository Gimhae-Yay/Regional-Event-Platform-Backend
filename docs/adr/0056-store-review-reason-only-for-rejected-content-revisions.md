# ADR-0056: 콘텐츠 수정본 반려에만 심사 사유를 저장

- 상태: 채택됨
- 기록 유형: 신규

- 결정일: 2026-07-31

- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증

## 맥락

콘텐츠 수정본 승인 API는 요청 본문을 받지 않지만, 현재 ERD는 `EDIT_APPROVED`와 `EDIT_REJECTED` 모두에
`review_reason`을 필수로 정의한다. 승인 요청에서 제공하지 않은 사유를 영속화하려면 서버가 임의 값을 만들거나 승인
API에 새 입력 계약을 추가해야 하므로 API와 영속 계약이 일치하지 않는다.

[ADR-0014](0014-store-published-content-edits-in-relational-revision-tables.md)는 반려·철회 수정본의 상태·처리자·시각·사유를
보존하도록 정했고, [ADR-0037](0037-block-automatic-publication-during-pre-publication-revision-review.md)은 공개 전
수정본까지 같은 심사 흐름을 확장했다. 두 ADR은 승인 사유를 입력하거나 저장하는 계약을 정하지 않았으므로 이 결정을
보완하며 대체하지 않는다.

## 결정 동인과 불변 조건

- 승인 API의 요청 본문 없음 계약을 유지한다.
- 반려 API는 앞뒤 공백을 제거한 비어 있지 않은 사유를 필수로 받고 그대로 보존한다.
- 승인과 반려 모두 처리 시각과 실제 처리자를 보존한다.
- 공개 콘텐츠와 공개 전 콘텐츠 수정본에 동일한 심사 정보 규칙을 적용한다.
- 승인·반려 상태와 심사 정보는 같은 트랜잭션에서 함께 저장되거나 함께 롤백된다.

| 3 | 승인과 반려 모두 `review_reason`을 선택으로 저장 | 단일 nullable 규칙으로 구현이 단순하다. | 반려 사유 누락을 허용해 운영자의 보완 근거와 현재 반려 API 계약을 훼손한다. | 낮음. 반려 사유 필수 검증을 다시 추가하면 된다. | 반려 이력 보존 조건을 충족하지 않아 채택하지 않는다. |

## 결정

`content_revision.status = EDIT_APPROVED`이면 `reviewed_at`, `reviewed_by_user_id`를 필수로 저장하고
`review_reason`은 `NULL`로 저장한다. 승인 API는 요청 본문 없이 이 상태 전이를 수행하며 응답에도 승인 사유를 추가하지
않는다.

`content_revision.status = EDIT_REJECTED`이면 `reviewed_at`, `reviewed_by_user_id`, 앞뒤 공백을 제거한 비어 있지
않은 `review_reason`을 모두 필수로 저장한다. 반려 API는 `reason`을 필수로 받고 저장된 값을 `reviewReason`으로
응답한다.

이 규칙은 공개 콘텐츠 수정본과 공개 전 콘텐츠 수정본에 동일하게 적용한다. Flyway migration, 엔티티 제약과 승인·반려
API 구현은 각 후속 Task에서 이 상태별 불변식을 강제한다.

## 결과와 트레이드오프

### 기대 효과

- 승인 API와 `content_revision` 영속 계약이 일치한다.
- 승인에 임의 문자열이나 의미 없는 기본 사유를 저장하지 않는다.
- 반려 사유는 운영자의 보완과 심사 이력 재현에 필요한 값으로 계속 보존한다.
- 처리자와 처리 시각은 승인·반려 모두 남아 심사 주체와 시점을 추적할 수 있다.

### 수용한 단점과 위험

- 승인 판단의 자유 형식 설명은 `content_revision`에서 조회할 수 없다.
- 상태별 null 조건을 애플리케이션 검증과 DB 제약에서 분리해 구현하면 계약이 다시 어긋날 수 있다.
- 향후 승인 사유가 필요해지면 요청·응답과 영속 계약을 함께 변경해야 한다.

## 전환과 롤백

현재는 구현 전 문서 확정 단계이므로 기존 수정본 데이터 이관은 없다. ERD의 상태별 필수값을 먼저 분리하고, 후속
Task에서 migration과 엔티티 상태 전이, 승인·반려 API를 같은 규칙으로 구현한다.

배포 전 문제가 발견되면 후속 구현을 중단하고 문서 계약의 불일치를 해결한 새 ADR로 이 결정을 대체한다. 배포 후 승인
사유 필수 정책으로 바꾸려면 승인 요청·응답 계약과 DB 제약을 함께 변경해야 하며, 기존 `EDIT_APPROVED` 행의 사유는
추측해 채우지 않고 별도 이관 정책을 먼저 확정한다.

## 검증 방법

- 승인 API가 요청 본문 없이 성공하고 `EDIT_APPROVED` 행에 처리 시각·처리자만 저장하며 `review_reason IS NULL`인지 검증한다.
- 반려 API가 누락·공백 사유를 거부하고, 정상 사유는 trim한 뒤 `EDIT_REJECTED` 행과 응답에 동일하게 보존하는지 검증한다.
- 승인·반려 저장 중 실패하면 상태, 처리 시각, 처리자와 사유가 모두 롤백되는지 검증한다.
- 공개 콘텐츠와 공개 전 콘텐츠 수정본에서 동일한 상태별 필수값이 적용되는지 검증한다.
- 승인·반려 API, ERD와 ADR 링크가 유효하고 서로 같은 계약을 설명하는지 검증한다.

## 대체 조건

- 감사·규제 또는 운영 요구로 승인 판단의 자유 형식 근거를 반드시 보존해야 한다.
- 승인 사유를 입력·조회하는 공개 API 계약이 별도로 확정된다.
- 자유 형식 사유 대신 구조화된 승인 체크리스트나 정책 버전을 저장하기로 결정한다.
