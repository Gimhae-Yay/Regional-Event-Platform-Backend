# ADR-0020: 행사·체험 상세 필드를 콘텐츠와 수정본에 통합

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-28
- 결정일: 2026-07-28
- 관련 요구사항: [지역·콘텐츠 카탈로그의 `CON-02`](../p0/content-catalog.md#con-02), [지역·콘텐츠 카탈로그의 `CON-05`](../p0/content-catalog.md#con-05)
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0006](0006-use-shared-content-root-with-type-specific-details.md)의 `Content`–`EventExperienceDetail` 1:1 상세 분리 범위와 [ADR-0014](0014-store-published-content-edits-in-relational-revision-tables.md)의 행사·체험 상세 수정본 자식 테이블·유형별 상세 원자 반영 범위

## 맥락

ADR-0006은 이후 가게·관광지 유형을 추가할 가능성을 고려해 공통 `Content`와 유형별 상세를 1:1로 분리했다.
ADR-0014는 이 구조를 따라 `content_revision`과 행사·체험 상세 수정본 테이블도 1:1로 분리했다.

현재 P0는 `EVENT_EXPERIENCE` 하나만 허용한다. 연령 조건, 준비물, 취소 안내는 모든 P0 콘텐츠에 항상 적용되며,
새 유형의 일정이나 구현 계획도 확정되지 않았다. 이 상황에서 원본과 수정본마다 1:1 상세 행을 유지하면 조회 조인과
생성·수정·승인 시 네 테이블 동기화만 늘어난다. 사용자는 현재 P0에서 이 1:1 분리를 제거하기로 채택했다.

## 결정 동인과 불변 조건

- 행사·체험 필드가 원본과 수정본에서 각각 한 행으로 완결되어 생성·수정·승인 경로를 단순하게 유지해야 한다.
- 심사 중인 수정본은 현재 공개 `content`를 바꾸지 않고, 승인된 수정본만 원본에 원자적으로 반영해야 한다.
- `content_type`은 P0에서 `EVENT_EXPERIENCE`만 허용하고 생성 뒤 변경하지 않는다.
- 연령 조건, 준비물, 취소 안내는 JSON이 아닌 명시적인 컬럼으로 보관한다.
- 아직 확정되지 않은 가게·관광지 테이블이나 API는 만들지 않는다.

## 결정

P0의 `content`에 `age_requirement`, `materials`, `cancellation_policy_text`를 직접 저장한다.
`content_revision`에도 같은 세 후보 필드를 직접 저장한다. `event_experience_detail`과
`event_experience_detail_revision`은 P0 ERD와 신규 구현에서 제거한다.

수정본 승인 시 원본이 `PUBLISHED`이고 수정본이 `EDIT_REQUESTED`이며 기준 버전이 일치하는지 조건으로 확인한다.
성공한 하나의 트랜잭션은 `content_revision`의 모든 후보 필드를 `content`에 반영하고, 원본 버전을 증가시키며,
수정본을 `EDIT_APPROVED`로 전이하고 성공 감사 이벤트를 기록한다. 반려·철회 수정본은 원본을 바꾸지 않는다.

`content_type`과 공통 콘텐츠 루트, 회차·예약이 `EVENT_EXPERIENCE`만 허용된다는 ADR-0006의 나머지 결정은 유지한다.
새 콘텐츠 유형이 실제 P0 범위로 확정되면 별도 ADR에서 통합 컬럼 유지, 새 1:1 상세 모델 또는 독립 모델을 다시 비교한다.

## 결과와 트레이드오프

### 기대 효과

- 현재 콘텐츠와 수정 후보의 행사·체험 필드를 각각 한 행에서 조회·검증한다.
- 콘텐츠 생성, 수정본 생성, 수정본 승인에 필요한 행 생성과 반영 대상이 줄어든다.
- `content_type`과 상세 행의 존재·종류 일치 제약 및 관련 오류 경로가 사라진다.
- P0 필수 필드는 명시적인 관계형 컬럼으로 계속 유지한다.

### 수용한 단점과 위험

- 이후 서로 다른 콘텐츠 유형이 추가되면 일부 필드가 특정 유형에만 적용될 수 있어 스키마 재설계와 데이터 이관이 필요하다.
- `content_type`이 하나뿐인 P0에서는 유형별 상세 확장성을 선구현하지 않는다.
- 수정본 행이 세 필드만큼 넓어지지만, 상세 수정본과의 조인·동기화 비용보다 작다고 판단한다.

## 전환과 롤백

신규 배포 전에는 `content`와 `content_revision`에 통합 필드만 포함해 생성하고 상세 테이블을 만들지 않는다.

이미 상세 테이블이 운영 DB에 배포된 경우에는 콘텐츠 생성·수정본 생성·심사 명령을 잠시 중지한 유지보수 구간에서 다음 순서로 전환한다.

1. 두 원본 테이블에 세 통합 컬럼을 추가하고 기존 상세 행에서 값을 복사한다.
2. 원본·수정본별 누락 행과 세 필드 값 불일치를 모두 0건으로 확인한 뒤 통합 컬럼의 필수 제약을 적용한다.
3. 애플리케이션 읽기·쓰기와 수정본 승인 반영을 통합 컬럼으로 전환한다.
4. 전환 뒤 생성·승인·반려·철회 검증과 운영 관측을 통과한 뒤 두 상세 테이블과 외래 키를 제거한다.

상세 테이블 제거 전 롤백이 필요하면 명령을 다시 중지하고 통합 필드 값을 기존 상세 테이블에 역복사한 뒤 이전
애플리케이션 버전으로 전환한다. 제거 후에는 백업에서 두 상세 테이블과 데이터를 복원하고 역복사해야 하므로 단순 롤백으로
간주하지 않는다. 데이터가 이미 통합 필드에 있으므로 우선은 전진 수정으로 복구하는 것을 기본으로 한다.

## 검증 방법

- 행사·체험 콘텐츠 생성 시 세 필드가 `content` 한 행에 저장되고 별도 상세 행을 요구하지 않는지 검증한다.
- 수정본 생성·제출·반려·철회가 현재 `content`를 변경하지 않는지, 승인만 세 후보 필드를 포함한 모든 후보 값을 원자적으로 반영하는지 검증한다.
- 기준 버전 불일치 또는 승인·반려·철회 경합에서 최초 하나만 성공하고 원본과 감사 이벤트가 부분 반영되지 않는지 검증한다.
- 운영 DB 전환 시 원본·수정본 행 수, 누락 필드 수, 원본/상세 값 비교 결과와 상세 테이블 참조 SQL 오류를 관측해 모두 0건인지 확인한다.
- ERD의 Mermaid 엔티티·관계, 문서 링크, `git diff --check`를 검증한다.

## 대체 조건

- `EVENT_EXPERIENCE`와 필드 집합이 실질적으로 다른 새 콘텐츠 유형이 P0 또는 후속 단계에 채택된다.
- 유형별 필드의 nullable 비율이나 조건부 검증이 높아져 통합 테이블의 명확성을 해친다.
- 통합된 콘텐츠·수정본의 조회 또는 승인 경로가 합의한 운영·성능 기준을 충족하지 못한다.
