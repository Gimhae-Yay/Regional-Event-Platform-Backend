# ADR-0048: 종결 멱등 결과를 24시간 보관하고 처리 중 요청을 자동 탈취하지 않는다

## 맥락

기존 영속 멱등성 결정은 완료 결과 재반환과 처리 중 요청 차단을 정했지만, `expires_at`의 기간과 DB 대기 제한을
운영 설정으로 남겼다. 따라서 같은 키 재시도의 보장 기간과 장시간 경합의 응답 의미가 일정하지 않았다.

사용자는 성공 및 저장 대상 결정적 실패 결과를 24시간 보관하고, 짧은 DB 대기 제한 뒤에는 새 작업 없이
`IDEMPOTENCY_REQUEST_IN_PROGRESS`를 반환하며 처리 중 요청을 자동 탈취하지 않는 정책을 선택했다.

## 결정 동인과 불변 조건

- 같은 actor·operation·키·요청 의미의 완료 결과를 보관 기간 안에 재반환해야 한다.
- 다른 요청 의미의 키 재사용, 서로 다른 키의 같은 홀드 확정, 중복 예약 생성을 모두 차단해야 한다.
- 처리 중 요청을 임의 재점유해 동시에 두 도메인 작업이 실행되면 안 된다.
- 트랜잭션 롤백, 저장소 장애와 장기 `PROCESSING` 상태를 구분해 관찰할 수 있어야 한다.

## 결정

`SUCCEEDED`와 API 명세에서 저장 대상으로 정한 `FAILED` 멱등 기록은 `completed_at`부터 24시간 보관한다.
종결 시 `expires_at = completed_at + 24시간`으로 기록하고, MySQL 현재 시각이 `expires_at`을 지난 종결 기록만
정리 작업에서 삭제한다. 이 기간이 지난 키에는 이전 결과 재반환을 보장하지 않는다.

동일 유일 키의 DB 경합 대기 제한은 짧은 운영 설정으로 관리한다. 제한을 넘긴 요청은
`409 IDEMPOTENCY_REQUEST_IN_PROGRESS`를 반환하고 새 도메인 작업을 실행하지 않는다. `PROCESSING` 기록은
만료·정리·재점유로 자동 탈취하지 않는다. 선행 트랜잭션이 실제로 롤백되어 기록이 남지 않은 뒤의 요청은
새 최초 요청으로 처리할 수 있으며, 이는 영속 `PROCESSING` 기록의 탈취가 아니다.

## 결과와 트레이드오프

### 기대 효과

- 24시간 동안 성공과 결정적 실패를 일관되게 재응답한다.
- DB 락 경합에서 추가 도메인 작업 없이 재시도 가능한 409을 반환한다.
- 만료 기반 재점유로 인한 예약·감사 중복을 막는다.

### 수용한 단점과 위험

- 장시간 `PROCESSING`은 사용자가 스스로 복구할 수 없으며 운영 경보와 조사가 필요하다.
- 24시간보다 긴 지연 재시도는 동일 결과 재반환을 보장하지 않는다.
- 정리 작업 지연은 저장량을 늘릴 수 있다.

## 전환과 롤백

기존 테이블의 `expires_at`과 `(status, expires_at)` 접근 경로를 유지한다. 구현 시 종결 전이에서 만료 시각을
갱신하고, 종결 상태만 대상으로 하는 정리 작업과 대기 제한 설정을 추가한다. 기존 V1 schema는 수정하지 않는다.

운영 중 보관 기간이 부족하거나 저장량이 과도하면 새 ADR로 기간과 정리 정책을 변경한다. 자동 탈취는 lease와
원자적 소유권 이전을 별도로 설계·검증하기 전에는 롤백 수단으로 사용하지 않는다.

## 검증 방법

- 같은 키·같은 요청의 성공과 저장 대상 실패가 완료 후 24시간 이내에 이전 결과를 반환하는지 검증한다.
- 같은 키의 다른 `holdId`와 서로 다른 키의 같은 홀드 경합이 각각 정해진 409로 거부되는지 검증한다.
- DB 대기 제한을 넘긴 동시 요청이 도메인 변경 없이 `IDEMPOTENCY_REQUEST_IN_PROGRESS`를 반환하는지 검증한다.
- 롤백된 선행 트랜잭션 뒤에는 새 요청만 처리되고, 남아 있는 `PROCESSING`은 자동 삭제·탈취되지 않는지 검증한다.
- 종결 기록의 만료·정리 지연·장기 `PROCESSING` 건수와 409 비율을 구조화 지표로 관찰한다.

## 대체 조건

- 24시간보다 긴 모바일·현장 재시도가 실제로 필요한 증거가 반복된다.
- 장기 `PROCESSING`으로 운영 개입이 합의한 한계를 넘는다.
- 저장량·정리 부하가 합의한 MySQL 운영 한계를 지속적으로 넘는다.
