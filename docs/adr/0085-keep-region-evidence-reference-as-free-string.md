# ADR-0085: 지역 증빙 참조를 1~500자 자유 문자열로 유지

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-07
- 결정일: 2026-08-07
- 관련 요구사항: [전체관리자](../p1/platform-admin.md)의 `ADM-05`, [P1 명세](../p1-spec.md)의 7.4 권한·감사·개인정보
- 관련 단계: 단계 3. 확장 의사결정
- 관련 이슈: 없음
- 대체 대상: [ADR-0082](0082-store-evidence-reference-in-region-visibility-failure-audits.md)의 `evidenceReference` 비밀값·개인정보 자동 검증 전제

## 맥락

지역 생성과 공개 여부 변경 API는 필수 `evidenceReference`를 성공 감사와 일부 실패 감사에 저장한다. 기존 계약은
개인정보, 토큰과 비밀값을 포함하지 않은 참조만 저장하도록 정했지만, 서버가 이를 어떤 형식과 규칙으로 판별할지는
확정하지 않았다.

티켓 ID 형식이나 증빙 시스템의 prefix를 제한하면 잘못된 입력을 선제적으로 거부할 수 있지만, 현재 P1에는 단일 증빙
시스템이나 공통 식별자 형식이 없다. 사용자는 API 형식을 추가로 제한하지 않고 현재의 앞뒤 공백 제거와 1~500자
검증만 유지하기로 결정했다.

## 결정 동인과 불변 조건

- 지역 변경 API의 기존 요청 구조와 `audit_event.evidence_reference` 저장 구조를 유지해야 한다.
- `evidenceReference`는 필수이며 앞뒤 공백 제거 후 1자 이상 500자 이하여야 한다.
- 호출자는 개인정보, 토큰과 비밀값을 포함하지 않아야 한다.
- 서버는 값의 의미와 출처를 추론하거나 개인정보·비밀값 탐지를 수행하지 않아야 한다.
- 감사 저장 장애를 위한 구조화 로그·알림과 API 응답에는 `evidenceReference`를 포함하지 않아야 한다.

## 결정

지역 생성과 공개 여부 변경의 `evidenceReference`는 JSON 문자열 타입의 필수 입력으로 유지한다. 서버는 앞뒤 공백을
제거한 뒤 1자 이상 500자 이하인지만 검증하며, 다음 항목은 검사하지 않는다.

- 허용 문자, prefix 또는 티켓 ID 형식
- 허용 증빙 시스템이나 URL 형식
- 이메일·전화번호 등 개인정보 포함 여부
- 토큰·비밀번호·결제 비밀값 등 비밀정보 포함 여부

검증을 통과한 값은 요청 계약에 따라 성공 감사 또는 지역 공개 여부 조건 실패 감사의
`audit_event.evidence_reference`에 그대로 저장한다. 호출자는 개인정보, 토큰과 비밀값을 포함하지 않은 내부 증빙
참조를 전달할 책임이 있다. 서버가 내용을 검사하지 않으므로 이 금지 규칙은 호출자와 운영 절차로 통제한다.

API 응답에는 `evidenceReference`를 포함하지 않는다. 감사 저장 장애를 포함한 구조화 로그와 운영 알림에도 요청
`evidenceReference`를 포함하지 않는다.

이 결정은 ADR-0082의 실패 감사 저장 여부와 저장 위치를 변경하지 않으며, 그 ADR의 비밀값·개인정보 검증 전제만
대체한다.

## 결과와 트레이드오프

### 기대 효과

- 기존 요청·응답과 DB 스키마를 변경하지 않는다.
- 서로 다른 증빙 시스템의 참조를 별도 형식 변경 없이 저장할 수 있다.
- 구현과 테스트의 검증 경계가 타입, 필수 여부, 앞뒤 공백과 길이로 명확해진다.

### 수용한 단점과 위험

- 호출자가 금지 정보를 보내면 서버가 이를 탐지하지 못하고 감사 이력에 저장할 수 있다.
- 증빙 참조의 형식과 조회 가능성을 서버가 보장하지 않는다.
- 감사 데이터 접근 통제와 보관 정책은 유출 영향을 줄일 뿐 잘못된 입력의 저장 자체를 예방하지 못한다.

## 전환과 롤백

지역 API가 구현 전이고 기존 데이터가 없어 스키마나 데이터 이관은 필요 없다. API 명세, 전체관리자 정책, P1 명세와
P1 ERD에 서버 검증 범위와 호출자 책임을 반영한 뒤 구현한다.

서버 검증을 강화하려면 이 ADR을 수정하지 않고 후속 ADR에서 허용 증빙 시스템, 식별자 형식, 기존 데이터 호환성과
오탐 처리 정책을 함께 확정한다.

## 검증 방법

- 앞뒤 공백 제거 후 1~500자인 문자열은 문자 구성이나 참조 형식과 무관하게 입력 검증을 통과하는지 확인한다.
- 누락, 문자열이 아닌 값, 공백만 있는 값과 500자를 초과한 값은 각각 계약된 오류로 거부되는지 확인한다.
- 저장된 `evidence_reference`가 앞뒤 공백을 제거한 요청값과 같은지 확인한다.
- API 응답, 구조화 로그와 운영 알림에 `evidenceReference`가 포함되지 않는지 확인한다.
- 서버가 URL·이메일 형태나 임의 prefix를 이유로 값을 거부하지 않는지 확인한다.

## 대체 조건

- 보안·개인정보 정책이 금지 정보의 저장을 서버에서 예방하도록 요구한다.
- 공통 증빙 시스템과 안정적인 식별자 형식이 확정된다.
- 잘못된 증빙 참조나 민감정보 저장 사고가 발생해 운영 통제만으로 위험을 수용할 수 없다.
