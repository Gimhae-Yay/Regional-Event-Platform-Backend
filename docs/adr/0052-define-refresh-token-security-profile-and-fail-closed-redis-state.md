# ADR-0052: Refresh Token 보안 프로필과 Redis 상태 소실의 페일 클로즈 경계를 확정한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-31
- 결정일: 2026-07-31
- 관련 요구사항: [FR-01 인증·역할·지역 권한](../p0/auth-profile.md#fr-01-인증역할지역-권한), [Access Token 재발급 API](../api/p0/auth-profile/refresh.md)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: [#162 Redis Refresh Token 계열·회전·폐기 기반 구현](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/162)
- 대체 대상: [ADR-0023](0023-manage-refresh-token-revocation-in-redis.md)의 Redis 키 계약 중 논리 키 범위와 회전 진행 상태 표현만 대체한다. 소비된 토큰·폐기 계열·사용자 활성 계열 인덱스의 TTL 의미와 탈퇴 선행 폐기 순서는 대체하지 않는다.

## 맥락

ADR-0005와 ADR-0023은 회전형 Refresh Token, 재사용 시 계열 폐기, Redis TTL 상태를 채택했다. 그러나
Refresh Token의 서명 키, 발급자·대상·토큰 유형, 수명과 회전 시 만료 연장 여부는 정해져 있지 않다.
`<refresh-token-ttl>`이라는 API 표기만으로는 새 토큰을 얼마 동안 허용할지 판단할 수 없다.

Access Token의 활성·직전 키와 최대 15분 검증 규칙을 Refresh Token에 그대로 공유하면 장기 Refresh Token의
정상 키 교체가 모두 재로그인을 유발하거나, 반대로 이전 대칭 키를 긴 기간 검증해야 한다. 또한 Redis의 소비·계열
폐기 표지만으로는 재시작, eviction 또는 오래된 스냅샷 복구로 일부 표지가 사라졌을 때 이미 소비된 Refresh
Token을 새 토큰처럼 허용할 수 있다. 현재의 Redis 연결 실패 정책만으로는 이 상태 소실을 구분하지 못한다.

마지막으로 재발급 API는 진행 중인 동일 요청을 `409 REFRESH_TOKEN_CONFLICT`로, 완료 뒤 이전 토큰 재사용을
계열 폐기와 `401 UNAUTHENTICATED`로 구분한다. 소비 표지만 두면 두 상황을 구별할 수 없다.

## 결정 동인과 불변 조건

- Refresh Token은 보호 업무 API의 Bearer 인증 수단이 될 수 없다.
- 토큰 원문·서명 키·`jti`·`family_id`·Redis 키와 값은 로그, 오류 응답, 감사 이벤트에 남기지 않는다.
- Refresh Token 원문·해시·계열·교체 관계를 MySQL에 저장하지 않는다.
- 회전된 Refresh Token의 재사용은 같은 계열의 아직 소비되지 않은 토큰도 즉시 무효화해야 한다.
- Redis 읽기·쓰기 실패와 Redis 상태 소실은 Refresh Token을 유효하다고 추정하는 근거가 될 수 없다.
- 로그인마다 독립된 계열을 만들며, P0에서는 기기 정보나 활성 계열 수 제한을 저장하지 않는다.
- 시간 검증과 TTL 계산은 주입된 `Clock`을 기준으로 수행한다.

## 결정

### Refresh Token JWT 프로필

Refresh Token은 JJWT로 발급·검증하는 HS256 JWS다. Access Token과 별도의 Base64 인코딩 256비트 이상 HMAC
활성 키를 `kid`와 함께 외부 설정 또는 비밀 저장소에서 주입한다. Refresh Token 검증은 활성 키 하나만 허용한다.
Refresh 서명 키를 교체하면 이전 키의 Refresh Token은 모두 거부하고 재로그인하게 한다. 장기 이전 키 검증 집합은
두지 않는다.

다음 claim만 발급·검증한다.

| Claim | 값 | 용도 |
| --- | --- | --- |
| `iss` | `regional-event-platform` | 발급자 검증 |
| `aud` | `regional-event-refresh` | Access Token과 대상 분리 |
| `sub` | 양의 사용자 ID의 10진 문자열 | 계열 소유자 식별 |
| `token_type` | `REFRESH` | Access Token과 사용 경계 분리 |
| `jti` | 암호학적으로 예측 불가능한 UUID v4 | 소비·재사용 탐지 식별자 |
| `family_id` | 암호학적으로 예측 불가능한 UUID v4 | 회전·폐기 단위 |
| `iat` | 발급 시각 | 수명 검증 |
| `exp` | 계열의 절대 만료 시각 | 만료·Redis TTL 계산 |

역할, 담당 지역, 콘텐츠 소유권, 개인정보와 Access Token claim은 넣지 않는다. 검증은 허용 알고리즘, `kid`, 서명,
`iss`, `aud`, `token_type`, 양의 `sub`, UUID 형식의 `jti`·`family_id`, `iat`, `exp`를 모두 확인한다. `exp`는
`iat`보다 늦고 `iat + 14일`을 넘을 수 없다.

로그인에서 새 계열을 만들 때만 `exp = iat + 14일`로 정한다. 회전으로 발급하는 토큰은 새 `iat`와 `jti`를 가지되,
기존 계열의 `family_id`, `exp`를 그대로 유지한다. 따라서 계열은 최초 로그인부터 정확히 최대 14일 후 끝나며,
회전이 수명을 연장하지 않는다. 로그인 응답의 Refresh Cookie `Max-Age`는 `1209600`초이고, 재발급 응답의
`Max-Age`는 해당 계열 만료까지 남은 전체 초다.

### Redis 상태와 상태 소실 처리

ADR-0023의 소비된 `jti`, 폐기된 `family_id`, 사용자→활성 계열 인덱스는 그대로 사용한다. 사용자 활성 계열
인덱스는 계열 ID를 멤버, 각 계열의 절대 만료 시각을 score로 갖는 정렬 집합으로 구현한다. 인덱스 자체의 TTL은
남은 계열 중 가장 늦은 만료 시각까지로 하고, 현재 계열 폐기·전체 계열 폐기 때 해당 멤버 또는 인덱스를 제거한다.

추가 논리 키는 다음 두 가지다.

| 논리 키 | 값·용도 | TTL |
| --- | --- | --- |
| 활성 계열 `family_id` | 현재 유효한 Refresh Token의 `jti` | 계열 절대 만료 시각까지 |
| 회전 진행 `jti` | 회전 시도 식별자 | 최대 5초 |

서명과 만료가 유효한 Refresh Token도 활성 계열 키의 값이 자신의 `jti`와 일치하고, 사용자→활성 계열 인덱스에
같은 `family_id`와 만료 시각이 있을 때만 유효하다. 표지의 부재를 활성 상태로 추정하지 않는다. 활성 계열 키나
사용자 인덱스가 유실되면 해당 계열의 Refresh Token은 모두 거부하고 새 로그인으로만 계열을 다시 만든다. 소비된
`jti` 표지가 유실된 경우에도 활성 계열의 현재 `jti`와 다르면 해당 계열을 폐기하므로 이전 토큰을 허용하지 않는다.

Refresh 상태는 `maxmemory-policy=noeviction`으로 운영하는 Redis 인스턴스에 둔다. Redis의 메모리 정책은
인스턴스 단위이므로 eviction을 허용하는 공개 조회 캐시는 이 인스턴스와 공유하지 않는다. 메모리 부족이나 Redis
연결·명령 실패는 발급·회전·폐기 성공으로 처리하지 않고 재시도 가능한 인증 서비스 실패로 반환한다. Redis
영속성은 재시작 뒤 사용자 재로그인을 줄이기 위해 사용할 수 있지만, 보안 판단은 활성 계열과 사용자 인덱스의
존재·일치 검증에 의존한다.

### 회전 경합과 재사용 처리

회전은 두 개의 원자 Redis 스크립트로 처리한다.

1. 시작 스크립트는 계열 폐기, 활성 계열의 현재 `jti`, 사용자 활성 계열 인덱스를 확인한다. 제시한 `jti`가 현재
   활성 값과 다르면 계열을 폐기하고 `UNAUTHENTICATED`를 반환한다. 현재 값과 같고 소비되지 않았으면 5초짜리
   회전 진행 표지를 만들고, 진행 중이면 `REFRESH_TOKEN_CONFLICT`를 반환한다.
2. 완료 스크립트는 같은 회전 시도 식별자를 확인한 뒤 이전 `jti`를 원래 만료 시각까지 소비 상태로 기록하고,
   활성 계열의 값을 새 `jti`로 교체하며 진행 표지를 제거한다. 새 Refresh Token과 Access Token은 완료
   스크립트가 성공한 뒤에만 응답으로 전달한다.

회전 진행 표지가 만료되면 이전 토큰은 아직 소비되지 않은 상태로 남는다. 완료가 늦은 시도는 실패하며 토큰을
전달하지 않고, 이후 요청은 새 회전 시도로 처리할 수 있다. 완료 후 이전 토큰을 다시 제시하는 요청은 진행 충돌이
아니므로 계열 전체 폐기 대상이다.

## 결과와 트레이드오프

### 기대 효과

- Access Token 키 회전과 장기 Refresh Token의 검증 범위를 분리한다.
- 활동만으로 계열이 무기한 연장되지 않으며, TTL 계산과 사용자→활성 계열 정리가 단순해진다.
- Redis 재시작·초기화·오래된 스냅샷 복구·상태 eviction 뒤 이미 소비된 토큰이 다시 유효해지는 것을 막는다.
- 동시 갱신의 일시적 충돌과 완료 뒤 재사용을 API 계약대로 구분한다.

### 수용한 단점과 위험

- Refresh 서명 키 교체 또는 Redis 상태 소실은 해당 사용자에게 재로그인을 요구한다.
- 절대 14일 수명으로 인해 장기간 로그인 상태를 유지하려면 재로그인이 필요하다.
- 회전이 두 단계 스크립트가 되어 단일 소비 표지보다 구현·테스트가 늘어난다.
- `noeviction` 인증용 Redis 인스턴스는 용량 부족 시 가용성보다 인증 안전을 우선해 503을 반환한다.

## 전환과 롤백

현재 운영 Refresh Token과 Redis 키 공간이 없으므로 데이터 이관은 하지 않는다. 전용 Refresh 서명 키, Redis
`noeviction` 설정, 활성 계열 상태, 회전 스크립트와 통합 테스트를 함께 준비한 뒤 로그인·재발급·로그아웃·
탈퇴 유스케이스가 각 상태 연산을 호출하도록 연결한다.

이 구현을 배포한 뒤 키 프로필·활성 계열 상태·회전 규칙을 되돌려야 하면 기존 Refresh Token을 호환하려 하지 않고
관련 Redis 상태를 폐기해 재로그인으로 전환한다. 소비 또는 폐기된 계열을 활성화하는
롤백은 허용하지 않는다.

## 검증 방법

- 전용 Refresh 키로 발급한 정상 토큰과 다른 `iss`·`aud`·`token_type`·`kid`·서명·`sub`·식별자·만료 토큰의
  거부를 `Clock` 기반 단위 테스트로 검증한다.
- 최초 로그인 계열의 만료가 14일이고, 반복 회전 뒤에도 `exp`와 Cookie `Max-Age`가 최초 계열 만료를 넘지 않는지
  검증한다.
- 같은 `jti`의 동시 회전에서 하나만 완료되고 진행 중 요청은 충돌이며, 완료 뒤 재사용은 계열 전체 폐기가 되는지
  Redis 통합 테스트로 검증한다.
- 현재 계열 폐기, 사용자 전체 계열 폐기, 만료된 인덱스 멤버 정리와 TTL이 계열 절대 만료를 넘지 않는지 검증한다.
- 활성 계열 키 또는 사용자 인덱스를 제거한 뒤 기존 Refresh Token이 거부되고, 새 로그인만 새 계열을 발급하는지
  검증한다. 소비 표지를 제거한 뒤 이전 토큰을 제시해도 활성 `jti` 불일치로 계열이 폐기되는지 검증한다.
- Redis 연결·명령 실패, `noeviction` 용량 오류에서 토큰 발급·회전·폐기를 성공으로 반환하지 않는지 검증한다.
- 로그·오류 응답·감사 이벤트에 토큰 원문, 키, `jti`, `family_id`와 Redis 키·값이 남지 않는지 검증한다.

## 대체 조건

- 외부 IdP나 독립 인증 서비스가 Refresh Token 수명주기와 키 회전을 제공한다.
- 모바일·다중 클라이언트 요구로 기기 식별, 활성 세션 목록 또는 계열 수 제한이 필요해진다.
- 14일보다 긴 슬라이딩 세션 또는 사용자별 세션 관리가 제품 요구가 되어 절대 만료 정책을 변경해야 한다.
- Redis 상태 유실에 따른 강제 재로그인 빈도나 `noeviction` 용량 오류가 수용 가능한 운영 한계를 넘는다.
