# ADR-0041: 사전 업로드 대표 이미지를 운영자와 지역에 귀속

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-30
- 결정일: 2026-07-30
- 관련 요구사항: [PRD](../local-stamp-platform-prd.md)의 `FR-03`, `FR-14`, `AUTH-01`, `CON-02`, `CON-05`
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: [#97](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/97), [#164](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/164)
- 대체 대상: 없음

## 맥락

대표 이미지 업로드 URL은 콘텐츠 생성·수정본 생성·수정 요청보다 먼저 발급된다. 따라서 URL 발급 시점에는
대상 `content_id`나 `content_revision_id`가 없고, 서버는 생성한 `imageObjectId`를 이후 API에서 다시 받아
대표 이미지로 연결한다.

기존 `image_object`는 S3 객체 키, 타입, 크기, 체크섬과 삭제 재시도 상태만 가진다. 이 구조만으로는 다른
운영자가 이미 발급된 `imageObjectId`를 알아낸 경우 자신의 콘텐츠에 연결하는 것을 데이터 모델 차원에서
검증하기 어렵다. 또한 `byteSize` 요청값이 실제 S3 객체 크기와 맞는지 확인해야 하며, URL 만료 뒤 연결되지
않은 `ACTIVE` 객체의 정리 기준도 필요하다.

## 결정 동인과 불변 조건

- 운영자는 자신의 담당 지역에 귀속된 사전 업로드 이미지 객체만 콘텐츠·수정본에 연결할 수 있어야 한다.
- 요청의 `byteSize`와 `checksum`은 실제 S3 객체의 `ContentLength`와 SHA-256 Base64 체크섬으로 재검증해야 한다.
- 만료 전 연결되지 않은 객체는 공개·운영 조회에 노출하지 않고 정리할 수 있어야 한다.
- P0의 대표 이미지는 한 장이며, ADR-0030의 콘텐츠·수정본 직접 FK 참조와 즉시 삭제 정책을 유지해야 한다.
- 별도 상태나 테이블이 없더라도 연결 후보와 이미 연결된 불변 이미지 객체를 구분할 수 있어야 한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |

| 3 | DB 컬럼 없이 서명 토큰만으로 연결 권한을 검증한다 | 스키마 변경이 없다. | 만료·소비 여부·운영자/지역 검증과 정리 대상을 서버 상태로 안정적으로 추적하기 어렵다. | 중간. 토큰 형식과 검증 실패 원인 추적을 다시 설계해야 한다. | 권한 경계와 운영 정리에 부적합하다. |

## 결정

`image_object`에 다음 컬럼을 추가한다.

| 컬럼 | 의미 |
| --- | --- |
| `created_by_user_id` | 업로드 URL을 발급받은 운영자. 대표 이미지 최초 연결 권한 검증에만 사용하며, 연결 성공 후 제거하고 응답·로그·감사 본문에 노출하지 않는다. |
| `region_id` | 업로드 당시 운영자의 담당 지역. 연결 대상 콘텐츠 지역과 같아야 한다. |
| `upload_expires_at` | presigned URL 만료 시각이자 사전 업로드 후보의 연결 가능 만료 시각이다. |
| `linked_at` | 이미지 객체가 처음 콘텐츠 또는 수정본 대표 이미지로 연결된 시각이다. 연결 전에는 `NULL`이다. |

대표 이미지 업로드 URL 발급 API는 인증된 운영자의 `user_id`와 담당 `region_id`를 위 컬럼에 저장한다.
콘텐츠 생성·수정본 생성·수정 API는 `image_object` 행을 잠근 뒤 `created_by_user_id`, `region_id`,
`upload_expires_at`, `linked_at`, `lifecycle_status`를 검증한다. 동시에 S3 `HEAD` 결과의 SHA-256 Base64
체크섬과 `ContentLength`가 DB에 저장된 `checksum`, `byte_size`와 같은지 확인한다. 모든 조건을 만족할 때만
대표 이미지 FK를 설정하고 같은 트랜잭션에서 `linked_at`을 현재 시각으로 저장한 뒤 `created_by_user_id`를 `NULL`로 제거한다.

만료 시각까지 `linked_at IS NULL`이고 콘텐츠·수정본 직접 FK 참조도 없는 `ACTIVE` 객체는 보관 작업이
`DELETE_PENDING`으로 전환한 뒤 S3 삭제를 시도한다. 삭제 실패 시 기존 삭제 재시도 컬럼으로 멱등 재시도한다.

ADR-0016의 “사용자 식별자는 이미지 식별 정보로 저장하지 않는다”는 공개 URL, 객체 키, 파일 메타데이터,
조회 응답과 로그에 사용자 식별자를 저장하지 않는다는 정책으로 유지한다. 이번 ADR의 `created_by_user_id`는
사전 업로드 객체의 내부 권한 검증용 임시 FK이며, 대표 이미지로 연결되면 제거하고 외부 식별 정보로 사용하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 다른 운영자가 발급된 `imageObjectId`를 재사용해 자신의 콘텐츠에 연결하는 경로를 차단한다.
- 요청 크기와 체크섬을 S3 실제 객체와 비교해 메타데이터 위조를 막는다.
- 연결되지 않은 업로드 객체의 만료와 정리 기준이 ERD와 API 명세에 남는다.
- 별도 업로드 의도 테이블 없이 P0 구현 범위를 작게 유지한다.

### 수용한 단점과 위험

- `image_object`가 순수 S3 객체 메타데이터 외에 업로드 검증 컬럼을 가진다.
- 새 이미지 객체의 최초 연결 여부는 `linked_at`으로만 판단하므로, 연결 API가 행 잠금과 조건부 갱신 및 `created_by_user_id` 제거를 반드시 지켜야 한다.
- 연결 뒤 동일 이미지 객체가 콘텐츠와 수정본 스냅샷에서 공유될 수 있으므로 `linked_at`은 전역 참조 수가 아니라 최초 소비 시각으로 해석해야 한다.

## 전환과 롤백

현재 대표 이미지 업로드 URL 발급 API는 문서 단계이므로 기존 운영 데이터 이관은 없다. 구현 시 새 migration으로
컬럼과 인덱스 후보를 추가하고, 연결 API에 행 잠금·S3 `HEAD` 재검증·`linked_at` 설정·`created_by_user_id` 제거를 함께 구현한다.

문제가 있으면 업로드 URL 발급 API를 비활성화하고 기존 콘텐츠·수정본 이미지 참조는 유지한다. 이후 복수 이미지
용도나 상세 업로드 이력 조회가 P0 범위에 들어오면 별도 ADR로 `image_upload_intent` 테이블 도입을 검토한다.

## 검증 방법

- 다른 운영자 또는 다른 지역 운영자가 발급한 `imageObjectId` 연결이 거부되는지 검증한다.
- `upload_expires_at`이 지난 객체와 이미 `linked_at`이 설정된 새 업로드 후보를 다시 연결할 수 없는지 검증한다.
- S3 `HEAD`의 체크섬 또는 `ContentLength`가 DB 값과 다르면 콘텐츠·수정본 연결이 실패하는지 검증한다.
- 연결 성공 시 대표 이미지 FK, `image_object.linked_at`, `created_by_user_id` 제거가 같은 트랜잭션에서 커밋되는지 검증한다.
- 만료된 미연결 `ACTIVE` 객체가 `DELETE_PENDING`으로 전환되고 S3 삭제 실패 시 멱등 재시도되는지 검증한다.

## 대체 조건

- 대표 이미지 외 갤러리, 후기 이미지, 동영상처럼 업로드 용도와 대상이 여러 개로 늘어난다.
- 업로드 의도 자체의 조회, 취소, 감사 이력 또는 장기 보관이 제품 요구사항으로 확정된다.
- 하나의 사전 업로드 객체를 여러 대상에 의도적으로 재사용하는 정책이 채택된다.
