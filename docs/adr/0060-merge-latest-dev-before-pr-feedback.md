# ADR-0060: PR 피드백 전 최신 dev 병합 커밋을 자동 생성한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-01
- 결정일: 2026-08-01
- 관련 요구사항: [PR 생성의 base 규칙](../../.agents/skills/pr-create/SKILL.md#저장소-규칙)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

Draft 또는 Open PR의 리뷰 피드백을 수정할 때, PR이 최신 `dev`를 포함하지 않으면 이미 통합된 변경과 충돌하거나 오래된 기준에서만 검증될 수 있다. 사용자는 피드백을 반영하기 전에 최신 `dev`를 PR 작업 브랜치에 병합하고, 병합이 성공하면 병합 커밋을 자동으로 생성하기로 결정했다.

기존 Task 구현 절차는 일반 변경의 커밋을 `commit` 절차로 분리하고, PR 피드백 모드에서는 커밋·push를 별도 요청으로 제한한다. 따라서 이 결정은 PR 피드백의 최신 `dev` 통합 병합 커밋만 그 제한의 예외로 명확히 한정한다.

## 결정 동인과 불변 조건

- 리뷰 피드백은 실제 PR의 head 브랜치에만 반영한다.
- 병합 기준은 로컬 `dev`가 아니라 `git fetch origin`으로 갱신한 `origin/dev`다.
- PR의 실제 base가 `dev`인지, 로컬 head가 원격 PR head와 일치하는지, 작업 트리가 깨끗한지를 병합 전에 확인한다.
- `origin/dev`가 이미 PR head에 포함돼 있으면 병합 커밋을 만들지 않는다.
- 병합 충돌, 원격 head 불일치, 작업 트리 변경 또는 base 불일치가 있으면 피드백 수정을 시작하지 않는다.
- 자동 수행 범위는 병합 커밋까지이며, push·PR 생성·Task TODO 갱신은 계속 별도 요청이 있어야 한다.

## 결정

PR 피드백 구현 모드는 실제 PR의 base가 `dev`인 경우에만 다음 순서로 시작한다.

1. PR 메타데이터로 head와 base를 확인하고, 작업 트리가 깨끗하며 현재 로컬 브랜치가 PR head이고 `HEAD`가 `origin/<head>`와 일치하는지 확인한다.
2. `git fetch origin`으로 원격 참조를 갱신한다. 로컬 `dev`를 체크아웃하거나 갱신하지 않는다.
3. `origin/dev`가 `HEAD`의 조상인지 확인한다. 이미 포함돼 있으면 병합과 커밋을 생략한다.
4. 최신 `dev`가 아직 포함되지 않았다면 PR head에서 `git merge --no-ff origin/dev`를 실행한다. 성공하면 생성된 병합 커밋은 이 모드에서 허용하는 유일한 자동 커밋이다.
5. 병합 충돌이면 `git merge --abort`로 병합 전 상태를 복원하고, 충돌 내용이나 피드백을 임의로 수정하지 않은 채 중단해 사용자에게 보고한다.

이후에만 선택된 리뷰 피드백을 수정하고 검증한다. 자동 병합 커밋을 포함해도 push, 새 PR 생성, Task TODO 갱신과 일반 변경 커밋은 자동으로 수행하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 피드백 수정과 검증이 최신 `dev`를 포함한 실제 PR head에서 수행된다.
- 통합 충돌을 코드 수정 전에 분리해, 리뷰 피드백의 원인과 충돌 원인을 섞지 않는다.
- 로컬 `dev`를 거치지 않아 다른 브랜치에서 수정하는 오류를 막는다.

### 수용한 단점과 위험

- 성공한 병합 커밋이 PR 이력과 이후 검증 범위에 포함된다.
- `dev` 자체의 회귀가 병합 뒤 검증 실패로 드러날 수 있으며, 이는 피드백 수정의 실패로 단정할 수 없다.
- 병합 충돌은 자동 해결하지 않으므로 사용자 조정이 필요하다.

## 전환과 롤백

Task 구현 스킬의 PR 피드백 모드와 책임 경계에 이 규칙을 적용한다. 데이터 이관이나 호환 계층은 필요 없다.

충돌 중인 병합은 `git merge --abort`로만 자동 복원한다. 성공한 병합 커밋은 자동으로 reset·rebase·force push하지 않는다. 이 결정을 철회하려면 새 ADR로 자동 병합 예외를 대체하고, 이미 생성된 병합 커밋의 처리 방법은 원격 반영 여부를 확인한 뒤 사용자가 별도로 결정한다.

## 검증 방법

- `origin/dev`가 이미 PR head에 포함된 경우 병합 커밋 없이 피드백 작업을 계속하는지 확인한다.
- `origin/dev`가 앞선 경우 PR head에서만 병합 커밋을 만들고, push·Task TODO 갱신·일반 변경 커밋을 수행하지 않는지 확인한다.
- 작업 트리 변경, base가 `dev`가 아닌 PR, 로컬·원격 head 불일치 또는 병합 충돌에서는 피드백 수정을 시작하지 않고 충돌 중인 병합만 취소하는지 확인한다.
- PR 피드백 수정 뒤에는 기존 Task 계약에 따른 관련 테스트, `./gradlew test`, `./gradlew build` 결과를 확인한다.

## 대체 조건

- 병합 커밋 때문에 PR 검토 이력이나 CI 분석이 반복적으로 어려워진다는 증거가 확인된다.
- `dev` 이외의 base를 사용하는 PR이 저장소 규칙으로 허용된다.
- 충돌 해결과 원격 반영을 안전하게 자동화할 별도 승인·복구 절차가 확정된다.
