# ADR-0005: 짧은 수명의 JWT Access Token과 회전형 Refresh Token 사용

## 맥락

방문자, 행사·체험 운영자, 지역 관리자와 전체 관리자는 서로 다른 권한을 사용한다. 백엔드는 인증된 사용자를 식별하면서 역할, 담당 지역과 콘텐츠 소유 관계를 서버에서 검증해야 한다. 초기 기술 스택은 Spring Security와 JWT Access/Refresh Token을 선택했다.

Access Token만 길게 유지하면 탈취와 권한 변경의 영향 시간이 길어진다. 모든 요청에서 서버 세션을 조회하면 폐기 제어는 쉽지만 세션 저장소가 인증 경로의 필수 의존성이 된다. 짧은 Access Token과 서버에서 수명주기를 통제하는 회전형 Refresh Token을 조합한다.

## 결정 동인과 불변 조건

- 인증되지 않은 사용자는 보호된 API를 호출할 수 없다.
- 토큰에 포함된 역할만으로 지역과 콘텐츠 소유 권한을 확정하지 않는다.
- 역할·담당 지역·운영자 승인 상태가 변경되면 허용되지 않은 작업을 계속 수행할 수 없어야 한다.
- Refresh Token 탈취와 재사용을 탐지하고 해당 토큰 계열을 폐기할 수 있어야 한다.
- 토큰, 서명 키와 Refresh Token 원문을 로그나 DB에 평문으로 남기지 않는다.
- 로그아웃, 탈퇴와 관리자의 강제 차단 경로가 존재한다.

## 결정

API 인증에는 짧은 수명의 서명된 JWT Access Token을 사용한다. Access Token은 사용자 식별자, 토큰 식별자와 거친 역할 정보를 담을 수 있지만 담당 지역과 콘텐츠 소유 관계의 최종 근거로 사용하지 않는다. 운영자·관리자 유스케이스는 현재 DB의 승인 상태, 담당 지역과 소유 관계를 추가로 확인한다.

Refresh Token은 Access Token 발급에만 사용하고 보호된 업무 API에는 사용할 수 없다. 갱신할 때마다 새 Refresh Token을 발급하고 이전 토큰을 폐기한다. 서버에는 Refresh Token 원문이 아닌 해시, 토큰 계열, 사용자, 만료, 폐기와 교체 관계를 저장한다. 이미 교체된 Refresh Token이 다시 사용되면 해당 계열 전체를 폐기하고 재로그인을 요구한다.

로그아웃은 해당 Refresh Token 계열을 폐기한다. 탈퇴, 계정 차단과 중요 권한 변경은 사용자의 Refresh Token 계열을 모두 폐기한다. Access Token의 구체적 유효기간, 서명 알고리즘, 쿠키 또는 헤더 전달 방식은 보안 설정과 API 명세에서 확정하되 Access Token을 장기 자격 증명으로 사용하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 일반 API 인증에서 중앙 세션 조회를 필수로 하지 않는다.
- Refresh Token 탈취 재사용을 탐지하고 계열 단위로 폐기할 수 있다.
- 담당 지역과 소유 관계를 현재 DB에서 확인해 오래된 JWT claim에만 의존하지 않는다.
- 클라이언트 종류가 추가되어도 동일한 Access/Refresh 계약을 사용할 수 있다.

### 수용한 단점과 위험

- Refresh Token 저장소와 회전 로직이 추가된다.
- Access Token은 만료 전까지 개별 폐기가 어려워 짧은 권한 지연이 남는다.
- 토큰 갱신 경쟁이 발생하면 정상 클라이언트의 병렬 요청이 재사용 탐지로 오인되지 않도록 직렬화가 필요하다.
- 브라우저 사용 시 XSS와 CSRF를 함께 고려한 전달·저장 방식이 필요하다.

## 전환과 롤백

신규 구현이므로 기존 세션이나 토큰 이관은 없다. Spring Security 인증 필터, 키 관리, Refresh Token 저장과 회전 API를 순서대로 구현한다.

토큰 회전에 문제가 생겨도 이미 사용한 Refresh Token을 다시 활성화하지 않는다. 모든 Refresh Token 계열을 폐기하고 사용자 재로그인으로 복구한다. 서버 세션 방식으로 전환할 경우 새 ADR을 작성하고 클라이언트 인증 계약, 로그인·로그아웃 API와 기존 토큰의 만료·차단 기간을 정의한다.

## 검증 방법

- 정상 로그인, Access Token 만료, Refresh Token 회전과 로그아웃을 통합 테스트한다.
- 교체된 Refresh Token 재사용 시 해당 계열이 폐기되는지 검증한다.
- 탈퇴·차단·역할 변경 후 Refresh Token이 폐기되고 운영자·관리자 권한 검사가 현재 DB 상태를 반영하는지 검증한다.
- 변조, 잘못된 발급자·대상·만료 토큰을 거부하는지 검증한다.
- 동시 갱신 요청에서 하나의 계열에 허용되지 않은 복수 활성 Refresh Token이 남지 않는지 검증한다.
- 로그와 예외에 토큰 원문, 키와 Refresh Token 해시가 노출되지 않는지 검사한다.

## 대체 조건

- 클라이언트가 브라우저 하나로 고정되고 서버 세션의 즉시 폐기 이점이 더 커진다.
- 보안 요구상 Access Token도 요청 즉시 개별 폐기해야 한다.
- 외부 IdP 또는 표준 OAuth/OIDC 공급자가 인증 수명주기를 대신 관리한다.
- Refresh Token 회전 경쟁과 운영 비용이 허용 범위를 지속적으로 넘는다.
