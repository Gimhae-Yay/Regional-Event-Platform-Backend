# ADR-0062: 병렬 구현 경계에 선택적으로 도메인 입력 Port를 사용한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-02
- 결정일: 2026-08-02
- 관련 요구사항: [아키텍처의 복합 유스케이스 규칙](../ARCHITECTURE.md#42-복합-유스케이스), [출력 Port 배치](0061-locate-output-ports-in-owning-domain.md#결정)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

현재 구조에서 복합 UseCase는 여러 Service를 조정하고, Service는 다른 Service를 직접 의존하지 않는다. 그러나
제공 Service가 아직 `dev`에 없을 때 소비 UseCase와 제공 Service를 별도 Task에서 병렬로 구현하려면, 소비
Task는 제공 Service의 컴파일 가능한 행위 계약 없이 구현·단위 테스트를 진행할 수 없다.

모든 Service에 인터페이스를 강제하면 기존 구현과 단순 흐름에 전달 전용 타입이 늘어난다. 반대로 계약 없이
제공 Service의 구현 완료만 기다리면 Task 구현 절차의 병렬화 목적을 달성하지 못한다. 따라서 아직 구현되지 않은
제공 Service와 이를 소비하는 UseCase 사이에만, 제공 도메인이 소유한 입력 Port 계약을 선택적으로 도입한다.

## 결정 동인과 불변 조건

- 제공 Service 전체가 아니라 확정된 행위 계약만으로 소비·제공 Task를 병렬 구현할 수 있어야 한다.
- 제공 도메인이 계약을 소유하며, 소비 Task가 메서드·오류·권한·트랜잭션 의미를 임의로 정하지 않는다.
- 이미 `dev`에 있는 Service와 단순 흐름에는 새 인터페이스를 만들지 않는다.
- Service 간 직접 의존 금지, UseCase의 Repository 직접 의존 금지, 외부 기술 출력 Port와 Adapter의 방향을 유지한다.
- 계약은 API·ERD·ADR·정책 문서로 확정된 범위만 표현하고, 제공 Service는 역할이 드러나는 이름으로 계약을 구현한다.

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 미구현 제공 Service와 병렬 Task 경계에만 제공 도메인 소유 `port.in`을 둔다 | 소비·제공 Task가 같은 계약으로 병렬 구현·테스트할 수 있고, 기존 Service의 불필요한 인터페이스화를 피한다. | 계약 Task가 선행되고 Port 소유·계약 의미를 검토해야 한다. | 낮음~중간. 불필요해진 Port와 의존을 제거하고 UseCase가 Service를 직접 의존하도록 되돌린다. | 병렬 구현 목적과 점진적 구조 전환을 함께 만족해 가장 적합하다. |
| 2 | 제공 Service가 `dev`에 들어올 때까지 소비 UseCase 구현을 기다린다 | 구조와 타입 수가 가장 단순하다. | 병렬 구현이 불가능하고 통합 Task가 선행 구현에 불필요하게 대기한다. | 낮음. 의존 순서만 유지하면 된다. | Task 스킬의 병렬 구현 목적에 맞지 않는다. |
| 3 | 모든 Service에 인터페이스를 강제한다 | 어떤 소비자도 구현체 없이 컴파일·mock할 수 있다. | 단순 흐름과 기존 Service에도 전달 전용 타입·구현체 명명이 늘고, 책임 없는 계약이 고착된다. | 중간~높음. 광범위한 인터페이스와 의존을 제거해야 한다. | 현재 MVP의 점진적 전환 원칙에는 과도하다. |

## 결정

제공 Service가 아직 `dev`에 없고, 별도 소비 UseCase Task와 병렬 구현해야 하는 경우에만 제공 도메인은
`domain.<도메인>.port.in`에 행위 중심 입력 Port를 둔다. 이 Port는 제공 도메인의 별도 계약 Task에서 API·ERD·
ADR·정책으로 확정된 메서드, 오류·권한·트랜잭션 의미를 표현하고 먼저 `dev`에 반영한다.

소비 UseCase는 `port.in` 계약을 의존하고 mock을 사용해 단위 테스트를 작성할 수 있다. 제공 Service Task는
역할이 드러나는 Service가 그 계약을 구현한다. 예를 들어 `domain.payment.port.in.AuthorizePayment`를 먼저
반영하면 예약 확정 UseCase와 `PaymentService`를 병렬 구현할 수 있다. `BServiceInterface`, `BServiceImpl`처럼
타입 역할이 드러나지 않는 이름은 사용하지 않는다.

이미 `dev`에 구현된 Service를 새로 소비하는 UseCase는 기존처럼 해당 Service를 직접 의존하며 `port.in`을
추가하지 않는다. `port.in`은 외부 기술 구현체를 위한 `port.out`과 다르며, 기존 Service 일괄 전환·테스트 편의·
미확정 메서드 가정·전달 전용 계층을 위한 도구로 사용하지 않는다.

이 결정은 ADR-0008의 점진적 경계 도입, ADR-0042의 Service 간 직접 의존 금지, ADR-0061의 출력 Port 배치를
대체하지 않는다. 이 결정은 그 규칙을 유지하면서 병렬 Task의 미구현 제공 Service 경계에만 입력 Port를 추가한다.

## 결과와 트레이드오프

### 기대 효과

- 제공 Service 구현 완료를 기다리지 않고 소비 UseCase와 제공 Service를 독립 Task에서 병렬 구현할 수 있다.
- 컴파일 가능한 계약을 통해 소비 UseCase의 mock 기반 단위 테스트를 먼저 작성할 수 있다.
- 기존 Service와 단순 흐름에는 인터페이스를 추가하지 않아 점진적 구조를 유지한다.

### 수용한 단점과 위험

- 계약 Task가 먼저 병합되어야 하므로 매우 짧은 선행 단계는 남는다.
- 제공 도메인이 계약을 충분히 확정하지 않으면 소비·제공 Task가 같은 잘못된 계약에 결합될 수 있다.
- `port.in`을 만든 뒤 유지 가치가 없는데도 제거하지 않으면 타입과 탐색 비용이 늘어난다.

## 전환과 롤백

현재 `dev`에 있는 Service는 이동하거나 인터페이스를 추가하지 않는다. 새 병렬 Task에서만 계약 Task를 먼저
만들어 `port.in`을 반영하고, 이후 소비 UseCase·제공 Service Task를 각각 구현한다. 통합 완료 후 계약이 다른
독립 소비자 또는 병렬 경계에 계속 필요하면 유지한다.

계약이 병렬화 외 가치를 잃었거나 전달만 하는 것으로 확인되면, 후속 리팩터링 Task에서 소비 UseCase를 구현된
Service의 직접 의존으로 되돌리고 `port.in`과 관련 mock을 제거한다. 계약 의미가 잘못 확정됐으면 소비·제공
구현을 동시에 수정하지 않고 Bug Issue 또는 ADR 절차로 계약을 먼저 바로잡는다.

## 검증 방법

- 계약 Task가 제공 도메인의 `port.in`에 행위 중심 Port를 만들고, 제공·소비 Task의 공식 `blocked by` 관계가
  계약 Task를 가리키는지 확인한다.
- 소비 UseCase가 `port.in`을 mock으로 사용해 정상·실패·권한 경로를 단위 테스트하고, 제공 Service가 같은
  계약을 구현하는지 컴파일·통합 테스트로 확인한다.
- 이미 `dev`에 있는 Service나 단순 흐름에 `port.in`을 새로 만들지 않고, Service 간 직접 의존도 생기지 않는지
  코드 리뷰로 확인한다.
- 제공·소비 구현을 통합한 뒤 트랜잭션, 멱등성, 상태 전이와 공개 API 결과가 계약 문서와 일치하는지 회귀 테스트로 확인한다.

## 대체 조건

- 병렬 Task의 대부분이 같은 입력 Port를 필요로 해 선택적 도입보다 모든 애플리케이션 경계를 명시하는 편이
  더 단순하다는 증거가 쌓인다.
- 계약 Task가 반복적으로 병목이 되거나 제공 도메인 소유권을 일관되게 결정할 수 없는 문제가 확인된다.
- 모듈 분리·독립 배포로 입력 Port 계약을 별도 모듈 또는 공통 애플리케이션 계층으로 분리할 필요가 생긴다.
