# ADR-0094: 쿠폰 정책 수정 이력을 관계형 전·후 컬럼으로 저장한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-11
- 결정일: 2026-08-11
- 관련 요구사항: `P1-FR-05`, [쿠폰 정책 수정 API](../api/p1/coupon/update-coupon-policy.md)
- 관련 단계: 단계 0. 정책·설계 확정
- 관련 이슈: #696
- 대체 대상: 없음

## 맥락

`DRAFT` 쿠폰 정책 수정은 처리자, 이전 값, 이후 값, 수정 사유와 수정 시각을 보존해야 한다. 공통 `audit_event`는 상태 전이와 처리자를 기록하지만, 정책의 수정 가능 필드별 전·후 값을 재구성하지 않는다.

수정 가능 필드는 이름, 설명, 할인 금액, 최소 결제 금액, 발급 후 유효 일수, 발급 시작·종료 시각, 전체 발급 한도로 고정돼 있다. 이 값들을 자유 형식 JSON으로 저장하면 필드별 제약과 조회 의미가 데이터베이스 계약에서 사라진다.

## 결정 동인과 반드시 지켜야 할 조건

- 수정 전·후의 모든 수정 가능 필드를 손실 없이 재현할 수 있어야 한다.
- 수정 이력은 정책 갱신 및 성공 공통 감사 이벤트와 하나의 MySQL 트랜잭션으로 커밋하거나 함께 롤백해야 한다.
- 처리자 식별은 기존 `audit_event_actor_link`의 탈퇴 시 연결 제거 규칙을 우회하지 않아야 한다.
- 정책 생성 뒤 수정할 수 없는 `content_id`, `region_id`, `issuance_type`, 상태·공개·종료 시각과 발급 사용량은 이력 스냅샷에 포함하지 않는다.

## 결정

`coupon_policy_update_history` 전용 관계형 테이블을 둔다. 각 행은 `coupon_policy_id`, `audit_event_id`, `actor_kind`, `actor_role`, `reason`, `request_id`, `updated_at`과 다음 전·후 컬럼을 가진다.

- `name`
- `description`
- `discount_amount`
- `minimum_payment_amount`
- `valid_days_after_issue`
- `issue_starts_at`
- `issue_ends_at`
- `total_issue_limit`

`audit_event_id`는 성공 공통 감사 이벤트를 참조한다. 이력 행을 만들 때 애플리케이션은 참조한 감사 이벤트가 `result = SUCCESS`, `target_type = COUPON_POLICY`, `target_id = coupon_policy_id`, `previous_state = DRAFT`, `next_state = DRAFT`인지와 actor 종류·역할, `reason`, `request_id`, 발생 시각이 이력 행과 같은지를 검증한다. 이 행 간 동일성은 단일 FK로 강제할 수 없으므로 같은 트랜잭션 안에서 검증한다. 사용자 식별은 이력 행에 중복 저장하지 않고 기존 `audit_event_actor_link`를 사용하며, 탈퇴 때 이 연결을 제거한다. 감사 보관 정책으로 공통 감사가 삭제될 때는 이력 행의 `audit_event_id`를 `NULL`로 만들고, 이력의 역할·사유·시각·전후 값은 유지한다.

정책 갱신 전 잠근 정책에서 이전 값을 복사하고, 갱신 뒤 값을 이후 컬럼에 기록한다. 요청 필드를 반영한 결과가 잠근 정책과 완전히 같으면 `200 OK` 무변경 성공으로 응답하고 정책·`updated_at`·수정 이력·성공 감사는 변경하거나 만들지 않는다. 정책 갱신, 이력 삽입, `COUPON_POLICY` 성공 감사 이벤트는 같은 `requestId`와 시각으로 하나의 트랜잭션에서 처리한다. 성공 감사 이벤트는 `DRAFT → DRAFT`를 기록하며, 전·후 필드 값의 근거는 전용 이력 테이블이 담당한다.

## 결과와 트레이드오프

### 기대 효과

- 감사 보관 기간 안에는 처리자 연결을, 그 이후에도 정책 변경의 전·후 값·역할·사유·시각을 재현할 수 있다.
- 수정 가능한 값의 타입과 nullable 규칙이 `coupon_policy`와 이력 테이블에 명시적으로 드러난다.
- 공통 상태 감사와 필드 변경 이력이 중복 역할을 갖지 않는다.

### 수용한 단점과 위험

- 새 수정 가능 필드를 도입할 때 이력 테이블과 구현을 함께 변경해야 한다.
- 이력 행은 생성 후 수정·삭제하지 않으며, 정정이 필요하면 새 정책 수정을 기록한다.

## 전환과 롤백

현재 구현에는 정책 수정 이력 데이터가 없으므로 기존 데이터 backfill은 하지 않는다. 후속 구현 Task에서 migration으로 테이블을 추가한 뒤 새 성공 수정부터 기록한다.

도입 중 문제가 발생하면 정책 수정 명령을 중단하고 기존 정책 데이터는 변경하지 않는다. 이미 커밋된 이력 행은 수정·삭제하지 않으며, 계약 변경이 필요하면 후속 ADR과 migration으로 보정한다.

## 검증 방법

- ERD가 전용 이력의 모든 전·후 컬럼, 공통 감사 연결, 탈퇴·보관 처리와 트랜잭션 경계를 명시하는지 확인한다.
- PATCH API 명세가 `reason` 필수 조건과 정책 갱신·이력·성공 감사의 원자성을 명시하는지 확인한다.
- 후속 구현 Task에서 성공 수정의 전·후 값 보존, 이력 저장 실패 시 정책 롤백, 탈퇴·감사 보관 처리 규칙을 검증한다.

## 대체 조건

- 수정 가능 필드가 빈번하게 바뀌어 관계형 이력 migration 비용이 반복적으로 문제가 된다.
- 이력의 필드별 조회·제약보다 임의 구조의 원문 보존이 더 중요한 새 제품 요구가 확정된다.
