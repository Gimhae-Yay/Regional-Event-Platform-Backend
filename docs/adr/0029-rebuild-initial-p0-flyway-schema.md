# ADR-0029: P0 전체 스키마를 단일 초기 Flyway migration으로 재구성

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-29
- 결정일: 2026-07-29
- 관련 요구사항: [ERD의 물리 스키마 계약](../erd.md#11-미확정-계약), [ERD의 핵심 키·참조 무결성](../erd.md#8-핵심-키참조-무결성)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: [#69](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/69)
- 대체 대상: 없음

## 맥락

현재 개발 브랜치의 Flyway migration에는 동일한 버전 V4 파일이 둘 존재해 검증이 실패한다. 테이블별로
분산된 초기 migration을 재번호화해 보정하는 방식은 이후 구현될 P0 테이블을 다시 증분 migration으로
추가해야 하며, 아직 적용하지 않은 전체 ERD를 한 번에 검증할 수 없다.

개발·공유 DB는 이 전환 전에 초기화할 수 있다는 전제에서, 사용자 선택에 따라 P0 ERD의 모든 테이블을
하나의 초기 migration으로 재구성한다.

## 결정 동인과 불변 조건

- 빈 P0 DB는 단 하나의 versioned migration으로 전체 ERD의 테이블과 확정된 핵심 제약을 생성해야 한다.
- 이미 엔티티로 구현된 테이블의 SQL 타입·길이와 JPA 매핑은 호환돼야 한다.
- ERD에서 미확정으로 남은 제품 정책, API 계약, 인덱스 후보와 FK 삭제 정책을 임의로 추가하지 않는다.
- 기존 개발·공유 DB의 Flyway 이력과 데이터는 이 전환 전에 초기화한다.
- 이후 스키마 변경은 적용된 V1을 수정하지 않고 새로운 `V2__...` 이상의 migration으로 추가한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | P0 전체 ERD를 단일 `V1__initial_p0_schema.sql`로 재구성 | 중복 버전 문제를 제거하고 빈 DB의 기준 스키마를 한 파일에서 검증할 수 있다 | 기존 DB를 초기화해야 하며, V1 변경은 이후 금지된다 | 초기화 전에는 낮고 적용 뒤에는 새 migration이 필요하다 | MVP 구현 시작 전인 현재 단계에 적합하다 |
| 2 | 기존 migration을 유지한 채 번호만 재정렬하고 새 테이블을 순차 추가 | 적용된 DB의 이력을 그대로 유지할 수 있다 | 분산된 초기 기준이 남고, 전체 ERD의 완결 시점까지 중간 migration이 계속 늘어난다 | 낮다 | 현재의 전체 재구성 목표와 맞지 않는다 |

## 결정

기존 `src/main/resources/db/migration`의 분산 migration을 제거하고,
`V1__initial_p0_schema.sql` 하나로 P0 전체 ERD를 생성한다. 기존 엔티티·migration에서 이미 사용한
`BIGINT`, `INT`, `VARCHAR`, `TEXT`, `TIMESTAMP(6)`의 타입과 길이는 유지한다.

ERD에 확정된 상태 카탈로그, PK·UK·FK, 복합 참조 일치와 상태별 null 조건만 DB 제약으로 넣는다.
ERD가 후보로만 둔 인덱스와 미확정인 길이·검증 정책, `ON DELETE` 동작은 이번 migration에서 새로
결정하지 않는다. 기존 migration에서 실제 사용 중인 인덱스만 유지한다.

## 결과와 트레이드오프

### 기대 효과

- Flyway 버전 중복 없이 빈 DB의 기준 스키마를 재현할 수 있다.
- 진행 중인 엔티티 작업은 같은 V1의 테이블 계약을 기준으로 JPA 매핑과 테스트를 검증할 수 있다.
- 이후 변경은 명시적인 증분 migration으로 추적된다.

### 수용한 단점과 위험

- 기존 개발·공유 DB의 데이터와 Flyway 이력을 보존하지 않는다.
- 아직 구현되지 않은 도메인의 일부 물리 세부 정책은 ERD가 확정하기 전까지 제약으로 강제하지 않는다.
- 진행 중인 migration PR은 V1 재구성 기준과 충돌 여부를 확인해 재정렬하거나 닫아야 한다.

## 전환과 롤백

1. 개발·공유 DB의 데이터와 `flyway_schema_history`를 초기화한다.
2. 새 V1만 적용해 전체 테이블과 핵심 제약이 생성되는지 검증한다.
3. 진행 중인 엔티티 PR은 migration 파일을 제거하고 V1의 해당 테이블 계약을 사용하도록 정리한다.

전환 중 빈 DB 검증이 실패하면 새 V1을 적용하기 전의 브랜치로 되돌리고, 원인 수정 후 다시 초기화한다.
V1이 공유 DB에 적용된 뒤에는 파일을 수정하지 않고 새 versioned migration으로 보정한다.

## 검증 방법

- 빈 H2 테스트 DB에서 Flyway 이력에 V1 하나만 기록되는지 확인한다.
- ERD의 18개 테이블과 대표적인 PK·UK·FK·CHECK 제약이 생성되는지 자동화 테스트로 확인한다.
- 기존 JPA repository 테스트와 `./gradlew build`로 엔티티 매핑을 검증한다.

## 대체 조건

- 초기화할 수 없는 운영 데이터가 생기면 baseline 또는 증분 migration 전환 전략을 별도 ADR로 결정한다.
- ERD의 미확정 물리 계약이나 인덱스 후보가 API·성능 검증으로 확정되면 새 migration과 필요 시 후속 ADR로 반영한다.
