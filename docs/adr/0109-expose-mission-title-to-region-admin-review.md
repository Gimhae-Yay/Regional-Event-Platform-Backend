# ADR-0109: 지역 관리자 미션 조회에 저장 제목을 제공한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-18
- 결정일: 2026-08-18
- 관련 요구사항: [지역 미션 `P1-FR-03`](../p1/regional-mission.md#p1-fr-03-지역-미션-운영조회), [지역 미션 `US-P1-03`](../p1/regional-mission.md#us-p1-03-운영-주체가-지역-미션을-공개한다), [지역 미션 `MSN-01`](../p1/regional-mission.md#3-지역-미션-정책)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0106](0106-store-mission-title-on-mission.md)의 지역 관리자 제목 응답 제외 범위, [ADR-0108](0108-apply-final-mission-title-contract-before-first-client.md)의 지역 관리자 조회 응답 유지 범위

## 맥락

ADR-0106은 방문자가 미션을 식별하지 못하는 문제를 해결하기 위해 미션이 제목을 직접 소유하도록 결정했지만,
당시 이슈 범위에 맞춰 제목 응답을 방문자 API 세 개로 제한하고 지역 관리자 조회 응답은 변경하지 않았다.
ADR-0108은 최초 운영자 클라이언트 배포 전 DB 전환을 단순화하면서 이 응답 범위를 그대로 유지했다.

현재 지역 관리자는 담당 지역의 미션 목록에서 미션 ID와 상태만 확인하고, 상세에서도 미션 자체 제목 없이 조건·대상
콘텐츠·보상·종료 시각을 검토한 뒤 공개 여부를 결정한다. 제목은 공개 뒤 변경할 수 없는 핵심 값이고 ADR-0106은 제목의
표현 품질을 지역 관리자 검토에 의존한다고 기록했으므로, 승인 주체가 제목을 확인할 수 없는 현재 응답은 검토 책임과
일치하지 않는다. `mission.title`은 이미 `VARCHAR(255) NOT NULL`로 저장되므로 새로운 DB 필드나 데이터 이관은 필요 없다.

## 결정 동인과 불변 조건

- 지역 관리자는 공개 승인 전에 방문자에게 노출될 미션 제목을 확인할 수 있어야 한다.
- 목록에서 같은 상태의 미션을 ID만이 아니라 제목으로 구분할 수 있어야 한다.
- 제목의 저장 위치, 필수성, 정규화, 길이, 중복 허용과 `DRAFT` 전용 수정 정책은 바꾸지 않는다.
- 담당 지역 `REGION_ADMIN` 인증·인가, 상태 필터, 정렬, 페이지네이션과 오류 계약은 바꾸지 않는다.
- 운영자 조회, 공개 미션 상세, 이력과 승인·반려 명령 응답은 이번 결정에서 변경하지 않는다.
- 제목 값을 감사 이벤트와 구조화 로그에 기록하지 않는다.

## 결정

`GET /api/v1/region-admin/missions`의 각 목록 항목과
`GET /api/v1/region-admin/missions/{missionId}`의 상세 응답에 `mission.title`을 `title`로 제공한다. 두 응답의
`title`은 null이 아닌 Unicode code point 기준 1~255자의 저장 제목이며, 목록과 상세는 같은 미션 행의 값을 반환한다.

두 API의 담당 지역 범위, 상태 필터, 정렬, 페이지 메타데이터와 나머지 상세 필드는 유지한다. 운영자 조회, 공개 미션
상세, 지역 관리자 이력과 승인·반려 명령 응답에는 이 결정을 근거로 제목을 추가하지 않는다. 제목 저장·수정 계약과
DB 스키마도 변경하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 지역 관리자는 목록에서 미션을 제목으로 구분하고 상세에서 공개될 제목을 조건·보상과 함께 검토할 수 있다.
- 목록과 상세가 별도 파생값 없이 `mission.title`을 사용해 화면 간 표시가 일치한다.
- 기존 `NOT NULL` 제목을 조회하므로 fallback, backfill과 신규 migration이 필요 없다.

### 수용한 단점과 위험

- 지역 관리자 목록의 각 행에 최대 255자의 문자열이 추가된다.
- 기존 응답 필드를 엄격히 고정해 역직렬화하는 클라이언트가 있다면 가산 필드를 수용하지 못할 수 있다. 최초 지역 관리자
  클라이언트 구현 전 단계라는 현재 전제를 사용한다.
- 운영자 조회와 공개 미션 상세에는 제목이 계속 없으므로 이 결정만으로 모든 미션 조회 표현을 통일하지 않는다.

## 전환과 롤백

먼저 지역 미션 정책과 두 지역 관리자 조회 API 명세를 새 응답 계약으로 확정한다. 이후 목록 조회 projection·결과·응답
DTO와 상세 응답 DTO에 저장 제목을 연결하고, 계약·통합 테스트로 담당 지역 범위와 기존 필드가 유지되는지 검증한다.
지역 관리자 클라이언트와 와이어프레임은 구현된 API 계약을 기준으로 제목을 표시한다.

DB migration, 기존 행 backfill과 호환 fallback은 수행하지 않는다. 서버 적용 전 실패하면 문서와 구현 변경을 함께
되돌릴 수 있다. 클라이언트가 `title`에 의존한 뒤 응답에서 제거해야 한다면 새 ADR과 API 호환 계획을 먼저 채택하며,
저장된 `mission.title`은 보존한다.

## 검증 방법

- 목록 응답의 모든 항목이 해당 미션의 null이 아닌 저장 제목을 반환하는지 검증한다.
- 상세 응답의 제목이 같은 미션의 목록 제목과 일치하는지 검증한다.
- `status`, `page`, `size`, `totalElements`, `totalPages`와 `missionId` 내림차순 정렬이 유지되는지 검증한다.
- 다른 지역 미션이 목록·상세에 노출되지 않고 기존 `401`, `403`, `404` 계약이 유지되는지 검증한다.
- 운영자 조회, 공개 미션 상세, 이력과 승인·반려 응답 필드가 변경되지 않는지 회귀 검증한다.
- 제목 값이 감사 이벤트와 구조화 로그에 추가되지 않는지 검증한다.

## 대체 조건

- 지역 관리자에게 제목을 노출하지 않아야 하는 개인정보·법적·운영 제한이 확인된다.
- 미션 제목이 별도 번역·버전·승인 상태를 갖는 모델로 변경된다.
- 목록 응답 크기로 인한 실제 성능 문제가 측정되고 제목 없이도 안전하게 대상을 식별하는 대체 계약이 채택된다.
