# ADR-0060: 콘텐츠 종료와 회차 생성을 같은 content 행 잠금으로 순서 보장

- 상태: 채택됨

- 결정일: 2026-08-04

- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0059](0059-automatically-end-content-after-all-sessions-terminate.md#결정)의 자동·수동 종료와 추가 회차 생성 간 경합 처리 범위. 조정 스케줄러와 자동 종료 조건은 유지한다.

## 맥락

자동·수동 종료는 `content` 상태를 `PUBLISHED → ENDED`로 바꾸고, 추가 회차 생성은 `content_session`에
`PENDING` 행을 추가한다. 두 처리가 서로 다른 행을 변경하므로 상태를 확인하고 조건부로 쓰는 것만으로는 실행
순서가 정해지지 않는다.

예를 들어 자동 종료가 모든 기존 회차의 종결을 확인한 직후 추가 회차 생성이 `PENDING` 행을 넣으면 두 트랜잭션이
모두 성공할 수 있다. 그러면 `ENDED` 콘텐츠에 `PENDING` 회차가 남는다. ADR-0059는 종료끼리의 중복 전이를
막는 규칙은 정했지만, 종료와 추가 회차 생성이 함께 사용할 잠금 기준은 정하지 않았다.

## 결정 동인과 불변 조건

- `ENDED` 콘텐츠에는 새 `PENDING` 회차가 생기지 않아야 한다.
- `PENDING`, `SCHEDULED`, `REJECTED` 회차가 하나라도 있으면 콘텐츠를 종료하지 않아야 한다.
- 자동 종료, 수동 종료와 추가 회차 생성은 같은 콘텐츠를 변경할 때 하나씩 순서대로 처리돼야 한다.
- 잠금을 얻기 전에 읽은 상태로 변경 여부를 결정하지 않고, 잠금을 얻은 뒤 콘텐츠와 회차 상태를 다시 확인해야 한다.
- 잠금 순서는 `content`를 첫 번째로 통일하고, 잠금을 잡은 트랜잭션 안에서 외부 API를 호출하지 않아야 한다.

## 결정

자동 종료, 지역 관리자의 수동 정상 종료와 추가 회차 생성은 쓰기 트랜잭션을 시작한 뒤 대상 `content` 행을
`PESSIMISTIC_WRITE`로 조회한다. MySQL에서는 `SELECT ... FOR UPDATE`에 해당한다. 세 처리 모두 이 행을 첫 번째
잠금 대상으로 사용한다.

스케줄러의 후보 목록 조회에는 잠금을 걸지 않는다. 후보별 실제 종료 트랜잭션에서 대상 `content` 한 행을 잠근
뒤 `content.status`, `deleted_at`과 연결된 전체 회차 상태를 다시 확인한다. 추가 회차 생성도 같은 잠금을 얻은 뒤
콘텐츠가 소프트 삭제되지 않은 `APPROVED` 또는 `PUBLISHED`인지 다시 확인하고 `PENDING` 회차를 추가한다.

추가 회차 생성이 잠금을 먼저 얻으면 `PENDING` 회차와 감사 기록을 커밋한 뒤 잠금을 해제한다. 뒤이어 잠금을 얻은
종료 처리는 새 `PENDING` 회차를 확인하고 종료하지 않는다. 종료가 잠금을 먼저 얻으면 `ENDED` 전이를 커밋한 뒤
잠금을 해제하며, 뒤이어 실행된 회차 생성은 `ENDED` 상태를 확인하고 회차를 만들지 않는다.

종료 과정에서 회차와 홀드를 추가로 잠가야 하면 `content → content_session → capacity_hold` 순서를 따른다.
잠금 대기 제한을 넘기거나 서로 잠금을 기다리는 문제로 트랜잭션이 실패하면 일부 변경을 커밋하지 않는다. API는
실패 응답 뒤 다시 요청할 수 있고, 스케줄러는 다음 실행에서 다시 시도한다.

## 결과와 트레이드오프

### 기대 효과

- API와 스케줄러가 서로 다른 진입점이어도 같은 `content` 행을 기준으로 실행 순서가 정해진다.
- `ENDED` 콘텐츠와 새 `PENDING` 회차가 함께 커밋되는 상태를 막는다.
- 잠금을 얻은 뒤 상태를 다시 확인하므로 잠금 대기 전에 읽은 오래된 값으로 처리하지 않는다.
- 별도 잠금 서버나 새 DB 컬럼이 필요하지 않다.

### 수용한 단점과 위험

- 같은 콘텐츠의 종료와 회차 생성은 동시에 끝나지 않고 앞선 트랜잭션이 끝날 때까지 기다린다.
- 종료 트랜잭션이 홀드 무효화와 정원 복구까지 수행하므로 잠금 유지 시간이 길어질 수 있다.
- 새 콘텐츠 쓰기 경로가 이 공통 잠금 규칙을 빠뜨리면 같은 문제가 다시 생길 수 있다.

## 전환과 롤백

데이터나 스키마 이관은 필요 없다. 먼저 자동 종료, 수동 종료와 회차 생성 명세에 공통 잠금과 잠금 뒤 재확인
규칙을 반영한다. 구현할 때 세 경로가 같은 `content` 잠금 조회를 사용하도록 연결하고 MySQL 동시 실행 테스트를
추가한다.

잠금 대기나 교착 상태가 운영을 방해하면 자동 종료 스케줄러를 중지해 자동 실행을 줄일 수 있다. 수동 종료와 회차
생성의 공통 잠금은 잘못된 상태를 막기 위해 유지한다. 잠금 방식을 제거하거나 다른 방식으로 바꾸려면 같은 안전 조건을
검증한 새 ADR로 이 결정을 대체한다.

## 검증 방법

- 추가 회차 생성이 `content` 잠금을 먼저 얻은 경우 자동·수동 종료가 새 `PENDING` 회차를 확인하고 종료하지 않는지 MySQL 통합 테스트로 검증한다.
- 자동·수동 종료가 `content` 잠금을 먼저 얻은 경우 뒤의 회차 생성이 `ENDED` 상태를 확인하고 회차와 감사 기록을 만들지 않는지 검증한다.
- 두 실행 순서를 반복해도 `ENDED` 콘텐츠에 `PENDING` 회차가 남지 않는지 검증한다.
- 잠금 대기 제한 또는 교착 상태로 한 처리가 실패하면 콘텐츠, 회차, 로그, 감사와 홀드·정원이 일부만 커밋되지 않는지 검증한다.
- 잠금 대기 시간, 잠금 시간 초과와 교착 상태를 구조화 로그와 MySQL 운영 지표로 관찰한다.

## 대체 조건

- 목표 부하에서 같은 콘텐츠의 잠금 대기나 교착 상태가 반복돼 정상 요청의 완료를 방해한다.
- 콘텐츠 종료가 MySQL 밖의 여러 저장소를 함께 바꿔야 해 한 행 잠금만으로 실행 순서를 보장할 수 없게 된다.
- 회차 생성과 종료를 함께 보장하는 DB 제약이나 한 번에 처리하는 SQL이 도입된다.
