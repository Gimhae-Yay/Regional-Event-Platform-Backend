# ADR-0030: 수정본 대표 이미지 스냅샷은 공유 참조로 보존

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-29
- 결정일: 2026-07-29
- 관련 요구사항: [PRD](../local-stamp-platform-prd.md)의 `FR-14`, `CON-05`, [ERD의 콘텐츠·회차 정규화 규칙](../erd.md#콘텐츠회차-정규화-규칙)
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: [#50](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/50), [#74](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/pull/74)
- 대체 대상: [ADR-0029](0029-store-representative-image-references-on-content-roots.md)의 이미지 객체 전역 단일 참조·수정본 승인 후 후보 FK 제거·교차 중복 이관 차단 범위, [ADR-0016](0016-use-private-s3-presigned-urls-and-immediate-image-deletion.md)의 수정본 반려·철회 뒤 대표 이미지 참조를 즉시 제거한다는 범위

## 맥락

`content_revision`은 공개 콘텐츠를 직접 바꾸지 않고 심사 당시 후보 상태를 보존하는 스냅샷이다. 대표 이미지가
변경되지 않은 수정본도 당시의 대표 이미지를 보존해야 하므로, 현재 `content`와 `content_revision`이 같은
불변 `image_object`를 참조하는 것은 정상이다.

ADR-0029는 즉시 S3 삭제 경합을 피하려고 하나의 이미지 객체가 두 직접 FK 중 정확히 한 곳에만 존재하도록
정했다. 그러나 이 규칙은 수정본 스냅샷을 불완전하게 만들며, 승인 후 수정본의 후보 FK를 제거하면 승인된
수정본의 이미지 상태도 재현할 수 없다. 문제의 본질은 중복 참조가 아니라, 참조가 남아 있는 객체를 삭제하는
것이다.

## 결정 동인과 불변 조건

- 수정본은 대표 이미지가 바뀌지 않은 경우에도 심사 시점의 이미지 객체 참조를 보존한다.
- 하나의 불변 `image_object`는 현재 콘텐츠와 여러 수정본이 함께 참조할 수 있다.
- 이미지 객체를 S3에서 삭제하거나 `DELETE_PENDING`으로 전환하기 전에는 `content`와 모든 `content_revision`의
  직접 FK 참조가 없는지 같은 MySQL 트랜잭션에서 검사한다.
- 수정본 승인 시 원본의 대표 이미지는 후보 이미지로 갱신하되, 승인된 수정본의 이미지 FK는 스냅샷으로 보존한다.
- 기존 V1 연결 테이블에 존재하는 콘텐츠·수정본 간 같은 이미지 객체 참조는 유효한 데이터이며 이관에서 거부하지 않는다.

## 결정

`content.representative_image_object_id`와 `content_revision.candidate_image_object_id`는 각각 nullable FK로
유지하되, 두 컬럼과 두 테이블 사이에 이미지 객체의 유일성을 강제하지 않는다. JPA에서는 두 참조를
`ImageObject`를 향한 지연 로딩 `@ManyToOne`으로 모델링한다.

수정본을 만들 때 대표 이미지가 바뀌지 않아도 현재 이미지 객체와 연결 시각을 수정본에 스냅샷으로 저장한다.
대표 이미지 변경 후보가 있으면 그 새 이미지 객체를 저장한다. 승인 시 후보 이미지 객체를 `content`에 반영하되
`content_revision`의 참조는 제거하지 않는다.

이미지 교체, 콘텐츠 삭제, 수정본 파기처럼 참조를 제거하는 명령은 대상 `image_object` 행을 잠근 뒤 `content`와
모든 `content_revision`의 FK 참조가 없는지 검사한다. 참조가 0개일 때만 `DELETE_PENDING`으로 전환하고 커밋 뒤
S3 삭제를 시도한다. 두 이미지 객체를 함께 처리할 때는 ID 오름차순으로 잠근다.

## 결과와 트레이드오프

### 기대 효과

- 승인·반려·철회된 수정본을 포함해 당시 대표 이미지 상태를 재현할 수 있다.
- 대표 이미지가 바뀌지 않은 수정본도 별도 `NULL` 의미 없이 완전한 스냅샷으로 보존한다.
- 이미지 삭제 안전성의 기준을 중복 금지가 아닌 실제 참조 수로 일관되게 둔다.

### 수용한 단점과 위험

- 수정본이 이미지를 참조하는 동안 S3 원본은 삭제할 수 있어 저장 공간이 더 든다.
- 삭제 명령은 두 루트 테이블을 모두 검사해야 하며, 이 규약을 빠뜨리면 참조 중 객체를 삭제할 수 있다.
- 수정본 보존·파기 기간이 확정되기 전에는 해당 수정본이 참조한 이미지도 함께 보존된다.

## 전환과 롤백

V2가 아직 `dev`에 병합·적용되지 않았으므로, V1은 변경하지 않고 V2에서 대표 이미지 FK의 `UNIQUE` 제약과
교차 중복 차단 임시 테이블을 제거한다. 기존 두 연결 테이블 값은 콘텐츠와 수정본 루트에 그대로 이관하며,
같은 이미지 객체가 양쪽에 있으면 두 참조를 모두 보존한다.

PR #74에서 `ContentRevision` 직접 FK 매핑과 승인 반영을 이 결정에 맞춘다. 이후 이미지 삭제 유스케이스를
도입할 때는 참조 0건 검사와 잠금 규약을 통합 테스트로 검증한다. 전환 중 문제가 생기면 V2를 병합하지 않고
작업 브랜치에서 수정한다. V2가 적용된 뒤의 정책 변경은 V3 이상의 새 migration으로만 수행한다.

## 검증 방법

- 같은 이미지 객체가 현재 콘텐츠와 하나 이상의 수정본에 함께 연결되는지 검증한다.
- 수정본 승인 뒤 원본은 후보 이미지로 바뀌고 수정본은 해당 이미지 참조를 유지하는지 검증한다.
- 이미지 교체·콘텐츠 삭제·수정본 파기에서 모든 직접 FK 참조가 제거되기 전에는 `DELETE_PENDING`으로 전환되지 않는지 검증한다.
- V1의 두 연결 테이블이 같은 이미지 객체를 참조한 데이터가 V2 뒤에도 두 직접 FK로 보존되는지 검증한다.
- 이미지 행 잠금과 참조 검사 동시 요청에서 참조 중 객체가 삭제되지 않는지 MySQL 통합 테스트로 검증한다.

## 대체 조건

- 수정본 대표 이미지 자체를 보존하지 않는 제품 정책으로 바뀐다.
- 이미지 객체의 버전·보존·공유 정책이 대표 이미지 범위를 넘어 별도 미디어 도메인을 요구한다.
- 수정본 보존으로 인한 저장 비용이 합의한 한계를 지속적으로 넘고 별도 보관·파기 정책이 채택된다.
