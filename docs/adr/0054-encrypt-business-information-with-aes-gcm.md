# ADR-0054: 사업자 정보를 AES-256-GCM으로 암호화해 보관한다

- 상태: 채택
- 기록 유형: 후속 결정
- 기록일: 2026-08-02
- 결정일: 2026-08-02
- 관련 요구사항: [FR-09 운영자 승인·정보 마스킹](../p0/auth-profile.md#fr-09-운영자-승인정보-마스킹), [AUTH-02](../p0/auth-profile.md#auth-02)
- 관련 단계: 단계 0. 정책·경계 확정
- 관련 이슈: #102
- 대체 대상: [ADR-0026](0026-select-signup-role-and-create-operator-application.md)의 사업자 정보 저장 보호·보관 정책 미확정 범위

## 맥락

운영자 신청에는 지역 관리자의 수동 심사를 위한 사업자 정보가 필요하다. [ADR-0036](0036-expose-business-information-only-in-protected-review-detail.md)은 담당 지역 관리자만 심사용 상세 조회에서 원문을 확인하도록 응답 경계를 정했지만, 현재 `operator_application.business_information`은 평문 `TEXT` 값이다.

비가역 마스킹이나 해시는 원문을 복원할 수 없어 지역 관리자의 수동 심사를 충족하지 못한다. 반면 애플리케이션 수준 암호화는 DB 원문 노출 면적을 줄이면서, 인가된 심사 경로에서만 복호화할 수 있다.

## 결정 동인과 불변 조건

- 담당 지역의 `REGION_ADMIN`은 심사용 상세 조회에서 원문을 확인할 수 있어야 한다.
- DB에는 사업자 정보 원문을 저장하지 않는다.
- 암호문 위·변조는 복호화 실패로 처리하며 원문이나 암호화 세부 정보를 응답·로그에 노출하지 않는다.
- 키는 소스·설정 파일·로그에 두지 않고 배포 비밀로만 주입한다.
- 회원 탈퇴 완료 시 모든 신청 상태의 사업자 정보와 신청자 연결을 제거한다.

## 결정

`businessInformation`은 UTF-8 바이트를 Java Cryptography Architecture의 AES-256-GCM으로 암호화한다. 매 암호화마다 새 96비트 IV를 생성하고, 인증 태그가 포함된 암호문을 사용한다. 암호화 키는 256비트 키만 허용한다.

기존 `operator_application.business_information` `TEXT` 컬럼에는 다음 정보를 담은 버전 있는 암호화 봉투를 저장한다.

- 형식 버전
- 키 식별자
- Base64 인코딩한 IV
- Base64 인코딩한 AES-GCM 암호문

활성 키와 이전 복호화 키는 배포 비밀 키링으로 주입한다. 새 신청은 활성 키로 암호화하고, 저장된 키 식별자에 대응하는 키로만 복호화한다. 키 교체 후에도 이전 키는 기존 행을 모두 재암호화해 검증할 때까지 복호화 키링에 유지한다. 키 원문과 봉투 전체는 로그·감사 이벤트·예외 메시지에 기록하지 않는다.

심사용 상세 조회는 [ADR-0036](0036-expose-business-information-only-in-protected-review-detail.md)의 지역 인가를 먼저 통과한 뒤에만 복호화한다. 회원가입·재신청·승인·반려·목록을 포함한 그 밖의 HTTP 응답과 애플리케이션·접근 로그, 감사 이벤트, 오류 응답, 지표에는 원문을 포함하지 않는다.

기존 평문 행은 제한된 일회성 이관 작업으로 암호화 봉투로 바꾸고, 원문이 남지 않았음을 검증한 뒤에만 완료한다. 이관 중에도 원문·키·암호문을 로그에 기록하지 않는다. 회원 탈퇴 완료 시에는 현재 정책대로 모든 상태의 `business_information`과 `applicant_user_id`를 제거한다.

## 결과와 트레이드오프

### 기대 효과

- DB 덤프 또는 조회만으로 사업자 정보 원문을 읽을 수 없다.
- 담당 지역 관리자는 기존 심사용 상세 조회에서 필요한 원문을 계속 확인할 수 있다.
- 키 식별자를 포함해 키 교체와 기존 행 재암호화를 지원한다.

### 수용한 단점과 위험

- 키 주입이 누락되거나 저장된 키 식별자에 대응하는 키가 없으면 심사를 진행할 수 없어야 한다.
- 암호화 봉투와 기존 평문 이관을 구현·운영해야 한다.
- 애플리케이션 실행 권한과 복호화 키가 함께 탈취되면 원문 노출을 막을 수 없다.

## 전환과 롤백

1. 배포 비밀로 활성 키와 키 식별자를 준비한다.
2. 암호화·복호화와 복호화 키링 검증을 배포한다.
3. 일회성 이관 작업으로 기존 평문 행을 암호화 봉투로 변경하고, 원문 잔존 여부를 검증한다.
4. 평문 행이 없는 것을 확인한 뒤 새 신청과 심사용 상세 조회에 암호화 규칙을 강제한다.

롤백 시에도 평문으로 되돌리지 않는다. 이전 배포본이 암호화 봉투를 읽을 수 없으므로, 키링을 유지한 수정 배포본으로 복구한다. 키 유출이나 복호화 실패는 해당 키로 암호화된 행을 안전한 새 키로 재암호화한 뒤 이전 키를 폐기한다.

## 검증 방법

- 저장된 `business_information`에 원문이 없고, 같은 입력도 서로 다른 IV로 다른 암호문이 되는지 검증한다.
- 담당 지역의 `REGION_ADMIN`만 심사용 상세 조회에서 복호화된 원문을 받는지 검증한다.
- 타 지역·다른 역할·회원가입·재신청·승인·반려·목록 응답과 로그, 감사 이벤트, 오류 응답, 지표에 원문이 없는지 검증한다.
- 암호문·IV·태그를 변조하거나 키가 없을 때 요청이 실패하고 원문이나 암호화 세부 정보가 노출되지 않는지 검증한다.
- 이전 키로 암호화한 행을 복호화하고 활성 키로 재암호화한 뒤 이전 키를 제거할 수 있는지 검증한다.
- 회원 탈퇴 완료 시 모든 신청 상태의 `business_information`과 `applicant_user_id`가 제거되는지 검증한다.

## 대체 조건

- AWS KMS 등 관리형 키 관리 체계로 전환해 키 주입·회전·폐기를 외부화한다.
- 외부 사업자 검증 서비스 또는 별도 온보딩 시스템이 심사를 대체한다.
- 법적·운영상 보관 기간 또는 사업자 정보의 구조화 요구사항이 확정된다.
