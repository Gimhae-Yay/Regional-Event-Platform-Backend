# ADR-0100: 콘텐츠 중단·종료 시 활성 수정본을 무효화 상태로 종결

- 결정일: 2026-08-15

- 관련 이슈: [#843](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/843), [#786](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/786)
- 대체 대상: 없음

## 맥락

공개 콘텐츠에 `EDIT_REQUESTED` 수정본이 남은 상태에서 `PUBLISHED → SUSPENDED` 또는
`PUBLISHED → ENDED`가 성공하면, 기존 계약은 수정본의 종결 상태를 정하지 않았다. 원본이 `PUBLISHED` 또는
공개 전 수정 심사의 `PENDING`이어야 한다는 심사 목록·상세 분류와 승인·반려·철회 검증이 더는 성립하지 않아,
수정본이 미종결 상태로 남고 목록·상세에서 서버 오류가 발생할 수 있다.

이슈 #843의 확정된 제품 정책은 콘텐츠 수명주기 전이가 심사 대기 수정본을 영구 미종결 상태로 남기지 않도록
같은 트랜잭션에서 자동 종결하는 것이다. 기존 `SUSPENDED`·`ENDED` 콘텐츠에 남은 과거 수정본도 배포 시
같은 상태 규칙으로 보정해야 한다.

## 결정 동인과 불변 조건

- `PUBLISHED → SUSPENDED` 또는 `PUBLISHED → ENDED`가 성공하면 활성 수정본이 남지 않아야 한다.
- 콘텐츠 상태·수정본 상태·수정본 이력·콘텐츠 로그·감사·홀드 변경은 부분 커밋되지 않아야 한다.
- 수정 심사·철회와 콘텐츠 중단·종료가 경합하면 `EDIT_REQUESTED`에서의 상태 전이는 하나만 성공해야 한다.
- 수동 중단·종료의 처리자, 시스템 종료의 처리자 없음, 무효화 시각과 원인은 재현 가능해야 한다.
- 과거 데이터 보정은 이미 보정된 행을 다시 바꾸거나 새 이력을 만들지 않아야 한다.

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |

| 1 | `EDIT_INVALIDATED` 터미널 상태와 이력 필드를 추가하고 수명주기 전이와 원자적으로 처리 | 종결 원인과 처리자를 보존하고, 목록·상세·심사 명령에서 명확히 제외할 수 있다. 상태 조건 기반 보정도 가능하다. | 새 상태·열·마이그레이션과 모든 심사 경로의 계약을 함께 유지해야 한다. | 중간. 배포된 상태값과 과거 보정값은 삭제하지 않고 전진 수정해야 한다. | 이슈에서 선택했으며 미종결·500 문제를 정보 손실 없이 해결한다. |

## 결정

`EDIT_REQUESTED` 콘텐츠 수정본에 `EDIT_INVALIDATED` 터미널 상태를 추가한다. 콘텐츠가 `PUBLISHED`에서
`SUSPENDED` 또는 `ENDED`로 전이할 때, 대상 `content` 행을 먼저 `PESSIMISTIC_WRITE`로 잠근 뒤 활성 수정본
행을 잠가 같은 쓰기 트랜잭션에서 `EDIT_INVALIDATED`로 전이한다.

무효화 수정본은 `invalidated_at`, `invalidated_by_user_id`, `invalidation_reason`을 보관한다.
`invalidation_reason`은 `CONTENT_SUSPENDED` 또는 `CONTENT_ENDED`만 허용한다. 중단과 수동 종료는 실제 지역
관리자를 기록하고, 시스템 종료는 처리자를 기록하지 않는다. 기존 수정본 상태 전이와 같은 방식으로 원본 콘텐츠를
대상으로 한 성공 `audit_event`에 `EDIT_REQUESTED → EDIT_INVALIDATED`와 원인 코드를 기록한다.

활성 수정본을 찾지 못하면 수명주기 전이는 계속 진행하며 수정본 행·수정본 감사는 추가하지 않는다. 수정본이 먼저
승인·반려·철회됐으면 콘텐츠 전이는 그 수정본을 다시 바꾸지 않는다. 콘텐츠 중단·종료가 먼저 무효화를 커밋하면
심사 상세는 `404 NOT_FOUND`, 승인·반려·철회는 `409 CONTENT_STATE_CONFLICT`, 대기 목록은 제외 결과를 반환한다.

마이그레이션은 기존 `SUSPENDED`·`ENDED` 콘텐츠의 `EDIT_REQUESTED` 수정본만 조건부로 보정한다. 해당 콘텐츠의
현재 상태와 같은 가장 최근 `content_log`의 시각·처리자를 사용하고, 상태 조건을 만족하는 행만 바꾸므로 재실행해도
같은 수정본을 다시 전이하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 정상 콘텐츠 수명주기 전이 뒤 심사 대기 수정본이 미종결로 남지 않는다.
- 수정본 무효화가 누가·언제·왜 발생했는지와 상태 전이 감사 이력이 보존된다.
- 콘텐츠와 수정본을 같은 잠금 순서로 처리해 중단·종료와 심사·철회의 경합 결과를 하나로 제한한다.
- 배포 전에 누적된 잘못된 상태도 정책에 맞게 한 번 보정한다.

### 수용한 단점과 위험

- `EDIT_INVALIDATED`를 이해하지 못하는 이전 애플리케이션 버전은 새 데이터를 올바르게 처리하지 못하므로
  스키마·코드·계약을 함께 배포해야 한다.
- 같은 콘텐츠의 중단·종료와 심사·철회는 콘텐츠 행 잠금 대기로 직렬화된다.
- 과거 보정의 처리자·시각은 별도 수정본 이력이 없으므로 콘텐츠 로그에서 확인되는 값만 사용할 수 있다.

## 전환과 롤백

먼저 상태값·무효화 이력 열과 제약을 추가하고, 다음 마이그레이션에서 기존 `SUSPENDED`·`ENDED` 콘텐츠의
활성 수정본을 조건부로 보정한다. 그 뒤 새 상태를 이해하는 애플리케이션 코드와 계약을 배포한다. 보정은
`EDIT_REQUESTED` 조건을 잃은 행을 다시 변경하지 않아 재실행 안전하다.

배포 후에는 `EDIT_INVALIDATED`를 기존 상태로 되돌리지 않는다. 문제가 있으면 중단·종료 경로를 일시 중지하거나
새 전진 수정으로 원인을 해결한다. 이전 애플리케이션으로만 롤백해야 하면 새 상태와 열을 이해하는 호환 배포를 먼저
마련해야 하며, 이미 기록된 무효화 이력은 삭제하지 않는다.

## 검증 방법

- 중단·수동 종료·시스템 종료가 활성 수정본을 각각 올바른 사유·처리자·시각으로 한 번만 무효화하는지 검증한다.
- 수정본 승인·반려·철회와 중단·종료가 경합할 때 하나의 상태 전이만 커밋되는지 MySQL 통합 테스트로 검증한다.
- 콘텐츠 상태·수정본 무효화·콘텐츠 로그·감사·홀드 처리 중 하나가 실패하면 모든 변경이 롤백되는지 검증한다.
- 과거 `SUSPENDED`·`ENDED` 행 보정이 상태 조건으로 한 번만 적용되고, 목록·상세가 500을 반환하지 않으며 재심사 명령이 거부되는지 검증한다.
- 배포 후 `EDIT_REQUESTED`인데 원본이 `SUSPENDED` 또는 `ENDED`인 행 수, 수정본 무효화 감사 이벤트와 실패 감사·잠금 대기 지표를 관찰한다.

## 대체 조건

- 콘텐츠가 중단·종료된 뒤에도 수정본 심사를 이어갈 제품 정책이 확정된다.
- 수정본 상태 이력을 범용 감사 이벤트가 아닌 별도 추가 전용 테이블로 분리해야 하는 감사·보관 요구가 채택된다.
- 콘텐츠 행 잠금 대기가 운영 목표를 지속적으로 위반해 다른 동시성 제어 방식이 필요한 증거가 누적된다.
