# ADR-0044: 교체 가능한 BCrypt 비밀번호 해싱을 사용한다

- 상태: 채택됨
- 기록 유형: 신규

- 관련 단계: 단계 1. MVP 구현·검증

## 맥락

회원가입과 로그인 명세는 비밀번호 원문을 저장·응답·로그에 남기지 않고 해시와 비교하도록 정했지만,
사용할 PasswordEncoder 알고리즘과 작업 강도, 향후 해싱 정책 변경 방법은 정하지 않았다. 현재 `app_user`에는
`password_hash` 컬럼만 있으며 기존 회원 비밀번호 해시는 없다.

비밀번호 해싱은 저장 뒤 알고리즘 또는 작업 강도를 바꾸기 어렵다. 단일 알고리즘 클래스를 직접 고정하면
기존 해시의 식별과 점진적 업그레이드가 어려워진다.

## 결정 동인과 불변 조건

- 비밀번호 원문은 DB, 로그, 감사 이벤트, 오류 응답에 남기지 않는다.
- 가입 시 저장한 해시는 로그인에서 안정적으로 검증할 수 있어야 한다.
- 해싱 알고리즘 또는 작업 강도를 바꿀 때 기존 회원을 일괄 초기화하지 않아야 한다.
- 현재 회원가입 명세의 영문자·숫자·특수문자 8~64자 입력은 BCrypt의 72바이트 제한을 넘지 않도록 검증한다.
- 해싱 강도를 테스트 편의 때문에 운영 환경에서 낮추지 않는다.

## 결정

비밀번호 저장과 검증은 `DelegatingPasswordEncoder`를 사용한다. 새 비밀번호는 강도 12의
`BCryptPasswordEncoder`로 해싱하고 `{bcrypt}` 접두사를 포함한 결과를 `app_user.password_hash`에 저장한다.

회원가입은 비밀번호 원문을 한 번만 `encode`에 전달하고 이후 흐름에는 해시만 전달한다. 로그인은
`matches(rawPassword, passwordHash)`로만 비교한다. 원문, 해시, 비교 실패 원인은 로그·감사 이벤트·오류 응답에
넣지 않는다.

로그인에 성공한 뒤 현재 해시가 `upgradeEncoding` 대상이면 같은 로그인 트랜잭션에서 새 기본 인코더로 재해싱해
저장할 수 있다. 향후 기본 알고리즘이나 강도를 바꿀 때는 기존 `{bcrypt}` 검증기를 유지하고 새 기본 식별자만
변경한다. 현재 회원이 없으므로 기존 해시 이관은 없다.

## 결과와 트레이드오프

### 기대 효과

- DB에 알고리즘 식별자가 포함된 비밀번호 해시만 남아 향후 검증 호환성을 유지한다.
- BCrypt 강도 12로 단순 해시보다 오프라인 대입 공격 비용을 높인다.
- 로그인 성공 시점의 점진적 재해싱으로 일괄 비밀번호 재설정 없이 정책을 바꿀 수 있다.

### 수용한 단점과 위험

- 강도 12는 가입·로그인 CPU 시간을 증가시킨다. 요청 제한과 모니터링 없이 과도한 인증 요청이 오면 자원 소모가 커질 수 있다.
- BCrypt의 입력 길이 제한을 넘는 비밀번호를 무단으로 허용하면 서로 다른 원문이 같은 입력으로 잘릴 위험이 있다. 회원가입 검증은 명세의 ASCII 범위를 유지해야 한다.
- Argon2id보다 메모리 비용 공격 저항성은 낮다. 운영 규모와 위협 모델이 바뀌면 별도 ADR로 재검토한다.

## 전환과 롤백

신규 구현이므로 기존 비밀번호 해시를 이관하지 않는다. `PasswordEncoder` 구성과 회원가입·로그인 테스트를 먼저
추가한 뒤 API 구현에서 이를 주입해 사용한다.

배포 직후 해싱 성능 문제가 확인되면 운영 강도를 무단으로 낮추지 않는다. 부하 원인과 허용 로그인 지연을
검토해 새 해싱 정책 ADR을 작성한 뒤, 기존 `{bcrypt}` 검증을 유지하면서 새 기본 정책으로 점진 전환한다.

## 검증 방법

- 새 해시가 `{bcrypt}` 접두사를 가지고 원문과 일치하지만 다른 원문과 일치하지 않는지 검증한다.
- 같은 원문을 여러 번 해싱해 서로 다른 salt 기반 결과가 나오는지 검증한다.
- 로그인 경로가 원문을 로그·응답·예외 메시지에 남기지 않는지 검증한다.
- 기존 `{bcrypt}` 해시의 검증과 `upgradeEncoding` 판정이 동작하는지 검증한다.
- 회원가입 명세가 허용하는 최장 비밀번호가 BCrypt 입력 길이를 넘지 않는지 검증한다.

## 대체 조건

- 운영 환경의 로그인 지연·CPU 사용량이 합의한 수준을 지속적으로 넘는다.
- 메모리 비용 기반 해싱 또는 규정상 특정 알고리즘이 필요해진다.
- 외부 IdP로 비밀번호 검증 책임을 이전한다.
- 비밀번호 입력 정책이 BCrypt의 안전한 입력 길이 범위를 넘도록 변경된다.
