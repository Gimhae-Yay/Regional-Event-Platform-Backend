# ADR-0076: P0 HTTP 시나리오는 재현 가능한 로컬 시드와 순서 실행으로 검증한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-07
- 결정일: 2026-08-07
- 관련 요구사항: [제품 PRD](../local-stamp-platform-prd.md)의 P0 콘텐츠·예약·QR·후기 흐름, [API 공통 계약](../api/common/README.md)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

P0 HTTP 파일은 인증 토큰, 콘텐츠·회차·예약 식별자, QR 토큰처럼 실행 시점에 생성되는 값을 다음 요청에 전달한다.
또한 콘텐츠 작성·심사·예약·체크인·후기는 상태를 바꾸므로 파일을 단독 또는 임의 순서로 반복 실행하면 이전 실행의
상태와 충돌한다. FakeImageStorage는 실행 중인 애플리케이션 메모리에 업로드 메타데이터를 보관하므로, 사전 서명과
이미지 연결 사이에 애플리케이션을 재기동해도 같은 시나리오가 성립하지 않는다.

개발자가 각 파일의 빈 변수를 수동으로 채우거나 현재 DB 상태를 추측하지 않고, 로컬에서 같은 출발 상태와 실행
순서를 재현할 수 있어야 한다.

## 결정 동인과 불변 조건

- P0 검증 데이터는 로컬 Docker MySQL·Redis에만 기록하고 운영 데이터나 migration을 변경하지 않는다.
- 시드는 식별 가능한 P0 전용 행만 초기 상태로 되돌리며, 일반 개발 데이터를 삭제하지 않는다.
- 액세스 토큰·QR 토큰은 저장소 파일과 콘솔 출력에 기록하지 않고 실행 프로세스에만 주입한다.
- HTTP 파일의 실행 순서는 `01`부터 `10`, `99`까지 고정하며, 이전 파일이 만든 상태를 다음 파일이 사용한다.
- FakeImageStorage가 필요한 이미지 작성 요청은 같은 애플리케이션 프로세스 안에서 사전 서명부터 이미지 연결까지 실행한다.

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | PowerShell 준비·실행 스크립트와 P0 전용 SQL 시드를 둔다 | DB·Redis 초기화, 런타임 변수 주입, 고정 순서를 한 명령으로 재현한다. IntelliJ와 Docker HTTP 클라이언트 모두 같은 DB 상태를 사용할 수 있다. | 로컬 Docker와 실행 중인 애플리케이션이 필요하며, 시드가 스키마 변경을 따라가야 한다. | 낮음. 스크립트와 P0 전용 행만 제거하면 된다. | 추천안이며 사용자가 채택했다. |

## 결정

`scripts/p0/prepare.ps1`가 Docker Compose의 MySQL·Redis 준비 상태를 확인하고 `scripts/p0/seed.sql`을 적용한다.
시드는 P0 전용 지역·계정·콘텐츠·회차·예약·QR 예외·후기 행을 멱등하게 초기 상태로 만든다.

`scripts/p0/run.ps1`는 먼저 준비 스크립트를 실행하고, 실행 중인 로컬 애플리케이션에서 새 액세스 토큰과 QR 토큰을
발급받아 JetBrains HTTP Client에만 `-V` 값으로 전달한다. 이후 `http/p0` 파일을 이름순으로 한 번에 실행한다.
토큰을 파일로 저장하거나 출력하지 않는다. IntelliJ에서 개별 파일을 실행할 때는 이 준비 스크립트로 공통 시드만
되돌린 뒤 필요한 런타임 변수를 HTTP Client 환경에 직접 넣는다.

이 결정은 제품 API, 데이터 모델, migration, 운영 Compose 구성을 변경하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 같은 로컬 DB·Redis 출발점에서 P0 상태 전이와 HTTP 검증을 반복 실행할 수 있다.
- 파일 간 전역 변수 누수와 수동 토큰 입력을 제거해 실패 원인을 API 계약 또는 시나리오 상태로 좁힐 수 있다.
- 이미지 작성 시나리오도 애플리케이션 재기동 없이 연속 실행돼 FakeImageStorage의 메모리 제약을 만족한다.

### 수용한 단점과 위험

- 스크립트는 Docker Compose와 로컬에서 기동한 애플리케이션을 전제로 한다.
- 시드는 P0 전용 식별자 범위만 재설정하므로, 해당 범위를 다른 로컬 작업에 재사용하면 충돌할 수 있다.
- 개별 HTTP 파일은 전체 순서 실행과 동일한 런타임 변수를 자동으로 만들지 않으며, 파일별 독립성은 목표가 아니다.

## 전환과 롤백

P0 전용 시드 SQL, 준비 스크립트, 순서 실행 스크립트 순으로 추가한다. 실행 실패 시 P0 전용 시드를 다시 적용하고,
애플리케이션 Health와 Docker Compose 상태를 확인한 뒤 재시도한다.

되돌릴 때는 P0 전용 스크립트와 시드만 제거한다. 스크립트가 만든 데이터는 로컬 MySQL의 P0 전용 식별자이므로
준비 스크립트의 초기화 구문으로만 삭제하며, migration이나 일반 개발 데이터는 되돌리지 않는다.

## 검증 방법

- 빈 로컬 MySQL·Redis에서 준비 스크립트를 두 번 실행해도 P0 전용 행의 상태와 수량이 동일한지 확인한다.
- 실행 스크립트가 Health 확인 뒤 `01`부터 `10`, `99`까지 정렬된 순서로 HTTP 파일을 실행하는지 확인한다.
- 액세스 토큰·QR 토큰이 Git 추적 파일과 표준 출력에 나타나지 않는지 확인한다.
- 콘텐츠 작성의 사전 서명·이미지 연결·심사, 예약·QR 예외·후기 흐름이 같은 애플리케이션 프로세스에서 연속 실행되는지 확인한다.

## 대체 조건

- P0 HTTP 시나리오가 독립적인 테스트 데이터 격리 또는 병렬 실행을 공식 요구한다.
- FakeImageStorage가 프로세스 외부 영속 저장소로 바뀌어 이미지 연결의 프로세스 연속성 제약이 사라진다.
- CI가 로컬 Docker HTTP Client 실행을 대체하는 공식 통합 시나리오 실행기를 제공한다.
