# ADR-0078: 지역 공개 여부 전환 실패 감사에 요청 증빙 참조를 저장

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-07
- 결정일: 2026-08-07
- 관련 요구사항: [전체관리자](../p1/platform-admin.md)의 `ADM-05`, [P1 명세](../p1-spec.md)의 7.4 권한·감사·개인정보
- 관련 단계: 단계 3. 확장 의사결정
- 관련 이슈: 없음
- 대체 대상: [ADR-0072](0072-use-allowlisted-reason-codes-for-region-changes.md)의 공개 여부 상태 조건 실패 증빙 저장 범위, [ADR-0074](0074-treat-repeated-region-visibility-as-no-op-success.md)의 실패 감사 필드 범위

## 맥락

지역 공개 여부 변경 요청은 검증된 `reasonCode`와 필수 `evidenceReference`를 받는다. 성공 감사에는 두 값을 모두
저장하지만, 비삭제 콘텐츠 때문에 `409 REGION_AVAILABILITY_CONFLICT`로 거부된 실패 감사에는 서버 판정
`reason_code`만 확정되어 요청의 증빙 참조를 저장하는지 명확하지 않았다.

실패 감사에서 업무 증빙과 요청을 연결하지 않으면 같은 지역에 반복된 거부가 어떤 결재·티켓에 근거했는지 재현하기
어렵다. 반면 요청의 업무 `reasonCode`를 실패 원인으로 저장하면 서버 판정과 클라이언트 의도가 섞이므로 기존
실패 코드 소유권은 유지해야 한다.

## 결정 동인과 불변 조건

- 실패 원인은 서버가 판정한 코드로 재현해야 한다.
- 상태 조건을 평가하기 전에 인증·인가와 `evidenceReference` 검증을 완료해야 한다.
- 증빙 참조에는 개인정보, 토큰과 비밀값을 저장하지 않아야 한다.
- 롤백된 변경과 실패 감사는 서로 다른 트랜잭션 경계를 유지해야 한다.
- 입력·인증·인가·대상 조회 실패와 동일 상태 무변경 성공에는 감사 이벤트를 만들지 않아야 한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 추천안: 검증된 요청 `evidenceReference`를 409 실패 감사에 저장 | 거부된 시도와 외부 결재·티켓을 연결하면서 서버 실패 원인을 별도 코드로 보존한다. | 실패 감사에도 외부 증빙 참조의 보관·비밀값 검증 책임이 생긴다. | 낮음. nullable 열을 그대로 사용하므로 스키마 이관이 없다. | ADM-05의 변경 시도 추적성과 현재 감사 모델에 적합하다. |

## 결정

인증·인가와 입력 검증을 통과한 지역 공개 여부 변경이 비삭제 콘텐츠 조건 때문에
`409 REGION_AVAILABILITY_CONFLICT`로 거부되면, 변경 트랜잭션 롤백 완료 뒤 실패 감사 이벤트를 별도
트랜잭션으로 기록한다.

실패 감사에는 다음 값을 저장한다.

- `region_id`, `target_type = REGION`, `target_id = regionId`
- 현재 `is_public`과 요청한 목표 `isPublic`
- `result = FAILURE`
- 서버 판정 `reason_code = REGION_AVAILABILITY_CONFLICT`
- 검증과 앞뒤 공백 제거를 마친 요청 `evidenceReference`
- `actor_kind = USER`, 실제 고권한 `actor_role`, 처리 시각과 `requestId`

클라이언트의 업무 `reasonCode`는 실패 감사의 `reason_code`에 저장하지 않는다. 활성 처리자는
`audit_event_actor_link`에 연결한다. 실패 감사의 `evidence_reference`에도 토큰, 비밀값과 개인정보를 저장하지
않는다.

입력·인증·인가 실패, 존재하지 않는 지역과 동일 상태 무변경 성공에는 감사 이벤트를 만들지 않는 기존 결정을
유지한다.

## 결과와 트레이드오프

### 기대 효과

- 거부된 특권 변경 시도와 외부 업무 증빙을 감사 이력에서 연결할 수 있다.
- 서버 실패 원인과 클라이언트의 업무 사유가 섞이지 않는다.
- 기존 nullable `audit_event.evidence_reference`를 사용하므로 스키마를 추가하지 않는다.

### 수용한 단점과 위험

- 실패 이벤트도 증빙 참조의 보관 기간과 접근 통제를 따른다.
- 클라이언트가 잘못된 증빙을 보냈더라도 형식·비밀값 검증을 통과한 참조 자체는 실패 감사에 남는다.
- 변경 롤백 뒤 실패 감사 저장을 별도로 수행해야 하므로 구현과 테스트에 트랜잭션 경계가 하나 더 필요하다.

## 전환과 롤백

P1 지역 공개 여부 변경 API가 아직 구현 전이고 `evidence_reference` 열이 이미 nullable로 정의되어 있어 데이터
이관은 필요 없다. API 명세, P1 정책, ERD와 테스트 계약에 실패 감사의 저장 필드를 함께 반영한 뒤 구현한다.

실패 감사의 증빙 저장을 중단하려면 후속 ADR로 보관·추적 요구의 변화와 기존 실패 이벤트 조회 호환성을 검토한다.
기존에 저장된 증빙 참조는 공통 감사 보관 정책에 따라 처리하며 소급 삭제하지 않는다.

## 검증 방법

- 유효한 요청이 비삭제 콘텐츠 조건으로 거부되면 409 응답 뒤 실패 감사 한 건이 별도 트랜잭션에 저장되는지 확인한다.
- 실패 감사의 `reason_code`는 서버 실패 코드이고 `evidence_reference`는 검증된 요청값인지 확인한다.
- 실패 감사에 활성 actor 연결, 대상, 이전·목표 상태, 처리 시각과 `requestId`가 포함되는지 확인한다.
- 입력·인증·인가·대상 조회 실패와 동일 상태 무변경 성공에는 감사 이벤트가 없는지 확인한다.
- 증빙 참조의 길이·비밀값·개인정보 검증 실패가 도메인 상태 확인 전에 거부되는지 확인한다.

## 대체 조건

- 감사 또는 개인정보 정책이 실패 시도의 외부 증빙 참조 저장을 금지한다.
- 외부 증빙 시스템이 `requestId`만으로 변경 시도를 안정적으로 조회할 수 있어 별도 참조 저장이 불필요해진다.
- 실패 감사의 보관 범위를 성공 감사와 다르게 운영해야 한다는 요구가 확정된다.
