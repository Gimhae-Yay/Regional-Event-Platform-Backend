# ADR-0003: 예약 확정과 체크인에 영속 멱등성 기록 사용

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-23
- 결정일: 2026-07-23
- 관련 요구사항: [PRD의 FR-06, FR-07, US-01, US-03](../local-stamp-platform-prd.md#8-기능-요구사항)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

모바일 네트워크 지연, 사용자의 중복 입력, 프록시 재시도와 운영자의 QR 재스캔으로 같은 명령이 반복될 수 있다. 예약 확정이 반복되면 예약과 정원 차감이 중복될 수 있고, 체크인이 반복되면 방문 기록이 중복 생성될 수 있다.

도메인 고유 제약은 중복 엔터티 생성을 막지만 동일 요청에 같은 결과를 반환하는 API 계약까지 보장하지 않는다. 반대로 멱등 키 기록만 사용하고 도메인 고유 제약이 없으면 키가 달라진 중복 요청을 막지 못한다. 두 방어선을 함께 사용한다.

## 결정 동인과 불변 조건

- 같은 홀드는 한 예약으로만 전환된다.
- 같은 예약에는 방문 기록이 최대 한 건만 생성된다.
- 같은 actor와 operation 범위에서 같은 멱등 키와 같은 요청은 이전 완료 결과를 반환한다.
- 같은 멱등 키에 의미가 다른 요청을 보내면 새 작업으로 처리하지 않는다.
- 멱등 기록과 도메인 변경 사이에 성공 여부가 어긋나지 않는다.
- 애플리케이션 재시작과 다중 인스턴스 환경에서도 멱등성이 유지된다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 영속 멱등 키 기록과 도메인 고유 제약 조합 | 같은 요청의 결과 재사용과 키가 다른 도메인 중복 방지를 함께 제공한다. 재시도 이력을 추적할 수 있다. | 저장 공간과 정리 정책이 필요하고 처리 중 충돌·응답 저장을 설계해야 한다. | 중간 | 예약·체크인의 재시도와 현장 운영 추적에 적합하다. |

| 4 | 분산 락으로 요청 직렬화 | 동시에 들어온 동일 요청을 직렬화할 수 있다. | 락 해제 뒤 재시도 결과를 재현하지 못하고 Redis 운영·장애 의미가 추가된다. | 중간 | 초기 MVP의 멱등성 요구를 완전히 충족하지 못한다. |

## 결정

예약 확정과 체크인 명령은 클라이언트가 전달한 멱등 키를 받는다. 서버는 `actor`, `operation`, `idempotency_key` 조합을 유일하게 관리하고 요청의 정규화된 의미를 나타내는 해시를 함께 저장한다.

같은 키와 같은 요청이 완료된 경우 기존 도메인 결과와 응답 상태를 반환한다. 같은 키에 다른 요청 해시가 들어오면 충돌로 거부한다. 첫 요청이 처리 중인 경우 새 도메인 작업을 실행하지 않는다. 동시 요청은 유일 제약으로 직렬화하고, 대기 제한을 넘으면 재시도 가능한 응답을 반환한다. 세부 HTTP 상태와 보관 기간은 API 명세와 운영 설정에서 확정한다.

멱등 키 점유, 성공 결과 기록과 예약 또는 방문 변경은 같은 MySQL 트랜잭션에서 커밋한다. 트랜잭션이 롤백되는 일시 장애는 성공 결과로 저장하지 않아 다음 요청이 다시 처리할 수 있게 한다. 검증 실패처럼 재시도해도 결과가 달라지지 않는 도메인 실패를 저장할지는 API 명세에서 오류별로 정한다. 또한 `Reservation.hold_id`와 `Visit.reservation_id`에 도메인 고유 제약을 두어 다른 멱등 키로 들어온 중복 명령도 차단한다.

## 결과와 트레이드오프

### 기대 효과

- 네트워크 재시도와 중복 입력에 이전 성공 결과를 안정적으로 반환할 수 있다.
- 예약·체크인 처리 이력과 실패 지점을 운영자가 추적할 수 있다.
- 멱등 키가 잘못 바뀐 중복 요청도 도메인 고유 제약으로 차단한다.
- 애플리케이션 재시작이나 인스턴스 변경 후에도 멱등성이 유지된다.

### 수용한 단점과 위험

- 멱등 기록 테이블, 응답 표현과 정리 작업이 추가된다.
- 큰 응답 본문을 그대로 저장하지 않고 도메인 결과 참조를 재구성하는 설계가 필요하다.
- 처리 중 장애가 발생한 기록의 만료·재개 기준이 필요하다.
- 클라이언트가 요청마다 올바른 키를 생성·재사용해야 한다.

## 전환과 롤백

신규 구현이므로 기존 멱등 기록 이관은 없다. Flyway로 멱등 기록과 도메인 고유 제약을 추가하고 예약 확정, 체크인 순서로 적용한다.

멱등 기록 구현에 장애가 있으면 도메인 고유 제약을 유지한 채 API 결과 재사용만 일시적으로 중단할 수 있다. 이 경우 중복 엔터티는 계속 차단하지만 동일 응답 보장은 약화됨을 운영 문서에 명시한다. 영속 기록 방식을 완전히 변경할 때는 보관 중인 키의 호환 기간과 중복 요청 위험을 새 ADR에 기록한다.

## 검증 방법

- 동일 actor, operation, key, payload를 직렬·동시로 반복해 예약과 방문이 한 건만 생성되고 같은 결과가 반환되는지 검증한다.
- 같은 키에 다른 홀드 또는 예약을 넣어 충돌로 거부되는지 검증한다.
- 서로 다른 키로 같은 홀드를 확정하거나 같은 예약을 체크인해 도메인 고유 제약이 중복을 차단하는지 검증한다.
- 처리 도중 예외를 발생시켜 멱등 성공 기록만 남거나 도메인만 커밋되는 불일치가 없는지 검증한다.
- actor, operation, key의 해시, 요청 해시, 처리 상태, 대상 엔터티 ID와 `requestId`를 구조화 로그로 연결한다.

## 대체 조건

- 모든 호출 주체가 안정적인 자연 키를 제공해 응답 재사용 요구가 사라진다.
- 공개 API 게이트웨이가 같은 수준의 영속 멱등성 계약을 제공하고 애플리케이션과 원자적으로 연계할 수 있다.
- 멱등 기록량이나 응답 재구성 비용이 합의한 저장·응답 SLO를 지속적으로 위반한다.
