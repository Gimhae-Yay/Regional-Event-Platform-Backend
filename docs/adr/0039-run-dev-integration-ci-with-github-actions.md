# ADR-0039: GitHub Actions로 dev 통합 CI를 실행

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-30
- 결정일: 2026-07-30
- 관련 요구사항: [P0 명세](../p0-spec.md)의 테스트 및 출시 수용 기준과 [내부 API 명세서](../api/api-specification.md)의 계약 검증 기준
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

MVP 구현 단계에서 `dev`에 병합할 변경은 Java 21과 Gradle Wrapper 기준으로 컴파일·테스트·패키징까지 일관되게
검증되어야 한다. 현재 저장소에는 GitHub Actions 워크플로가 없어 개발자의 로컬 실행 여부에 따라 검증 결과가 달라질 수
있다.

프로젝트는 Gradle Java Toolchain 21과 Gradle Wrapper 9.5.1을 사용한다. 사용자는 GitHub 호스팅 러너에서
Amazon Corretto 21을 사용하고, `dev` 대상 Pull Request와 `dev` 푸시에서 CI를 실행하기로 선택했다.

## 결정 동인과 불변 조건

- `dev`에 병합되기 전과 병합된 직후에 동일한 빌드·테스트 검증을 실행한다.
- CI JDK는 프로젝트 Java Toolchain과 같은 Amazon Corretto 21을 사용한다.
- Gradle Wrapper로 빌드해 로컬 Gradle 설치나 버전에 의존하지 않는다.
- CI는 배포, 데이터 변경, 비밀값 사용, 외부 서비스 호출을 수행하지 않는다.
- 워크플로 권한은 소스 읽기에 필요한 최소 범위로 제한한다.
- 테스트가 실패해도 결과 리포트를 확인할 수 있어야 한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | GitHub 호스팅 Ubuntu 러너에서 `dev` PR·푸시에 Gradle 빌드·테스트 실행 | 별도 러너 운영 없이 깨끗한 환경에서 병합 전후를 검증하고, Gradle 캐시로 반복 시간을 줄일 수 있다. | GitHub Actions 가용성과 외부 의존성 다운로드에 영향을 받으며, OS 특화 검증은 하지 않는다. | 낮음. 워크플로 파일을 수정하거나 제거하면 된다. | 사용자가 선택했으며 MVP의 기본 통합 검증에 적합하다. |
| 2 | `dev` 대상 Pull Request에서만 Gradle 빌드·테스트 실행 | CI 사용량을 줄이고 병합 전 검증을 강제할 수 있다. | 직접 `dev` 푸시나 병합 후 상태를 검증하지 못한다. | 낮음. 푸시 트리거를 추가하면 된다. | 병합 후 검증이 필요한 현재 단계에 부적합하다. |
| 3 | 자체 호스팅 러너에서 Gradle 빌드·테스트 실행 | 사내 네트워크와 특수 도구를 사용할 수 있다. | 러너 보안 패치·격리·가용성 관리가 필요하고 Pull Request 코드가 운영 환경에 영향을 줄 수 있다. | 중간. 러너 인프라와 워크플로를 함께 정리해야 한다. | 별도 인프라 요구가 없는 MVP에 과도하다. |

## 결정

`.github/workflows/ci.yml`에 GitHub 호스팅 `ubuntu-latest` 러너를 사용하는 단일 `build-and-test` 작업을 둔다.

- 트리거는 `dev` 대상 `pull_request`와 `dev` 브랜치 `push`로 한정한다.
- `actions/checkout@v4`로 소스를 가져오고 `actions/setup-java@v4`에서 `distribution: corretto`, `java-version: "21"`을 사용한다.
- `gradle/actions/setup-gradle@v4`로 Gradle 의존성과 빌드 캐시를 설정한다.
- `./gradlew --no-daemon clean build`로 컴파일, 테스트와 패키징을 검증한다.
- `permissions`는 `contents: read`만 부여한다.
- 같은 참조의 새 실행이 시작되면 이전 실행을 취소해 오래된 커밋의 중복 검증을 피한다.
- 작업 성공·실패와 관계없이 JUnit 결과와 HTML 테스트 리포트를 7일 동안 아티팩트로 보관한다.

정적 분석, 커버리지 임계값, 보안 스캔, 배포와 브랜치 보호 규칙은 현재 프로젝트 설정이나 사용자 요구사항에 없으므로 이
결정의 범위에 포함하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- `dev` 통합 전후에 Java 21 환경에서 Gradle 빌드와 테스트를 반복 가능하게 확인한다.
- 빌드 실패나 테스트 실패 시 CI 로그와 저장된 리포트로 원인을 확인할 수 있다.
- 최소 권한과 GitHub 호스팅 격리 환경으로 CI가 저장소 상태나 운영 자격 증명에 미치는 영향을 제한한다.

### 수용한 단점과 위험

- GitHub 호스팅 러너와 Maven Central 등 외부 의존성의 일시적 장애로 CI가 실패할 수 있다.
- `clean build`는 단위·통합 테스트보다 넓은 품질 기준을 새로 추가하지 않으며, 별도 성능·보안 검증도 수행하지 않는다.
- Gradle 캐시는 실행 시간을 줄이지만 외부 의존성 다운로드와 첫 실행 비용을 완전히 없애지 못한다.
- CI 통과만으로 GitHub의 브랜치 보호 규칙이나 병합 제한이 자동 적용되지는 않는다.

## 전환과 롤백

새 워크플로만 추가하므로 데이터 이관이나 호환 계층이 필요하지 않다. Pull Request에서 워크플로 실행과 테스트 리포트
업로드를 확인한 뒤 적용한다.

워크플로가 프로젝트에 부적합하거나 GitHub Actions 장애가 지속되면 `ci.yml`을 되돌려 CI 실행을 중지한다. 소스 코드,
데이터, 배포 환경은 변경하지 않으므로 별도 복구 절차는 필요하지 않다.

## 검증 방법

- 로컬에서 Gradle Wrapper로 `./gradlew --no-daemon clean build`를 실행해 현재 Java 21 프로젝트의 빌드·테스트가 통과하는지 확인한다.
- `actionlint`로 워크플로 YAML과 GitHub Actions 식을 정적으로 검증한다.
- `cicd/ci-config` Pull Request에서 `dev` 대상 `pull_request` 트리거가 실행되고, `build-and-test` 작업이 Corretto 21에서 성공하는지 확인한다.
- 의도적인 테스트 실패 시에도 `test-reports` 아티팩트가 생성되고 JUnit XML과 HTML 리포트를 조회할 수 있는지 확인한다.
- `dev` 푸시에서 같은 작업이 실행되고, 같은 참조의 새 커밋이 이전 실행을 취소하는지 확인한다.

## 대체 조건

- 운영 환경 또는 외부 서비스와의 통합 테스트에 전용 네트워크·자격 증명·특수 도구가 필요해 GitHub 호스팅 러너만으로 검증할 수 없다.
- 정적 분석, 커버리지, 보안 스캔 또는 다중 JDK·운영체제 호환성이 릴리스 합격 조건으로 확정된다.
- CI 실행 시간, 대기 시간 또는 외부 의존성 실패율이 팀이 합의한 기준을 지속적으로 넘는다.
- 브랜치 보호 규칙 또는 배포 파이프라인과 결합해 필수 상태 검사 이름이나 실행 조건을 변경해야 한다.
