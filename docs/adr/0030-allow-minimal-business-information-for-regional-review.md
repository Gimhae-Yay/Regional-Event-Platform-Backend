# ADR-0030: 담당 지역 관리자에게 최소 사업자 정보 조회를 허용

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-30
- 결정일: 2026-07-30
- 관련 요구사항: [PRD](../local-stamp-platform-prd.md)의 `FR-09`, `AUTH-01`, `AUTH-02`, `AUTH-04`
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0026](0026-select-signup-role-and-create-operator-application.md)의 사업자 정보 HTTP 응답 비노출 범위

## 맥락

`AUTH-02`는 담당 지역 관리자가 운영자 승인 전에 사업자 정보를 수동 확인하도록 요구한다. 그러나
ADR-0026은 사업자 정보를 모든 HTTP 응답과 로그에 포함하지 않도록 정해, 지역 관리자용 신청 상세 API로
수동 검증을 수행할 수 없었다.

사용자는 담당 지역 관리자만 신청 상세에서 최소 사업자 정보를 보도록 허용하고, 일반 사용자·운영자·다른 지역
관리자에게는 계속 비노출하도록 선택했다. 이 선택은 모든 API 응답에 사업자 정보를 공개하는 결정이 아니라,
`GET /region-admin/operator-requests/{requestId}`의 인가된 조회 범위를 좁게 여는 결정이다.

## 결정 동인과 불변 조건

- 신청 상세를 조회하는 지역 관리자의 담당 `region_id`는 신청의 `requested_region_id`와 일치해야 한다.
- 상세 응답은 수동 검증에 필요한 `businessInformation` 단일 값만 원문으로 제공하며, 다른 API·목록·일반 운영자
  응답에는 원문을 포함하지 않는다.
- 사업자 정보 원문은 애플리케이션 로그, 감사 로그, 오류 응답, 캐시와 지표에 절대 기록하지 않는다.
- 원문을 반환하는 신청 상세 HTTP 응답은 `Cache-Control: no-store`로 브라우저·프록시 캐시 저장을 금지한다.
- 인가 실패·대상 없음·정합성 오류에서도 다른 지역 신청의 존재나 사업자 정보 일부를 노출하지 않는다.
- 승인 시 `OPERATOR` 역할과 요청 지역 부여, 신청 상태 종결과 성공 감사 기록은 하나의 MySQL 트랜잭션에서 처리한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 담당 지역 관리자 상세 API에만 최소 사업자 정보 원문을 제공 | 수동 심사에 필요한 정보를 API에서 확인하면서 노출 범위를 하나의 인가된 경로로 제한한다. | 응답 캡처와 운영 화면 노출 위험이 있으므로 로그·감사·오류·지표의 원문 차단을 지속 검증해야 한다. | 중간. API 응답과 접근 제어를 바꿔야 한다. | 사용자가 선택했으며 P0 수동 심사에 적합하다. |

| 3 | 사업자 정보를 모든 지역 관리자·운영자에게 마스킹해 제공 | 구현과 목록 조회가 단순하다. | 담당 지역 경계를 넓히고 마스킹된 값은 실제 수동 검증에 충분하지 않다. | 중간 | 최소 권한 원칙에 맞지 않는다. |

## 결정

ADR-0026의 사업자 정보 HTTP 응답 비노출 규칙은 신청 상세 조회 범위에서만 대체한다.

인증 주체가 `REGION_ADMIN`이고 신청의 `requested_region_id`가 인증 주체의 담당 지역과 같은 경우에만
`GET /region-admin/operator-requests/{requestId}`가 `businessInformation` 원문을 반환한다. 이 값은
`operator_application.business_information`의 수동 심사 목적 값이며, 목록 응답·`GET /me`·일반 사용자·운영자와
다른 지역 관리자의 응답에는 포함하지 않는다.

서버는 원문 대신 요청 식별자, 담당 지역 식별자, 결과 코드와 비개인 상태만 관측 데이터에 남긴다. 감사 이벤트는
심사자·대상 신청·지역·상태 전이·시각을 재현하되 사업자 정보 원문을 저장하지 않는다.
신청 상세 성공 응답에는 `Cache-Control: no-store`를 설정한다.

## 결과와 트레이드오프

### 기대 효과

- 지역 관리자 승인자가 별도 비공개 채널 없이 신청 상세에서 수동 검증 정보를 확인할 수 있다.
- 원문 노출 API와 역할·지역 범위를 하나의 상세 조회 계약으로 제한한다.
- 승인 감사에는 필요한 처리 사실만 남겨 사업자 정보의 복제를 피한다.

### 수용한 단점과 위험

- 권한 있는 지역 관리자 화면에는 원문이 표시되므로 클라이언트 화면·브라우저 저장소의 별도 보안 책임이 생긴다.
- 응답 직렬화·예외·관측 경로 중 하나라도 원문을 기록하면 정책 위반이므로 회귀 테스트가 필요하다.

## 전환과 롤백

구현 전 문서·API 계약 결정이므로 데이터 이관은 없다. 먼저 상세 조회 DTO와 로그 마스킹 기준을 확정하고,
역할·지역 인가를 통과한 뒤에만 원문을 매핑한다. 이후 승인·반려 API는 기존 `operator_application`의 상태
전이와 역할·지역 원자 부여 규칙을 유지한다.

노출 사고나 외부 사업자 검증 경로 도입으로 원문 조회가 불필요해지면 상세 응답에서 이 필드를 제거하고,
ADR-0026의 전면 비노출 규칙으로 되돌리는 후속 ADR을 작성한다.

## 검증 방법

- 같은 담당 지역의 `REGION_ADMIN`만 신청 상세에서 `businessInformation`을 받는지 검증한다.
- 일반 사용자·운영자·다른 지역 관리자와 인증 실패 요청은 원문·마스킹 조각·신청 존재 여부를 받지 않는지 검증한다.
- 성공·실패·예외 경로의 애플리케이션 로그, 감사 이벤트, 오류 응답, 캐시와 지표에 원문이 없는지 검증한다.
- 신청 상세의 성공 응답에 `Cache-Control: no-store`가 있어 브라우저·프록시 캐시를 허용하지 않는지 검증한다.
- 승인 시 신청 상태, `OPERATOR` 역할, 요청 지역 배정과 감사 이벤트가 함께 커밋되고 실패 시 모두 롤백되는지 검증한다.

## 대체 조건

- 사업자 정보의 구조화·암호화·보관 기간 또는 외부 검증 연동 정책이 확정된다.
- 운영자 심사가 별도 온보딩 시스템으로 이전되어 애플리케이션 상세 조회가 필요 없어진다.
- 원문 노출 사고나 권한 경계 위반이 발생해 API 응답 경로를 유지할 수 없게 된다.
