# ADR-0028: 운영자 보조 조회를 위해 예약번호를 전역 유일하게 관리한다

- 상태: 채택됨

## 맥락

QR을 표시하지 못하거나 QR 검증에 실패한 경우, 소유 운영자는 예약 번호로 담당 콘텐츠의 예약을 보조 조회해야 한다.
기존 ERD는 `reservation_no` 컬럼만 두고 전역·지역·콘텐츠·회차별 고유 범위를 미확정으로 남겼다.

그러나 `GET /operator/reservations/search?reservationNo={reservationNo}`는 예약 번호 하나만 받아 단건 결과를 반환한다.
예약 번호가 전역에서 중복될 수 있으면 어떤 예약을 반환해야 하는지 결정할 수 없고, 서로 다른 콘텐츠의 예약 정보가 노출될 위험이 있다.

사용자는 전역 유일 예약 번호를 권장안으로 확정했다.

## 결정 동인과 불변 조건

- 예약 번호 하나만으로 정확히 한 예약을 식별할 수 있어야 한다.
- 운영자는 자신의 콘텐츠이면서 담당 지역이 일치하는 예약만 조회할 수 있어야 한다.
- 운영자 조회 응답의 이름·연락처는 마스킹하고, 예약 번호 자체와 개인정보 원문을 감사·로그에 남기지 않아야 한다.
- 예약 번호는 이름·연락처·사용자 식별자를 포함하지 않고 서버가 생성해야 한다.
- DB 유일 제약이 동시 생성과 중복을 막는 최종 기준이어야 한다.
- QR 실패 보조 조회는 예약·방문·체크인·정원 상태를 변경하지 않고, 확인 사유·처리자·시각만 감사할 수 있어야 한다.

## 결정

`reservation.reservation_no`에 시스템 전체 `UNIQUE` 제약을 둔다. 서버가 개인정보를 포함하지 않는 예약 번호를 생성하며,
삽입 시 유일 제약 충돌이 나면 새 번호를 생성해 재시도한다. 번호의 문자열 형식·길이는 현재 확정하지 않되,
향후 형식 변경도 전역 유일성과 기존 발급 번호의 조회 가능성을 유지해야 한다.

`GET /operator/reservations/search?reservationNo={reservationNo}`는 전역 유일 예약 번호로 최대 한 건을 찾은 뒤,
콘텐츠 소유 운영자와 담당 지역을 검증한다. 성공 응답은 예약자 이름·연락처를 마스킹하고, QR 토큰·QR 참조·사용자 식별자와
개인정보 원문을 포함하지 않는다.

QR 실패 보조 조회 성공은 `QR_VERIFICATION_FAILED` 사유와 처리자·시각을 감사 이벤트에 기록한다.
이 감사 기록은 예약, 방문, 체크인, 홀드와 정원 상태를 변경하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 운영자가 예약 번호 하나로 정확히 한 예약을 찾아 현장 QR 실패를 처리할 수 있다.
- 데이터베이스가 동시 예약 생성에서도 예약 번호 충돌을 방지한다.
- 범위 파라미터와 후보 목록을 추가하지 않아 운영 화면과 API 계약이 단순하다.
- 다른 콘텐츠 예약을 잘못 반환하는 개인정보 노출 위험을 줄인다.

### 수용한 단점과 위험

- 번호 생성기는 전체 시스템에서 충돌 가능성을 고려해야 하며, 유일 제약 충돌을 처리해야 한다.
- 향후 외부 예약 시스템을 연동하거나 예약 번호 공간이 부족해지면 형식·생성 전략을 변경해야 할 수 있다.
- 이미 데이터가 존재하는 환경에서는 유일 제약 추가 전에 중복 예약 번호를 확인하고 해소해야 한다.

## 전환과 롤백

신규 스키마에서는 `reservation_no` 생성 규칙과 `UNIQUE` 제약을 하나의 Flyway migration으로 적용한다.
기존 데이터가 있으면 migration 전에 중복 예약 번호를 조회하고, 중복이 있으면 migration을 중단해 운영자가 해소한다.
기존 번호를 자동으로 재번호 부여하지 않는다. 발급된 예약 번호가 외부 안내나 현장 확인에 사용될 수 있기 때문이다.

장애가 발생하면 새 예약 번호 발급과 보조 조회 배포를 중단하고, 데이터 정합성을 확인한다. 이미 전역 유일한 번호를 발급한 뒤에는
유일 제약을 제거하지 않는다. 범위 유일 방식으로 전환하려면 기존 번호 조회 호환 계층, 추가 범위 입력과 개인정보 영향 평가를 포함한
새 ADR을 먼저 채택한다.

## 검증 방법

- 서로 다른 지역·콘텐츠·회차를 포함해 같은 `reservation_no` 저장이 DB 유일 제약으로 실패하는지 검증한다.
- 예약 번호 생성 충돌 시 새 번호로 재시도하고, 최종 저장된 번호가 전역 유일한지 검증한다.
- 소유 운영자는 담당 콘텐츠의 예약만 조회하고, 다른 운영자·다른 지역 운영자는 `FORBIDDEN`을 받는지 검증한다.
- 운영자 조회 응답의 이름·연락처가 마스킹되고, QR 참조·사용자 식별자·개인정보 원문이 응답과 로그에 없는지 검증한다.
- 보조 조회 성공이 감사 이벤트만 남기고 예약·방문·체크인·홀드·정원을 바꾸지 않는지 검증한다.
- migration 전 중복 검사에서 중복 예약 번호가 발견되면 유일 제약 적용을 진행하지 않는지 검증한다.

## 대체 조건

- 예약 번호 생성 충돌률이나 재시도 지연이 운영 목표를 지속적으로 초과한다.
- 외부 예약 시스템이 전역 유일 번호와 충돌하거나 별도 식별 체계를 강제한다.
- 현장 운영이 지역·콘텐츠 범위 입력을 안정적으로 제공할 수 있고, 전역 유일 번호 유지 비용보다 범위 유일 방식의 이점이 커진다.
