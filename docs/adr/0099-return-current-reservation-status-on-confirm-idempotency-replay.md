# ADR-0099: 예약 확정 멱등 재응답에 현재 예약 상태를 반환

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-14
- 결정일: 2026-08-14
- 관련 요구사항: [활성 홀드의 무료 예약 확정](../api/p0/reservation/confirm-reservation-hold.md#4-활성-홀드의-무료-예약-확정)의 `Response`, `처리 규칙`
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: [#759](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/759)
- 대체 대상: [ADR-0003](0003-use-persisted-idempotency-for-reservation-and-checkin.md)의 동일 완료 요청에 이전 응답 상태를 반환한다는 해석과 [ADR-0022](0022-store-idempotent-results-in-one-record.md)의 예약 확정 재응답 상태 의미. 영속 멱등성, 동일 결과 예약 참조, 결과 FK 물리 모델은 대체하지 않는다.

## 맥락

같은 회원·`RESERVATION_CONFIRM`·멱등 키·`holdId`의 완료 요청은 이미 생성된 하나의 예약을
`idempotency_record.result_reservation_id`로 참조한다. 기존 API 명세는 이 재요청을 최초 성공 응답으로
재구성해 `data.status = CONFIRMED`로 반환하도록 적었다.

그러나 예약은 최초 확정 뒤 취소, 체크인 또는 노쇼 만료될 수 있다. 현재 구현은 성공 멱등 기록이 가리키는
예약을 다시 조회해 응답을 만들므로, 이 재요청에는 조회 시점의 예약 상태가 포함된다. MySQL 재현에서도
최초 `CONFIRMED` 예약을 취소한 뒤 같은 요청을 재전송하면 같은 예약 식별자를 유지하면서
`CANCELLED`를 반환했다. 새 예약·홀드 소비·감사 이벤트는 추가로 발생하지 않았다.

재응답의 `status`를 최초 명령의 과거 결과로 볼지, 같은 식별자가 가리키는 예약의 현재 상태로 볼지
공개 계약을 하나로 정해야 한다.

## 결정 동인과 불변 조건

- 같은 회원·작업·멱등 키·`holdId`의 완료 재요청은 새 예약, 홀드 소비 또는 감사 이벤트를 만들지 않고 같은 예약 식별자를 반환해야 한다.
- 재응답의 `data.status`는 클라이언트가 이어서 수행할 수 있는 동작을 오도하지 않아야 한다.
- `reservationId`, `reservationNo`, `holdId`, `sessionId`, `confirmedAt`은 최초 확정으로 생성된 같은 예약에서 재구성해야 한다.
- `SUCCEEDED` 기록과 결과 예약 참조는 같은 MySQL 트랜잭션에서 커밋한다는 ADR-0003·ADR-0022의 정합성 규칙을 유지해야 한다.
- 재응답 HTTP `201 Created`는 최초 확정이 성공해 같은 예약이 생성되었음을 나타내며, 재요청 시점에 상태 전이가 새로 발생했다는 뜻이 아니어야 한다.

## 결정

동일한 멱등 키와 `holdId`의 `SUCCEEDED` 예약 확정 재요청에는
`result_reservation_id`가 가리키는 **같은 예약의 재응답 시점 현재 상태**를 `data.status`로 반환한다.
허용 상태는 `CONFIRMED`, `CANCELLED`, `CHECKED_IN`, `EXPIRED`다.

재응답은 최초 확정의 도메인 명령을 다시 실행하지 않는다. `reservationId`, `reservationNo`,
`holdId`, `sessionId`, `confirmedAt`은 결과 예약에서 재구성하고, `data.status`만 그 예약의 현재
상태를 나타낸다. `201 Created`는 최초 요청이 이미 성공해 해당 예약이 생성됐고 재요청이 그 결과를
식별했다는 의미로 유지한다. 재요청이 새 상태 전이나 새 자원을 만들었다는 의미는 아니다.

## 결과와 트레이드오프

### 기대 효과

- 재시도 응답이 실제 예약 상태와 일치해 취소·체크인·만료 뒤의 후속 사용자 흐름을 오도하지 않는다.
- 결과 예약 참조만으로 재응답을 만들 수 있어 응답 스냅샷 테이블과 보관 정책을 추가하지 않는다.
- 동일 예약 식별자 재사용과 중복 부수 효과 차단이라는 멱등성 보장을 유지한다.

### 수용한 단점과 위험

- 같은 멱등 요청의 `data.status`는 시간에 따라 달라질 수 있으며, 응답 본문 전체의 바이트 단위 동일성은 보장하지 않는다.
- `201 Created`를 재요청 시점의 상태 생성으로 해석하는 클라이언트는 상태 필드를 기준으로 동작하도록 계약 변경을 반영해야 한다.
- 최초 확정 상태 자체가 필요한 감사·이력 조회는 이 API 재응답이 아니라 `confirmedAt`과 감사 이벤트를 사용해야 한다.

## 전환과 롤백

현재 구현은 결과 예약을 재조회해 현재 상태를 반환하므로 코드·DB 이관은 필요 없다. API 명세와 이 ADR을
같이 배포해 클라이언트가 `data.status`의 네 값을 처리하도록 알린다.

이 계약을 되돌리려면 후속 ADR로 현재 결정을 대체하고, 최초 성공 상태를 저장하거나 재현할 스키마·코드·MySQL
회귀 테스트를 별도 Fix Task에서 추가해야 한다. 현재 상태 반환에 의존하는 클라이언트가 배포된 뒤에는 문서만
되돌리지 않는다.

## 검증 방법

- MySQL에서 최초 확정 후 같은 키·홀드로 재요청해 예약·홀드 소비·성공 감사 이벤트가 각각 한 번이며 같은 예약 식별자를 반환하는지 검증한다.
- 최초 확정 뒤 각각 `CANCELLED`, `CHECKED_IN`, `EXPIRED` 상태로 전이한 뒤 재요청해 `data.status`가 각 현재 상태이고 HTTP 상태가 `201`인지 검증한다.
- 같은 멱등 키에 다른 `holdId`를 보내면 현재 상태를 조회하거나 새 예약을 만들지 않고 `IDEMPOTENCY_KEY_CONFLICT`인지 검증한다.
- API 명세, ADR-0003·ADR-0022·이 ADR 사이에 최초 응답 상태 재현을 요구하는 문구가 남지 않았는지 링크와 문구를 검사한다.

## 대체 조건

- 클라이언트가 최초 명령의 상태 스냅샷을 법적 증빙 또는 외부 정산에 사용해야 하고 현재 상태와 분리된 응답 표현이 필요해진다.
- 재응답의 상태 변동으로 사용자 흐름 오류 또는 운영 장애가 재현되고, 현재 상태를 별도 조회 API로 제공하는 방식이 더 적합하다는 근거가 생긴다.
- 멱등 결과 보관 기간이나 결과 참조 모델이 바뀌어 상태 스냅샷 보관 비용과 호환성 정책을 다시 결정해야 한다.
