# ADR-0006: 공통 콘텐츠 루트와 유형별 상세 모델을 명시적 연관관계로 구성

- 상태: 채택됨
- 기록 유형: 소급
- 기록일: 2026-07-23
- 결정일: 2026-07-21
- 관련 요구사항: [PRD의 FR-02, FR-03, FR-04](../local-stamp-platform-prd.md#8-기능-요구사항)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음

## 맥락

초기 MVP는 예약형 행사·체험만 구현하지만 이후 가게와 관광지를 지역 콘텐츠로 추가할 수 있다. 세 유형은 지역, 운영자, 공개 상태, 기본 소개와 위치 등 공통 정보를 가지지만 예약 회차, 메뉴, 관람 정보처럼 서로 다른 필드와 규칙도 가진다.

모든 유형의 필드를 하나의 테이블에 두면 빈 컬럼과 유형별 조건이 늘어나고, 자유 형식 JSON에 규칙 필드를 넣으면 DB 제약과 검색·마이그레이션이 어려워진다. 반대로 유형별 최상위 모델을 완전히 분리하면 공통 탐색, 승인, 소유권과 방문 연결이 중복된다.

## 결정 동인과 불변 조건

- 모든 콘텐츠는 하나의 안정적인 콘텐츠 식별자, 지역, 운영자와 공개 수명주기를 가진다.
- 행사·체험에만 회차와 예약을 생성할 수 있다.
- 유형별 필수 필드와 관계를 명시적으로 검증할 수 있어야 한다.
- 유형이 추가되어도 기존 공통 탐색·승인·소유권 계약을 유지한다.
- 아직 범위에 없는 가게·관광지 테이블과 API를 미리 구현하지 않는다.
- 예약·인증 규칙에 영향을 주는 값을 자유 형식 JSON에 저장하지 않는다.

## 결정

모든 콘텐츠의 공통 루트로 `Content`를 사용하고 콘텐츠 식별자, `region_id`, `operator_id`, `content_type`, 공개·승인 상태와 공통 소개 정보를 저장한다.

유형 고유 필드는 별도 상세 테이블에 두고 `Content`와 명시적인 1:1 연관관계로 연결한다. JPA 엔터티 상속으로 DB 모델을 표현하지 않는다. 초기 MVP에서는 `EVENT_EXPERIENCE`와 `EventExperienceDetail`만 구현하며, 가게와 관광지 상세 테이블·API는 실제 후속 범위가 확정될 때 추가한다.

`content_type`은 생성 후 다른 유형으로 직접 변경하지 않는다. 유형 전환이 필요하면 새 콘텐츠 생성과 기존 콘텐츠 종료를 기본으로 한다. 회차 생성과 예약 유스케이스는 연결된 콘텐츠의 유형이 `EVENT_EXPERIENCE`인지 확인한다.

예약, 인증, 가격처럼 비즈니스 규칙과 검색 조건에 사용되는 값은 명시적인 컬럼과 테이블에 저장한다. 표시 전용의 비정형 보조 정보에 JSON을 도입할지는 별도 요구가 생길 때 판단한다.

## 결과와 트레이드오프

### 기대 효과

- 지역 홈, 목록, 승인, 소유권과 이미지 같은 공통 기능을 하나의 콘텐츠 계약으로 제공한다.
- 행사·체험 규칙을 다른 콘텐츠 유형의 빈 필드나 조건문과 분리한다.
- 가게·관광지 도입 시 기존 콘텐츠 식별자와 방문 연결을 유지하면서 상세 모델만 추가할 수 있다.
- 현재 범위에 없는 상세 테이블을 만들지 않아 초기 구현 범위를 제한한다.

### 수용한 단점과 위험

- 콘텐츠 상세 조회에 공통·상세 테이블 조인이 필요하다.
- DB 외래 키만으로 `content_type`과 상세 테이블 종류의 일치를 완전히 강제하기 어려울 수 있다.
- 공통 필드와 유형별 필드의 경계를 잘못 잡으면 이후 스키마 이동이 필요하다.
- 명시적 연관관계 매핑과 유형별 검증 코드가 추가된다.

## 전환과 롤백

신규 구현이므로 기존 콘텐츠 데이터 이관은 없다. Flyway로 `content`와 `event_experience_detail`을 먼저 생성하고 공통 콘텐츠 생성과 행사·체험 상세 생성을 하나의 트랜잭션에서 처리한다.

공통 모델이 부적합하다고 확인되면 새 ADR로 분리 또는 통합 전략을 결정한다. 유형별 독립 모델로 전환할 경우 기존 `content_id`를 외부 식별자로 유지하는 호환 계층과 외래 키 이관이 필요하다. 단일 테이블로 합칠 경우 상세 데이터를 공통 테이블로 옮긴 뒤 읽기 경로를 전환하고 기존 상세 테이블을 마지막에 제거한다.

## 검증 방법

- 행사·체험 콘텐츠 생성 시 `Content`와 `EventExperienceDetail`이 함께 커밋·롤백되는지 검증한다.
- `EVENT_EXPERIENCE`가 아닌 콘텐츠에 회차와 예약을 생성할 수 없는지 검증한다.
- 상세 행이 없거나 다른 유형과 불일치하는 콘텐츠를 공개할 수 없는지 검증한다.
- 지역·운영자·공개 상태 필터가 유형 상세와 무관하게 일관되게 적용되는지 검증한다.
- 향후 새 상세 모델을 추가하는 Flyway 마이그레이션이 기존 콘텐츠 테이블과 API를 변경하지 않고 가능한지 설계 검토한다.

## 대체 조건

- 콘텐츠 유형별 공통 필드와 수명주기가 실제 운영에서 크게 달라진다.
- 공통·상세 조인이 핵심 조회 SLO를 인덱스와 쿼리 최적화로도 충족하지 못한다.
- 외부 콘텐츠 공급자가 유형별로 독립된 식별자·승인·보존 계약을 요구한다.
- 콘텐츠 유형 변경이 빈번해 생성·종료 방식으로 감당할 수 없다.
