# ADR-0101: 전체 콘텐츠 철회 요청을 별도 영속화하고 심사를 직렬화한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-16
- 결정일: 2026-08-16
- 관련 요구사항: [지역·콘텐츠 카탈로그](../p0/content-catalog.md)의 `CON-05`~`CON-07`, `CON-09`, `SES-02`
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: [#789](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/789), [#743](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/743)
- 대체 대상: 없음. [ADR-0100](0100-invalidate-active-content-revisions-on-content-termination.md)의 수정본 무효화 원인 범위를 전체 철회까지 확장한다.

## 맥락

`CON-07`은 소유 운영자가 공개 콘텐츠의 전체 철회를 요청하고 담당 지역 관리자가 승인하면
`PUBLISHED → WITHDRAWN`으로 전환하도록 정한다. 그러나 기존 ERD는 요청 보관, 승인·반려, 재요청과 재시도를
미확정으로 남겼고, `content_log`와 90일 보관 `audit_event`만으로는 심사 대기 중인 현재 요청 상태를 표현할 수
없다. 요청과 심사는 서로 다른 시각과 actor가 수행하며, 반려 뒤에는 이전 사실을 보존한 채 새 요청을 제출할 수
있어야 한다.

Issue #789의 기준 커밋 `f4d2490cb1697326586e5b9699d368c46899c532`에는 ADR-0100에 따라
`PUBLISHED → SUSPENDED | ENDED`가 활성 `EDIT_REQUESTED` 수정본을 `EDIT_INVALIDATED`로 종결하는 계약이
반영돼 있다. 전체 철회 승인도 원본을 더는 수정할 수 없는 터미널 상태로 만들므로 활성 수정본을 남길 수 없다.
또한 요청 대기 중 중단 또는 종료가 먼저 성공하면 해당 요청을 승인 가능한 것처럼 계속 보관해서는 안 된다.
작성 시점의 최신 `origin/dev` `88a3199ed5cc81f5852eb94f6027fe1e82f0adb3`까지 비교했으며, 기준 커밋 이후
전체 철회·수정본 종결·홀드 종결의 관련 계약 문서 변경은 없다.

전체 철회 승인은 콘텐츠 상태뿐 아니라 활성 홀드, 정원, 연결된 대기 결제와 선점 쿠폰에 영향을 준다. 반면 반려는
요청만 종결해야 한다. 요청·심사와 수정본 심사, 운영 중단·종료, 홀드 생성, 예약 확정이 경합해도 하나의 허용된
결과만 커밋되도록 상태 원천, 잠금 순서와 트랜잭션 경계를 확정해야 한다.

## 결정 동인과 불변 조건

- 심사 대기 요청의 현재 상태 원천은 장기 업무 엔티티여야 하며 `content_log`나 `audit_event`에서 추론하지 않는다.
- 콘텐츠당 처리 대기 요청은 최대 한 건이고, 반려된 요청은 보존한 채 새 행으로 재요청한다.
- 요청 생성 재시도와 반려 후 의도적인 재요청은 영속 식별자로 구분한다.
- 승인·반려·무효화는 `PENDING`을 조건으로 최초 한 전이만 성공한다.
- 전체 철회 승인 뒤 활성 콘텐츠 수정본과 `ACTIVE` 홀드가 남지 않는다.
- `ACTIVE` 홀드가 종결될 때 정원은 한 번만 복구하고 연결된 `PENDING` 결제와 `RESERVED` 쿠폰을 기존 홀드 종결 계약대로 정리한다.
- 콘텐츠 상태 변경만으로 기존 `CONFIRMED` 예약, 방문, 후기, 회차를 취소하거나 환불하지 않는다.
- 성공한 도메인 상태 전이와 성공 감사는 하나의 MySQL 트랜잭션에서 함께 커밋하거나 롤백한다.
- 공개 캐시 삭제는 커밋 뒤 최선 노력 작업이며 MySQL 원자성 범위에 포함하지 않는다.

| --- | --- | --- | --- | --- | --- | --- |
| 1 | `PENDING → {APPROVED, REJECTED, INVALIDATED}` | 관리자 결정과 외부 상태 변화에 의한 종결을 구분한다. | 상태와 무효화 메타데이터가 추가된다. | ADR-0100이 반려·철회와 무효화를 구분한 의미를 그대로 적용한다. | 중단·종료가 먼저 커밋되면 요청을 같은 트랜잭션에서 종결해 영구 대기를 막는다. | 채택. `CONTENT_SUSPENDED`, `CONTENT_ENDED` 원인을 보존한다. |

| 3 | 중단·종료를 허용하고 요청을 `PENDING`으로 유지 | 기존 경로 변경이 적다. | 승인 불가능한 요청이 영구 대기로 남고 새 요청 유일 제약도 해제되지 않는다. | 상태 전이 재현과 종결 불변 조건에 맞지 않는다. | 늦은 승인마다 콘텐츠 상태 충돌만 반복한다. | 미채택. 데이터 정합성 문제가 남는다. |
| 4 | 시스템 종결도 `REJECTED`로 기록 | 상태 수가 적다. | 관리자 반려와 콘텐츠 수명주기 종결을 구분하지 못한다. | ADR-0100이 거부한 의미 왜곡을 반복한다. | 재요청 가능 여부와 처리자 의미가 모호해진다. | 미채택. 감사 사실을 왜곡한다. |

## 결정

### 1. 영속 모델과 상태

별도 `content_withdrawal_request`를 둔다. 이 엔티티가 요청 이유, 요청자·시각, 상태, 심사자·시각·반려 사유,
무효화 시각·처리자·원인을 소유한다. `content_log`는 실제 콘텐츠 상태 전이만, `audit_event`는 90일 감사만
담당한다.

상태 전이는 다음과 같다.

```text
PENDING -> APPROVED
PENDING -> REJECTED
PENDING -> INVALIDATED
```

- `APPROVED`: 담당 지역 관리자가 전체 철회를 승인했다.
- `REJECTED`: 담당 지역 관리자가 필수 사유와 함께 요청을 반려했다.
- `INVALIDATED`: 요청 대기 중 콘텐츠가 먼저 `SUSPENDED` 또는 `ENDED`가 되어 심사할 수 없게 됐다.
- 세 상태는 터미널이며 역전이하지 않는다. 운영자 요청 취소 API는 #789 범위에 추가하지 않는다.
- 반려 뒤 콘텐츠가 계속 `PUBLISHED`이면 새 `Idempotency-Key`로 새 행을 생성해 재요청할 수 있다. 이전 요청과
  심사 이력은 보존한다.
- 무효화 뒤에는 콘텐츠가 `PUBLISHED`가 아니므로 재요청할 수 없다. `SUSPENDED` 이후 재개 계약은 현재 범위에 없다.

콘텐츠당 `PENDING` 요청은 최대 한 건이다. MySQL 생성 컬럼
`active_request_content_id = CASE WHEN status = 'PENDING' THEN content_id ELSE NULL END`와 유일 제약으로 강제한다.
요청 생성 키 원문은 저장하지 않고 해시만 `idempotency_key_hash`에 보관한다. 같은 콘텐츠에서 같은 키를 다시
사용하지 못하도록 `(content_id, idempotency_key_hash)` 유일 제약을 둔다.

### 2. 승인·반려와 재시도

- 요청 API는 필수 `Idempotency-Key`와 사유를 검증하고 키 원문의 해시를 계산한다. 같은 콘텐츠·같은 키 해시의
  기존 요청이 있으면 상태가 이미 종결됐더라도 정규화 사유가 같을 때 최초 `201 Created` 생성 결과를 반환하고
  새 요청·감사를 만들지 않는다. 사유가 다르면 `409 IDEMPOTENCY_KEY_CONFLICT`를 반환한다.
- 새 키를 사용했는데 같은 콘텐츠에 `PENDING` 요청이 있으면 사유가 같아도 `409 CONTENT_STATE_CONFLICT`다.
  반려 뒤 의도적인 재요청은 새 키를 사용해야 하며 새 요청 행과 새 감사를 만든다.
- 승인 API는 요청 본문이 없다. 이미 `APPROVED`인 같은 요청의 재시도는 저장된 `200 OK` 결과를 반환하고
  부수 효과를 다시 실행하지 않는다. `REJECTED` 또는 `INVALIDATED` 요청은 `409 CONTENT_STATE_CONFLICT`다.
- 반려 API는 사유를 정규화한다. 이미 `REJECTED`인 요청에 같은 사유로 재시도하면 저장된 `200 OK` 결과를
  반환한다. 다른 사유, `APPROVED` 또는 `INVALIDATED` 상태는 `409 CONTENT_STATE_CONFLICT`다.
- 승인·반려 API는 별도 `Idempotency-Key`를 사용하지 않는다. 요청 생성 트랜잭션이 롤백된 `500`은 같은 키로,
  승인·반려 트랜잭션이 롤백된 `500`은 같은 요청 ID와 의미로 재시도할 수 있다.

### 3. 승인 결과와 활성 수정본

승인은 요청을 `PENDING → APPROVED`, 콘텐츠를 `PUBLISHED → WITHDRAWN`으로 전이한다. `WITHDRAWN`
`content_log.reason`에는 운영자가 요청할 때 저장한 사유를, `actor_id`와 `date`에는 승인한 지역 관리자와 승인
시각을 기록한다.

승인 시 활성 `EDIT_REQUESTED` 수정본이 있으면 `EDIT_INVALIDATED`로 종결한다. `invalidated_at`은 승인 시각,
`invalidated_by_user_id`는 승인 관리자, `invalidation_reason`은 새 사유 `CONTENT_WITHDRAWN`이다. 후보 필드는
원본에 반영하지 않는다. 수정본 승인·반려·철회가 먼저 커밋됐으면 그 터미널 상태를 유지하고 전체 철회 승인은
계속 진행한다. 전체 철회가 먼저 커밋되면 뒤의 수정본 심사·철회는 `409 CONTENT_STATE_CONFLICT`다.

### 4. 반려와 요청 무효화 결과

반려는 철회 요청만 `PENDING → REJECTED`로 바꾸고 심사자·심사 시각·반려 사유와 성공 감사를 기록한다.
`content`, `content_revision`, `content_log`, `capacity_hold`, `content_session.remaining_capacity`,
`reservation`, `reservation_price_snapshot`, `payment`, `payment_idempotency`, `coupon`을 변경하지 않는다.

`PENDING` 요청이 있는 콘텐츠가 `PUBLISHED → SUSPENDED | ENDED`로 전이하면 해당 수명주기 트랜잭션에서 요청을
`INVALIDATED`로 종결한다. 원인은 각각 `CONTENT_SUSPENDED`, `CONTENT_ENDED`다. 수동 중단·종료는 실제 지역
관리자를 기록하고 시스템 종료는 처리자를 기록하지 않는다. 요청이 이미 승인·반려됐으면 다시 변경하지 않는다.

### 5. 감사 계약

`audit_event.target_type`에 `CONTENT_WITHDRAWAL_REQUEST`를 추가하고 요청 ID를 `target_id`로 사용한다.

- 요청 생성: `NULL → PENDING`, 사유 코드 `CONTENT_WITHDRAWAL_REQUESTED`, 요청 운영자
- 승인: `PENDING → APPROVED`, 사유 코드 `CONTENT_WITHDRAWAL_APPROVED`, 승인 관리자
- 반려: `PENDING → REJECTED`, 사유 코드 `CONTENT_WITHDRAWAL_REJECTED`, 반려 관리자
- 무효화: `PENDING → INVALIDATED`, 사유 코드 `CONTENT_SUSPENDED | CONTENT_ENDED`, 수동 처리자 또는 시스템
- 콘텐츠 승인 결과: 대상 `CONTENT`, `PUBLISHED → WITHDRAWN`, 사유 코드 `CONTENT_WITHDRAWN`
- 수정본 무효화: 기존 ADR-0100과 같이 대상 `CONTENT`, `EDIT_REQUESTED → EDIT_INVALIDATED`, 사유 코드
  `CONTENT_WITHDRAWN`

모든 성공 감사 이벤트는 해당 도메인 변경과 같은 `requestId` 및 MySQL 트랜잭션을 사용한다. 자유 텍스트 요청·반려
사유의 장기 업무 원천은 요청 행과 `content_log`이며, 감사 이벤트의 90일 보관이 이를 대신하지 않는다.

### 6. 동시성 및 잠금 규칙

권한용 사용자·역할 잠금 뒤 상태를 변경하는 도메인 행의 공통 순서는 다음과 같다.

```text
region -> content -> content_withdrawal_request -> content_revision
       -> content_session -> capacity_hold -> reservation_price_snapshot
       -> payment -> coupon
```

- 심사 API는 요청 ID로 `content_id`를 잠금 없이 찾은 뒤 `region`, `content`, 요청 행을 순서대로 잠그고 지역·상태를
  다시 검증한다. 요청 행을 먼저 잠근 뒤 콘텐츠 행으로 역행하지 않는다.
- 요청 생성은 `content`를 먼저 잠그고 `PUBLISHED`, 담당 지역과 소유 관계를 다시 검증한 뒤 활성 요청을 조회·생성한다.
- 중단·종료는 `content` 뒤 활성 철회 요청, 활성 수정본 순서로 잠근다. 대기 요청은 같은 트랜잭션에서
  `INVALIDATED`로 종결한다.
- 수정본 심사·철회도 기존처럼 `content`를 먼저 잠근다. 수정본 전이가 먼저 끝나면 전체 철회 승인은 현재 활성
  수정본 없이 진행하고, 전체 철회가 먼저 무효화하면 수정본 명령은 충돌한다.
- 홀드 생성은 `content → content_session`, 예약 확정은 `content → content_session → capacity_hold` 순서를
  유지한다. 요청 생성·반려는 예약 가능 상태를 바꾸지 않는다.
- 승인과 홀드 생성에서 먼저 커밋한 상태가 기준이다. 홀드 생성이 먼저면 승인이 그 홀드를 한 번 무효화·복구하고,
  승인이 먼저면 홀드 생성은 `WITHDRAWN`을 확인해 실패한다.
- 승인과 예약 확정에서 확정이 먼저면 홀드는 `CONSUMED`, 예약은 `CONFIRMED`로 유지되고 승인은 그 예약을 바꾸지
  않는다. 승인이 먼저면 홀드는 `INVALIDATED`가 되고 예약 확정은 상태 충돌로 실패한다.
- 승인·반려가 경합하면 요청 행의 `PENDING` 조건부 전이에 먼저 성공한 하나만 커밋한다.

### 7. 원자성 범위

전체 철회 승인 한 건의 MySQL 쓰기 트랜잭션에는 다음을 모두 포함한다.

1. 철회 요청 `PENDING → APPROVED`, 심사자와 심사 시각
2. 콘텐츠 `PUBLISHED → WITHDRAWN`
3. 요청 사유를 가진 `WITHDRAWN` `content_log`
4. 활성 수정본의 선택적 `EDIT_INVALIDATED`, 사유·처리자·시각
5. 요청·콘텐츠·수정본과 실제로 전이된 홀드·결제·쿠폰의 성공 감사 이벤트 및 actor link
6. 남은 모든 `ACTIVE` 홀드의 단일 `INVALIDATED` 전이와 홀드별 정원 단일 복구
7. 연결된 `PENDING` 결제의 `EXPIRED` 종결, `finalized_at`과 결제 멱등 결과 만료 시각 설정
8. 연결된 `RESERVED` 쿠폰을 원래 만료 시각에 따라 `AVAILABLE` 또는 `EXPIRED`로 전이하고 상태 이력 추가

`reservation_price_snapshot`은 불변이며 변경하지 않는다. 기존 `CONSUMED` 홀드와 `CONFIRMED` 예약,
`CHECKED_IN` 예약, 방문, 후기, 회차는 변경하지 않는다. 외부 결제 승인·취소 API를 호출하거나 환불·회차 취소를
만들지 않는다.

공개 콘텐츠 캐시는 MySQL 커밋 뒤 최선 노력으로 삭제한다. 캐시 삭제 실패는 승인 트랜잭션을 롤백하지 않으며,
공개 조회가 MySQL의 `WITHDRAWN` 상태를 먼저 검증하므로 이전 캐시를 정상 응답에 사용하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 요청과 심사의 현재 상태, 반려·무효화·재요청 이력을 콘텐츠 로그와 감사 보관 기간에 의존하지 않고 재현한다.
- 운영 중단·종료를 막지 않으면서 승인 불가능한 대기 요청을 자동 종결한다.
- 전체 철회와 수정본 철회, 운영 중단, 콘텐츠 종료의 상태·사유 의미를 분리한다.
- 콘텐츠·수정본·홀드·결제·쿠폰을 기존 잠금 순서와 한 MySQL 트랜잭션으로 정합화한다.
- 재시도와 경합이 최초 결과 하나로 수렴하고 정원·결제·쿠폰을 중복 변경하지 않는다.

### 수용한 단점과 위험

- 요청 테이블, `INVALIDATED` 상태, 감사 대상 유형과 수정본 무효화 사유가 추가된다.
- 기존 중단·수동 종료·자동 종료 경로도 대기 철회 요청을 같은 트랜잭션에서 무효화해야 한다.
- 전체 철회 승인은 다수 회차·홀드·결제·쿠폰을 잠글 수 있어 같은 콘텐츠의 명령 대기 시간이 증가한다.
- 대기 요청의 사유를 바꾸려면 기존 요청이 반려된 뒤 새 `Idempotency-Key`로 요청을 제출해야 하며 별도 수정 API는 없다.
- 클라이언트는 원래 요청 재시도에는 같은 키를, 반려 후 새 요청 세대에는 새 키를 사용해야 한다.
- Redis 캐시 삭제는 MySQL 원자성 범위 밖이므로 실패 관측과 TTL 정리가 계속 필요하다.

### 기존 계약 변경 이유와 영향

- ADR-0100의 `EDIT_INVALIDATED` 모델은 유지하고 무효화 사유에 `CONTENT_WITHDRAWN`만 확장한다. 전체 철회가
  `WITHDRAWN` 원본에 승인 불가능한 활성 수정본을 남기지 않기 위한 변경이며, 기존 `CONTENT_SUSPENDED`,
  `CONTENT_ENDED`의 의미와 처리자 규칙은 바꾸지 않는다.
- 운영 중단·수동 종료·자동 종료 트랜잭션은 새 `PENDING` 철회 요청을 각각 `CONTENT_SUSPENDED`,
  `CONTENT_ENDED`로 무효화하는 단계를 추가한다. 기존 중단·종료의 콘텐츠·수정본·홀드·예약 결과는 바뀌지 않는다.
- 홀드 무효화, 정원 복구, `PENDING` 결제 종결과 `RESERVED` 쿠폰 해제는 기존 계약을 재사용한다. 전체 철회는
  이를 실행하는 새 콘텐츠 비예약 가능 전이일 뿐 상태 의미와 계산식을 바꾸지 않는다.
- 예약 확정의 `content → content_session → capacity_hold` 잠금과 `CONFIRMED` 예약 유지 계약은 바꾸지 않는다.
  전체 철회 승인 경합 결과만 명시적으로 연결한다.

## 전환과 롤백

후속 구현은 새 테이블·상태·제약과 `CONTENT_WITHDRAWN` 수정본 무효화 사유를 순방향 migration으로 추가해야 한다.
현재 전체 철회 요청 API가 없어 이관할 기존 요청 데이터는 없다. `SUSPENDED` 또는 `ENDED` 콘텐츠에 과거
`PENDING` 철회 요청이 존재할 수 없으므로 요청 보정 migration도 필요하지 않다.

배포 뒤 요청·심사 명령을 중지할 수는 있지만 이미 저장한 종결 요청과 감사 사실을 삭제하거나 상태를 되돌리지 않는다.
모델 변경이 필요하면 새 ADR과 전진 migration으로 대체한다. 기존 중단·종료·예약 경로는 새 요청 상태를 이해하는
애플리케이션과 함께 배포해야 한다.

## 검증 방법

다음 조건은 H2가 아닌 MySQL 8 Testcontainers, 서로 다른 DB 연결과 시작 장벽을 사용해 검증한다. 각 경합은 두
실행 순서를 모두 만들고 락 대기 상한 안에 종료되는지 확인한다.

1. 같은 콘텐츠·같은 키·같은 정규화 사유의 동시 요청은 `PENDING` 행과 성공 감사가 각각 한 건이고 두 응답이 같은 요청 ID다.
2. 같은 키를 다른 사유로 재사용하면 `IDEMPOTENCY_KEY_CONFLICT`이고, 서로 다른 키의 동시 요청은 한 건만 생성되며 다른 요청은 `CONTENT_STATE_CONFLICT`다.
3. 최초 요청 반려 뒤 같은 키 재시도는 이전 요청 ID와 최초 생성 결과를 반환하고 새 행·감사를 만들지 않는다. 새 키 재요청은 새 ID로 생성되며 이전 반려 사유·처리자·시각이 보존된다.
4. 같은 요청의 동시 승인, 같은 사유의 동시 반려와 순차 재시도는 종결 행·성공 감사·부수 효과를 한 번만 만든다.
5. 승인과 반려 경합은 `APPROVED` 또는 `REJECTED` 하나로 끝나며, 반려가 이기면 콘텐츠·수정본·홀드·정원·결제·쿠폰이 바뀌지 않는다.
6. 승인과 수정본 승인·반려·철회 경합은 수정본 터미널 전이 하나만 만든다. 전체 철회가 이기면 사유
   `CONTENT_WITHDRAWN`의 `EDIT_INVALIDATED`와 수정본 감사가 한 건이고, 수정본 명령이 이기면 그 결과를 유지한다.
7. 대기 요청과 중단·수동 종료·자동 종료 경합에서 수명주기 전이가 이기면 요청은 정확한 사유의
   `INVALIDATED`가 되고, 전체 철회 승인이 이기면 콘텐츠는 `WITHDRAWN`이며 다른 전이는 적용되지 않는다.
8. 승인과 홀드 생성 경합에서 승인 뒤 `ACTIVE` 홀드가 남지 않고, 생성된 홀드가 있으면 정원이 정확히 한 번 복구된다.
9. 승인과 예약 확정 경합에서 승인 선행 시 확정이 충돌하고, 확정 선행 시 `CONFIRMED` 예약과 `CONSUMED` 홀드를 유지한다.
10. 여러 활성 홀드, 연결된 `PENDING` 결제와 `RESERVED` 쿠폰을 준비해 승인하면 각 홀드·정원·결제·쿠폰과 이력이 한 번만 종결된다.
11. 요청 상태, 콘텐츠, 수정본, 로그, 성공 감사, 홀드, 정원, 결제, 결제 멱등, 쿠폰 이력의 각 저장 단계에 예외를 주입하면 전체 MySQL 변경이 롤백된다.
12. 기존 `CONFIRMED` 예약, 회차, 방문, 후기와 불변 가격 스냅샷은 승인 전후 동일하다.
13. DB CHECK가 상태별 필수·null 조합을 거부하고, 활성 요청 생성 컬럼 유일 제약이 콘텐츠당 `PENDING` 두 건을,
    `(content_id, idempotency_key_hash)` 유일 제약이 같은 콘텐츠의 키 재사용 행을 거부한다.

문서 검증은 #789 Acceptance Criteria, 관련 API 색인 링크, ADR 번호·링크와 `git diff --check`를 확인한다.

## 대체 조건

- 운영자가 심사 전 요청을 취소하거나 대기 요청의 사유를 수정해야 한다는 제품 요구가 채택된다.
- 콘텐츠당 여러 독립 철회 요청을 병렬 심사해야 한다.
- 전체 철회 승인에서 MySQL 밖의 외부 결제 취소·환불을 원자적으로 보장해야 한다.
- 잠금 대기와 승인 트랜잭션 시간이 합의한 운영 목표를 지속적으로 위반한다는 MySQL 측정 근거가 누적된다.
- `SUSPENDED` 콘텐츠 재개 정책이 채택되어 무효화된 철회 요청의 재사용 여부를 새로 결정해야 한다.
