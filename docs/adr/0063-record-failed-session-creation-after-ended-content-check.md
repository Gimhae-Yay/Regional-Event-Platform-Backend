# ADR-0063: 종료된 콘텐츠 확인 뒤 거부된 회차 생성 요청의 실패 감사를 기록한다

- 상태: 채택됨
- 기록 유형: 후속
- 기록일: 2026-08-05
- 결정일: 2026-08-05
- 관련 요구사항: [추가 회차 생성](../api/p0/content-catalog/session-create.md), [감사 정규화 규칙](../erd.md#감사-정규화-규칙)
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: #383
- 대체하는 결정: [ADR-0060](0060-serialize-content-ending-and-session-creation-with-content-lock.md#결정)의 회차 생성 요청이 `ENDED` 콘텐츠를 확인한 뒤 거부될 때 감사 기록을 만들지 않는 범위. `content` 선점 잠금, 잠금 획득 뒤 상태 재확인, 종료와 회차 생성의 직렬화 결정은 대체하지 않는다.

## 맥락

ADR-0060은 콘텐츠 종료와 추가 회차 생성이 같은 `content` 행을 잠가 순서를 보장하도록 정했다. 그러나 회차 생성이 잠금을 얻은 뒤 이미 `ENDED`인 콘텐츠를 확인한 경우, 회차·`content_log`·성공 감사가 생성되지 않는다는 사실과 인증된 운영자의 거부 요청을 어떻게 감사할지는 분리해 정하지 않았다.

종료와 회차 생성이 경합한 결과는 운영자가 재현하거나 원인을 추적해야 하는 거부 결과다. 반면 요청 본문을 해석하지 못했거나 인증되지 않았거나 존재하지 않는 콘텐츠는 안전한 콘텐츠 상태를 확인한 뒤 거부한 사건이 아니므로 같은 감사 대상으로 삼을 수 없다. 스케줄러가 오래된 종료 후보를 다시 확인한 뒤 건너뛰는 것은 시스템의 정상적인 후보 무효화이며 요청 실패가 아니다.

## 결정 동인과 반드시 지킬 조건

- `ENDED` 콘텐츠를 잠금 획득 뒤 확인한 인증된 운영자의 추가 회차 생성 거부는 한 건의 실패 감사로 남겨야 한다.
- 거부 경로에서는 콘텐츠 상태가 바뀌지 않으므로 `content_log`를 만들지 않고, 회차가 생성되지 않으므로 성공 감사를 만들지 않아야 한다.
- 실패 감사는 원래 회차 생성 트랜잭션이 롤백된 뒤 독립 트랜잭션으로 기록해야 한다.
- 감사 본문은 [ERD](../erd.md#감사-정규화-규칙)의 비개인 정보 규칙과 허용 `target_type`을 따라야 한다.
- 잘못된 JSON, 미인증 요청, 존재하지 않는 콘텐츠, 스케줄러의 오래된 후보 건너뛰기는 실패 감사 대상에서 제외해야 한다.

## 결정

추가 회차 생성에서 인증과 운영자 권한 검증을 통과한 요청이 `content` 행의 `PESSIMISTIC_WRITE` 잠금을 얻은 뒤 `content.status = ENDED`를 확인하면, 회차를 만들지 않고 기존 `404 NOT_FOUND` 응답으로 거부한다. 이때 원래 트랜잭션의 롤백이 끝난 뒤 독립 트랜잭션으로 실패 감사 이벤트 한 건을 기록한다.

실패 감사 이벤트는 다음 값을 사용한다.

| 항목 | 값 |
| --- | --- |
| 대상 | `target_type = CONTENT`, `target_id = contentId`, `region_id = content.region_id` |
| 처리자 | `actor_kind = USER`, `actor_role = OPERATOR`, 활성 운영자만 `audit_event_actor_link`로 연결 |
| 요청 식별자 | 서버가 발급한 해당 요청의 `request_id` |
| 상태와 결과 | `previous_state = ENDED`, `next_state = NULL`, `result = FAILURE` |
| 실패 코드 | `reason_code = NOT_FOUND` |

이 실패는 상태 전이가 아니므로 `content_log`와 성공 감사 이벤트를 만들지 않는다. 감사 기록 자체가 실패해도 이미 결정된 `404 NOT_FOUND` 응답이나 원래 롤백 결과를 성공으로 바꾸거나 재시도하지 않으며, 구조화 로그로만 관찰한다.

잘못된 JSON, 미인증 요청, 존재하지 않는 콘텐츠, 잠금 전에 거부되는 권한·입력 검증 실패에는 실패 감사를 기록하지 않는다. `endBySystem`과 같은 자동 종료 경로에서 오래된 후보가 현재 종료 조건을 만족하지 않아 건너뛰는 경우도 정상 결과이므로 실패 감사를 기록하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 콘텐츠 종료와 회차 생성의 경합으로 인증된 운영자 요청이 거부된 사실을 `request_id`, 대상, 처리자, 확인 상태와 실패 코드로 추적할 수 있다.
- 상태 변경 기록인 `content_log`, 성공 감사, 실패 감사를 서로 다른 사실로 유지한다.
- ADR-0060의 잠금·상태 재확인 규칙을 유지하면서 실패 감사의 트랜잭션 경계를 명확히 한다.

### 수용하는 단점과 위험

- 실패 감사는 원래 트랜잭션과 원자적으로 커밋되지 않으므로 감사 저장 실패 시 거부 사건이 누락될 수 있다.
- `NOT_FOUND`가 존재하지 않는 콘텐츠와 종료된 콘텐츠를 외부 응답에서 구분하지 않으므로, 운영 추적은 감사 이벤트의 대상과 `previous_state`로만 구분한다.

## 전환과 롤백

스키마 변경이나 기존 감사 데이터 이관은 필요 없다. 회차 생성 구현과 명세에 이 실패 감사 경로를 연결하고, 감사 저장 실패는 구조화 로그로 관찰한다.

문제가 발생하면 실패 감사 생성만 중단할 수 있으며, ADR-0060의 잠금·상태 확인과 회차 생성 거부 규칙은 그대로 유지한다. 이미 기록된 감사 이벤트는 추가 전용이므로 삭제하거나 수정하지 않는다. 감사 대상 또는 실패 코드 정책을 바꾸려면 이 ADR을 대체하는 후속 ADR을 작성한다.

## 검증 방법

- 인증된 `OPERATOR`가 종료와 경합한 뒤 잠금 획득 후 `ENDED`를 확인하면 `404 NOT_FOUND`, 회차 미생성, `content_log` 미생성, 성공 감사 미생성과 실패 감사 한 건을 검증한다.
- 실패 감사가 `CONTENT`, 콘텐츠 ID, 지역, `request_id`, `USER`·`OPERATOR`, `ENDED`, `FAILURE`, `NOT_FOUND`를 기록하고 actor link를 가진 것을 검증한다.
- 잘못된 JSON, 미인증 요청, 존재하지 않는 콘텐츠, 잠금 전 권한·입력 검증 실패에는 실패 감사가 없는 것을 검증한다.
- 자동 종료가 오래된 후보를 건너뛰는 경우 실패 감사가 없는 것을 검증한다.
- 실패 감사 저장이 실패해도 원래 회차 생성 트랜잭션의 롤백과 `404 NOT_FOUND` 응답이 바뀌지 않는 것을 검증한다.

## 대체 조건

- 종료된 콘텐츠 거부 외의 실패 감사 범위를 추가하거나, 외부 응답의 오류 코드를 세분화해야 할 때
- 감사 저장의 누락 허용이 감사·운영 요구를 만족하지 않을 때
- 자동 종료 후보 건너뛰기를 실패 사건으로 재정의하는 제품 요구가 확정될 때
