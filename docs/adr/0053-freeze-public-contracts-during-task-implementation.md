# ADR-0053: Task 구현 중 공개 계약을 변경하지 않고 결함을 별도 Bug Issue로 분리한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-01
- 결정일: 2026-08-01
- 관련 요구사항: [Java 코드 컨벤션의 도메인과 API 경계](../code-convention.md#33-도메인과-api-경계), [응답·오류 공통 계약](../api/common/response-and-error.md)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

기존 코드 컨벤션은 새 공개 계약을 구현 전에 갱신하도록 했지만, 구현 Task에서 계약 문서까지 변경하면 이슈의 승인된 범위와 구현 범위가 함께 변한다. 이 경우 발견된 계약 오류의 원인과 수정 범위를 분리하기 어렵고, 구현 중 정책을 선점할 위험이 있다.

사용자는 구현 Task가 이미 확정된 공개 API·오류 계약만 구현하고, 구현 중 확인된 계약 결함은 별도 Bug Issue로 관리하기로 결정했다.

## 결정 동인과 불변 조건

- 구현 Task는 승인된 이슈와 이미 확정된 공개 계약을 벗어나지 않는다.
- 구현 중 공개 계약 문서와 코드를 함께 변경해 결함을 숨기지 않는다.
- 재현 가능한 결함만 Bug Issue 후보로 삼고, 원인이 불명확하면 먼저 조사한다.
- 원격 Bug Issue 생성은 `issue-create`의 사용자 승인 절차를 따른다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 구현 Task에서는 확정된 계약만 구현하고 계약 결함은 별도 Bug Issue로 분리 | 이슈 범위와 공개 계약 변경을 분리하고 결함의 재현 근거를 보존한다. | 새 계약이 필요하면 구현을 즉시 끝낼 수 없고 별도 확정 절차가 필요하다. | 낮음 | 사용자가 선택했으며 MVP 구현 범위를 통제하기에 적합하다. |
| 2 | 구현 Task에서 계약 문서와 코드를 함께 갱신 | 계약과 구현을 한 번에 반영할 수 있다. | 구현 중 정책·API 범위가 확장되고 결함과 기능 변경이 섞일 수 있다. | 중간 | 승인된 Task 범위를 고정하려는 현재 운영 방식에 맞지 않는다. |

## 결정

Task 구현은 이미 확정된 공개 API·오류 계약만 대상으로 한다. 구현 중 새 공개 계약이나 기존 계약의 변경 필요가 드러나면 해당 Task에서 계약 문서와 코드를 변경하지 않고, 근거와 영향을 보고한다.

재현 가능한 계약 결함은 `issue-create` 절차로 Bug Issue 초안을 만들고 사용자 승인 뒤 원격 이슈로 생성한다. 현재 스프린트 배정은 생성 시점의 GitHub Project 설정과 사용자 승인을 확인해 반영한다. 원인이 불명확한 오류는 Bug Issue로 단정하지 않고 `troubleshooting`으로 재현과 원인을 먼저 확인한다.

새 공개 계약이 필요한 기능은 구현 Task를 시작하기 전에 별도 정책·문서 절차에서 계약을 확정한 뒤 새 Task로 구현한다. 이 결정은 `ApiResponse` 형식과 전역 `ErrorCode` 소유권을 정한 ADR-0024의 계약 내용은 변경하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 구현 중 계약 범위가 넓어지는 일을 막고 Task의 완료 조건을 안정적으로 유지한다.
- 계약 결함을 재현 근거, 영향, 우선순위와 함께 별도 이슈로 추적한다.
- 미확정 계약을 코드로 선점하지 않는다.

### 수용한 단점과 위험

- 계약 결함이 발견되면 현재 Task의 완료가 지연될 수 있다.
- 새 계약이 필요한 기능은 별도 확정 절차와 후속 Task가 필요하다.
- Bug Issue를 잘못 분류하면 실제 정책 결정이나 환경 장애를 결함으로 처리할 수 있으므로, 재현과 원인 확인이 필요하다.

## 전환과 롤백

코드와 데이터의 이관은 필요 없다. 코드 컨벤션과 Task 구현 절차에서 계약 변경 금지와 Bug Issue 분리 규칙을 함께 적용한다.

이 규칙이 반복적으로 승인 지연이나 중복 이슈를 만들면, 구현 전 계약 확정 절차와 이슈 템플릿의 계약 필드를 보완한다. 구현 중 계약 변경을 다시 허용하려면 이 ADR을 대체하고 API 호환성과 승인 경계를 다시 결정한다.

## 검증 방법

- Task 구현 시 계약 문서와 공개 API·오류 코드 변경이 같은 변경에 포함되지 않는지 확인한다.
- 계약 결함 후보는 재현 조건·기대 결과·실제 결과를 갖춘 Bug Issue 초안으로 분리됐는지 확인한다.
- 원인이 불명확한 실패가 Bug Issue로 바로 생성되지 않고 조사 절차를 거쳤는지 확인한다.
- 원격 Bug Issue가 사용자 승인 없이 생성되지 않는지 확인한다.

## 대체 조건

- 구현 중 계약 변경을 허용하지 않아 MVP 배포 지연이나 중복 작업이 반복적으로 발생한다.
- 이슈 생성 단계에서 공개 계약을 충분히 확정할 수 있도록 이슈 폼과 승인 절차가 바뀐다.
- 외부 클라이언트 호환성을 유지하면서 긴급 계약 변경을 처리할 별도 운영 절차가 확정된다.
