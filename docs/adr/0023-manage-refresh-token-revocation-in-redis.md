# ADR-0023: Refresh Token 폐기를 Redis TTL 블랙리스트로 관리한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-29
- 결정일: 2026-07-29
- 관련 요구사항: [P0 명세](../p0-spec.md#82-설계-원칙)의 Redis 사용 범위, [인증·프로필](../p0/auth-profile.md#fr-01-인증역할지역-권한)의 `PRV-02`, [토큰 갱신 API](../api/p0/auth-profile/refresh.md)의 Redis 계약
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0005](0005-use-jwt-access-and-rotating-refresh-tokens.md)의 Refresh Token 수명주기 저장소 선택과 해시·계열·교체 관계 영속 방식, [ADR-0017](0017-serialize-withdrawal-with-conditional-user-state.md)의 Refresh Token 계열 폐기를 MySQL 트랜잭션 안에서 처리하고 외부 I/O를 배제하는 범위

## 맥락

ADR-0005는 회전형 Refresh Token의 재사용 탐지와 계열 폐기를 요구했지만, 저장소를 MySQL 관계형
모델로 해석할 수 있는 해시·계열·교체 관계 저장 문구를 남겼다. 그에 따라 ERD에 Refresh Token 테이블을
요구하는 리뷰가 발생했다.

현재 P0의 확정 방향은 Refresh Token 원문·해시·계열을 MySQL에 영속하지 않고, 서명 검증된 JWT의
`jti`, `family_id`, `sub`, 발급·만료 시각을 기준으로 Redis TTL 블랙리스트에서 폐기 상태만 관리하는 것이다.
그러므로 MySQL ERD에 Refresh Token 엔티티를 추가하지 않는다.

탈퇴는 모든 사용자 역참조를 제거해야 한다. 활성 Refresh Token 계열을 모두 찾기 위한 Redis의
사용자→계열 인덱스도 탈퇴 완료 뒤 남겨서는 안 된다. 사용자는 Redis 계열 폐기를 먼저 성공시킨 뒤 MySQL
탈퇴를 커밋하고, 그 사이 MySQL이 롤백되면 기존 세션을 복구하지 않고 재로그인을 요구하는 선택지 1을
채택했다.

## 결정 동인과 불변 조건

- Refresh Token 원문, 해시, 사용자·계열·교체 관계를 MySQL 테이블에 저장하지 않는다.
- Refresh Token 원문·서명 키·`jti`·`family_id`와 Redis 키·값을 로그, 감사 이벤트, 오류 응답에 남기지 않는다.
- 회전된 Refresh Token 재사용은 계열 전체를 즉시 폐기하고 재로그인을 요구한다.
- 로그아웃은 현재 Refresh Token 계열만, 탈퇴·강제 차단·중요 권한 변경은 해당 사용자의 활성 계열 전체를 폐기한다.
- Redis 장애 중에는 폐기 여부를 확인할 수 없는 Refresh Token을 허용하지 않는다.
- 탈퇴 성공 뒤 Redis에 사용자에서 계열로 역참조할 수 있는 키를 남기지 않는다.
- MySQL의 예약 정원·예약·방문 정합성은 Redis에 위임하지 않는다.

## 결정

### Redis 키 계약

Refresh Token JWT에는 예측 불가능한 `jti`, `family_id`, `sub`, 발급 시각과 만료 시각을 넣고 서명·만료를
먼저 검증한다. Redis에는 토큰 원문이나 해시를 저장하지 않고 다음과 같은 논리 키만 둔다. 실제 키 접두사와
직렬화 형식은 구현 설정에서 확정하되, 키의 의미와 TTL은 바꾸지 않는다.

| 논리 키 | 값·용도 | TTL |
| --- | --- | --- |
| 소비된 토큰 `jti` | 회전으로 이미 소비된 `jti`와 계열 식별자 | 해당 Refresh Token의 원래 만료 시각까지 |
| 폐기된 계열 `family_id` | 해당 계열 전체가 폐기됐다는 표지 | 계열에서 아직 유효할 수 있는 Refresh Token 중 가장 늦은 만료 시각까지 |
| 사용자→활성 계열 인덱스 | 활성 `family_id` 집합 | 그 사용자 활성 계열 중 가장 늦은 만료 시각까지 |

`jti`와 `family_id`는 사용자 ID나 개인정보를 포함하지 않는 암호학적으로 예측 불가능한 식별자다.
사용자→활성 계열 인덱스만 활성 계정과 계열을 연결하며, 성공 탈퇴 시 반드시 제거한다. 폐기된 계열 키에는
사용자 ID나 계정 역참조를 넣지 않고 TTL 만료 뒤 자동 삭제한다.

### 회전·로그아웃·재사용 탐지

로그인 시 새 `family_id`를 만들고 사용자→활성 계열 인덱스에 추가한다. 갱신 요청은 Redis의 원자 스크립트로
현재 계열 폐기 여부와 소비된 `jti` 여부를 검사한 뒤, 최초 요청일 때만 기존 `jti`를 소비된 상태로 표시하고
새 Refresh Token을 발급한다. 이 스크립트는 같은 `jti`의 갱신을 직렬화한다. 진행 중인 동시 갱신은
재시도 가능한 인증 충돌로 거부하며, 클라이언트는 Refresh Token 갱신을 단일 비행으로 실행한다.

소비된 `jti`가 다시 제시되면 해당 `family_id`를 폐기하고 재로그인을 요구한다. 계열 폐기는 같은 계열의
소비되지 않은 Refresh Token도 즉시 거부한다. 로그아웃은 현재 `family_id`를 폐기하고 사용자→활성 계열
인덱스에서 해당 계열을 제거한다. 강제 차단과 중요 권한 변경은 사용자→활성 계열 인덱스의 모든 계열을
원자적으로 폐기한 뒤 인덱스를 제거한다.

Redis를 읽거나 쓰지 못하면 로그인에서 Refresh Token을 발급하지 않고, 갱신·로그아웃·강제 폐기는
재시도 가능한 실패로 반환한다. Redis 장애 중 만료되지 않은 Access Token의 자연 만료보다 긴 권한을
부여하지 않으며, Refresh Token만으로 보호 업무 API를 호출할 수 없다.

### 탈퇴 순서와 실패 의미

탈퇴는 먼저 `app_user`의 `ACTIVE → WITHDRAWING` 조건부 갱신으로 MySQL 회원 행 잠금을 얻는다. MySQL
커밋 전에 Redis 원자 스크립트로 해당 사용자의 활성 계열 전체를 폐기하고 사용자→활성 계열 인덱스를 제거한다.
Redis 작업이 실패하면 예외를 전파해 `WITHDRAWING` 전환과 MySQL 도메인 종결을 모두 롤백하고 사용자에게
재시도를 요청한다.

Redis 폐기 성공 뒤에는 활성 홀드·예약·신청·방문·후기·멱등·감사 연결을 정리하고 계정 행을 파기하는 MySQL
변경만 수행한다. 이 단계에서 MySQL이 롤백되면 계정은 남고 `WITHDRAWING` 상태도 롤백되지만, 이미 폐기된
Refresh Token 계열은 복구하지 않는다. 사용자는 다시 로그인해 새 계열을 발급받은 뒤 탈퇴를 재시도한다.
이는 선택지 1에서 명시적으로 수용한 보안 우선의 부분 실패다.

성공 탈퇴 뒤 Redis에는 사용자 ID로 계정을 찾을 수 있는 활성 계열 인덱스가 남지 않는다. 만료 전까지 남는
폐기 계열·소비된 `jti` 키는 무작위 식별자와 TTL만 가지며 MySQL 계정이나 사용자별 안정 가명으로 연결하지
않는다.

ADR-0017의 회원 행 조건부 갱신, MySQL 도메인 종결·연결 제거의 원자성, 실패 시 사용자 재시도 정책은
유지한다. 다만 이 ADR이 정한 Refresh Token 폐기는 위 Redis 선행 단계에만 예외를 둔다.

## 결과와 트레이드오프

### 기대 효과

- MySQL ERD·migration에 Refresh Token 계열과 토큰 해시 테이블을 만들지 않는다.
- Redis TTL로 재사용 탐지와 계열 폐기를 토큰 만료와 함께 자동 정리한다.
- 성공 탈퇴 뒤 Redis의 사용자→계열 역참조를 제거해 계정 파기 정책과 정렬한다.
- Redis 원자 스크립트로 회전·재사용 경합의 최초 처리와 계열 폐기를 한 키 공간에서 판정한다.

### 수용한 단점과 위험

- Redis는 Refresh Token 발급·갱신·폐기의 보안 경로 의존성이 된다. 장애 중 갱신과 로그아웃은 실패하고
  사용자는 재시도해야 한다.
- Redis가 먼저 성공한 뒤 MySQL 탈퇴가 실패하면 활성 계정의 기존 세션이 사라져 재로그인이 필요하다.
- 사용자→활성 계열 인덱스는 계정이 활성인 동안 사용자와 계열을 연결한다. 탈퇴 흐름의 삭제 누락은
  개인정보 역참조가 되므로 통합 테스트와 관측이 필요하다.
- 하나의 Refresh Token을 여러 요청이 동시에 갱신하는 클라이언트는 단일 비행을 지켜야 하며, 갱신 충돌은
  재시도 가능한 인증 실패로 처리한다.

## 전환과 롤백

현재 MySQL Refresh Token 테이블과 migration은 없으므로 데이터 이관은 없다. 구현 전 Redis 원자 스크립트,
TTL 설정, 보안 오류 계약과 사용자→활성 계열 인덱스 정리 순서를 추가한다. 기존에 정의되지 않은 Refresh
Token Redis 키가 운영 환경에 있다면 배포 시 모두 만료시키고 사용자의 재로그인을 요구한다.

전환 중 Redis 오류율 또는 Redis 지연이 허용 기준을 넘으면 새 Refresh Token 발급·갱신을 중지하고 재시도
가능한 인증 오류를 반환한다. 이미 소비되거나 폐기된 `jti`·계열을 활성 상태로 되돌리지 않는다. 구현을
되돌릴 때도 기존 Redis 폐기 키의 TTL이 끝날 때까지 그 키를 읽어 거부를 유지한다. MySQL 저장소나 Outbox로
전환하려면 개인정보 역참조·실패 보상·이관을 포함한 후속 ADR을 작성한다.

## 검증 방법

- 로그인, 정상 회전, 로그아웃, 만료된 토큰 거부와 계열 TTL 정리를 Redis 통합 테스트로 검증한다.
- 이미 소비된 `jti` 재사용이 해당 `family_id` 전체를 폐기하고, 그 계열의 다른 Refresh Token도 거부하는지 검증한다.
- 동시 갱신에서 하나만 최초 처리하고 나머지는 재시도 가능한 인증 충돌 또는 재사용 탐지 결과를 받는지 검증한다.
- Redis 장애 시 Refresh Token 발급·갱신·로그아웃을 성공으로 반환하지 않고 보호 업무 API가 Refresh Token을
  직접 허용하지 않는지 검증한다.
- 탈퇴에서 Redis 실패 시 MySQL의 `WITHDRAWING` 전환과 모든 도메인 변경이 롤백되는지 검증한다.
- Redis 폐기 성공 뒤 MySQL 예외를 발생시켜 계정은 유지되지만 기존 Refresh Token이 거부되고 새 로그인 뒤
  탈퇴를 재시도할 수 있는지 검증한다.
- 성공 탈퇴 뒤 사용자→활성 계열 인덱스가 없고, Redis·MySQL 로그에 토큰 원문·`jti`·`family_id`·사용자
  식별자가 남지 않는지 검증한다.
- 소비·계열 폐기·Redis 오류·탈퇴 인덱스 제거 실패 건수를 비개인 지표로 관측하고, Redis 오류율과 갱신
  거부율의 급증에 경보를 설정한다.

## 대체 조건

- Redis의 가용성·지연·데이터 손실 특성이 Refresh Token 갱신 보안 경로의 합의된 운영 한계를 지속적으로 넘는다.
- 여러 리전 또는 외부 IdP 도입으로 단일 Redis 키 공간의 계열 폐기·TTL 계약을 유지할 수 없다.
- 탈퇴에서 Redis 선행 폐기 뒤 MySQL 롤백으로 발생한 강제 재로그인 비율이 수용 가능한 수준을 넘는다.
- 법적·보안 요구가 Refresh Token 폐기 증적을 Redis TTL보다 오래 관계형 또는 변경 불가 저장소에 보관하도록 요구한다.
