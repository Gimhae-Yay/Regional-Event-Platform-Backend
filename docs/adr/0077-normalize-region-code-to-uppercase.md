# ADR-0077: 지역 코드를 대문자 정규형으로 저장

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-07
- 결정일: 2026-08-07
- 관련 요구사항: [전체관리자](../p1/platform-admin.md)의 `P1-FR-09`, `ADM-02`
- 관련 단계: 단계 3. 확장 의사결정
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

P0 `region.region_code`는 유일한 시스템 지역 코드지만 허용 문자, 대소문자와 비교 정규형이 확정되지 않았다.
P1 전체관리자가 지역을 생성할 때 `JEONJU`, `jeonju`, `JeonJu`를 서로 다른 코드로 취급하면 애플리케이션과
MySQL collation의 비교 결과가 어긋날 수 있다. 반대로 관리자 입력을 대문자로 정규화하면 단일 저장형을 유지할 수
있지만 서버가 요청값을 바꾸는 규칙을 공개 API 계약으로 명시해야 한다.

## 결정 동인과 불변 조건

- 같은 영문 코드의 대소문자 변형은 하나의 지역 코드로 취급해야 한다.
- 입력·저장·응답·유일성 검사가 하나의 정규형을 사용해야 한다.
- 로케일과 Unicode 대문자 변환에 따라 저장 결과가 달라지지 않아야 한다.
- 공백, 비 ASCII 문자, 밑줄, 연속 하이픈과 끝 하이픈을 코드로 허용하지 않는다.
- 동시 생성 요청의 최종 중복 방지는 `region(region_code)` 유일 제약이 담당한다.

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 추천안: ASCII 형식 검증 뒤 `Locale.ROOT` 대문자로 정규화 | 관리자 입력 편의와 단일 저장형을 함께 확보하고 대소문자 중복을 막는다. | 서버가 입력 대소문자를 바꾸므로 계약과 응답에서 정규형을 명확히 알려야 한다. | 중간. 입력 검증과 기존 데이터 확인이 필요하다. | 전체관리자가 직접 입력하는 P1 운영 API에 가장 적합하다. |

## 결정

지역 생성 API는 `regionCode`를 다음 순서로 처리한다.

1. 입력의 앞뒤 공백을 제거한다.
2. 1자 이상 50자 이하이고 `^[A-Za-z][A-Za-z0-9]*(?:-[A-Za-z0-9]+)*$`를 만족하는지 검증한다.
3. 검증된 ASCII 값을 `Locale.ROOT` 기준 대문자로 변환한다.
4. 변환 결과가 `^[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)*$`를 만족하는 정규형인지 확인한다.
5. 정규형을 `region.region_code`에 저장하고 모든 API 응답에서도 같은 값을 반환한다.

예를 들어 ` jeonju `는 `JEONJU`, `Gyeonggi-do`는 `GYEONGGI-DO`로 저장한다. `서울`, `JEON_JU`,
`JEON--JU`, `JEONJU-`는 `400 INVALID_INPUT`으로 거부한다. 정규화된 값이 기존 `region_code`와 충돌하면
`409 REGION_CODE_ALREADY_EXISTS`를 반환한다. 같은 정규형으로 수렴하는 동시 요청은 유일 제약으로 하나만
성공시킨다.

## 결과와 트레이드오프

### 기대 효과

- 대소문자가 다른 논리적 중복 지역 코드를 만들 수 없다.
- DB collation에 의존하지 않고 애플리케이션의 지역 코드 비교 기준을 설명할 수 있다.
- 생성 응답과 이후 조회 응답이 항상 같은 정규형을 반환한다.

### 수용한 단점과 위험

- 클라이언트가 보낸 원래 대소문자는 보존하지 않는다.
- 영문 외 행정구역 표기는 `region.name`에만 둘 수 있다.
- 하이픈 외 구분자가 필요한 새 코드 체계는 현재 정규식으로 표현할 수 없다.

## 전환과 롤백

P1 지역 생성 API 구현 전에 기존 `region.region_code`가 정규형을 만족하는지 검사한다. 정규형으로 변환했을 때
충돌하는 기존 값이 있으면 자동 이관하지 않고 배포를 중단해 데이터를 정리한다. 충돌이 없으면 비정규 기존 값을
대문자 정규형으로 한 번 이관한 뒤 API를 활성화한다.

정규화 도입을 중단해도 이미 저장된 대문자 코드는 엄격한 대문자 입력 계약과 호환된다. 대소문자 보존이나 다른
문자 체계로 바꾸려면 이 ADR을 수정하지 않고 후속 ADR에서 기존 코드·외부 참조·캐시 키의 이관과 호환 정책을 정한다.

## 검증 방법

- 대문자·소문자·혼합 대소문자 입력이 같은 대문자 정규형으로 저장·응답되는지 확인한다.
- 비 ASCII 문자, 밑줄, 연속·끝 하이픈, 빈 값과 50자 초과 입력이 `400 INVALID_INPUT`인지 확인한다.
- 같은 정규형으로 수렴하는 순차·동시 생성 요청에서 하나만 성공하고 나머지는 `409`인지 확인한다.
- 생성, 전체 지역 조회와 공개 여부 변경 응답이 모두 저장된 정규형을 반환하는지 확인한다.
- 배포 전 기존 데이터 정규형 검사에서 충돌을 발견하면 이관과 API 활성화가 중단되는지 확인한다.

## 대체 조건

- 외부 행정구역 표준이 소문자, 밑줄, 비 ASCII 문자 또는 별도 코드 체계를 요구한다.
- 지역 코드가 사용자 입력이 아닌 외부 시스템의 불변 원문 식별자로 바뀐다.
- 정규화로 인해 외부 연동이나 캐시 키 호환성 문제가 관측된다.
