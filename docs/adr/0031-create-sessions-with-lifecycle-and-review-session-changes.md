# ADR-0031: 회차는 상태 전이로 생성하고 일정 변경만 별도 심사한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-30
- 결정일: 2026-07-30
- 관련 요구사항: [지역·콘텐츠 카탈로그](../p0/content-catalog.md), `FR-03`, `FR-04`, `AUTH-01`, `SES-01`, `SES-02`
- 관련 단계: 단계 0. 정책·계약 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

콘텐츠는 `APPROVED` 또는 `PUBLISHED` 상태를 유지한 채 여러 회차를 운영할 수 있다. 운영자는 승인된 콘텐츠에
새 회차를 추가할 수 있어야 하고, 이미 공개된 이번 주 금·토 회차를 다음 주 금·토로 바꾸고 싶을 수 있다.

새 회차는 아직 실제 운영 일정이 없으므로 `content_session`을 `PENDING`으로 만든 뒤 지역 관리자 승인으로
`SCHEDULED`로 전이하면 충분하다. 반면 이미 `SCHEDULED`인 회차를 직접 바꾸면 심사 중에도 고객에게 보이는 일정과
예약 대상이 바뀌고, 반려됐을 때 기존 일정을 안전하게 복구하기 어렵다.

따라서 생성과 수정은 같은 후보 저장 모델이 아니다. 생성은 실제 회차의 상태 전이로 처리하고, 수정만 현재 회차와
분리된 후보를 보관해야 한다.

## 결정 동인과 불변 조건

- 공개·예약 대상은 `PUBLISHED` 콘텐츠의 `SCHEDULED` 회차만이어야 한다.
- `PENDING` 생성 회차는 공개·예약 대상이 아니며, 승인된 뒤에만 실제 운영 회차가 된다.
- 수정 요청 심사 중·반려 후에도 기존 `SCHEDULED` 회차와 콘텐츠 `APPROVED`·`PUBLISHED` 상태가 유지돼야 한다.
- 수정 승인으로 기존 회차를 바꿀 때 예약·홀드·정원 정합성을 보장해야 한다.
- 콘텐츠가 `PENDING`이면 최초 콘텐츠·회차 심사 범위를 유지하고 회차만 따로 생성·수정하지 않는다.
- 모든 생성·심사와 승인에 따른 실제 회차 변경은 감사 기록과 같은 트랜잭션으로 확정해야 한다.

## 결정

1. `content_session`은 실제 회차와 생성 심사 상태를 함께 보관한다. 추가 회차 생성 시 소프트 삭제되지 않은
   `APPROVED` 또는 `PUBLISHED` 콘텐츠에 `PENDING` 회차를 만들고 `remaining_capacity = capacity`로 초기화한다.
2. 지역 관리자가 생성 회차를 승인하면 `PENDING → SCHEDULED`, 반려하면 `PENDING → REJECTED`로 전이한다.
   `PENDING`·`REJECTED` 회차는 공개·예약 대상이 아니다.
3. 콘텐츠가 `PENDING`이면 최초 회차를 콘텐츠 승인 요청과 함께 완성하고, 별도 회차 생성·수정 API는 허용하지 않는다.
   최초 회차의 `PENDING → SCHEDULED` 전이는 콘텐츠 승인과 같은 심사 흐름에서 처리한다.
4. `session_revision`은 기존 `SCHEDULED` 회차의 수정 후보만 보관한다. 수정본은 대상 회차와 요청 시점의
   `base_session_version`, 후보 일정·체크인 창·정원을 가진다. 생성 요청에는 사용하지 않는다.
5. 수정 요청이 `PENDING`인 동안 기존 회차의 일정·정원·공개·예약 가능 상태는 그대로 유지한다. 요청 상태는
   `PENDING → APPROVED` 또는 `PENDING → REJECTED`만 허용한다.
6. 수정 승인 시 콘텐츠가 계속 `APPROVED` 또는 `PUBLISHED`이고, 대상 회차가 `SCHEDULED`이며, 버전이 일치하고,
   활성 홀드와 `CONFIRMED` 예약이 없을 때만 후보 값을 기존 회차에 원자적으로 반영한다. 조건을 만족하지 않으면
   승인하지 않고 기존 회차를 유지한다.
7. 회차 생성·승인·반려와 수정 요청 생성·심사, 수정 승인에 따른 실제 회차 변경은 각각 처리자·사유·전후 상태·
   시각을 가진 감사 이벤트와 하나의 트랜잭션으로 커밋한다. 회차 심사·반려 HTTP 계약은 생성·수정 요청 API와
   분리해 후속 명세로 확정한다.

## 결과와 트레이드오프

### 기대 효과

- 새 회차는 실제 `content_session`을 바로 만들되 심사 전에는 `PENDING`으로 격리할 수 있다.
- 수정 요청이 반려돼도 기존 이번 주 회차와 콘텐츠 `APPROVED`·`PUBLISHED` 상태가 그대로 유지된다.
- 예약·활성 홀드가 있는 회차를 일정 변경으로 조용히 이동시키지 않아 예약 정합성을 보존한다.

### 수용하는 단점과 위험

- 회차 생성 심사와 수정 심사의 저장 모델·목록은 구분된다.
- 심사 대기 중에도 기존 회차의 예약을 계속 받으므로, 승인 시점에 새 예약·홀드가 생기면 변경안을 승인할 수 없다.
- 예약이 있는 회차를 다른 날짜로 옮기려면 P0에서는 회차 취소 정책을 사용해야 하며 자동 이전하지 않는다.

## 전환과 롤백

- `content_session` 상태 카탈로그에 `PENDING`, `REJECTED`를 추가하고, 수정 전용 `session_revision` 테이블을 추가한다.
- 기존 `SCHEDULED` 회차는 상태와 일정이 바뀌지 않는다. 새 정책은 추가 생성·수정 요청부터 적용한다.
- 배포 전 롤백이 필요하면 새 `PENDING` 회차와 수정 요청 접수를 중단하고 심사 대기 대상을 반려로 종결한다.
  이미 `SCHEDULED`로 승인되었거나 수정이 반영된 회차는 롤백으로 되돌리지 않고 일반 변경·취소 정책으로 처리한다.

## 검증 방법

- `PENDING` 콘텐츠에서는 생성·수정 요청이 거부되고, `APPROVED`·`PUBLISHED` 콘텐츠에서만 소유 운영자가 요청할 수 있는지 확인한다.
- 추가 회차가 `PENDING`으로 생성되고 승인 뒤에만 `SCHEDULED`·공개·예약 가능 상태가 되는지 확인한다.
- 수정 요청을 제출한 뒤와 반려한 뒤에 기존 회차의 일정·정원·노출·예약 가능 상태가 불변인지 확인한다.
- 수정 승인 시 버전·콘텐츠 상태·회차 상태·활성 홀드·확정 예약을 같은 트랜잭션에서 다시 검사하는지 확인한다.
- 생성·반려·수정·동시 예약 경합에서 실제 회차, `session_revision`, 감사 이벤트가 함께 원자적으로 확정되는지 통합 테스트로 확인한다.

## 대체 조건

- 예약·홀드를 다른 회차나 다른 일자로 이전하거나, 여러 회차를 하나의 묶음으로 원자 심사해야 하면 이용자 통지·동의와
  정원 처리 규칙을 포함한 후속 ADR로 이 결정을 대체한다.
