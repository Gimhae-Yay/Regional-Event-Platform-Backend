# ADR-0107: 클라우드 성능 fixture는 내부 초기화 API로 재설정한다

- 결정일: 2026-08-17

## 맥락

로컬 k6 실행기가 클라우드 성능 환경을 대상으로 측정할 때, 실행기에서 RDS에 직접 접속해 fixture SQL을 적용하면 MySQL CLI, DB 네트워크 경로 및 삭제 권한을 실행기마다 관리해야 한다. 특히 쓰기 응답시간 러너는 독립 라운드마다 초기 상태를 복원해야 하므로, 실행기 자격 증명의 잘못된 대상 지정은 성능 환경 밖의 데이터 손실로 이어질 수 있다.

사용자는 클라우드 성능 환경이 자신이 사용하는 DB를 스스로 초기화하고, 로컬 실행기는 HTTP로 초기화를 요청한 뒤 k6만 실행하기로 선택했다. 기존 로컬 Docker `Container` 모드는 계속 지원해야 한다.

## 결정 동인과 불변 조건

- 로컬 실행기는 클라우드 DB의 호스트, 포트, 사용자, 비밀번호 또는 MySQL CLI를 요구하지 않는다.
- 초기화는 `k6-local.seed.sql`과 `api-success-coverage-bootstrap.sql`의 고정된 조합만 실행하며, 요청에서 임의 SQL·경로·fixture 이름을 받지 않는다.
- 초기화 API는 기본적으로 등록되지 않으며, 성능 전용 환경에서 명시적 활성화와 별도 비밀 토큰이 모두 있어야 한다.
- 초기화 성공 응답은 두 SQL의 실행과 트랜잭션 커밋 뒤에만 반환한다. 쓰기 러너의 다음 라운드는 이 응답 뒤에 시작한다.
- 초기화 호출 시간은 k6 업무 API 응답시간 집계에 포함하지 않는다.
- 운영 환경에는 API 라우트와 fixture 실행 권한을 활성화하지 않는다.

## 결정

`POST /internal/performance/fixtures/reset`은 성능 전용 설정이 활성화된 경우에만 등록한다. 이 API는 별도 헤더의 비밀 토큰을 상수 시간 비교로 검증하고, 요청 본문 없이 classpath에 패키징된 고정 SQL 두 개를 순서대로 실행한다. 응답은 fixture 식별자와 완료 시각만 포함한다.

실행기는 기존 `Container` 모드를 기본값으로 유지한다. 클라우드 성능 환경을 대상으로 할 때는 API fixture 모드를 명시적으로 선택하고 reset URL과 토큰 환경 변수 이름을 제공한다. 인증 조회 러너는 k6 시작 전에 한 번, 쓰기 러너는 각 독립 라운드 전에 한 번 초기화 API를 호출한다.

## 결과와 트레이드오프

### 기대 효과

- 로컬 실행기는 `BaseUrl`과 초기화 API 토큰만으로 클라우드 성능 측정을 시작할 수 있다.
- 쓰기 API의 각 라운드는 동일한 fixture 상태에서 시작하고, 초기화 작업은 측정 지표와 분리된다.
- DB 자격 증명과 SQL 실행 권한은 성능 환경 서버 내부로 제한된다.

### 수용한 단점과 위험

- 성능 환경 서버는 fixture SQL과 초기화 트랜잭션을 포함하므로, fixture 변경은 애플리케이션 배포와 함께 검증해야 한다.
- API 활성화 설정이나 토큰이 유출되면 성능 환경 데이터가 반복 초기화될 수 있다. 운영 환경·네트워크·비밀을 분리해도 초기화 호출 자체는 감사 로그로 남겨야 한다.
- API 초기화 중 장애가 나면 해당 라운드는 시작하지 않고 실패한다. 자동 재시도는 실행기가 아닌 사용자가 원인을 확인한 뒤 수행한다.

## 전환과 롤백

고정 SQL을 애플리케이션 리소스로 패키징하고, 성능 전용 설정이 참일 때만 초기화 Controller와 Service를 등록한다. 이후 두 k6 러너에 API fixture 모드와 reset 호출을 추가한다.

문제가 생기면 성능 환경에서 초기화 기능을 비활성화하고 러너의 기존 `Container` 또는 명시적 `Rds` 모드로 되돌린다. API는 제품 업무 API와 DB 스키마를 변경하지 않으므로 데이터 이관이나 호환 계층은 필요하지 않다.

## 검증 방법

- 비활성화 환경에서 초기화 Controller가 등록되지 않는지, 활성화 환경에서 토큰 누락·불일치 요청이 거절되는지 MVC 테스트로 확인한다.
- 격리된 MySQL에서 API를 두 번 호출해도 고정 fixture 행의 상태와 수량이 같고, SQL 실행 실패 시 커밋되지 않는지 통합 테스트로 확인한다.
- 읽기 러너가 API 초기화 뒤 한 번 실행되고, 쓰기 러너가 각 라운드 전에 API 초기화 성공을 확인한 뒤에만 k6를 실행하는지 PowerShell 테스트로 확인한다.
- 초기화 감사 로그에는 fixture 식별자·결과·requestId만 남고 토큰·DB 비밀번호·SQL 본문은 남지 않는지 확인한다.

## 대체 조건

- 성능 fixture를 전용 테스트 데이터 서비스가 더 작은 권한 범위와 독립적인 감사·락 체계로 제공하면 이 API를 대체한다.
- 성능 환경이 운영과 DB·네트워크·비밀을 분리할 수 없거나, API 초기화가 운영 배포에 활성화되는 증거가 나오면 이 방식을 중단하고 DB 직접 초기화도 허용하지 않는다.
