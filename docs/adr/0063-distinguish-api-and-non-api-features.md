# ADR-0063: API Feature와 비-API Feature의 생성 범위를 구분한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-04
- 결정일: 2026-08-04
- 관련 요구사항: [이슈 생성 스킬의 이슈 분해 규칙](../../.agents/skills/issue-create/SKILL.md#이슈를-분해하기), [비-API Feature 이슈 양식](../../.github/ISSUE_TEMPLATE/new_non_api_feature.yaml), [저장소의 이슈 생성 라우팅](../../AGENTS.md#스킬-라우팅)
- 관련 단계: 단계 0. 정책·설계 확정
- 관련 이슈: [Task #250](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/250), [PR #252](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/pull/252)
- 대체 대상: 없음

## 맥락

기존 이슈 생성 규칙은 Feature를 확정 API 명세의 HTTP 메서드·경로 조합 하나로만 정의한다. Task는 Feature 또는 Bug의 직속 하위 이슈여야 하므로, API 엔드포인트를 추가하지 않고 재현 가능한 실패도 복구하지 않는 문서·CI·개발 절차 작업은 유효한 부모 이슈를 가질 수 없다. 이러한 작업을 독립 Task로 만들면 Task 계층 규칙을 위반하고, API Feature 아래에 넣으면 부모의 API 범위와 Task의 결과가 일치하지 않는다.

문서·CI·개발 절차 작업을 API Feature에 억지로 포함하지 않으면서도, Task가 하나의 검증 가능한 상위 결과에 기여하도록 비-API Feature의 생성 범위를 정의해야 한다. 비-API Feature는 Task를 담기 위한 빈 컨테이너가 아니라, 기준 문서와 완료 조건으로 독립적으로 검증할 수 있는 프로젝트·플랫폼 역량을 나타내야 한다.

## 결정 동인과 불변 조건

- API Feature는 계속해서 HTTP 메서드·경로 조합 하나와 그 엔드포인트만 정의하는 확정 API 명세 하나를 단위로 생성해야 한다.
- Bug는 실제 결과와 기대 결과가 다른 하나의 재현 가능한 실패를 단위로 생성해야 한다.
- API 엔드포인트 추가나 재현 가능한 실패 복구와 무관한 문서·CI·개발 절차 Task도 같은 저장소의 Feature 또는 Bug를 직속 부모로 가져야 한다.
- 비-API Feature는 원격 커밋에 존재하는 기준 문서, 명확한 포함·제외 범위와 검증 가능한 완료 조건을 가져야 한다.
- Feature의 유형과 Task의 작업 성격을 혼동하지 않아야 한다. `API Feature`와 `비-API Feature`는 모두 GitHub Issue Type `Feature`이고, 직속 하위 Task의 작업 모드는 `work-type` 선택값과 같은 작업 성격 라벨 하나로 판정한다. Feature 이슈 폼의 기본 라벨은 하위 Task의 작업 성격을 결정하거나 상속시키지 않는다.
- 같은 프로젝트·플랫폼 역량이나 같은 완료 조건을 가진 Feature를 중복 생성하지 않아야 한다.

## 결정

Feature를 `API Feature`와 `비-API Feature`로 구분한다. 두 유형은 모두 GitHub Issue Type `Feature`를 사용하고, 하나 이상의 직속 하위 Task로 구현하거나 검증할 수 있다.

`API Feature`는 HTTP 메서드·경로 조합 하나와 그 엔드포인트만 정의하는 확정 API 명세 하나를 단위로 생성한다. 기존 `.github/ISSUE_TEMPLATE/new_feature.yaml`은 API Feature 전용 양식으로 유지한다.

`비-API Feature`는 다음 조건을 모두 만족할 때 생성한다.

1. 만들려는 문서·CI·개발 절차 Task가 API 엔드포인트 추가나 변경에 속하지 않는다.
2. 만들려는 Task가 실제 결과와 기대 결과의 차이를 재현하고 복구하는 Bug에 속하지 않는다.
3. 만들려는 Task가 기존 Feature 또는 Bug의 범위와 완료 조건에 포함되지 않는다.
4. 여러 파일이나 절차의 단순 묶음이 아니라, 완료 후 달라지는 상태를 문서 링크 검사, CI 실행 결과, 명령 출력 또는 절차 점검으로 독립적으로 확인할 수 있다.
5. 범위와 완료 조건을 확정한 기준 문서가 원격 커밋에 존재하고, 포함 범위·제외 범위·검증 방법을 구체적으로 작성할 수 있다.

비-API Feature의 단위인 `프로젝트·플랫폼 역량`은 위 검증 수단으로 완료 여부를 독립적으로 판정할 수 있는 하나의 결과를 뜻한다. 예를 들어 이슈 계층과 개발 절차의 표준화, 통합 테스트를 실행하는 CI 기반, 공통 문서 검증 절차는 각각 완료 상태를 독립적으로 확인할 수 있을 때 비-API Feature가 될 수 있다. 반면 `문서 정리`, `CI 개선`, `기타 개발 작업`처럼 완료 후 상태와 검증 방법을 특정하지 못하는 표현은 비-API Feature로 인정하지 않는다.

비-API Feature는 `.github/ISSUE_TEMPLATE/new_non_api_feature.yaml`로 생성한다. 이 양식은 기준 문서의 원격 커밋 permalink, 현재 문제, 포함·제외 범위, 완료 후 상태, 검증 가능한 완료 조건과 직속 하위 Task를 필수로 받는다. 동일하거나 실질적으로 같은 프로젝트·플랫폼 역량, 완료 조건 또는 기준 문서를 가진 기존 Feature가 있으면 새 Feature를 만들지 않고 기존 이슈의 잔여 범위인지 먼저 판단한다.

Task는 선택한 Feature 또는 Bug 범위의 일부를 하나의 PR 결과로 구현한다. 각 Task에는 `work-type` 선택값과 같은 작업 성격 라벨을 정확히 하나 적용한다. Feature 이슈 폼에 같은 이름의 기본 라벨이 있더라도 그 라벨은 하위 Task로 상속되지 않으며, Task의 작업 성격 선택을 대신하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- API 계약과 무관한 문서·CI·개발 절차 Task도 범위가 일치하는 Feature를 직속 부모로 가질 수 있다.
- API Feature의 엔드포인트 단위 규칙을 완화하지 않고 유지할 수 있다.
- 기준 문서와 완료 조건을 통해 비-API Feature가 단순 작업 묶음인지 독립적인 결과인지 구분할 수 있다.
- Feature의 Issue Type과 완료 조건, 각 Task의 `work-type` 선택값을 서로 다른 기준으로 추적할 수 있다.

### 수용한 단점과 위험

- 이슈 생성 요청마다 API Feature, 비-API Feature와 Bug 중 어느 범주인지 먼저 판정해야 한다.
- 같은 프로젝트·플랫폼 역량을 서로 다른 문장으로 표현하면 중복 검색이 어려울 수 있으므로 제목뿐 아니라 기준 문서와 완료 조건도 비교해야 한다.
- 작은 문서 수정이나 일회성 절차 변경은 독립적인 역량으로 인정되지 않을 수 있다. 이 경우 기존 Feature·Bug 범위에 포함되는지 다시 확인하고, 어느 범위에도 속하지 않으면 이슈 생성 전에 상위 결과를 명확히 정의해야 한다.

## 전환과 롤백

기존 API Feature 양식은 파일 경로를 유지하고 이름과 설명에서 API Feature 전용임을 명시한다. 비-API Feature 양식을 새로 추가한 뒤 이슈 생성 스킬과 Task 구현 스킬이 요청 성격, 부모 유형, 기준 문서와 완료 조건을 검증하도록 갱신한다. 기존 Feature·Bug·Task의 유형이나 부모 관계는 자동으로 변경하지 않는다.

새 양식이 추상적이거나 중복된 Feature를 반복해서 만든다는 증거가 확인되면 비-API Feature 신규 생성을 중단한다. 이미 생성된 이슈는 삭제하지 않고 각각의 범위와 하위 Task를 보존한다. 후속 ADR에서 생성 조건을 강화하거나 다른 계층으로 전환한 뒤 양식과 스킬을 함께 변경한다.

## 검증 방법

- API 엔드포인트 하나의 생성 요청이 `new_feature.yaml`을 선택하고, 확정 API 명세 permalink와 HTTP 메서드·경로 조합을 검증하는지 확인한다.
- API 엔드포인트나 재현 가능한 Bug와 무관한 문서·CI·개발 절차 작업이 `new_non_api_feature.yaml`을 선택하고, 기준 문서 permalink, 포함·제외 범위, 완료 후 상태와 검증 가능한 완료 조건을 요구하는지 확인한다.
- 재현 가능한 실패 복구 요청이 비-API Feature가 아니라 Bug로 분류되는지 확인한다.
- 기존 Feature 또는 Bug 범위에 포함되는 작업이 새 비-API Feature를 만들지 않고 해당 부모의 직속 하위 Task로 제안되는지 확인한다.
- 두 Feature 양식과 Task 양식이 유효한 YAML인지 검사하고, Task에 작업 성격 라벨이 정확히 하나 적용되는지 확인한다.
- 열린 이슈와 닫힌 이슈 전체에서 제목, 기준 문서와 완료 조건을 비교해 중복 비-API Feature 생성을 차단하는지 확인한다.

## 대체 조건

- GitHub가 Feature의 하위 유형이나 사용자 정의 필드를 제공해 API Feature와 비-API Feature를 하나의 양식에서 오해 없이 구분할 수 있게 된다.
- 비-API Feature의 대부분이 직속 하위 Task 하나만 포함하고 별도 상위 결과를 제공하지 않아 계층 유지 비용이 이점보다 커진다.
- 기준 문서와 완료 조건 비교만으로 중복을 안정적으로 찾을 수 없어 별도 식별자나 카탈로그가 필요해진다.
