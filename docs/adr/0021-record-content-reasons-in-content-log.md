# ADR-0021: 콘텐츠 사유를 `content_log`에 추가 전용으로 기록한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-28
- 결정일: 2026-07-28
- 관련 요구사항: [지역·콘텐츠 카탈로그의 `CON-03`](../p0/content-catalog.md#con-03), [지역·콘텐츠 카탈로그의 `CON-06`~`CON-09`](../p0/content-catalog.md#con-06), [P0 명세](../p0-spec.md)의 `FR-04`, `FR-11`, `FR-14`, `AC-11`, `AC-12`, `AC-17`
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0019](0019-use-minimal-content-status-log.md)의 `content_log` 다섯 컬럼 제한, `content` 사유 컬럼 보관 및 소프트 삭제를 로그에서 제외한 범위

## 맥락

ADR-0019는 사용자가 지정한 다섯 컬럼만으로 `content_log`를 구성하고, 중단·철회·삭제 사유는 현재
`content`의 각 사유 컬럼에 유지하도록 했다. 이 방식은 현재 상태와 이력을 분리했지만, 같은 콘텐츠의
사유가 현재 행과 상태 로그로 나뉘고 삭제 이력은 로그에서 빠지는 문제가 있다.

사용자는 사유를 로그에 추가하고 `content`의 사유 관련 컬럼을 제거하도록 지시했다. P0에서 중단·철회는
현재 상태의 최신 로그로 안내할 수 있고, 소프트 삭제는 `deleted_at`만 현재 차단 표지로 유지하면 된다.

## 결정 동인과 불변 조건

- 중단·철회·삭제의 처리자, 사유와 시각은 하나의 추가 전용 `content_log` 행에서 함께 조회해야 한다.
- `content`는 현재 공개 상태와 소프트 삭제 차단을 위한 최소 스냅샷으로 유지한다.
- 소프트 삭제는 `content.status` 전이가 아니며 `deleted_at`으로 현재 삭제 여부를 판정한다.
- 사유가 필요한 콘텐츠 상태 전이와 소프트 삭제는 현재 행 갱신·로그·감사 기록을 같은 MySQL 트랜잭션에서 처리한다.
- 로그의 actor 익명화는 기존처럼 탈퇴 완료 전 `actor_id`만 `NULL`로 갱신한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | `content_log.reason`을 추가하고 삭제는 `DELETED` 로그로 기록 | 상태·삭제의 처리자·사유·시각이 한 행에 모이고 `content` 사유 컬럼을 없앨 수 있다. | `status`에 현재 콘텐츠 상태가 아닌 `DELETED` 이벤트 코드가 추가된다. | 중간. 운영 데이터가 있으면 사유 이관과 삭제 로그 보강이 필요하다. | 사용자가 채택했으며, 추가 테이블·이벤트 유형 컬럼 없이 P0 로그를 단순하게 유지한다. |

## 결정

`content_log`의 컬럼은 `id`, `content_id`, `actor_id`, `status`, `reason`, `date` 여섯 개로 한다.
`reason`은 사유가 없는 생성·승인·자동 공개·종료 로그에서는 `NULL`을 허용하고, `REJECTED`,
`SUSPENDED`, `WITHDRAWN`, `DELETED` 로그에서는 필수다.

상태 전이는 변경 뒤의 `content.status`를 `status`에 기록한다. 소프트 삭제는 `content.status`를 바꾸지 않고
`content.deleted_at`을 설정한 뒤 `status = DELETED` 로그를 추가한다. `DELETED`는 로그 전용 이벤트 코드이며
`content` 상태 카탈로그의 값이 아니다.

`content`에서 `suspension_reason`, `withdrawal_reason`, `deletion_reason`을 제거한다. 방문자에게 표시할 운영
중단·철회 사유는 해당 콘텐츠의 최신 `SUSPENDED` 또는 `WITHDRAWN` 로그의 `reason`에서 파생한다.
`content_revision`의 심사·철회 사유는 수정본 수명주기의 독립 사실이므로 이번 결정으로 변경하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 콘텐츠 상태·삭제 사유가 처리자·시각과 같은 로그 행에 보관된다.
- `content`가 현재 상태, 공개 예정 시각, 소프트 삭제 표지만 가진 더 작은 현재 스냅샷이 된다.
- 소프트 삭제도 콘텐츠 이력 조회에서 빠지지 않는다.

### 수용한 단점과 위험

- `content_log.status = DELETED`는 현재 `content.status`와 다른 로그 전용 코드이므로 조회·검증에서 구분해야 한다.
- 중단 또는 철회가 장차 재개·반복될 경우 방문자 안내는 최신 로그 조회 순서(`date`, `id`)에 의존한다.
- `reason`은 추가 전용이므로 오기 정정은 기존 로그 수정이 아니라 감사 가능한 후속 처리로 남겨야 한다.

## 전환과 롤백

신규 배포 전에는 여섯 컬럼의 `content_log`만 만들고 `content` 사유 컬럼을 만들지 않는다.

이미 운영 DB에 ADR-0019 구조가 배포된 경우에는 콘텐츠 상태 변경·삭제 명령을 잠시 중지한 뒤 다음 순서로 전환한다.

1. `content_log.reason`을 nullable로 추가하고, `content`의 중단·철회 사유를 동일 콘텐츠·상태의 최신 로그에 복사한다.
2. 소프트 삭제 행마다 `deleted_at` 시각, 확인 가능한 처리자와 삭제 사유를 가진 `DELETED` 로그를 보강한다. 처리자를 신뢰성 있게 복원할 수 없으면 `actor_id = NULL`로 기록해 잘못 귀속하지 않는다.
3. 필수 사유 로그의 누락을 0건으로 검증한 뒤 애플리케이션을 여섯 컬럼 로그와 `DELETED` 이벤트 기록으로 전환한다.
4. 전환 검증을 통과한 뒤 `content`의 세 사유 컬럼을 제거한다.

사유 컬럼 제거 전 롤백이 필요하면 명령을 중지하고 최신 `SUSPENDED`·`WITHDRAWN`·`DELETED` 로그의 사유를
각 기존 `content` 컬럼에 역복사한 뒤 이전 애플리케이션 버전으로 전환한다. 제거 후에는 백업에서 컬럼을
복원해야 하므로 단순 롤백으로 간주하지 않으며, 로그가 보존돼 있으므로 전진 수정이 기본 복구 방식이다.

## 검증 방법

- 생성, 반려, 승인, 자동 공개, 중단, 철회, 종료마다 처리자·사유·시각 규칙을 충족하는 로그가 한 건씩 추가되는지 검증한다.
- 중단·철회·삭제에서 `content` 갱신, `content_log` 삽입과 성공 `audit_event`가 함께 커밋되고 어느 하나의 실패에도 모두 롤백되는지 검증한다.
- 소프트 삭제가 `content.deleted_at`만 설정하고 `content.status`는 유지하며, 사유가 있는 `DELETED` 로그를 정확히 한 건 만드는지 검증한다.
- `REJECTED`, `SUSPENDED`, `WITHDRAWN`, `DELETED` 로그의 `reason IS NULL` 건수와 이관 시 사유 불일치 건수가 모두 0인지 관측한다.
- 회원 탈퇴 시 `actor_id`만 제거되고 `status`, `reason`, `date`가 보존되는지 검증한다.

## 대체 조건

- 로그 전용 `DELETED` 코드가 외부 API나 분석 계약에서 현재 상태와 명확히 구분될 수 없게 된다.
- 재개·반복 중단 등으로 사유의 전체 전후 상태를 별도 이벤트 모델로 표현해야 한다.
- 사유의 수정·승인·다국어 관리가 실제 요구가 되어 단일 자유 텍스트 로그로 충족할 수 없다.
