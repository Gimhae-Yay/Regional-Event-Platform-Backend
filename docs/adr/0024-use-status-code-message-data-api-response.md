# ADR-0024: 상태 코드·응답 코드·메시지·데이터 형식으로 HTTP 응답을 통일한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-29
- 결정일: 2026-07-29
- 관련 요구사항: [응답·오류 공통 계약](../api/common/response-and-error.md), [API 공통 규칙](../api/common/api-conventions.md), [P0 명세](../p0-spec.md#7-기능-요구사항과-소유-문서)
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

공통 응답·오류 계약은 `ApiResponse`를 사용하도록 정했지만, 최상위 필드명과 실제 성공·오류 코드는
자리표시자로 남아 있었다. 이 상태에서는 Controller, 전역 예외 처리기와 Spring Security 경계가 서로 다른
본문을 만들 수 있고, 클라이언트도 HTTP 상태만으로 입력 오류의 원인을 안정적으로 구분할 수 없다.

사용자는 본문 HTTP 상태, 메시지와 데이터를 함께 담는 `ApiResponse` 형식을 선택했다. 실패 응답 본문에는
`requestId`를 넣지 않는다. `requestId`는 모든 요청을 서버 로그에서 추적하기 위한 내부 관측 정보로만 둔다.
오류 코드의 공개 문자열·HTTP 상태·메시지는 공통·도메인 구분 없이 전역 `ErrorCode` enum 하나에서 관리한다.

## 결정 동인과 불변 조건

- 본문이 있는 모든 JSON 성공·실패 응답은 같은 네 최상위 필드 순서를 사용한다.
- HTTP 상태와 본문의 `statusCode`는 항상 같아야 한다.
- 클라이언트는 `message`가 아닌 안정적인 `code`로 실패를 분기한다.
- 실패 응답의 `data`는 항상 `null`이며, 내부 예외명·SQL·스택 트레이스·비밀값·개인정보는 노출하지 않는다.
- 데이터 없는 성공은 `data: null`을 사용하고, `204 No Content`는 본문을 만들지 않는다.
- 모든 요청에는 서버가 생성한 `requestId`를 부여해 로그에 남기되 JSON 본문과 응답 헤더에는 노출하지 않는다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | `statusCode`, `code`, `message`, `data`를 가진 `ApiResponse` | HTTP 상태와 업무·입력 오류 코드를 함께 제공하고, 성공·실패 응답을 한 형식으로 직렬화한다. | 본문의 HTTP 상태가 중복되므로 구현과 테스트에서 두 값의 일치를 지켜야 한다. | 중간. 모든 API 클라이언트의 역직렬화 계약을 바꿔야 한다. | 사용자가 선택했으며, 초기 MVP의 공통 응답과 오류 처리를 명확히 한다. |
| 2 | `success` 불리언, 메시지와 데이터만 사용 | 형식이 단순하다. | 같은 HTTP 상태의 서로 다른 실패를 안정적으로 구분하기 어렵고, 메시지 변경이 클라이언트 동작을 깨뜨릴 수 있다. | 중간 | 공통 오류 코드 요구와 맞지 않는다. |
| 3 | 성공은 개별 DTO, 실패는 Spring `ProblemDetail`을 사용 | 표준 오류 표현을 사용할 수 있다. | 성공·실패 응답의 형식이 분리되고 프로젝트의 `ApiResponse` 계약과 맞지 않는다. | 중간 | 현재 공통 응답 방향에 적합하지 않다. |

### 오류 코드 소유 선택

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 전역 `ErrorCode` enum 하나에 공통·도메인 오류를 모두 정의 | 오류 코드·HTTP 상태·메시지의 위치가 하나로 고정되고 `BusinessException`의 타입이 단순하다. | 도메인이 늘면 enum이 커지고 여러 도메인의 변경이 같은 파일에 모인다. | 낮음 | 사용자가 선택했으며 초기 MVP의 오류 목록을 한 곳에서 검토하기 쉽다. |
| 2 | `ErrorCode` 인터페이스와 공통·도메인별 enum을 분리 | 도메인별 코드의 응집도를 높일 수 있다. | 코드 정의 위치가 둘 이상이고 현재 단계에서는 인터페이스와 enum의 역할이 중복된다. | 낮음 | 중앙 관리 정책과 맞지 않는다. |

## 결정

본문이 있는 JSON 응답은 아래 `ApiResponse<T>` 형식을 사용한다.

```java
public record ApiResponse<T>(
    int statusCode,
    String code,
    String message,
    T data
) {
}
```

성공 응답의 `code`는 항상 `SUCCESS`다. 성공 메시지와 `data`의 구체 형식은 API별 명세가 정한다.
`global.error.ErrorCode` enum은 `INVALID_INPUT`, `INVALID_JSON`, `INVALID_TYPE`, `UNAUTHENTICATED`,
`FORBIDDEN`, `METHOD_NOT_ALLOWED`, `INTERNAL_SERVER_ERROR` 등 공통 오류와 이후 도메인 오류를 모두
정의한다. 각 상수는 HTTP 상태, 안정적인 기계 판독용 코드와 공개 메시지를 가진다.

`ApiResponse`는 Controller와 전역 HTTP 예외 처리 경계에서만 조립한다. `BusinessException`과 입력·바인딩
예외는 전역 예외 처리기가 `ErrorCode`로 변환한다. 도메인과 Service는 필요한 `ErrorCode`를 가진
`BusinessException`만 던지며, 오류 코드별 예외 하위 타입이나 도메인별 오류 enum은 만들지 않는다. Spring
Security의 인증·인가 오류도 같은 형식으로 직렬화한다.

`toResponseEntity(String accessToken)`은 로그인이나 토큰 갱신처럼 Access Token을 발급하는 HTTP 경계에서만
사용하며, `Authorization: Bearer <accessToken>` 응답 헤더를 추가한다. Refresh Token 전달 방식은 인증 API를
구현하기 전에 별도 인증 API 명세에서 정한다.

## 결과와 트레이드오프

### 기대 효과

- 클라이언트가 HTTP 상태와 별도로 실패 원인을 `code`로 안정적으로 분기할 수 있다.
- Controller, 전역 예외 처리기와 이후 Spring Security 오류 경계가 같은 본문을 사용한다.
- 데이터가 없는 성공·실패의 `data: null` 의미가 일관된다.

### 수용한 단점과 위험

- 본문의 `statusCode`가 HTTP 상태를 중복한다. 직접 레코드를 생성하지 않고 팩터리와 `toResponseEntity()`를
  사용하며 HTTP 테스트로 일치를 검증한다.
- 검증 오류의 개별 필드·다건 상세는 현재 응답에 제공하지 않는다. 필드 상세가 필요해지면 공통 계약, ADR과
  클라이언트 호환성 검토를 먼저 갱신해야 한다.
- 응답 본문에 `requestId`가 없으므로 사용자 문의와 서버 로그를 직접 연결하는 외부 추적 기능은 제공하지 않는다.
- 도메인 수가 증가하면 전역 `ErrorCode` enum의 상수 수가 늘고 여러 도메인의 변경이 같은 파일에 모인다.

## 전환과 롤백

신규 구현이므로 기존 API 클라이언트나 응답 데이터를 이관하지 않는다. 공통 응답과 전역 `ErrorCode` enum을
먼저 구현하고, 도메인 API를 추가할 때 필요한 오류 상수를 같은 enum에 추가한다.

클라이언트 출시 뒤 응답 형식을 바꾸어야 하면 기존 네 필드를 유지하는 호환 기간을 두거나 새 API 버전을
도입한다. 오류 상세나 `requestId` 노출을 추가하는 경우에도 새 필드의 포함 조건과 개인정보 영향을 검토한
후 별도 ADR로 결정한다.

## 검증 방법

- 성공, 데이터 없는 성공, 공통 오류와 처리되지 않은 예외에서 HTTP 상태와 본문 `statusCode`가 같은지 HTTP
  테스트로 검증한다.
- 검증·역직렬화·타입 변환 오류가 각각의 공통 `code`와 일반화된 메시지로 응답하고 내부 정보가 노출되지 않는지
  검증한다.
- 인증·인가 오류를 구현할 때도 같은 네 필드 응답을 사용하는지 보안 통합 테스트로 검증한다.
- 모든 요청의 서버 로그에 `requestId`가 남고 JSON 본문과 응답 헤더에는 없는지 검증한다.
- `BusinessException`이 전역 `ErrorCode`만 받고 `CommonErrorCode` 또는 도메인별 오류 enum 참조가 없는지
  소스 검색과 전체 빌드로 검증한다.

## 대체 조건

- 클라이언트가 RFC 9457 Problem Details 상호운용성을 요구한다.
- 검증 오류에서 필드별·다건 상세가 필요해져 현재의 일반화된 메시지로 충분하지 않다.
- 운영 지원에 응답 본문 또는 헤더로 `requestId`를 노출해야 할 명확한 요구가 생긴다.
- 전역 `ErrorCode` enum이 여러 도메인의 동시 변경 병목이나 코드 소유권 혼란을 반복적으로 만든다.
