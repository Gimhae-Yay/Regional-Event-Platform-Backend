# ADR-0055: 사업자 정보 암호화 전환을 운영자 재신청 구현 뒤로 분리한다

- 상태: 채택
- 기록 유형: 대체
- 기록일: 2026-08-02
- 결정일: 2026-08-02
- 관련 요구사항: [FR-01 인증·역할·지역 권한](../p0/auth-profile.md#fr-01-인증역할지역-권한), [FR-09 운영자 승인·정보 마스킹](../p0/auth-profile.md#fr-09-운영자-승인정보-마스킹), [AUTH-02](../p0/auth-profile.md#auth-02)
- 관련 단계: 단계 1. 운영자 재신청 구현·검증, 단계 2. 사업자 정보 암호화 전환
- 관련 이슈: #102, [#266 운영자 신청 사업자 정보 암호화 전환](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/266)
- 대체 대상: [ADR-0054](0054-encrypt-business-information-with-aes-gcm.md)의 즉시 적용 시점과 현재 P0 저장 정책 범위

## 맥락

ADR-0054는 사업자 정보를 AES-256-GCM으로 암호화해 보관하는 목표 설계를 정했다. 그러나 이 전환은 회원가입·운영자 재신청·심사용 상세 조회·회원 탈퇴와 기존 평문 행 이관을 함께 바꿔야 한다.

#102의 범위는 반려된 운영자 신청의 재신청 API다. 현재 가입과 신청 모델은 평문 `TEXT` 저장을 사용하므로, 재신청 API와 암호화 전환을 한 작업으로 묶으면 독립 검증·병합이 불가능해지고 암호화 전환 실패가 재신청 기능 전체를 지연시킨다.

## 결정 동인과 불변 조건

- #102는 기존 평문 저장 모델을 재사용해 재신청 상태 전이와 권한·동시성 규칙만 구현한다.
- 평문 여부와 무관하게 사업자 정보는 회원가입·재신청·승인·반려·목록 응답과 애플리케이션·접근 로그, 감사 이벤트, 오류 응답, 지표에 포함하지 않는다.
- 담당 지역의 `REGION_ADMIN`만 [ADR-0036](0036-expose-business-information-only-in-protected-review-detail.md)에 따른 심사용 상세 조회에서 원문을 확인한다.
- 암호화 전환은 #102 이후 독립 이슈와 PR로 회원가입·재신청·심사용 상세 조회·탈퇴·기존 데이터 이관을 함께 완료한다.
- 실제 사업자 정보를 받는 운영 배포 전에는 암호화 전환 이슈를 완료한다.

## 결정

#102은 현재 `operator_application.business_information` 평문 `TEXT` 저장을 그대로 사용한다. AES-GCM 암호화, 키링 설정, 암호화 봉투, 기존 평문 행 이관은 #102에 추가하지 않는다.

ADR-0054의 AES-256-GCM 목표 설계는 별도 사업자 정보 암호화 전환 이슈에서 구현한다. 이 이슈는 #102이 병합된 뒤 회원가입·재신청·심사용 상세 조회·회원 탈퇴의 저장·조회 경로와 기존 평문 행을 한 번에 전환한다.

암호화 전환 전에도 ADR-0036의 심사용 상세 조회 인가와 `Cache-Control: no-store`를 유지한다. 사업자 정보 원문은 심사용 상세 조회를 제외한 HTTP 응답과 로그·감사·지표에 포함하지 않는다. 회원 탈퇴 완료 시 모든 신청 상태에서 `business_information`과 `applicant_user_id`를 제거한다.

## 결과와 트레이드오프

### 기대 효과

- #102은 재신청 상태 전이와 동시성 검증에 집중해 독립적으로 병합할 수 있다.
- 암호화 전환은 모든 사업자 정보 생성·조회·삭제 경로와 데이터 이관을 하나의 검증 단위로 다룬다.

### 수용한 단점과 위험

- 암호화 전환 전 DB 접근 권한이 있는 주체에게 사업자 정보 원문이 노출될 수 있다.
- 암호화 전환 이슈가 완료되기 전에는 실제 사업자 정보를 받는 운영 배포를 진행할 수 없다.

## 전환과 롤백

1. #102을 평문 저장 계약으로 구현·검증·병합한다.
2. 별도 이슈에서 ADR-0054의 AES-GCM 암호화, 키링 주입, 기존 행 이관과 전체 경로 회귀 테스트를 구현한다.
3. 기존 평문 행이 없는 것을 검증한 뒤 암호화된 버전으로 운영 배포한다.

암호화 전환 이슈를 시작하기 전 #102을 평문 저장 상태로 유지한다. 암호화 전환 이후에는 평문으로 되돌리지 않고, 키링을 유지한 수정 배포본으로 복구한다.

## 검증 방법

- #102의 재신청 성공·반려 이력·중복 `PENDING` 차단·권한·동시성 테스트가 기존 평문 모델에서 통과하는지 검증한다.
- 심사용 상세 조회만 담당 지역 관리자에게 원문을 반환하고, 다른 응답과 로그·감사·지표에는 원문이 없는지 검증한다.
- 별도 암호화 전환 이슈에서 저장 암호문·복호화 인가·변조 실패·키 교체·기존 행 이관·탈퇴 시 제거를 검증한다.

## 대체 조건

- #102 구현 전에 암호화 전환을 함께 완료해야 하는 운영·보안 요구사항이 확정된다.
- 실제 사업자 정보를 받지 않는 외부 검증 토큰만 보관하도록 신청 계약이 변경된다.
