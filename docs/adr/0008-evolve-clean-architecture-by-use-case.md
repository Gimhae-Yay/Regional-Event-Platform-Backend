# ADR-0008: 도메인 중심 3-Layer에서 유스케이스별로 아키텍처 경계 진화

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-25
- 결정일: 2026-07-25
- 관련 요구사항: [P0 명세](../p0-spec.md)의 인증·예약·체크인·감사 요구사항과 [내부 API 명세서](../api/api-specification.md)의 도메인 계약
- 관련 단계: 단계 0. 정책·설계 확정
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

현재 구현은 애플리케이션 진입점만 존재하며 도메인 코드는 아직 작성되지 않았다.
[코드 컨벤션](../code-convention.md#4-패키지와-소스-구성)은 도메인별로 `controller`, `dto`, `entity`,
`repository`, `service`를 나누는 도메인 중심 3-Layer 구조를 기본으로 하고, 복잡도가 실제로 증가했을 때
Application Service나 Facade 같은 추가 경계를 검토하도록 규정한다.

현재 팀이 Clean Architecture의 계층별 책임과 의존성 역전을 충분히 공유하지 않은 상태에서 엄격한 구조를 전면
도입하면 모든 클래스에 인터페이스를 만들거나
`Controller → Facade → ApplicationService → Service → Port → Adapter`처럼 책임 없이 전달만 하는 계층이
생길 위험이 있다. 반대로 단순한 3-Layer 구조만 고정하면 예약 확정, QR 체크인, 콘텐츠 승인과 자동 공개처럼
권한·멱등성·트랜잭션·여러 저장소·외부 기술을 함께 조정하는 흐름이 하나의 Service에 누적될 수 있다.

초기 MVP의 구현 속도와 학습 비용을 통제하면서도 복잡성이 확인된 흐름에는 명확한 유스케이스 경계와 의존성
역전을 적용할 수 있는 점진적 전략이 필요하다.

## 결정 동인과 불변 조건

- 초기 구현은 팀이 이해하고 일관되게 리뷰할 수 있는 구조여야 한다.
- 최상위 구성은 기술 계층보다 지역, 콘텐츠, 예약, 방문, 후기 같은 업무 도메인을 우선한다.
- Controller는 입력 검증과 변환, 인증 정보 전달, 응답 변환만 담당한다.
- Service는 유스케이스 흐름과 트랜잭션 경계를 담당하고 도메인 규칙은 엔티티, 값 객체 또는 도메인 서비스가
  보호한다.
- QR 서명, 저장소, Redis, S3, 외부 API처럼 구체 기술과의 경계는 핵심 정책에서 분리한다.
- 인터페이스, Application Service와 Facade는 이름이나 계층 수를 맞추기 위해 만들지 않는다.
- 같은 유스케이스를 위한 전달 전용 계층과 순환 패키지 의존성을 허용하지 않는다.
- 구조를 리팩터링하더라도 [ADR-0002](0002-isolate-regions-in-a-shared-schema.md)의 지역·소유 범위 검증을
  Controller에서 끝내거나 생략하지 않는다.
- 구조를 리팩터링하더라도 [ADR-0001](0001-use-mysql-conditional-update-for-capacity-consistency.md)의 정원
  트랜잭션, [ADR-0003](0003-use-persisted-idempotency-for-reservation-and-checkin.md)의 멱등 기록
  원자성, [ADR-0007](0007-use-transactional-outbox-with-spring-scheduler.md)의 거래와 Outbox 저장
  원자성을 훼손하지 않는다.

| 3 | 도메인 중심 3-Layer 구조를 장기적으로 고정 | 구조가 단순하고 초기 개발 속도가 빠르다. | 복합 유스케이스가 Service와 Repository 직접 의존으로 집중되고, 외부 기술 변경과 여러 진입점 추가 시 결합과 테스트 비용이 커질 수 있다. | 중간. 복잡성이 누적된 뒤에는 한 번에 많은 책임과 의존성을 분리해야 한다. | 단순 CRUD에는 적합하지만 예약·체크인·Outbox 흐름까지 고정하기에는 부족하다. |
| 4 | 현재 구조에 인터페이스만 우선 추가 | 파일 이동 없이 의존성 역전 형태를 일부 만들 수 있다. | 책임과 트랜잭션 경계는 그대로인 채 간접 호출과 Mock만 증가한다. 인터페이스의 소비자와 변경 이유가 불분명해진다. | 낮음. 사용하지 않는 인터페이스를 제거하면 된다. | 문제를 해결하지 못하므로 채택하지 않는다. |

## 결정

초기 구현은 코드 컨벤션의 도메인 중심 3-Layer 구조를 따른다. 각 도메인 안에서 Controller, Service,
Repository와 Entity의 책임을 분리하고, 단순 조회와 CRUD에는 추가 아키텍처 계층을 만들지 않는다.

명백한 외부 기술 경계는 초기에도 인터페이스로 격리할 수 있다. QR 서명기, 외부 저장소, 결제사나 외부 API
클라이언트처럼 핵심 정책이 구체 구현에 의존해서는 안 되는 지점이 대상이다. 내부 Service나 도메인 객체에는
대체 구현, 독립된 소비자 또는 테스트 경계가 있다는 이유 없이 인터페이스를 만들지 않는다.

다음 신호가 반복되거나 둘 이상 결합되어 변경·테스트 비용을 실제로 높일 때 해당 유스케이스를 세로 단위
리팩터링 후보로 검토한다. 협력자 수나 클래스 수 하나만으로 전환을 결정하지 않는다.

- 하나의 유스케이스가 여러 Aggregate, Repository 또는 외부 기술을 하나의 트랜잭션 흐름으로 조정한다.
- 권한, 멱등성, 상태 전이, Outbox 저장과 실패 복구가 하나의 Service에 누적된다.
- HTTP Controller, Scheduler, 이벤트 리스너 등 여러 입력 경로가 같은 흐름을 중복 구현한다.
- 비즈니스 규칙을 검증하기 위해 항상 Spring Context나 실제 영속성 구성이 필요하다.
- 다른 도메인의 Repository 또는 구체 Adapter를 직접 참조하거나 순환 의존이 생긴다.
- 하나의 Service에 서로 독립적으로 변경되는 유스케이스가 섞여 수정과 테스트 영향 범위가 지속적으로 커진다.

리팩터링 대상 유스케이스는 다음 책임을 구분한다.

- Application Service는 유스케이스의 진입점이며 실행 순서, 권한 범위, 출력 Port 조정과 트랜잭션 경계를
  책임진다.
- 도메인 객체와 도메인 서비스는 상태 전이와 불변식을 책임진다.
- 출력 Port는 Application Service가 필요한 기술 독립 계약을 표현한다.
- Adapter는 JPA, Redis, QR, 외부 API 같은 구체 기술로 출력 Port를 구현한다.
- 입력 Adapter는 HTTP, Scheduler 또는 이벤트 입력을 애플리케이션 입력으로 변환한다.

기존 Service가 이미 Application Service의 책임을 수행하면 별도 `ApplicationService` 래퍼를 추가하지 않는다.
Facade는 Clean Architecture의 필수 계층으로 간주하지 않는다. 여러 유스케이스를 특정 호출자에게 안정된 하나의
인터페이스로 제공해야 할 때만 검토하며, 트랜잭션과 도메인 흐름을 조정한다면 Facade가 아니라 Application
Service로 분류한다. 전달만 하는 `Facade → ApplicationService → Service` 계층은 만들지 않는다.

예약 확정과 QR 체크인을 첫 리팩터링 후보로 본다. 이는 즉시 해당 구조를 구현하라는 의미가 아니며, 위 신호와
테스트 근거가 확인된 후 별도 작업 범위로 전환한다.

## 결과와 트레이드오프

### 기대 효과

- 팀이 익숙한 구조로 MVP 구현을 시작하면서 아키텍처 학습 비용을 실제 문제와 연결할 수 있다.
- 단순 CRUD에는 불필요한 Port와 Adapter를 만들지 않고 복잡한 흐름에만 분리 비용을 지불한다.
- 리팩터링 단위를 한 유스케이스로 제한해 공개 API와 다른 도메인의 변경 범위를 줄인다.
- Application Service와 Facade의 역할 중복을 방지하고 트랜잭션 소유자를 명확히 할 수 있다.
- 외부 기술과 핵심 도메인 규칙 사이의 결합을 복잡성이 증가하는 시점에 통제할 수 있다.

### 수용한 단점과 위험

- 초기에는 엄격한 Clean Architecture 수준의 프레임워크 독립성을 보장하지 않는다.
- 전환된 유스케이스와 기존 3-Layer 유스케이스가 같은 저장소에 공존할 수 있다.
- 복잡성 신호를 리뷰에서 놓치면 큰 Service와 도메인 간 직접 의존이 누적될 수 있다.
- 유스케이스별 전환 과정에서 DTO, 도메인 모델과 영속성 타입의 매핑 비용이 일부 발생할 수 있다.
- 팀이 구조 차이의 이유를 이해하지 못하면 새 코드가 기존 방식으로 되돌아가거나 불필요한 계층이 다시 생길 수 있다.

## 전환과 롤백

신규 구현이므로 데이터 이관이나 호환 계층은 필요하지 않다. 초기에는 현재 코드 컨벤션의 도메인 중심 패키지와
3-Layer 책임을 적용한다.

복잡성 신호가 확인되면 다음 순서로 전환한다.

1. 대상 유스케이스의 정상, 경계, 실패, 권한, 중복 요청과 트랜잭션 동작을 회귀 테스트로 고정한다.
2. 현재 Service에서 도메인 규칙과 유스케이스 조정 책임을 구분한다.
3. 필요한 외부 의존에만 출력 Port를 정의하고 기존 구현을 Adapter로 이동한다.
4. Controller 또는 Scheduler가 Application Service라는 하나의 유스케이스 경계를 호출하도록 정리한다.
5. 해당 경계가 코드 컨벤션의 패키지 예시와 달라지면 코드 변경에 착수하기 전에 별도의 문서 단계에서 코드
   컨벤션을 먼저 갱신하고 구조를 확정한다.
6. 한 유스케이스의 효과를 검증한 뒤에만 다른 유스케이스로 확장한다.

전환 결과가 단순 전달 계층과 매핑만 늘리고 테스트 격리, 변경 영향 축소 또는 외부 기술 격리 중 어느 것도
개선하지 못하면 공개 API와 도메인 동작을 유지한 채 불필요한 Port, Adapter와 래퍼를 제거하고 기존 Service
구조로 되돌린다. 이미 검증한 도메인 규칙과 회귀 테스트는 유지한다.

## 검증 방법

- 코드 리뷰에서 Controller에 비즈니스 흐름과 트랜잭션이 들어가지 않았는지 확인한다.
- 초기 3-Layer Service가 다른 도메인의 Repository나 구체 외부 클라이언트에 직접 의존하는지 확인한다.
- 리팩터링한 유스케이스는 Application Service 하나가 트랜잭션 경계를 소유하는지 검증한다.
- 도메인 규칙은 가능한 한 Spring Context 없이 단위 테스트로 검증한다.
- 출력 Port 계약은 단위 테스트로, JPA·Redis·외부 연동 Adapter는 목적에 맞는 통합 테스트로 검증한다.
- 리팩터링 전후에 동일한 정상·경계·실패·권한·멱등성 결과가 유지되는지 확인한다.
- 정원 조건부 갱신, 멱등 기록, 예약 또는 방문 변경과 Outbox 저장의 기존 원자성 테스트를 모두 통과시킨다.
- 실질적 책임 없이 위임만 하는 Service, Application Service 또는 Facade가 추가되면 실패로 판정한다.

## 대체 조건

- 두 개 이상의 복잡한 유스케이스에 같은 경계를 적용한 결과 테스트 격리와 변경 영향 축소가 반복적으로 확인되고,
  팀이 의존 방향과 계층 책임을 일관되게 설명할 수 있게 된다.
- 도메인 간 직접 의존, 순환 참조 또는 Service 비대화가 반복돼 유스케이스별 점진 전환 속도로 통제할 수 없다.
- 외부 Adapter 수와 입력 채널이 증가해 모든 신규 기능에 일관된 Port와 Adapter 구조가 더 저렴해진다.
- 반대로 분리된 구조의 매핑과 간접 호출 비용이 지속적으로 유지보수 이득보다 크고 기술 교체나 독립 테스트 요구가
  발생하지 않는다.
- 모듈 분리, 독립 배포 또는 팀 경계가 필요해 현재 단일 애플리케이션과 패키지 수준 경계만으로 요구를 충족할 수
  없다.
