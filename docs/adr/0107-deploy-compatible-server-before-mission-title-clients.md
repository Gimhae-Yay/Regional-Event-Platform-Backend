# ADR-0107: 호환 서버를 먼저 배포해 미션 제목 계약을 전환한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-18
- 결정일: 2026-08-18
- 관련 요구사항: [지역 미션 `MSN-01`](../p1/regional-mission.md#3-지역-미션-정책), [미션 생성·수정 API](../api/p1/mission/mission.md#기능별-api-명세)
- 관련 단계: 단계 0. 정책·설계 확정
- 관련 이슈: [#912](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/912)
- 대체 대상: [ADR-0106](0106-store-mission-title-on-mission.md)의 `전환과 롤백` 및 그 전환 순서에 대한 검증 범위

## 맥락

ADR-0106은 운영자 클라이언트를 먼저 전환한 뒤 제목을 필수 검증하는 애플리케이션을 배포하도록 정했다. 그러나
현재 `CreateOperatorMissionRequest`와 `UpdateOperatorMissionRequest`에는 `title` 필드가 없고, 구버전 서버가
알 수 없는 `title`을 수용한다는 명시적 계약도 없다. 따라서 구버전 서버와 새 클라이언트가 만나는 혼재 구간의
생성·수정 성공을 보장할 수 없다.

반대로 제목을 즉시 필수로 검증하는 서버를 먼저 배포하면 제목을 보내지 않는 기존 클라이언트가 실패한다. 최종
API 계약은 제목 필수지만, 서버와 클라이언트를 독립적으로 전환할 수 있는 한시적 호환 단계와 단계별 null 검증이
필요하다.

## 결정 동인과 불변 조건

- 어떤 배포 순서에서도 운영자 미션 생성·수정 요청의 가용성을 유지한다.
- 새 클라이언트는 모든 요청을 처리할 서버가 `title`을 수용한 뒤에만 배포한다.
- 구버전 서버가 남아 있는 동안 생길 수 있는 null을 최종 backfill과 `NOT NULL` 적용 전에 모두 제거한다.
- 호환 서버와 최종 서버는 커밋되는 새 미션에 null 제목을 남기지 않는다.
- ADR-0106의 최종 제목 검증·수정·응답 계약과 기존 행의 `미션 {mission_id}` backfill 형식은 유지한다.
- 제목 원문을 로그나 배포 관측 지표에 기록하지 않는다.

## 결정

ADR-0106의 최종 API·저장 계약은 유지하되 전환·롤백 순서는 이 ADR로 대체한다. 새 클라이언트보다 먼저
`title`을 선택적으로 수용하는 호환 서버를 배포한다. 호환 동작은 전환 기간에만 적용하며 최종 공개 계약으로
유지하지 않는다.

호환 서버는 다음 규칙을 사용한다.

- 생성 요청에 유효한 `title`이 있으면 ADR-0106과 동일하게 정규화·검증해 저장한다.
- 생성 요청에서 `title`이 누락되거나 null이면 식별자 할당 뒤 `미션 {mission_id}`를 같은 트랜잭션에서 저장하고,
  null 제목이 남아 있으면 커밋하지 않는다.
- 수정 요청에 `title`이 누락되거나 null이면 기존 제목을 유지한다.
- 요청에 포함된 제목이 공백만 있거나 정규화 뒤 255자를 넘으면 `400 INVALID_INPUT`으로 거부한다.
- 제목 값은 로그에 남기지 않고, 호환 누락 처리 건수와 null 행 수만 관측한다.

최종 서버는 호환 누락 처리를 제거한다. 생성·수정 모두 `title`을 필수로 검증하며 누락과 null을
`400 INVALID_INPUT`으로 거부한다.

## 결과와 트레이드오프

### 기대 효과

- 구버전·신규 클라이언트와 호환 서버가 공존하는 동안 생성·수정 요청을 계속 처리할 수 있다.
- 새 클라이언트가 구버전 서버에 도달하는 순서 역전을 배포 게이트로 차단한다.
- 애플리케이션과 DB의 필수 제약을 분리해 null 발생 주체를 제거한 뒤 `NOT NULL`을 적용할 수 있다.

### 수용한 단점과 위험

- 호환 서버에는 최종 API 계약보다 느슨한 한시적 요청 처리가 필요하다.
- 호환 기간에 생성된 미션은 운영자가 제목을 보내지 않으면 `미션 {mission_id}`를 표시한다.
- 서버 인스턴스와 지원 클라이언트의 전환 완료를 확인하지 못하면 다음 단계로 진행할 수 없다.
- 호환 누락 처리를 제거하는 후속 서버 배포가 필요하다.

## 전환과 롤백

1. `mission.title`을 nullable `VARCHAR(255)`로 추가한다. 구버전 서버가 남아 있으므로 이 단계에서는 새 null 행이
   생길 수 있으며, null 0건을 완료 조건으로 사용하지 않는다.
2. 호환 서버를 배포한다. 제목이 있는 요청과 없는 기존 요청의 생성·수정 계약 테스트를 통과하고, 호환 서버가
   처리한 생성 트랜잭션에 null 제목이 없음을 확인한다. 모든 구버전 서버 인스턴스가 종료되기 전에는 새
   클라이언트를 배포하지 않는다.
3. 구버전 서버 인스턴스가 없음을 확인한 뒤 모든 null 기존 행을 `미션 {mission_id}`로 backfill한다. 전체 행 수와
   식별자·조건·상태·보상·시각이 유지되고 null·빈 문자열·길이 위반이 0건인지 확인한다. 이후 null 행이 다시
   생기면 전환을 중단한다.
4. 운영자 클라이언트를 `title` 전송 버전으로 전환한다. 지원 대상 클라이언트의 전환과 제목 누락 요청 0건을
   확인하기 전에는 호환 누락 처리를 제거하지 않는다.
5. 제목을 필수 검증하는 최종 서버를 배포한다. 유효한 제목을 가진 생성·수정만 저장되고 누락·null 요청은
   `400 INVALID_INPUT`이며, 모든 writer가 이 버전이고 null 행이 0건인지 확인한다.
6. 후속 migration에서 `title`을 `NOT NULL`로 변경한다. 영구 기본값은 두지 않는다.
7. 세 방문자 조회의 제목 응답과 기존 API 회귀 검증을 완료한다.

클라이언트 전환 전에는 DB를 nullable로 유지한 채 호환 서버를 구버전 서버로 되돌릴 수 있다. 이 경우 구버전
서버가 만든 null은 다음 전환 시 다시 backfill한다. 클라이언트 전환 뒤에는 먼저 호환 서버를 유지하거나 복구하고
클라이언트를 제목 미전송 버전으로 되돌린 뒤에만 구버전 서버로 롤백한다.

최종 서버 배포 뒤에는 호환 서버로 먼저 롤백해 두 요청 형식을 모두 수용한다. `NOT NULL` 적용 뒤 구버전 서버까지
되돌려야 하면 미션 쓰기를 중단하고 제목 값을 보존한 채 컬럼을 nullable로 변경한 다음, 클라이언트와 서버를
구버전으로 되돌리고 쓰기를 재개한다.

## 검증 방법

- 호환 서버가 제목이 없는 기존 생성 요청에는 `미션 {mission_id}`를 저장하고 기존 수정 요청에는 저장된 제목을
  유지하는지 계약 테스트로 검증한다.
- 호환 서버가 유효·무효 제목을 ADR-0106 규칙대로 처리하고 생성 커밋마다 제목이 non-null인지 검증한다.
- 서버 혼재 테스트에서 구버전 서버가 모두 제거되기 전 새 클라이언트 배포 게이트가 열리지 않는지 확인한다.
- 구버전 서버 제거 뒤 backfill 대상·결과 행 수가 일치하고 null·빈 문자열·길이 위반이 0건인지 검증한다.
- 클라이언트 전환 뒤 제목 누락 요청 건수가 0이고, 최종 서버가 누락·null을 `400 INVALID_INPUT`으로 거부하는지
  검증한다. 관측에는 제목 값을 포함하지 않는다.
- `NOT NULL` migration 전후 모든 writer의 정상 생성·수정과 null 행 0건을 확인한다.
- 호환 서버, 클라이언트, 최종 서버와 DB 제약을 정해진 역순으로 되돌리는 롤백 검증을 수행한다.

## 대체 조건

- 서버와 운영자 클라이언트를 원자적으로 함께 배포해 혼재 구간이 없다는 배포 계약이 채택된다.
- API 버전 분리나 별도 호환 게이트웨이가 제목 누락·추가 필드 전환을 책임지도록 변경된다.
- 제목 없는 기존 요청을 중단해도 된다는 운영 중단 정책이 별도로 채택된다.
