# ADR-0063: 기존 역할 연결에 전역 PLATFORM_ADMIN 역할을 추가한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-05
- 결정일: 2026-08-05
- 관련 요구사항: [P1-FR-09](../p1-spec.md#6-기능-요구사항과-소유-문서), [ADM-01](../p1/platform-admin.md#3-전체관리자-정책)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

ADR-0010은 전체관리자 기능을 P1로 승격했지만, 전체관리자 권한을 기존 사용자·역할 모델에 어떻게 저장하고
인가할지는 확정하지 않았다. P1의 전역 사용자 목록 조회는 활성 전체관리자만 호출할 수 있어야 하며, 기존 역할·지역
연결과 다른 별도 계정 모델을 추가하면 인증과 역할 조회 경로가 이중화된다.

## 결정 동인과 불변 조건

- 전체관리자도 기존 `app_user` 인증 수단과 `user_role_assignment` 역할 연결을 사용한다.
- `PLATFORM_ADMIN`은 전역 역할이므로 담당 `region_id`를 가져서는 안 된다.
- `PLATFORM_ADMIN`이 아닌 역할의 기존 지역 격리 규칙을 완화하지 않는다.
- 전역 사용자 목록은 특권 조회이므로 활성 `PLATFORM_ADMIN`만 호출하며, 비밀번호·전화번호·사업자 정보는 반환하지 않는다.
- 이 결정은 최초 전체관리자 준비, 비활성화 효과, 역할 임명·회수 보호 규칙을 확정하지 않는다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 기존 `user_role_assignment`에 지역 없는 `PLATFORM_ADMIN` 역할을 추가한다 | 기존 인증·역할 조회·권한 검사 구조를 재사용하고 ERD 변경이 역할 값과 지역 제약으로 제한된다. | 전역 역할 검사가 지역 역할 검사와 혼동되지 않도록 전용 API에서 명시적으로 제한해야 한다. | 낮음 | P1의 최소 전체관리자 기능에 적합하다. |
| 2 | 별도 전체관리자 계정·권한 테이블을 만든다 | 전역 권한을 물리적으로 분리할 수 있다. | 인증·계정 수명주기·역할 조회가 이중화되고 별도 동기화 규칙이 필요하다. | 높음 | 현재 필요한 읽기 전용 목록 조회보다 과하다. |

## 결정

P1 전체관리자는 `app_user`에 연결된 `user_role_assignment(role = PLATFORM_ADMIN, region_id = NULL)` 한 행으로 표현한다.
`PLATFORM_ADMIN` 역할은 지역 범위와 콘텐츠 소유권을 우회하는 일반 권한이 아니며, 전체관리자 전용 API에서만 허용 역할로
명시한다. 기존 `VISITOR`도 `region_id = NULL`을 유지하고, `OPERATOR`와 `REGION_ADMIN`은 담당 지역을 반드시
가져야 한다.

`GET /api/v1/platform-admin/users`는 활성 `PLATFORM_ADMIN`만 호출할 수 있다. 목록에는 사용자를 식별하고 현재 역할을 확인하는 데
필요한 `userId`, `loginIdentifier`, `name`, 역할·담당 지역, 생성 시각만 반환하며 전화번호, 비밀번호 해시, 사업자
정보와 토큰은 반환하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- P1 전체관리자 인가가 기존 JWT·사용자·역할 연결 모델 안에서 일관되게 동작한다.
- 전역 사용자 목록에 필요한 ERD 변경이 새 테이블 없이 역할 제약 추가로 끝난다.

### 수용한 단점과 위험

- `PLATFORM_ADMIN`은 담당 지역이 없으므로 전용 API가 아닌 경로에서 지역 검사를 생략하는 근거로 사용하면 안 된다.
- 로그인 식별자는 개인정보이므로 이 API의 응답을 로그·감사 이력에 복사하지 않는다.

## 전환과 롤백

현재 P1 전체관리자 데이터와 구현이 없으므로 데이터 이관과 호환 계층은 필요하지 않다. 구현 시 DB 제약과 JWT 역할
매핑을 추가한 뒤, 승인된 최초 관리자 준비 절차로 대상 사용자에게 `PLATFORM_ADMIN` 역할을 부여한다.

도입을 중단하면 새 `PLATFORM_ADMIN` 역할을 부여하지 않고 전용 API를 노출하지 않는다. 이미 부여한 역할을 회수하거나 다른
역할 모델로 전환해야 하면, 최초 관리자·권한 회수 보호 규칙을 확정한 후 후속 ADR과 전진 migration으로 처리한다.

## 검증 방법

- 활성 `PLATFORM_ADMIN`만 `/api/v1/platform-admin/users`를 호출할 수 있고, `VISITOR`, `OPERATOR`, `REGION_ADMIN`은 `FORBIDDEN`인지 검증한다.
- `PLATFORM_ADMIN` 역할은 `region_id = NULL`이고, `OPERATOR`·`REGION_ADMIN` 역할은 지역 없이 생성되지 않는지 DB 제약을 검증한다.
- 목록 응답에 전화번호, 비밀번호 해시, 사업자 정보, 토큰이 포함되지 않는지 API 테스트로 검증한다.
- 빈 결과에서 `users: []`를 반환하고, 활성 회원만 정렬된 목록에 포함되는지 검증한다.

## 대체 조건

- 전체관리자에 별도 인증 수단, 다중 승인 또는 조직별 권한 계층이 필요해 기존 역할 연결만으로 표현할 수 없게 된다.
- 사용자 목록에 전화번호 등 추가 개인정보가 반드시 필요하다는 승인된 운영 요구가 생긴다.
