# ADR-0031: 공개 콘텐츠에 버전 검증형 Cache-Aside를 사용한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-29
- 결정일: 2026-07-29

- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음

## 맥락

P0는 Redis를 지역 홈·공개 콘텐츠 목록·상세의 캐시에 사용하되, 잔여 정원과 예약 가능 여부는 캐시하지
않고 MySQL을 최종 정합성 기준으로 사용한다. 그러나 공개 콘텐츠의 정적 표시 정보를 어떤 키로 저장하고,
수정 승인이나 상태 변경 뒤 이전 값을 어떻게 배제하며, Redis 장애나 무효화 실패 시 어떤 결과를 반환할지는
확정하지 않았다.

공개 콘텐츠는 수정본 승인 시 기존 공개본을 유지한 채 새 버전으로 원자 반영된다. 명시적 무효화만 사용하면
Redis 삭제 실패나 처리 순서 경합으로 이전 공개본이 노출될 수 있다. 반대로 전체 지역 홈 응답을 캐시하면
회차 상태·잔여 정원·예약 가능 여부가 MySQL 현재 상태와 달라질 수 있다. 캐시를 사용하지 않으면 구현은
단순하지만 공개 조회 트래픽이 모두 MySQL의 정적 표시 필드 조회 비용으로 이어진다.

따라서 공개 범위와 버전을 MySQL에서 매 요청 검증하고, 검증된 버전의 정적 표시 정보만 Redis에서 재사용하는
Cache-Aside 전략을 채택한다.

## 결정 동인과 불변 조건

- 공개 응답에는 현재 지역에 속하고 `PUBLISHED`이며 삭제되지 않은 콘텐츠만 포함한다.
- 회차 상태, 표시 회차, 잔여 정원과 예약 가능 여부는 Redis에 저장하지 않고 MySQL 현재 상태로 계산한다.
- 수정 승인이나 상태 전이 뒤 이전 공개본을 정상 응답으로 반환하지 않는다.
- MySQL은 공개 상태, 콘텐츠 버전과 동적 예약 정보의 최종 기준이다.
- Redis 장애만으로 공개 조회를 실패시키지 않으며 MySQL 원본으로 같은 응답을 만들 수 있어야 한다.
- MySQL에서 현재 공개 상태와 버전을 검증할 수 없으면 캐시 값만으로 응답하지 않는다.
- presigned URL, URL 만료 시각, S3 객체 키와 개인정보는 정적 콘텐츠 캐시에 저장하지 않는다.
- 모든 캐시 키에는 유한 TTL을 적용해 사용되지 않는 이전 버전 값을 자동 정리한다.

## 결정

### 캐시 범위와 키

지역 홈, 공개 콘텐츠 목록과 상세 조회는 지역명·콘텐츠 제목·위치·안내처럼 변경 빈도가 낮은 정적 표시
정보에만 Cache-Aside를 적용한다. 논리 콘텐츠 키는 다음 구성요소를 포함한다.

```text
public-content:{regionId}:{contentId}:v{versionNo}
```

공개 지역의 정적 표시 정보는 `public-region:{regionId}` 논리 키를 사용할 수 있다. 실제 접두사와 직렬화
형식은 구현 설정에서 정하되, 키의 지역·콘텐츠·버전 경계와 저장 필드의 범위는 바꾸지 않는다.

캐시 값에는 회차 상태, `displaySession`, `remainingCapacity`, `reservationAvailable`, presigned URL과
그 만료 시각을 포함하지 않는다. 콘텐츠 키와 값에도 S3 객체 키, 사용자 식별정보와 개인정보를 저장하지
않는다.

### 조회와 버전 검증

서버는 요청마다 MySQL에서 지역 공개 여부와 대상 콘텐츠의 `region_id`, `status`, `deleted_at`,
`version_no`를 동적 회차 정보와 함께 조회한다. 콘텐츠가 현재 공개 대상이 아니면 이전 캐시 키가 남아
있어도 사용하지 않는다.

현재 `version_no`의 키가 있으면 정적 표시 정보만 재사용하고, 회차와 예약 가능 정보는 MySQL 조회 결과로
조립한다. 캐시가 없거나 값의 지역·콘텐츠·버전이 검증 결과와 다르면 캐시 값을 버리고 MySQL 원본의 정적
표시 정보로 응답한 뒤 현재 버전 키를 다시 적재한다.

MySQL 조회가 실패하면 캐시 값만으로 공개 상태와 버전을 추정하지 않고 서버 오류를 반환한다. Redis 읽기나
쓰기가 실패하면 해당 요청에서는 캐시를 우회하고 MySQL 원본으로 응답한다.

### 무효화와 TTL

수정본 `EDIT_APPROVED` 반영은 콘텐츠의 `version_no`를 증가시킨다. 반영 트랜잭션이 커밋된 뒤 이전 버전
키를 최선 노력으로 삭제한다. 공개 중단·철회·종료·삭제처럼 공개 범위를 벗어나는 상태 전이도 커밋 뒤 관련
정적 캐시를 최선 노력으로 삭제한다.

삭제가 실패해도 다음 요청은 MySQL의 현재 공개 상태와 버전을 먼저 검증하므로 이전 값을 반환하지 않는다.
삭제 실패는 원본 트랜잭션을 롤백하지 않으며 구조화 로그와 비개인 지표로 기록한다.

정적 표시 정보 캐시의 기본 TTL은 10분으로 하고 환경별 설정으로 조정할 수 있다. TTL은 공개본 최신성을
보장하는 수단이 아니라 사용되지 않는 이전 버전 키와 누락된 무효화 결과를 정리하는 상한이다. 운영에서
TTL을 조정하더라도 무제한 TTL, 동적 필드 캐시와 MySQL 버전 검증 생략은 허용하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- Redis 무효화 실패와 수정 승인 경합에도 이전 공개본을 정상 응답으로 반환하지 않는다.
- 동적 회차·정원 정보와 공개 상태의 최종 기준을 MySQL 하나로 유지한다.
- Redis 장애 시 공개 조회를 MySQL로 우회할 수 있고 별도의 캐시 복구 트랜잭션이 필요하지 않다.
- 버전별 키와 TTL로 이전 값의 즉시 배제와 지연 정리를 분리한다.

### 수용한 단점과 위험

- 캐시 적중 요청에도 MySQL의 공개 상태·버전과 회차 정보를 조회하므로 DB 왕복이 남는다.
- 버전별 키는 무효화 실패 시 TTL까지 중복 공간을 사용한다.
- 캐시 적중률, 직렬화 비용과 MySQL projection 비용을 함께 측정하지 않으면 캐시 효과가 제한될 수 있다.
- 커밋 뒤 삭제는 원본 갱신과 원자적이지 않으므로 실패 관측과 TTL 정리가 필요하다.

## 전환과 롤백

현재 공개 콘텐츠 캐시 구현과 운영 데이터가 없으므로 데이터 이관은 없다. 구현 시 MySQL 공개 상태·버전
projection, 버전별 Cache-Aside와 커밋 뒤 최선 노력 무효화를 순서대로 추가한다.

Redis 오류율이나 지연이 허용 범위를 넘거나 캐시가 성능을 개선하지 못하면 캐시 읽기·쓰기를 비활성화하고
MySQL 원본 조회로 즉시 우회한다. 이미 생성된 키는 삭제 작업에 의존하지 않고 TTL로 만료시킨다. 이 우회는
공개 범위와 응답 의미를 바꾸지 않는다.

매 요청 MySQL 버전 검증을 제거하거나 이벤트 기반 최종 일관성으로 전환하려면 실패 시 오래된 공개본 허용
범위, 이벤트 전달 보장과 전환 절차를 후속 ADR로 확정한다.

## 검증 방법

- 현재 `PUBLISHED`·지역 일치·미삭제 콘텐츠만 캐시 유무와 관계없이 동일하게 반환하는지 통합 테스트한다.
- 수정 승인으로 `version_no`가 증가하면 이전 키가 남아 있어도 이전 표시 정보를 반환하지 않는지 검증한다.
- 중단·철회·종료·삭제 뒤 기존 캐시가 남아 있어도 콘텐츠를 공개하지 않는지 검증한다.
- 캐시 적중 시에도 회차 상태, 잔여 정원과 예약 가능 여부가 MySQL 현재 값으로 반환되는지 검증한다.
- Redis 읽기·쓰기·삭제 실패 시 MySQL 조회가 성공하면 API가 성공하고, MySQL 조회 실패 시 캐시만으로
  응답하지 않는지 검증한다.
- 정적 캐시가 10분 기본 TTL을 가지며 presigned URL, S3 객체 키와 개인정보를 포함하지 않는지 검증한다.
- 캐시 적중률·조회 지연·MySQL 쿼리 수·무효화 실패·Redis 우회 건수를 비개인 지표로 관측하고 캐시 적용
  전후를 같은 조건에서 비교한다.

## 대체 조건

- 매 요청 버전 검증의 MySQL 부하가 공개 조회 SLO를 지속적으로 위반한다.
- 신뢰할 수 있는 변경 이벤트 전달·재시도 체계가 도입돼 버전 검증 없이도 허용 가능한 일관성을 보장한다.
- 공개 콘텐츠 트래픽과 데이터 크기가 단일 Redis Cache-Aside 운영 범위를 넘는다.
- CDN 또는 다중 리전 캐시를 도입해 키, 무효화와 장애 복구 경계를 다시 정의해야 한다.
