# ADR-0014: 공개 콘텐츠 수정본을 관계형 리비전 테이블에 저장

- 상태: 채택됨
- 기록 유형: 소급
- 기록일: 2026-07-28
- 결정일: 2026-07-23
- 관련 요구사항: [지역·콘텐츠 카탈로그](../p0/content-catalog.md)의 `FR-14`, `CON-05`, [P0 명세](../p0-spec.md)의 `AC-09`
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

공개된 콘텐츠는 방문자에게 이미 노출되고 회차·예약과 연결될 수 있으므로 운영자가 수정 요청을 작성하거나 지역
관리자가 심사하는 동안 현재 공개본을 직접 바꾸면 안 된다. 현재 정책은 수정본의 `EDIT_DRAFT → EDIT_REQUESTED`
제출, 승인·반려·철회와 승인된 수정본만 원본에 반영하는 흐름을 정의한다.

2026-07-23 PRD에는 `content_revision_id`를 가진 콘텐츠 수정본 데이터와 공개본 유지 정책이 이미 명시되어
있었다. 당시의 대안 비교와 선택 근거는 남아 있지 않으므로, 이 ADR은 확인 가능한 정책과 현재 사용자가 재확인한
관계형 리비전 테이블 선택을 소급 기록한다.

[ADR-0006](0006-use-shared-content-root-with-type-specific-details.md)은 공통 `Content`와 유형별 상세를 관계형으로
분리하고 비즈니스 규칙·검색 값을 JSON에 저장하지 않도록 정했다. 수정본도 같은 제약을 지키면서 공개 원본과
후보 데이터를 분리할 영속 모델이 필요하다.

## 결정 동인과 불변 조건

- 심사 중인 수정본은 공개 상세·목록·예약 가능 여부에 영향을 주지 않는다.
- 공개 조회와 예약 경로는 항상 승인된 현재 `Content`와 유형별 상세·회차만 읽는다.
- 수정본의 `EDIT_*` 상태와 원본 콘텐츠의 공개 상태를 혼합하지 않는다.
- 수정본 생성·조회·제출·철회와 심사는 저장된 `operator_id`, `region_id`와 `content_type`을 기준으로 권한을
  검사하며, 클라이언트가 보낸 소유자·지역·유형을 신뢰하지 않는다.
- 수정본 승인 시 원본 반영, 수정본 상태 전이와 감사 기록은 하나의 트랜잭션에서 함께 성공하거나 롤백한다.
- 반려·철회된 수정본은 원본을 변경하지 않고 상태·처리자·시각·사유를 보존한다.
- 예약이 연결된 회차를 수정본 승인으로 조용히 삭제·재배정·정원 변경하지 않는다. 명시적 회차 취소는 기존
  `RSV-06` 정책만 적용한다.

## 결정

공개 콘텐츠의 수정 후보는 `content_revision` 관계형 루트 테이블에 저장한다. 각 수정본은 원본 `content_id`,
콘텐츠별 `revision_no`, 기준 원본 버전, 서버가 확인한 `editor_id`와 수정본 상태를 가진다. P0에서는 콘텐츠당
`EDIT_DRAFT` 또는 `EDIT_REQUESTED` 상태의 활성 수정본을 한 건만 허용한다.

공통 수정 필드와 유형별 수정 필드는 원본 테이블과 분리된 관계형 리비전 테이블에 저장한다. 초기
`EVENT_EXPERIENCE`에는 `content_revision`과 행사·체험 상세 수정본 테이블을 함께 두며, 회차 수정이 P0 범위에
포함되는 필드는 회차 리비전 자식 테이블로 분리한다. 비즈니스 규칙과 검색에 쓰이는 값을 JSON 스냅샷으로 저장하지
않는다.

`content_id`, `region_id`, `operator_id`, `content_type`은 수정본으로 변경할 수 없다. `EDIT_REQUESTED`가 된
후보 값은 동결한다. 지역 관리자의 승인 처리에서는 수정본이 아직 `EDIT_REQUESTED`이고 원본이 여전히
`PUBLISHED`이며 기준 원본 버전이 일치하는지 조건으로 확인한 뒤, 원본과 유형별 상세·허용된 자식 데이터를 반영하고
수정본을 `EDIT_APPROVED`로 전이하며 감사 기록을 같은 트랜잭션에서 커밋한다.

승인·반려·철회는 `EDIT_REQUESTED` 상태를 조건으로 한 전이로 최초 하나만 성공하게 한다. `EDIT_REJECTED`와
`EDIT_WITHDRAWN`은 원본에 어떤 값도 반영하지 않는다. 이미 승인된 수정본의 오류는 상태를 되돌리거나 직접
원복하지 않고, 새 수정본을 만들어 보정한다.

## 결과와 트레이드오프

### 기대 효과

- 심사 중에도 공개 콘텐츠와 예약 경로가 승인된 원본만 일관되게 읽는다.
- 승인·반려·철회 이력과 후보 데이터가 원본과 분리되어 감사와 문제 재현이 가능하다.
- 유형별 상세와 이후 허용된 회차 변경을 명시적 관계·제약으로 확장할 수 있다.
- 서버가 소유·지역 경계를 유지한 채 수정 권한과 승인 반영을 검증할 수 있다.

### 수용한 단점과 위험

- 원본과 수정본·유형별 자식 테이블의 매핑과 승인 트랜잭션이 복잡해진다.
- 하나의 콘텐츠에 활성 수정본을 하나만 허용하므로 병렬 편집이나 여러 대안 심사를 지원하지 않는다.
- 회차의 일정·정원 변경 허용 범위는 API·ERD 계약에서 별도로 제한하지 않으면 예약 정합성 위험이 생긴다.
- 이미 승인된 수정본을 잘못 반영해도 직접 롤백하지 않고 보정 수정본을 거쳐야 한다.

## 전환과 롤백

현재 구현은 신규 단계이므로 기존 수정본 데이터 이관은 없다. Flyway로 리비전 루트·유형별 자식 테이블, 외래 키,
조회 인덱스와 상태 제약을 먼저 추가한 뒤 수정본 생성·제출, 조건부 심사와 원자 반영 순으로 구현한다. 공개 조회와
예약 경로는 리비전 테이블을 읽지 않은 상태로 유지한다.

도입 중 문제가 발생하면 수정본 명령을 중지하고 원본 공개 경로를 유지한다. 승인 전 후보는 원본에 영향을 주지
않으므로 삭제나 직접 복구 없이 보존한다. 이미 승인된 반영은 자동으로 되돌리지 않고 새 수정본으로 보정한다.
구체적인 테이블·컬럼·제약과 API 요청·응답은 구현 전에 ERD와 API 명세에 확정한다.

## 검증 방법

- `EDIT_DRAFT`와 `EDIT_REQUESTED` 수정본이 있어도 공개 상세·목록·예약 가능 여부가 원본과 같은지 검증한다.
- 한 콘텐츠에 활성 수정본이 두 건 생성되지 않고, 다른 운영자·지역의 수정본 명령과 임의 소유자·지역 지정이
  거부되는지 검증한다.
- 승인 시 원본 공통·유형별 상세·허용된 자식 반영, 수정본 상태 전이와 감사 기록이 함께 커밋되고 중간 예외 시
  모두 롤백되는지 검증한다.
- 승인·반려·철회를 동시에 요청하면 하나만 성공하고, 철회 재시도는 기존 결과를 반환하며 뒤늦은 종결 요청은
  거부되는지 검증한다.
- 반려·철회 수정본이 원본을 변경하지 않고 상태·사유·처리자·시각을 보존하는지 검증한다.
- 예약이 연결된 회차의 파괴적 삭제·재배정이나 예약 정원 변경이 수정본 승인으로 발생하지 않는지 검증한다.
- ADR 링크·번호·기록일을 확인하고 `git diff --check`를 통과한다.

## 대체 조건

- 한 콘텐츠의 병렬 편집, 다수 후보 비교·병합 또는 공동 편집이 실제로 필요해진다.
- 공개본과 수정본의 전체 버전 이력·시점 조회를 외부 계약으로 제공해야 한다.
- 관계형 리비전 조인과 원자 반영이 합의한 조회·승인 SLO를 지속적으로 충족하지 못한다.
- 콘텐츠 유형별 수정 계약이 크게 달라져 공통 리비전 루트와 상세 자식 모델을 유지할 수 없게 된다.
