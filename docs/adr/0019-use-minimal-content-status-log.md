# ADR-0019: 콘텐츠 상태 이력을 최소 `content_log` 테이블로 기록한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-28
- 결정일: 2026-07-28
- 관련 요구사항: [P0 명세](../p0-spec.md)의 `FR-04`, `FR-11`, `FR-14`, `AC-11`, `AC-12`, `AC-17`, [콘텐츠 카탈로그](../p0/content-catalog.md)의 `CON-03`, `CON-06`~`CON-09`
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0018](0018-store-content-lifecycle-history-in-mysql.md)의 `content_lifecycle_event`·actor link 스키마와 그 이력 모델 전체

## 맥락

ADR-0018은 콘텐츠 상태 이력의 장기 보존과 탈퇴 익명화를 위해 전후 상태, 순번, 이벤트 유형, actor 역할과
별도 actor link를 가진 생명주기 이벤트 모델을 채택했다. 그러나 현재 P0에서 필요한 콘텐츠 이력 조회는
"어떤 콘텐츠가 어떤 상태로 언제 바뀌었는가"와 그 처리자 확인이다. 전후 상태·순번·별도 actor link는 이
조회와 상태 전이의 현재 조건부 갱신에 필수적이지 않다.

사용자는 추가 전용의 간결한 `content_log` 테이블을 선택하고, 컬럼을 `id`, `content_id`, `actor_id`,
`status`, `date`로 한정했다.

## 결정 동인과 불변 조건

- `content`는 현재 상태와 자동 공개·일반 조회 조건을 위한 원본 스냅샷으로 남아야 한다.
- 콘텐츠 상태 변경 시 어떤 콘텐츠·처리자·변경 후 상태·시각인지를 MySQL에 추가 전용으로 남겨야 한다.
- 성공 상태 전이, `content` 갱신, 로그 삽입과 성공 `audit_event` 기록은 같은 MySQL 트랜잭션에서 함께
  커밋하거나 함께 롤백해야 한다.
- 자동 공개·종료처럼 시스템이 처리한 로그는 사용자 actor가 없어야 한다.
- 회원 탈퇴 뒤 로그를 통해 탈퇴 회원을 역참조할 수 없어야 한다.
- 방문자 안내에 필요한 중단·철회 사유와 소프트 삭제 사유는 현재 `content`에 유지한다.
- P0에서 상태가 아닌 소프트 삭제는 상태 로그로 억지로 표현하지 않는다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | `id`, `content_id`, `actor_id`, `status`, `date`만 가진 `content_log` | 현재 상태와 상태 이력의 책임이 명확하고, 필요한 상태·처리자·시각만 간결하게 저장한다. | 전후 상태·처리 역할·상태별 사유의 과거 변경 이력은 로그 자체에 없다. | 낮음. 신규 migration과 콘텐츠 전이 기록만 구현하면 된다. | 사용자가 선택했으며 현재 P0의 단순한 콘텐츠 상태 흐름에 적합하다. |
| 2 | ADR-0018의 생명주기 이벤트와 별도 actor link | 전후 상태·순번과 actor 익명화 경로를 엄격하게 모델링할 수 있다. | 현재 요구보다 테이블·제약·탈퇴 처리 단계가 많아지고 조회 모델이 복잡해진다. | 중간. 두 테이블과 일관성 규칙을 함께 운영해야 한다. | 현재 P0에는 과도하다. |
| 3 | `content.updated_at`만 사용 | 테이블을 추가하지 않는다. | 마지막 일반 수정 시각이 상태 변경 시각을 덮어쓰므로 상태 이력을 재현할 수 없다. | 낮음 | `FR-04`, `FR-11`의 상태 이력 요구를 충족하지 못한다. |

## 결정

`content_log`를 MySQL의 콘텐츠 상태 로그로 둔다. 상태 정보는 추가 전용이고, 개인정보 파기를 위한
`actor_id` 제거만 예외적으로 허용한다. 컬럼은 다음 다섯 개만 사용한다.

| 컬럼 | 의미 |
| --- | --- |
| `id` | 로그 행 식별자(PK) |
| `content_id` | 상태가 변경된 콘텐츠(FK) |
| `actor_id` | 처리 사용자(FK). 시스템 처리와 탈퇴 완료 뒤에는 `NULL` |
| `status` | 생성 또는 상태 전이 뒤의 콘텐츠 상태 |
| `date` | 상태 변경이 발생한 MySQL 기준 시각 |

콘텐츠 생성 시 `PENDING` 로그를 한 건 추가한다. 이후 상태 전이는 `content.status`의 기대 상태를 조건으로
갱신하고 같은 트랜잭션에서 변경 뒤 상태를 `content_log`에 삽입한다. 자동 공개·종료는 `actor_id = NULL`로
기록한다. 삽입된 로그의 `content_id`, `status`, `date`는 수정·개별 삭제하지 않으며, 콘텐츠별 이력은
`date`, `id` 순으로 조회한다.

회원 탈퇴 완료 전 `content_log.actor_id`를 `NULL`로 갱신한다. 이 경우 actor 표시는 공통
`WITHDRAWN_MEMBER`로 파생하며, 별도 actor link·안정 가명·재식별 매핑은 만들지 않는다.

중단·철회·소프트 삭제 사유는 각각 `content.suspension_reason`, `content.withdrawal_reason`,
`content.deletion_reason`에 유지한다. 소프트 삭제는 P0에서 콘텐츠 상태가 아니므로 `content_log`를 추가하지
않고, `content.deleted_at`과 `deletion_reason`을 같은 트랜잭션에서 기록한다. `audit_event`는 콘텐츠를
포함한 전 도메인의 성공·실패 감사와 90일 보관 책임을 계속 가진다.

## 결과와 트레이드오프

### 기대 효과

- 콘텐츠 상태 이력이 다섯 컬럼의 단일 테이블로 단순해진다.
- 일반 필드 수정으로 `updated_at`이 변해도 상태 변경 시각·처리자·상태는 로그에 남는다.
- 상태 변경 경합은 기존 `content.status` 조건부 갱신으로 판정하므로 로그에 전후 상태·순번이 필요 없다.
- 시스템 처리와 탈퇴 사용자 처리를 `actor_id = NULL` 하나로 표현한다.

### 수용한 단점과 위험

- 로그만으로 직전 상태나 상태 전이 사유의 과거 변경 이력을 조회할 수 없다.
- 같은 시각의 로그는 `date`만으로 순서가 완전히 결정되지 않으므로 `id`를 보조 정렬 기준으로 사용한다.
- 중단·철회 사유는 현재 `content`에 남으므로, 향후 재개·다중 중단 전이가 도입되면 별도 이력 모델을 다시
  검토해야 한다.
- 로그 actor를 탈퇴 때 `NULL`로 바꾸므로 탈퇴 후 개인별 처리 이력을 추적할 수 없다.

## 전환과 롤백

아직 콘텐츠 migration과 구현이 없으므로 데이터 이관이나 호환 계층은 필요 없다. ADR-0018에서 정의한
`content_lifecycle_event`와 `content_lifecycle_event_actor_link`는 만들지 않는다. 대신 `content_log`를
먼저 생성하고 콘텐츠 생성·상태 전이 유스케이스에서 현재 상태 갱신과 로그 삽입을 같은 트랜잭션으로 구현한다.

도입 전에 문제가 확인되면 `content_log` migration과 상태 기록 기능을 함께 제거한다. 운영 데이터가 생긴 뒤
로그 오류는 기존 행을 수정하지 않고 운영 감사 기록과 후속 상태 전이로 설명한다. 재개·다중 상태 사유 이력 또는
장기 외부 감사가 실제 요구가 되면 새 ADR에서 확장 모델을 결정한다.

## 검증 방법

- 콘텐츠 생성, 승인, 반려, 자동 공개, 중단, 철회와 종료마다 변경 뒤 상태·처리자·시각을 가진 로그가 한 건씩
  추가되는지 검증한다.
- 동일 콘텐츠의 동시 상태 전이에서 `content.status` 조건부 갱신이 하나만 성공하고, 성공한 전이에만 로그와
  성공 `audit_event`가 기록되는지 검증한다.
- `content` 갱신, 로그 삽입, 감사 이벤트 삽입 각각에 실패를 발생시켜 셋이 함께 롤백되는지 검증한다.
- 자동 공개·종료 로그의 `actor_id`가 `NULL`이고, 사용자 처리 로그의 `actor_id`가 실제 처리자와 일치하는지
  검증한다.
- 탈퇴 완료 전 `content_log.actor_id`가 제거되고 해당 회원을 로그로 역참조할 수 없는지 검증한다.
- 소프트 삭제는 로그가 아닌 `deleted_at`·`deletion_reason`으로만 기록되고 이후 상태 전이가 거부되는지 검증한다.

## 대체 조건

- 콘텐츠가 같은 상태로 재개·중단을 반복해 과거 전후 상태와 사유를 모두 장기 보존해야 한다.
- 콘텐츠 상태 이력을 외부 전달·재생하는 보장된 이벤트 계약이 실제 출시 범위로 채택된다.
- 탈퇴 뒤에도 개인별 처리 이력을 보존해야 한다는 법률·계약 요구가 확인된다.
- `content_log`의 조회량·보관량이 MySQL의 합의한 운영 한계를 지속적으로 넘는다.
