# ADR-0112: 운영자 소유 콘텐츠의 회차를 별도 목록 API로 조회한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-20
- 결정일: 2026-08-20
- 관련 요구사항: [지역·콘텐츠 카탈로그](../p0/content-catalog.md)의 `FR-03`, `SES-01`, [운영자 소유 콘텐츠 회차 목록 API](../api/p0/content-catalog/list-operator-content-sessions.md)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

운영자 콘텐츠 목록·상세 응답은 콘텐츠 정보만 반환하고 회차 상세를 포함하지 않는다. 공개 회차 목록은
`PUBLISHED` 콘텐츠의 `SCHEDULED` 회차만 반환하므로 소유 운영자가 생성한 `PENDING` 회차, 심사 대기 변경 요청,
`REJECTED`·`COMPLETED`·`CANCELLED` 회차를 화면 새로고침 뒤 복구할 수 없다.

생성·변경 요청·취소 명령 응답만 클라이언트 상태에 추가하면 요청 직후에는 표시할 수 있지만, 재접속이나 새로고침 뒤에는
서버의 현재 상태를 다시 구성할 읽기 계약이 필요하다. 기존 운영자 콘텐츠 상세에 회차 배열을 추가할지, 콘텐츠별 회차
목록 API를 분리할지 결정해야 한다.

## 결정 동인과 불변 조건

- 활성 `OPERATOR`는 담당 지역과 콘텐츠 소유 관계를 모두 만족한 경우에만 회차를 조회할 수 있다.
- 소유 운영자는 공개 여부와 관계없이 소프트 삭제되지 않은 자신의 콘텐츠에 연결된 모든 회차 상태를 복구할 수 있어야 한다.
- `PENDING` 변경 요청은 실제 `SCHEDULED` 회차를 바꾸지 않으므로 현재 회차와 후보 값을 구분해 반환해야 한다.
- 공개 회차 API의 `PUBLISHED`·`SCHEDULED` 필터와 운영자 콘텐츠 상세 응답은 변경하지 않는다.
- 조회는 콘텐츠·회차·수정 요청·정원·예약·감사 기록을 변경하지 않는다.
- [ADR-0091](0091-store-content-wide-reservation-price-and-snapshot-at-payment-creation.md)의 콘텐츠 공통 예약 가격 결정을
  유지하고 회차별 가격을 도입하지 않는다.

## 결정

`GET /api/v1/operator/contents/{contentId}/sessions`를 운영자 소유 콘텐츠 회차 목록 API로 분리한다. 인증 주체가
활성 `OPERATOR`이고 현재 담당 지역이 콘텐츠 지역과 일치하며 `content.operator_id`가 인증 사용자와 같을 때만 조회한다.
콘텐츠가 소프트 삭제되지 않았다면 콘텐츠 상태와 관계없이 연결된 `PENDING`, `SCHEDULED`, `REJECTED`, `COMPLETED`,
`CANCELLED` 회차를 모두 반환한다.

각 목록 항목은 실제 `content_session`의 현재 상태·버전·일정·체크인 창·총정원·잔여 정원과 상태별 종결 정보를 반환한다.
대상 회차에 현재 `PENDING`인 `session_revision`이 있으면 `pendingChangeRequest`에 수정 요청 식별자, 기준 회차 버전,
후보 일정·체크인 창·정원과 제출 시각을 반환한다. 활성 변경 요청이 없으면 `pendingChangeRequest`는 `null`이다.
승인·반려로 종결된 변경 요청 이력은 이 목록에 포함하지 않는다.

목록은 `startsAt` 오름차순, 같은 시각이면 `sessionId` 오름차순으로 고정하고 P0에서는 페이지네이션과 상태 필터를
제공하지 않는다. 별도 운영자 회차 상세 API를 만들지 않으며 기존 운영자 콘텐츠 상세와 공개 회차 목록 응답은 변경하지 않는다.
가격은 `content.reservation_price`의 콘텐츠 공통 값으로 유지하고 회차 목록에 가격 필드를 추가하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 운영자 화면이 생성·변경 요청·취소 명령의 로컬 상태에 의존하지 않고 새로고침 뒤 서버 상태를 복구할 수 있다.
- 공개 API에 노출되지 않는 `PENDING`, `REJECTED`, `COMPLETED`, `CANCELLED` 회차를 소유 운영자에게만 제공한다.
- 심사 대기 후보와 실제 `SCHEDULED` 회차를 분리해 변경 요청 중에도 현재 예약 대상 값을 정확히 표시한다.
- 기존 콘텐츠 상세와 공개 회차 목록의 책임·응답 호환성을 유지한다.

### 수용한 단점과 위험

- 운영자 콘텐츠 상세와 회차 목록을 각각 호출해야 한다.
- P0 비페이지 목록이므로 한 콘텐츠의 회차 수가 크게 늘면 응답 크기와 조회 비용이 증가한다.
- 종결된 변경 요청 이력은 제공하지 않으므로 과거 승인·반려 내역을 이 API만으로 재현할 수 없다.

## 전환과 롤백

기존 스키마와 데이터 이관은 필요하지 않다. API 명세를 먼저 확정한 뒤 기존 `content_session`과 대상 회차별 현재
`PENDING` `session_revision`을 읽는 조회 경계, 응답 DTO와 권한·상태 회귀 테스트를 추가한다. 기존 운영자 콘텐츠 상세,
공개 회차 목록과 명령 API는 그대로 유지한다.

문제가 발생하면 신규 목록 API 라우팅을 비활성화하고 기존 명령 API를 유지한다. 배포된 응답 계약을 임의로 축소하지 않으며,
페이지네이션·상태 필터·상세 API가 필요해지면 새 API 계약과 호환 범위를 먼저 확정한다.

## 검증 방법

- 소유 운영자가 콘텐츠 상태와 관계없이 모든 회차 상태를 고정 정렬로 조회하고 회차가 없으면 빈 배열을 받는지 검증한다.
- `SCHEDULED` 회차에 `PENDING` 변경 요청이 있으면 실제 회차와 후보 값이 구분되고, 없으면
  `pendingChangeRequest = null`인지 검증한다.
- 다른 운영자의 콘텐츠, 다른 담당 지역, 비활성 역할과 인증 없는 요청이 회차·변경 요청 정보를 노출하지 않는지 검증한다.
- 없는 콘텐츠와 소프트 삭제된 콘텐츠가 `NOT_FOUND`이고 조회 과정에서 도메인 상태와 감사 기록이 바뀌지 않는지 검증한다.
- 기존 운영자 콘텐츠 상세와 공개 회차 목록의 응답·필터 회귀 테스트가 유지되는지 확인한다.

## 대체 조건

- 한 콘텐츠의 회차 수가 P0 비페이지 목록으로 감당할 수 없을 만큼 증가해 페이지네이션이나 상태·기간 필터가 필요해진다.
- 종결된 변경 요청의 승인·반려 사유와 처리 이력을 운영자 화면에서 조회해야 한다.
- 운영자 회차 상세 화면이나 회차 단건 딥 링크가 독립 제품 요구사항으로 확정된다.
