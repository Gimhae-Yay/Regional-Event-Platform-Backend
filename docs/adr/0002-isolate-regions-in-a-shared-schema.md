# ADR-0002: 공유 스키마에서 `region_id`와 소유 관계로 지역 격리

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-23
- 결정일: 2026-07-23
- 관련 요구사항: [PRD의 FR-01, FR-09, US-02, US-05](../local-stamp-platform-prd.md#8-기능-요구사항), [파일럿 콘텐츠 모델](../../docs-ref/local-stamp-pilot-scope-and-content-model-memo.md#2-콘텐츠-모델-원칙)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

초기 파일럿은 김해시와 동해시를 하나의 서비스에서 운영한다. 지역 관리자는 담당 지역만, 행사·체험 운영자는 자신에게 연결된 콘텐츠와 예약만 조회·변경할 수 있어야 한다. 전체 관리자는 지역 생성과 역할 부여를 위해 모든 지역을 관리해야 한다.

지역별 데이터베이스나 스키마를 분리하면 물리적 격리는 강화되지만, 두 지역으로 시작하는 MVP의 배포·마이그레이션·운영 비용이 커진다. 현재 콘텐츠 모델은 모든 콘텐츠와 운영 주체를 `region_id`로 연결하는 공유 모델을 전제로 한다.

## 결정 동인과 불변 조건

- 지역 관리자와 운영자는 권한이 없는 지역의 데이터에 접근할 수 없다.
- 역할만 검사하지 않고 담당 지역과 콘텐츠 소유 관계를 함께 검사한다.
- 전체 관리자 권한은 명시된 관리 기능에서만 지역 범위를 넘어 사용할 수 있다.
- 지역이 추가돼도 애플리케이션과 스키마를 지역별로 복제하지 않는다.
- 모든 지역 범위 작업은 감사 가능한 actor, region, entity 정보를 남긴다.
- 하위 데이터의 지역은 연결된 상위 데이터의 지역과 모순될 수 없다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 공유 DB·공유 스키마와 `region_id` 격리 | 배포와 마이그레이션이 단순하고 지역 추가 비용이 낮다. 지역 간 통합 운영이 쉽다. | 모든 조회·변경 경로에서 지역 조건 누락 위험이 있다. 애플리케이션 검증과 테스트가 필수다. | 높음. 물리 분리 전환 시 지역별 데이터 이관과 라우팅 계층이 필요하다. | 두 지역 파일럿과 단일 운영팀에 적합하다. |
| 2 | 공유 DB·지역별 스키마 | 물리적 네임스페이스가 분리되어 쿼리 누락 위험이 줄어든다. | 지역마다 Flyway 적용과 연결 라우팅이 필요하고 통합 조회가 복잡하다. | 높음 | 두 지역 규모에 비해 운영 비용이 크다. |
| 3 | 지역별 데이터베이스 | 장애와 접근 권한을 가장 강하게 격리할 수 있다. | 배포, 백업, 모니터링, 연결 관리와 전체 관리자 기능이 복잡해진다. | 매우 높음 | 규제나 독립 운영 요구가 없는 파일럿에는 과도하다. |

## 결정

초기 MVP는 하나의 MySQL 데이터베이스와 공유 스키마를 사용한다. 지역 범위가 있는 주요 집계와 운영 조회 대상에는 `region_id`를 저장하고, 콘텐츠에는 `operator_id`를 함께 저장해 `사용자-담당 지역-운영자-콘텐츠` 소유 관계를 검증한다.

컨트롤러의 역할 검사만으로 권한을 완료하지 않는다. 애플리케이션 서비스와 저장소 쿼리는 현재 사용자의 허용 `region_id`와 필요한 소유 식별자를 입력받아 범위를 제한한다. 하위 엔터티를 생성할 때 요청의 지역 값을 그대로 신뢰하지 않고 상위 엔터티에서 지역을 확인한다.

전체 관리자의 지역 범위 우회는 전체 관리자 전용 유스케이스에만 명시적으로 허용한다. 일반 사용자·운영자·지역 관리자 경로에서 전역 조회 메서드를 재사용하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 두 지역과 이후 추가 지역을 하나의 배포·마이그레이션으로 운영할 수 있다.
- 지역별 필터, 집계와 전체 관리자 운영 기능을 같은 모델에서 제공할 수 있다.
- 지역 단위 데이터 이관이 필요할 때 `region_id`를 추출 기준으로 사용할 수 있다.

### 수용한 단점과 위험

- 저장소 쿼리에서 지역 조건이 누락되면 교차 지역 정보 노출이 발생할 수 있다.
- MySQL 자체의 행 수준 보안에 의존하지 않으므로 애플리케이션 검증과 테스트 책임이 커진다.
- 하위 엔터티에 `region_id`를 중복 저장하면 상위 엔터티와 불일치할 위험이 있다.
- 하나의 DB 장애가 모든 지역에 영향을 준다.

## 전환과 롤백

신규 서비스이므로 기존 지역 데이터 이관은 없다. Flyway 스키마에서 지역 범위 엔터티의 `region_id` 외래 키와 조회 인덱스를 정의하고, 저장소 인터페이스에 지역 범위 메서드를 우선 제공한다.

지역별 물리 분리가 필요해지면 새 ADR로 분리 단위를 결정한다. `region_id`별 데이터 내보내기, 전역 식별자 유지, 지역 라우팅, 전체 관리자 통합 조회와 단계별 이중 쓰기 여부를 정의한 뒤 전환한다. 물리 분리 도중에도 기존 공유 스키마를 즉시 제거하지 않는다.

## 검증 방법

- 김해시 담당자가 동해시 콘텐츠·회차·예약·방문을 ID 직접 지정과 목록 조회 모두에서 접근할 수 없는지 통합 테스트한다.
- 같은 지역의 다른 운영자가 소유한 콘텐츠와 예약에 접근할 수 없는지 검증한다.
- 전체 관리자 전용 기능과 일반 기능의 권한 경계를 검증한다.
- 하위 엔터티 생성 시 요청 지역과 상위 엔터티 지역이 다르면 거부되는지 검증한다.
- 권한 거부 로그에 actor, requested region, resource owner와 `requestId`를 남기되 개인정보는 남기지 않는다.
- 교차 지역 접근이 한 건이라도 허용되면 실패로 판정한다.

## 대체 조건

- 법률·계약·공공기관 요구로 지역별 물리 데이터 격리가 필요해진다.
- 특정 지역의 장애나 부하를 다른 지역과 분리해야 한다.
- 지역별 독립 배포, 스키마 버전 또는 데이터 보존 정책이 필요해진다.
- 지역 수와 데이터 규모 증가로 단일 DB의 운영 한계를 지속적으로 초과한다.
