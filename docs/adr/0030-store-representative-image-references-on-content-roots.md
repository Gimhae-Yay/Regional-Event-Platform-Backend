# ADR-0030: 대표 이미지 참조를 콘텐츠와 수정본 루트에 직접 저장

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-29
- 결정일: 2026-07-29
- 관련 요구사항: [지역·콘텐츠 카탈로그](../p0/content-catalog.md)의 `FR-03`·`FR-14` 이미지 정책과 [대표 이미지 업로드 API](../api/p0/content/upload-representative-image.md)
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: [#50](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/50), [#76](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/pull/76)
- 대체 대상: [ADR-0029](0029-rebuild-initial-p0-flyway-schema.md)의 `V1__initial_p0_schema.sql` 내 대표 이미지 연결 테이블 구성과 이후 이관 범위

## 맥락

대표 이미지 모델은 현재 콘텐츠와 수정본의 이미지 객체 연결을 각각 별도 테이블에 저장한다. 그러나 연결 자체에는
`assigned_at` 외 별도 상태·행위·이력이 없고, 대표 이미지는 `Content` 또는 `ContentRevision`의 속성이다.

[ADR-0029](0029-rebuild-initial-p0-flyway-schema.md)는 P0 전체 스키마를 단일 V1으로 재구성하면서 당시 ERD의
두 대표 이미지 연결 테이블을 포함했다. 이 ADR은 단일 V1을 기준으로 삼는 결정은 유지하고, 대표 이미지 연결의
물리 모델과 그 이후 증분 이관 범위만 대체한다.

PR #76의 검토에서 하나의 `image_object`가 두 연결 테이블에 동시에 연결될 수 있고, 한쪽 연결 제거 뒤 즉시 S3
원본을 삭제하면 다른 쪽 조회 경로가 깨질 수 있음이 확인됐다. 이는
[ADR-0016](0016-use-private-s3-presigned-urls-and-immediate-image-deletion.md)의 즉시 삭제 정책과 충돌한다.

수정본은 공개 콘텐츠를 직접 바꾸지 않고 심사 당시 후보 상태를 보존하는 스냅샷이다. 대표 이미지가 변경되지 않은
수정본도 당시의 대표 이미지를 재현해야 하므로, 현재 `content`와 `content_revision`이 같은 불변 `image_object`를
참조하는 것은 정상이다. 문제의 본질은 중복 참조가 아니라 참조가 남은 객체를 삭제하는 것이다.

## 결정 동인과 불변 조건

- 콘텐츠와 수정본은 각각 대표 이미지 객체를 최대 한 개만 가질 수 있다.
- 하나의 불변 `image_object`는 현재 콘텐츠와 여러 수정본 스냅샷이 함께 참조할 수 있다.
- 이미지 객체를 S3에서 삭제하거나 `DELETE_PENDING`으로 전환하기 전에는 `content`와 모든 `content_revision`의
  직접 FK 참조가 없는지 같은 MySQL 트랜잭션에서 검사한다.
- 수정본 심사 중 현재 공개 콘텐츠와 이미지는 바뀌지 않으며, 승인 반영·수정본 종결·감사 기록은 하나의 MySQL
  트랜잭션에서 처리한다.
- [ADR-0016](0016-use-private-s3-presigned-urls-and-immediate-image-deletion.md)의 비공개 S3, 서명 URL, 참조 제거 뒤 즉시 삭제와 실패 재시도 정책은 유지한다.

## 결정

`content.representative_image_object_id`와 `content_revision.candidate_image_object_id`를 각각
`image_object.image_object_id`의 nullable FK로 둔다. 두 FK 사이와 각 테이블 안에서 이미지 객체의 유일성을
강제하지 않으며, 연결 시각은 각 루트의 `representative_image_assigned_at`, `candidate_image_assigned_at`에
저장한다. JPA에서는 두 참조를 `ImageObject`를 향한 지연 로딩 `@ManyToOne`으로 모델링한다. 기존
`content_representative_image`, `content_revision_representative_image` 테이블은 사용하지 않는다.

수정본을 만들 때 대표 이미지가 바뀌지 않아도 현재 이미지 객체와 연결 시각을 수정본에 스냅샷으로 저장한다.
대표 이미지 변경 후보가 있으면 그 새 이미지 객체를 저장한다. 승인 시 후보 이미지 객체를 `content`에 반영하되
`content_revision`의 참조는 제거하지 않는다.

이미지 교체, 콘텐츠 삭제, 수정본 파기처럼 참조를 제거하는 명령은 대상 `image_object` 행을 잠근 뒤 `content`와
모든 `content_revision`의 FK 참조가 없는지 검사한다. 참조가 0개일 때만 `DELETE_PENDING`으로 전환하고 커밋 뒤
S3 삭제를 시도한다. 두 이미지 객체를 함께 처리할 때는 ID 오름차순으로 잠근다.

## 결과와 트레이드오프

### 기대 효과

- 대표 이미지를 소유한 콘텐츠·수정본 루트에서 직접 읽고 변경할 수 있다.
- 연결 테이블, 공유 PK 매핑, 추가 조인을 제거한다.
- 승인·반려·철회된 수정본을 포함해 당시 대표 이미지 상태를 재현할 수 있다.
- 이미지 삭제 안전성의 기준을 중복 금지가 아닌 실제 참조 수로 일관되게 둔다.

### 수용한 단점과 위험

- 수정본이 이미지를 참조하는 동안 S3 원본은 삭제할 수 있어 저장 공간이 더 든다.
- 이미지 명령이 `ImageObject` 행 잠금과 참조 0건 검사 규약을 빠뜨리면 참조 중 객체를 삭제할 수 있다.
- 수정본 보존·파기 기간이 확정되기 전에는 해당 수정본이 참조한 이미지도 함께 보존된다.

## 전환과 롤백

Flyway로 두 직접 FK와 연결 시각 컬럼을 먼저 nullable로 추가한다. 기존 연결 테이블의 값을 각 루트 컬럼에
이관하며, 같은 이미지 객체가 양쪽에 있으면 두 참조를 모두 보존한다. 애플리케이션의 조회·연결·교체·삭제 경로를
직접 FK와 참조 0건 검사 규약으로 전환한 뒤 기존 연결 테이블을 제거한다.

V2가 아직 `dev`에 병합·적용되지 않았으므로 V1은 변경하지 않고 V2에서 대표 이미지 FK의 `UNIQUE` 제약과
교차 중복 차단을 제거한다. 전환 중 문제가 생기면 V2를 병합하지 않고 작업 브랜치에서 수정한다. V2가 적용된
뒤의 정책 변경은 V3 이상의 새 migration으로만 수행한다.

## 검증 방법

- 같은 이미지 객체가 현재 콘텐츠와 하나 이상의 수정본에 함께 연결되는지 검증한다.
- 수정본 승인 뒤 원본은 후보 이미지로 바뀌고 수정본은 해당 이미지 참조를 유지하는지 검증한다.
- 이미지 교체·콘텐츠 삭제·수정본 파기에서 모든 직접 FK 참조가 제거되기 전에는 `DELETE_PENDING`으로 전환되지 않는지 검증한다.
- V1의 두 연결 테이블이 같은 이미지 객체를 참조한 데이터가 V2 뒤에도 두 직접 FK로 보존되는지 검증한다.
- 이미지 행 잠금과 참조 검사 동시 요청에서 참조 중 객체가 삭제되지 않는지 MySQL 통합 테스트로 검증한다.

## 대체 조건

- 콘텐츠당 여러 이미지, 순서·캡션·노출 기간 또는 복수 이미지 역할이 P0 범위에 들어온다.
- 대표 이미지 연결 자체의 변경 이력이나 별도 승인 상태를 조회 계약으로 제공해야 한다.
- 수정본 보존으로 인한 저장 비용이 합의한 한계를 지속적으로 넘고 별도 보관·파기 정책이 채택된다.
