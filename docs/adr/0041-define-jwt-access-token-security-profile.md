# ADR-0041: JWT Access Token 보안 프로필을 확정한다

- 상태: 채택됨
- 기록 유형: 신규

- 결정일: 2026-07-30

- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: [#161 Spring Security와 JWT Access Token 인증 기반 구현](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/161)

## 맥락

ADR-0005는 짧은 수명의 서명된 JWT Access Token을 채택했지만, 구체적인 유효기간과 서명 알고리즘,
발급자·대상 검증 및 claim 계약은 보안 설정과 API 명세에서 확정하도록 남겼다. 현재 저장소에는 Spring
Security 의존성만 있고 Access Token의 서명·검증 라이브러리, 키 설정, 발급·검증 규칙이 없다.

보호 업무 API는 Refresh Token을 인증 수단으로 받아서는 안 되며, 변조·만료·다른 발급자·다른 대상의
토큰을 같은 방식으로 거부해야 한다. 역할, 담당 지역, 콘텐츠 소유권은 변화할 수 있으므로 오래된
JWT claim을 최종 권한 근거로 사용해서는 안 된다.

## 결정 동인과 불변 조건

- Access Token은 일반 보호 API에서 `Authorization: Bearer <accessToken>`으로만 수신한다.
- 토큰 서명 키와 토큰 원문은 코드·저장소·로그·오류 응답에 남기지 않는다.
- Refresh Token은 Bearer Access Token으로 사용될 수 없어야 한다.
- 검증은 알고리즘, 키 식별자, 서명, 발급자, 대상, 토큰 유형, 만료 시각을 모두 확인한다.
- 인증 경계는 사용자를 식별할 뿐이며, 역할·지역·소유권의 최종 검증은 현재 DB 상태로 수행한다.
- 키 교체 중에도 정상적인 배포는 가능해야 하며, 키 유출 시에는 즉시 해당 키를 검증 집합에서 제거할 수 있어야 한다.

## 결정

Access Token은 Spring Security JOSE/Nimbus 기반으로 발급·검증하는 HMAC-SHA256 JWT로 한다. 구현은
직접 서명 문자열을 조립하거나 파싱하지 않는다.

발급·검증 키는 저장소에 넣지 않고 외부 설정 또는 비밀 저장소에서 Base64로 주입한다. 활성 키는 256비트
이상이어야 하며 JWT 헤더의 `kid`로 식별한다. 발급은 활성 키 하나만 사용하고, 검증은 활성 키와 직전 키를
최대 Access Token 유효기간 동안만 허용한다. 정상 회전은 새 키를 활성화한 뒤 직전 키를 15분 후 제거한다.
키 유출은 직전 키 유예 없이 유출 키를 즉시 제거하고, 해당 키로 발급한 Access Token의 조기 무효화를
수용한다.

Access Token의 유효기간은 발급 시각부터 15분으로 고정한다. 발급자(`iss`)는
`regional-event-platform`, 대상(`aud`)은 `regional-event-api`로 고정해 발급과 검증에서 모두 일치해야 한다.
시간 검증은 주입된 `Clock`을 기준으로 수행하며 별도의 만료 유예는 두지 않는다.

Access Token에는 아래 claim만 넣는다.

| Claim | 값 | 용도 |
| --- | --- | --- |
| `iss` | `regional-event-platform` | 발급자 검증 |
| `aud` | `regional-event-api` | 대상 검증 |
| `sub` | 양의 사용자 ID를 10진 문자열로 표현한 값 | 인증 주체 식별 |
| `token_type` | `ACCESS` | Refresh Token과의 사용 경계 검증 |
| `iat` | 발급 시각 | 수명 검증과 추적 |
| `exp` | 발급 시각으로부터 15분 | 만료 검증 |

`role`, `region_id`, 콘텐츠 소유권, 개인정보, Refresh Token의 `family_id`와 `jti`는 Access Token에 넣지 않는다.
성공한 검증은 `Long` 사용자 ID를 `SecurityContext`의 인증 주체로만 설정한다. Security 체인의 역할 기반
인가에 JWT claim을 사용하지 않으며, 업무 Service가 현재 DB의 활성 상태·역할·담당 지역·소유 관계를
검증한다.

## 결과와 트레이드오프

### 기대 효과

- 단일 백엔드에서 짧은 수명의 Access Token을 서명 검증만으로 처리하면서도 발급자·대상·유형 혼동을 막는다.
- Refresh Token을 보호 업무 API에 제시해도 `token_type` 검증에서 거부한다.
- 역할·지역·소유권을 claim에 넣지 않아 승인·권한 변경 뒤 오래된 토큰 정보에 의존하지 않는다.
- `kid`와 제한된 직전 키 검증으로 무중단 정상 키 회전과 유출 키의 즉시 차단 경로를 함께 둔다.

### 수용한 단점과 위험

- HMAC 키를 가진 애플리케이션 인스턴스는 토큰을 발급할 수 있다. 외부 검증자가 필요해지면 비대칭 키 방식으로 전환해야 한다.
- Access Token은 개별 폐기하지 않는다. 키 유출이 아니면 최대 15분의 자연 만료까지 유효할 수 있다.
- 역할 정보를 매 요청의 JWT에서 바로 읽지 않으므로 도메인 권한 검증에 DB 조회가 필요하다.
- 직전 키 유예 중에는 이전 키로 발급된 Access Token이 최대 15분 더 유효하다.

## 전환과 롤백

신규 인증 구현이므로 이관할 기존 Access Token은 없다. 키와 발급자·대상 설정을 먼저 운영 환경에 주입하고,
발급기·검증기·Bearer 필터를 같은 배포에 넣는다. 설정이 없거나 활성 키가 256비트 미만이면 애플리케이션은
인증 기능을 시작하지 않는다.

정상 키 교체는 새 `kid`로 발급을 전환하고 15분 뒤 직전 검증 키를 제거한다. 검증 또는 배포 결함이 발생하면
직전 키를 활성 키로 되돌릴 수 있다. 키 유출은 단순 롤백으로 유출 키를 다시 활성화하지 않고, 유출 키를 제거한
뒤 모든 사용자의 재로그인을 요구한다.

## 검증 방법

- 정상 토큰, 만료 토큰, 변조 토큰, 다른 `iss`·`aud`·`token_type` 토큰, 알 수 없는 `kid`, 허용하지 않은 서명 알고리즘을 각각 거부하는지 검증한다.
- `sub`가 양의 사용자 ID가 아니면 인증 주체를 만들지 않는지 검증한다.
- Access Token에 역할·지역·소유권·Refresh Token 계열 claim이 없고, 검증 후 인증 주체가 사용자 ID뿐인지 검증한다.
- 활성 키 발급, 직전 키 검증, 유출 키 제거 후 거부를 `Clock` 기반 테스트로 검증한다.
- 토큰 원문·키·claim 값이 오류 응답과 로그에 포함되지 않는지 보안 통합 테스트로 검증한다.

## 대체 조건

- 외부 IdP, 별도 인증 서버 또는 독립 검증 서비스가 도입되어 검증자와 발급자가 분리된다.
- 키 유출 위험 또는 규정이 대칭 키 공유를 허용하지 않는다.
- Access Token의 개별 즉시 폐기, 더 짧거나 더 긴 유효기간, 다중 대상 API가 보안·제품 요구로 필요해진다.
- 역할·권한 정보를 JWT 기반으로 처리해야 하는 명확한 성능 요구가 생기고, 현재 DB 검증 원칙을 변경할 근거가 마련된다.
