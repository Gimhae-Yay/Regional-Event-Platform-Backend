# ADR-0032: 콘텐츠 철회 요청을 상태 로그 이벤트로 기록

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-07-30
- 결정일: 2026-07-30
- 관련 요구사항: [PRD](../local-stamp-platform-prd.md)의 `FR-14`, `CON-07`, `CON-09`
- 관련 단계: 단계 0. 정책·설계 확정, 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

운영자는 공개 콘텐츠의 철회를 요청하고 담당 지역 관리자가 승인해야 한다. 기존 ERD에는 철회 요청 전용 테이블이나
요청 상태 컬럼이 없지만, `content_log`에는 요청자, 사유와 시각을 담을 `actor_id`, `reason`, `date`, `status`
컬럼이 있다. `content` 상태를 요청 중 상태로 바꾸면 방문자에게 공개 중인 콘텐츠를 조기에 숨기므로 사용할 수 없다.

사용자는 기존 컬럼으로 요청을 보존할 수 있으면 별도 모델을 추가하지 않는 방식을 선택했다.

## 결정 동인과 불변 조건

- 철회 요청은 소유 운영자와 콘텐츠의 담당 지역이 일치할 때만 허용한다.
- 요청 중 콘텐츠는 계속 `PUBLISHED`이며 공개 목록·상세·예약 가능 여부의 현재 상태를 바꾸지 않는다.
- 요청 사유, 요청자와 요청 시각은 승인 전후에도 재현할 수 있어야 한다.
- 담당 지역 관리자만 미종결 철회 요청을 승인할 수 있고, 승인 시 최종 상태 전이·로그·감사 기록은 원자적이어야 한다.
- 중복 요청은 로그를 중복 생성하지 않고 기존 미종결 요청 결과를 반환한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | `content_log`에 `WITHDRAWAL_REQUESTED` 이벤트를 추가 | 기존 요청자·사유·시각 컬럼을 재사용하며, 콘텐츠의 공개 상태와 요청 이력을 분리한다. | 미종결 판정과 중복 요청 방지를 서비스 조건부 쓰기로 지켜야 한다. | 낮음. 상태 로그 카탈로그와 조회 규칙을 확장한다. | 사용자의 조건을 충족하고 P0에 가장 작다. |
| 2 | 별도 콘텐츠 철회 요청 테이블과 상태를 추가 | 요청·승인·반려·취소를 독립적으로 확장하기 쉽다. | 현재 목록에 없는 반려·취소 API, FK·인덱스·상태 전이가 추가돼 P0 범위를 넓힌다. | 중간. 새 테이블과 이관 경로가 필요하다. | 현재 최소 운영 API에는 과하다. |
| 3 | 운영자 요청 시 즉시 `WITHDRAWN`으로 전이 | 저장 모델이 가장 단순하다. | 지역 관리자 승인 요구와 `POST /region-admin/contents/{contentId}/withdraw` API가 무의미해진다. | 낮음 | 정책과 맞지 않는다. |

## 결정

`content_log.status`에 콘텐츠 현재 상태와 구별되는 `WITHDRAWAL_REQUESTED` 이벤트를 추가한다. 소유 운영자의
철회 요청은 대상 `content` 행을 `SELECT ... FOR UPDATE` 또는 동등한 행 잠금으로 잠근 뒤, 같은 트랜잭션에서
`content.status = PUBLISHED`와 가장 최근 철회 관련 로그를 다시 확인하고 요청 사유·actor·시각을 가진 이 로그를
추가한다. 콘텐츠의 현재 상태는 계속 `PUBLISHED`다.

가장 최근 철회 관련 로그가 `WITHDRAWAL_REQUESTED`이면 같은 운영자의 재요청은 새 로그를 만들지 않고 기존
요청 결과를 반환한다. 담당 지역 관리자의 승인 API도 같은 행 잠금 뒤 콘텐츠가 여전히 `PUBLISHED`이고 이 미종결
요청이 있는지 확인한 뒤, 요청 사유를 보존한 `WITHDRAWN` 로그 추가, `PUBLISHED → WITHDRAWN` 상태 전이와 성공
감사 이벤트를 하나의 MySQL 트랜잭션에서 커밋한다. `SUSPENDED`, `ENDED`, 이미 `WITHDRAWN` 상태이거나 미종결
요청이 없는 콘텐츠는 승인할 수 없다. 최신 철회 로그 판정은 `content_log(content_id, status, date, id)` 접근
경로를 사용한다.

P0에는 철회 요청 반려·취소 API를 추가하지 않는다. 새 반려·취소 요구가 생기면 요청 전용 모델과 전이 상태를
재검토한다.

## 결과와 트레이드오프

### 기대 효과

- 공개 상태를 훼손하지 않고 철회 요청과 승인 사실·사유를 재현할 수 있다.
- 새 테이블 없이 기존 콘텐츠 감사·상태 이력 경로를 재사용한다.
- 행 잠금 뒤 상태를 재검사해 중복 요청과 승인 경합에서 하나의 요청·최종 전이만 남기도록 제한할 수 있다.

### 수용한 단점과 위험

- `content_log`에 현재 상태가 아닌 이벤트 코드가 추가되어 조회 시 두 의미를 구분해야 한다.
- 반려·취소·다단계 심사 같은 요구에는 현재 이벤트만으로 충분하지 않아 별도 모델이 필요하다.

## 전환과 롤백

구현 전 결정이므로 데이터 이관은 없다. 상태 로그 카탈로그와 요청 API 계약을 먼저 반영하고, 조건부 로그 삽입과
승인 트랜잭션을 구현한다. 도입 중 문제가 발생하면 철회 요청·승인 명령을 중지하고 현재 `PUBLISHED` 콘텐츠를
그대로 유지한다. 이미 승인된 `WITHDRAWN` 상태를 자동으로 되돌리지 않는다.

## 검증 방법

- 소유 운영자만 `PUBLISHED` 콘텐츠에 철회 요청을 만들고, 요청 뒤에도 방문자 공개 상태가 유지되는지 검증한다.
- 같은 요청의 재시도와 동시 요청이 행 잠금 뒤 하나의 `WITHDRAWAL_REQUESTED` 로그만 남기고 기존 결과를 반환하는지 검증한다.
- 다른 지역 관리자와 다른 운영자가 요청·승인할 수 없는지 검증한다.
- 승인 시 `WITHDRAWN` 상태, 요청 사유를 보존한 로그와 감사 이벤트가 함께 커밋되고 실패 시 모두 롤백되는지 검증한다.
- 중단·종료·기철회·미요청 콘텐츠의 승인이 상태를 바꾸지 않고 충돌로 거부되는지 검증한다.

## 대체 조건

- 철회 요청의 반려·취소·재제출·복수 단계 심사 또는 SLA 조회가 필요해진다.
- 요청 건별 별도 식별자·첨부 자료·담당자 배정이 공개 또는 운영 계약으로 필요해진다.
- 상태 로그 이벤트와 현재 상태 조회의 결합이 운영 조회 성능이나 이해 가능성을 지속적으로 해친다.
