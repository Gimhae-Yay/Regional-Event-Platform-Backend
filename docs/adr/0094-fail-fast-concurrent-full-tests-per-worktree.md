# ADR-0094: 동일 작업 트리의 동시 전체 테스트를 OS 파일 잠금으로 빠르게 실패시킨다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-11
- 결정일: 2026-08-11
- 관련 요구사항: [P0 명세](../p0-spec.md#9-테스트-및-출시-수용-기준)의 자동화 테스트 합격 기준
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: [#687](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/687), [#691](https://github.com/Gimhae-Yay/Regional-Event-Platform-Backend/issues/691)
- 대체 대상: 없음

## 맥락

BUG #687에서 동일 작업 트리에서 시작한 두 전체 Gradle 테스트가 Testcontainers MySQL의 정리 경로와 Docker
자원을 함께 사용하면서 `MySqlDatabaseCleaner.truncate()`의 응답을 장시간 기다렸다. Testcontainers 컨테이너가
실행별로 분리돼도 Docker CPU·메모리·디스크 I/O와 Gradle 산출물 경로는 같은 작업 트리에서 공유된다.

ADR-0093은 정상적인 순차 실행의 Docker 디스크 I/O 병목만 줄이며, 중복 전체 실행을 막거나 DB 잠금 대기 시간을
제한하지 않는다. #691의 확정 범위는 첫 번째 전체 테스트는 계속 실행하고, 같은 실제 작업 트리에서 뒤늦게
시작한 전체 테스트만 즉시 실패시키는 것이다.

## 결정 동인과 불변 조건

- 같은 작업 트리의 두 번째 전체 테스트는 DB 정리 또는 Gradle 산출물 충돌까지 진행하지 않고, 이유가 드러나는
  안내와 함께 즉시 실패해야 한다.
- 잠금 범위는 실제 작업 트리의 정규화된 절대 경로로 구분한다. 브랜치명, 저장소명, 전역 Gradle 경로는 식별자로
  사용하지 않는다.
- 별도 git worktree와 독립 CI shard는 서로 차단하지 않는다.
- 정상 종료·테스트 실패·JVM 비정상 종료 뒤에는 다음 실행이 수동 정리 없이 잠금을 획득할 수 있어야 한다.
- 제품 코드와 제품 DB 설정은 변경하지 않는다.

## 결정

Gradle의 표준 전체 테스트 진입점인 `test`에 빌드 수명과 같은 테스트 전용 서비스를 연결한다. 서비스는
작업 트리 절대 경로의 `.gradle` 하위 잠금 파일에 Java NIO `FileChannel.tryLock()`으로 OS 배타 잠금을 획득한다.
이미 잠겨 있으면 두 번째 `test`는 테스트 worker를 시작하지 않고, 동일 작업 트리에서 전체 테스트가 실행 중임을
알리는 `GradleException`으로 즉시 종료한다.

첫 번째 실행은 서비스가 닫힐 때 잠금을 해제한다. 프로세스가 비정상 종료하면 OS가 보유한 파일 잠금을 해제하므로
잠금 파일 자체가 남아도 다음 실행을 막지 않는다. CI는 `fastTest`, `containerTestShard1`,
`containerTestShard2`처럼 독립 Gradle 작업 트리에서 실행되는 shard task를 사용하며, `test` 잠금을 적용하지
않는다.

## 결과와 트레이드오프

### 기대 효과

- 동일 작업 트리에서의 중복 전체 테스트가 Docker·MySQL 정리 단계까지 진행하지 않아 #687 증상을 증폭하지 않는다.
- 첫 실행은 중단되지 않고, 두 번째 실행은 확인 가능한 오류와 Gradle 테스트 결과를 남긴다.
- worktree별 잠금 파일 경로가 달라 별도 worktree와 독립 CI shard의 병렬성은 유지된다.

### 수용한 단점과 위험

- 같은 작업 트리에서 의도적으로 두 전체 테스트를 병렬 실행할 수 없다.
- `test` 이외에 새 전체 테스트 진입점을 추가하면 이 보호 장치 적용 여부를 함께 검토해야 한다.
- 파일 잠금이 신뢰되지 않는 파일 시스템에서 개발할 때는 재현 검증이 필요하다.

## 전환과 롤백

1. `test` 시작 직전에 작업 트리별 OS 파일 잠금을 획득하고, Gradle 빌드 종료 시 해제하도록 구현한다.
2. 첫 번째 실행 유지·두 번째 실행 fail-fast·정상 및 비정상 종료 후 해제·별도 worktree와 CI shard 비차단을
   회귀 검증한다.
3. 파일 잠금이 정상 실행을 차단하거나 CI shard를 직렬화하면 해당 테스트 서비스와 회귀 테스트를 함께 되돌리고,
   재현 환경·파일 시스템·명령을 troubleshooting 기록으로 남긴다.

이 결정은 제품 데이터나 외부 계약을 바꾸지 않으므로 데이터 이관·호환 계층은 필요 없다.

## 검증 방법

- 같은 작업 트리에서 장시간 실행 중인 첫 `test`를 유지한 채 두 번째 `test`를 실행해, 즉시 안내와 실패 코드가
  남는지 확인한다.
- 첫 `test`의 정상 종료와 강제 종료 뒤 각각 새 `test`가 잠금을 획득하는지 확인한다.
- 별도 git worktree의 `test`와 CI의 `fastTest`·`containerTestShard1`·`containerTestShard2`가 서로
  차단되지 않는지 확인한다.
- 전체 `./gradlew test`, `./gradlew build`가 통과하고 기존 MySQL 테스트 데이터 격리가 유지되는지 확인한다.

## 대체 조건

- CI 또는 로컬의 분리된 작업 트리가 같은 OS 잠금으로 잘못 차단된다.
- 파일 시스템이 프로세스 비정상 종료 뒤 잠금을 해제하지 않아 stale 잠금이 재현된다.
- 동일 작업 트리에서 병렬 전체 테스트가 반드시 필요한 확정 요구사항이 생겨, 테스트 DB와 Gradle 산출물을
  완전히 격리하는 새 정책이 필요해진다.
