# ADR-0102: QR 재스캔 충돌에도 기존 체크인 검증 우선순위를 유지

- 대체 대상: [ADR-0101](0101-reject-new-qr-rescans-after-check-in.md)의 새로운 키 검증 항목 나열을 검증 실행 순서로 해석할 수 있는 부분만 대체

## 맥락

ADR-0101은 새로운 `Idempotency-Key`의 QR 요청이 토큰, 예약·회차 참조, 인증·인가, 상태와 시간 검증을
거친다고 기록했다. 그러나 항목의 나열 순서가 기존 QR 체크인 API의 실행 순서와 달라, 토큰 검증을 인증과 멱등
결과 재생보다 먼저 수행하는 새 우선순위로 해석될 수 있다.

Issue #868은 이미 체크인된 예약의 새로운 키 재스캔 응답만 바꾸며, QR 만료, 인증·인가, 취소된 예약,
체크인 가능 시간 밖 요청과 그 밖의 기존 검증 우선순위·실패 계약은 변경하지 않는다. 따라서 ADR-0101의 항목
나열은 새 검증 순서를 결정한 것이 아니라는 점을 명확히 해야 한다.

## 결정 동인과 불변 조건

- 동일 키·동일 요청의 완료 결과 재생은 새로운 키의 QR 검증보다 먼저 판정해야 한다.
- 새로운 키 요청의 인증, 토큰, 예약·회차 참조, 권한, 상태와 시간 검증 우선순위는 기존 QR API 계약을 유지해야 한다.
- `QR_ALREADY_CHECKED_IN`은 기존 검증을 통과해 과거에는 기존 방문 성공을 반환하던 분기에서만 적용해야 한다.
- 기존 검증 실패를 이미 체크인 오류로 덮어쓰거나 공개 오류 코드·감사 사유를 바꾸면 안 된다.

## 결정

ADR-0101의 새로운 키 검증 항목 나열은 실행 순서를 새로 정의하지 않는다. QR 체크인의 정확한 검증 실행 순서와
실패 계약은 [QR 체크인 API 처리 규칙](../api/p0/check-in/check-in-by-qr.md#처리-규칙)을 계속 단일 기준으로 삼는다.

동일 키·동일 요청의 완료 기록은 기존과 같이 현재 QR 검증을 다시 수행하지 않고 저장 결과를 재생한다. 새로운 키는
기존 QR API의 인증, 멱등 키 점유, 토큰, 예약·회차 참조, 지역·소유 권한, 활성 회원 연결, 회차 상태와 체크인 창,
예약·방문 상태 판정 순서를 변경하지 않는다. 이 모든 기존 판정을 통과하여 과거에 기존 방문 성공을 반환하던
분기에서만 `409 QR_ALREADY_CHECKED_IN`으로 교체한다.

따라서 만료, 인증·인가, 취소·만료 예약, 취소·완료 회차, 체크인 창 밖 요청, 관계·방문 정합성 오류와
멱등 키 충돌·처리 중 응답은 ADR-0101을 이유로 우선순위나 공개 오류·감사 사유가 바뀌지 않는다.

## 결과와 트레이드오프

### 기대 효과

- QR 재스캔 정책 변경이 이미 체크인된 예약의 최종 응답 분기에만 제한된다.
- 동일 키 재생과 만료·권한·상태 실패의 기존 공개 결과가 유지된다.
- ADR과 API 명세 사이에서 검증 순서를 다르게 해석할 여지가 줄어든다.

### 수용한 단점과 위험

- 검증 순서의 상세 내용은 ADR에 중복하지 않고 API 명세를 함께 확인해야 한다.
- 향후 QR API 처리 순서를 의도적으로 바꾸려면 API 명세와 이 ADR의 유지 조건을 함께 재검토해야 한다.

## 전환과 롤백

데이터 이관과 스키마 변경은 없다. 문서에서는 ADR-0101의 재스캔 충돌 결정과 이 ADR의 검증 우선순위 보존을 함께
참조한다. 후속 구현은 기존 검증 흐름을 재배치하지 않고 기존 방문 성공 반환 분기만 충돌 실패로 교체한다.

이 보정을 되돌릴 데이터는 없다. 검증 순서를 실제로 변경해야 하면 이 ADR을 단순 삭제하거나 ADR-0101을 수정하지
않고, 새 ADR에서 변경할 우선순위와 공개 오류 호환성을 결정한다.

## 검증 방법

- 동일 키 성공·저장 실패 재시도가 현재 토큰 상태를 다시 검증하지 않고 최초 결과를 재생하는지 검증한다.
- 새로운 키의 만료·위변조 QR, 인증·인가 실패, 취소·만료 예약, 회차 상태와 체크인 창 실패가 기존 공개 오류와 감사 사유를 유지하는지 검증한다.
- 기존 검증을 모두 통과한 `CHECKED_IN` 예약과 일치하는 방문에만 `QR_ALREADY_CHECKED_IN`이 적용되는지 검증한다.
- `origin/dev`의 QR API 처리 규칙과 비교해 기존 검증 단계가 이동·삭제·재분류되지 않았는지 문서 diff와 회귀 테스트로 확인한다.

## 대체 조건

- QR 검증 우선순위를 의도적으로 바꿔야 하는 보안·개인정보·운영 요구가 별도로 확정된다.
- 공개 오류 우선순위의 변경을 수용하는 새 API 버전 또는 호환 정책이 채택된다.
