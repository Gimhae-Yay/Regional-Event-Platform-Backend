# ADR-0007: Transactional Outbox와 Spring Scheduler로 비동기 이벤트 전달

- 상태: 제안됨
- 기록 유형: 소급
- 기록일: 2026-07-24
- 결정일: 2026-07-22
- 관련 요구사항: [PRD의 FR-11, FR-12](../local-stamp-platform-prd.md#7-기능-요구사항), [기술 구성과 설계 원칙](../local-stamp-platform-prd.md#10-기술-구성과-설계-원칙), [M3 무료 예약·정원 정합성](../local-stamp-platform-milestones.md#m3-무료-예약정원-정합성), [M6 통합 기술 검증·파일럿 준비](../local-stamp-platform-milestones.md#m6-통합-기술-검증파일럿-준비)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

예약 확정·취소·변경 같은 핵심 거래가 커밋된 뒤에는 알림과 분석에 사용할 이벤트를 전달해야 한다.
외부 전달 실패를 예약 트랜잭션 안에서 처리하면 일시적인 전달 대상 장애가 예약 실패로 번질 수 있다. 반대로 거래
커밋 뒤 메모리에서만 이벤트를 생성하면 프로세스 종료 시 커밋된 거래의 이벤트가 유실될 수 있다.

2026-07-22 PRD와 기술 스택 문서는 MySQL 기반 Transactional Outbox에 이벤트를 저장하고 Spring Scheduler가
이를 폴링해 전달하며, MVP에서는 Kafka를 도입하지 않는다고 확정했다. 당시 대안 비교와 세부 운영 계약의 전체 기록은
남아 있지 않으므로, 이 ADR은 확인 가능한 선택을 소급해 기록하고 해당 선택에 필요한 전달·재시도 계약을 구체화한다.
알림 전달 채널은 현재 릴리스에서 확정하지 않았으며 이 ADR도 이메일, 문자, 푸시 같은 채널을 선택하지 않는다.

## 결정 동인과 불변 조건

- 예약 변경과 그 결과로 반드시 발생해야 하는 Outbox 이벤트는 하나의 MySQL 트랜잭션에서 함께 커밋하거나 함께
  롤백한다.
- 거래 커밋 뒤의 이벤트 전달 실패는 이미 성공한 예약 변경을 롤백하지 않는다.
- 프로세스 종료와 일시적인 전달 대상 장애가 발생해도 커밋된 이벤트를 유실하지 않는다.
- 정확히 한 번 전달을 주장하지 않고 최소 한 번 전달을 보장하며, 중복 전달을 소비자의 멱등 처리로 안전하게 만든다.
- 여러 애플리케이션 인스턴스가 동시에 폴링해도 같은 이벤트를 정상 경로에서 동시에 처리하지 않는다.
- 한 이벤트의 반복 실패가 뒤에 있는 다른 이벤트의 전달을 막지 않는다.
- 재시도, 수동 재처리와 정리 이력을 운영자가 추적할 수 있어야 한다.
- 예약 트랜잭션의 응답 시간과 정합성이 비동기 전달 대상의 가용성에 의존하지 않는다.
- Outbox payload에는 전달에 필요한 최소 정보만 저장하고 개인정보, 토큰과 비밀값을 포함하지 않는다.

## 결정

### 저장과 이벤트 계약

예약 확정·취소·변경처럼 FR-11과 FR-12에서 추적 또는 발행을 요구하는 상태 변경은 해당 변경과 같은 MySQL
트랜잭션에서 Outbox 행을 생성한다. Outbox 저장에 실패하면 거래도 롤백한다. 거래가 커밋된 뒤의 전달과 재시도는
별도 트랜잭션에서 수행하며 전달 실패로 원래 거래를 되돌리지 않는다.

Outbox 이벤트에는 다음 정보를 둔다.

- 변경되지 않는 `event_id`와 이벤트 계약 버전
- `event_type`, `aggregate_type`, `aggregate_id`와 필요한 경우 `region_id`
- 상태 변경 시각인 `occurred_at`과 최소화한 JSON payload
- `status`, `attempt_count`, `next_attempt_at`
- 점유 복구를 위한 `worker_id`, `locked_until`
- 성공·실패 추적을 위한 `published_at`, `last_error`, `resolved_at`, `resolution_reason`

한 Outbox 행은 알림 또는 분석 중 하나의 논리적 전달 단위를 나타낸다. 같은 거래가 두 목적의 이벤트를 모두 요구하면
각 이벤트를 같은 거래 트랜잭션에 별도 행으로 저장하여 한쪽 실패가 다른 쪽을 막지 않게 한다. 구체적인 알림 채널은
별도 결정으로 남긴다.

전달 순서는 전체 또는 집계 단위로 정확히 보장하지 않는다. 이벤트에 집계 식별자와 계약 버전을 포함하고, 순서가
정확성에 영향을 주는 소비자는 현재 집계 상태나 단조 증가하는 집계 버전을 확인해 오래된 이벤트를 무시한다.

### 전달 의미와 소비자 멱등성

전달 보장은 최소 한 번이다. 전달 대상이 성공 응답을 반환한 뒤 Outbox의 완료 상태를 기록하기 전에 프로세스가
종료되면 같은 `event_id`가 다시 전달될 수 있다. DB와 전달 대상 사이에 분산 트랜잭션을 만들거나 정확히 한 번 전달을
주장하지 않는다.

모든 소비자는 `event_id`를 멱등 키로 사용한다. 소비자의 처리 이력에 `event_id` 고유 제약을 두거나 결과 저장과
이벤트 처리 기록을 같은 트랜잭션에서 커밋한다. 이미 처리한 이벤트가 다시 들어오면 외부 효과를 반복하지 않고 이전
성공 결과를 반환한다. 외부 API를 호출하는 어댑터는 지원되는 경우 같은 `event_id`를 외부 멱등 키로 전달한다.

### 폴링과 동시 처리

Spring Scheduler는 기본 5초의 fixed-delay 방식으로 실행하고 한 번에 최대 100건을 점유한다. 이 값은 설정으로
관리하고 M6 부하 검증 결과에 따라 조정할 수 있다.

각 실행은 `next_attempt_at`이 현재 시각 이하인 `PENDING` 이벤트와 점유 시간이 만료된 이벤트를 대상으로 한다.
MySQL 8의 `SELECT ... FOR UPDATE SKIP LOCKED`와 조건부 상태 변경을 사용해 짧은 트랜잭션에서 대상 행을
`PROCESSING`으로 점유하고 `worker_id`, `locked_until`을 기록한다. 행 잠금은 점유 정보가 커밋되면 해제하며
외부 전달 중에는 DB 트랜잭션과 행 잠금을 유지하지 않는다.

여러 인스턴스에서 Scheduler가 실행되어도 DB 점유가 처리 권한의 기준이다. 작업자가 종료되면 `locked_until`이
지난 이벤트를 다른 작업자가 다시 점유한다. 점유 시간은 전달 타임아웃보다 길게 설정하고, 처리 중 안전하게 갱신할 수
있게 한다.

### 재시도, 실패 격리와 수동 재처리

일시적인 네트워크·전달 대상 오류는 지수 백오프와 지터를 적용해 최대 10회 재시도한다. 초기 지연은 10초, 최대
지연은 1시간으로 두며 모두 설정으로 관리한다. payload 또는 계약 검증처럼 재시도로 회복되지 않는 오류는 즉시
`FAILED`로 전환한다. 재시도 한도를 소진한 이벤트도 `FAILED`로 격리하고 다음 이벤트 처리를 계속한다.

`FAILED` 이벤트는 자동 삭제하지 않는다. 운영자는 원인을 수정한 뒤 같은 `event_id`와 payload를 유지한 채
`PENDING`으로 되돌려 수동 재처리할 수 있다. 이벤트가 더 이상 유효하지 않아 폐기해야 하면 `DISCARDED`로 종결하고
처리자, 시각과 사유를 기록한다. 수동 재처리와 폐기는 보호된 운영 명령으로만 수행하며 이벤트 payload를 임의로
수정하지 않는다. 계약을 정정해야 하면 새 `event_id`를 가진 보정 이벤트를 생성하고 두 이벤트의 관계를 남긴다.

### 완료 데이터 보관과 정리

`COMPLETED`와 운영자가 종결한 `DISCARDED` 이벤트는 종결 시점부터 30일 동안 보관한 뒤 작은 배치로 하드 삭제한다.
정리 작업도 조건과 배치 크기를 고정해 반복 실행에 안전하게 만든다. `FAILED`와 처리 중인 이벤트는 보관 기간이
지났다는 이유로 삭제하지 않는다.

5초 폴링, 100건 배치, 최대 10회 재시도와 30일 보관은 MVP의 초기 운영값이다. 측정 결과에 따라 이 값을 변경하는
것은 같은 저장 원자성, 최소 한 번 전달, 멱등성, 점유와 실패 격리 원칙을 유지하는 한 이 ADR을 대체하지 않는다.

## 결과와 트레이드오프

### 기대 효과

- 예약 변경과 이벤트 기록 사이에 유실 구간이 없고 애플리케이션 재시작 뒤에도 전달을 재개할 수 있다.
- 전달 대상의 지연과 장애가 예약 트랜잭션의 성공을 되돌리지 않는다.
- MySQL과 Spring Boot만으로 MVP의 재시도, 장애 격리와 운영 추적 요구를 충족한다.
- 여러 인스턴스가 같은 Outbox를 처리할 수 있고 작업자 종료 뒤 점유를 회수할 수 있다.
- `event_id`를 기준으로 중복 전달과 수동 재처리를 안전하게 처리할 수 있다.

### 수용한 단점과 위험

- Outbox 쓰기, 폴링과 상태 변경이 MySQL 부하를 늘린다.
- 폴링 주기만큼 전달 지연이 발생하며 엄격한 실시간 전달을 보장하지 않는다.
- 성공 전달 뒤 완료 기록 전 장애가 발생하면 중복 전달되므로 모든 소비자가 멱등 계약을 구현해야 한다.
- 전체 또는 집계 단위의 전달 순서를 보장하지 않으므로 순서에 민감한 소비자는 오래된 이벤트를 식별해야 한다.
- 점유 만료, 독성 이벤트, 수동 재처리와 보관 정리를 애플리케이션 운영 범위에서 관리해야 한다.
- Outbox 행 저장 실패는 이벤트 유실을 막기 위해 원래 거래도 실패시킨다.

## 전환과 롤백

신규 구현이므로 기존 Outbox 데이터 이관은 없다. Flyway로 Outbox 테이블, 조회 인덱스와 상태 제약을 추가한 뒤
거래 트랜잭션의 이벤트 저장, 소비자 멱등 처리, Scheduler 전달기, 재시도·수동 재처리, 정리 작업 순으로 구현한다.
Scheduler를 활성화하기 전에 저장과 멱등성 검증을 완료한다.

전달기에 장애가 생기면 Scheduler를 중지해 새 이벤트를 `PENDING`으로 보존한다. 원래 거래 처리는 계속 Outbox에
이벤트를 적재하며, 원인을 수정한 뒤 폴링을 재개한다. 이미 외부 효과가 발생한 이벤트는 삭제나 상태 되돌리기로
취소하지 않고 멱등 재처리 또는 별도의 보정 이벤트로 복구한다.

Kafka나 CDC로 전환할 때도 거래와 Outbox 저장의 원자성 및 `event_id` 계약을 먼저 유지한다. 새 전달기를 병행해
전달 수와 지연을 비교하고, 기존 Scheduler의 backlog가 없음을 확인한 뒤 읽기 주체를 전환한다. 전환 검증 중에는
새 전달기를 중지하고 Scheduler로 돌아갈 수 있어야 한다. Outbox 자체를 제거하려면 DB와 새 전달 인프라 사이의
원자성 및 복구 방법을 새 ADR에서 먼저 확정한다.

## 검증 방법

- 예약 변경과 Outbox 저장 사이에 예외를 발생시켜 두 변경이 함께 롤백되는지 MySQL Testcontainers 통합 테스트로
  검증한다.
- 거래 커밋 뒤 전달 전에 프로세스를 종료하고 재시작해 이벤트가 유실되지 않는지 검증한다.
- 전달 성공 뒤 완료 상태 기록 전에 장애를 발생시켜 같은 `event_id`가 재전달되고 소비자 효과는 한 번만 발생하는지
  검증한다.
- 두 개 이상의 Scheduler 인스턴스가 같은 이벤트를 경합할 때 DB 점유와 만료 복구가 동작하는지 검증한다.
- 일시 오류의 백오프·재시도, 영구 오류의 즉시 격리와 한 이벤트 실패 뒤의 후속 이벤트 처리를 검증한다.
- `FAILED` 이벤트를 수동 재처리해 같은 `event_id`가 유지되고 처리자와 사유가 기록되는지 검증한다.
- 정리 작업이 30일이 지난 `COMPLETED`·`DISCARDED`만 삭제하고 `FAILED`·`PROCESSING`은 보존하는지 검증한다.
- `outbox_pending_count`, `outbox_failed_count`, 가장 오래된 대기 이벤트의 나이, 시도·성공·실패 수와 처리 시간을
  지표로 수집한다. `FAILED`가 한 건이라도 생기거나 가장 오래된 대기 시간이 운영 임계값을 넘으면 알림한다.
- 구조화 로그에는 `event_id`, 이벤트 유형, 집계 식별자, 시도 횟수와 결과를 남기되 payload와 개인정보는 남기지
  않는다.

## 대체 조건

- 인덱스, 배치와 폴링 주기를 조정한 뒤에도 Outbox 부하가 예약 거래의 DB 응답 시간이나 가용성 목표를 침해한다.
- 가장 오래된 대기 이벤트의 전달 지연이 M6에서 확정한 운영 목표를 반복적으로 충족하지 못한다.
- 독립 소비자 수가 늘어 소비자별 offset, 장기간 재생, fan-out 또는 파티션 단위 순서 보장이 필요해진다.
- 이벤트 발생량과 보관량이 MySQL의 운영 가능한 범위를 지속적으로 넘는다.
- 조직이 Kafka 또는 CDC를 안정적으로 운영할 인력, 관측과 장애 복구 절차를 갖추고 전환 편익이 운영 비용보다 커진다.
- 외부 규제나 계약이 현재의 최소 한 번 전달과 30일 운영 보관 정책보다 강한 전달·감사 보장을 요구한다.
