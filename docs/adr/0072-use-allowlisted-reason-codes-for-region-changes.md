# ADR-0072: 지역 변경 감사 사유 코드를 허용 목록으로 관리

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-08-07
- 결정일: 2026-08-07
- 관련 요구사항: [전체관리자](../p1/platform-admin.md)의 `ADM-05`, [P1 명세](../p1-spec.md)의 7.4 권한·감사·개인정보
- 관련 단계: 단계 3. 확장 의사결정
- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

P1은 전체관리자의 지역 변경에 사유와 증빙 참조를 남기고, P0의 `audit_event.reason_code`를 재사용한다.
자유 입력 사유를 저장하는 열은 없으며, API가 형식만 검사한 임의 코드를 허용하면 `A`처럼 업무 의미를
재현할 수 없는 값도 기준 감사 기록에 남을 수 있다. 지역 생성과 공개 여부 변경에서 클라이언트가 선택할 수 있는
사유의 범위와 성공·실패 감사 코드의 소유권을 확정해야 한다.

## 결정 동인과 불변 조건

- 지역 변경의 업무 사유를 코드만으로 안정적으로 해석할 수 있어야 한다.
- 사유 코드와 증빙 참조에는 개인정보, 토큰, 비밀값을 저장하지 않는다.
- 지역 생성과 공개 여부 변경 요청은 사유 코드와 증빙 참조를 모두 제공해야 한다.
- 성공 감사에는 검증된 요청 사유 코드를 저장하고, 실패 감사에는 요청값이 아닌 서버가 판정한 실패 코드를 저장한다.
- 허용하지 않은 사유 코드는 도메인 변경 전에 `400 INVALID_INPUT`으로 거부한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 추천안: API별 사전 정의 `reasonCode`만 허용 | 감사 의미가 안정적이고 개인정보·무의미한 코드 유입을 차단한다. | 새 업무 사유가 생기면 API 계약과 클라이언트를 함께 갱신해야 한다. | 중간. 허용 코드와 저장·검증 경로를 함께 바꿔야 한다. | 기존 `reason_code` 모델과 P1 감사 요구에 가장 적합하다. |
| 2 | 자유 입력 `reason`을 별도 열에 저장 | 구체적인 사유를 직접 기록할 수 있다. | 스키마, 개인정보, 길이, 검색과 보관 정책이 추가되고 현재 ERD를 변경해야 한다. | 높음 | 자유 입력 요구와 저장 근거가 없어 현재 범위를 넘는다. |
| 3 | 형식만 맞는 임의 `reasonCode` 허용 | 새 코드 추가에 서버 계약 변경이 필요 없다. | 코드 의미를 보장할 수 없어 감사 재현성과 집계가 약해진다. | 낮음 | `ADM-05`의 사유 기록을 충족하기에 부족하다. |

## 결정

지역 생성과 공개 여부 변경 API는 다음 허용 목록에 포함된 `reasonCode`만 받는다.

| 작업 | 허용 `reasonCode` |
| --- | --- |
| 지역 생성 | `PILOT_REGION_ADDITION`, `SERVICE_AREA_EXPANSION`, `ADMINISTRATIVE_REORGANIZATION` |
| 공개 전환 (`isPublic = true`) | `REGION_LAUNCH`, `REGION_REOPEN` |
| 비공개 전환 (`isPublic = false`) | `REGION_PREPARATION`, `REGION_OPERATION_ENDED`, `ADMINISTRATIVE_REORGANIZATION` |

서버는 앞뒤 공백을 제거한 뒤 요청 작업과 목표 공개 여부에 맞는 허용 목록을 검증한다. 성공하면 선택한
`reasonCode`를 `audit_event.reason_code`에 저장한다. `evidenceReference`는 별도 필수 입력으로 받아
`audit_event.evidence_reference`에 저장하며, 상세 설명 자체가 아니라 비밀값 없는 업무 티켓·결재·증빙의
참조를 전달한다.

허용하지 않은 코드는 `400 INVALID_INPUT`으로 거부하고 감사 이벤트를 만들지 않는다. 지역 상태 조건을 확인한 뒤
거부된 요청의 실패 감사에는 클라이언트가 보낸 업무 사유가 아니라 `REGION_AVAILABILITY_CONFLICT`처럼 서버가
판정한 실패 코드를 저장한다. 허용 코드를 추가하거나 의미를 바꿀 때는 API 명세와 검증 테스트를 같은 변경에서
갱신한다. 기존 코드의 제거·의미 변경은 호환성 영향을 먼저 검토한다.

## 결과와 트레이드오프

### 기대 효과

- 지역 변경 감사의 업무 사유를 코드별로 일관되게 조회·집계할 수 있다.
- 임의 문자열과 개인정보가 `reason_code`에 유입되는 경로를 차단한다.
- 성공의 업무 사유와 실패의 서버 판정 코드를 구분할 수 있다.

### 수용한 단점과 위험

- 허용 목록에 없는 새 사유로는 계약을 갱신하기 전까지 지역 변경을 완료할 수 없다.
- 클라이언트는 작업과 목표 공개 여부에 맞는 코드 목록을 알고 있어야 한다.
- 증빙 시스템의 상세 내용은 `evidenceReference`가 가리키는 외부 운영 문맥에서 확인해야 한다.

## 전환과 롤백

P1 지역 변경 API가 아직 구현되지 않았으므로 기존 데이터 이관과 호환 계층은 필요 없다. 구현 전에 API 명세,
요청 검증과 테스트에 같은 허용 목록을 반영한다. 도입을 중단해도 기존 P0 지역·감사 데이터에는 영향을 주지 않는다.
자유 입력 사유나 동적 코드 관리가 필요해지면 이 ADR을 수정하지 않고 후속 ADR로 저장 모델과 호환 정책을 정한다.

## 검증 방법

- 작업별 허용 코드는 성공하고 다른 작업의 코드와 미등록 코드는 `400 INVALID_INPUT`으로 거부되는지 확인한다.
- 성공 감사의 `reason_code`가 검증된 요청 코드이고 `evidence_reference`가 필수로 저장되는지 확인한다.
- 공개 여부 상태 조건 실패 감사에는 요청 사유가 아니라 서버 실패 코드가 저장되는지 확인한다.
- 사유 코드와 증빙 참조에 개인정보·토큰·비밀값이 저장되지 않는지 확인한다.
- 동시 요청에서도 성공한 변경과 성공 감사가 함께 커밋되고 거부된 변경이 성공 사유로 기록되지 않는지 확인한다.

## 대체 조건

- 운영에서 허용 코드 추가가 지역 변경을 반복적으로 지연시킨다는 증거가 축적된다.
- 법률·감사 요구가 코드 외의 원문 사유 보관을 요구한다.
- 중앙 사유 코드 레지스트리나 증빙 시스템과의 동적 연동이 P1 이후 범위로 확정된다.
