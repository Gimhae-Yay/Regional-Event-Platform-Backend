# 로컬스탬프 개선 근거 기록

## 시작하기

1. [PRD](../../../docs/local-stamp-platform-prd.md)에서 대상 요구사항, 불변 조건과 출시 단계를 확인한다.
2. 가장 가까운 `AGENTS.md`, 관련 프로젝트 문서, 현재 코드·테스트·Git diff를 확인한다.
3. 문서를 만들 때 [개선 로그 템플릿](assets/improvement-log-template.md)을 복사해 모든 항목을 채운다.
4. 기록만 요청받으면 코드나 설정을 변경하지 않는다.
5. 사용자가 수정 중인 파일과 관련 없는 변경을 보존한다. 임의로 되돌리거나 stash하지 않는다.

## 개선인지 먼저 판별하기

- 변경 전 기능이 관련 요구사항과 계약 테스트를 만족해야 한다.
- 변경 전부터 실패한 기능이나 장애는 개선으로 포장하지 말고 문제 해결 기록으로 분리한다.
- 신규 기능, 제품 정책, API·DB·이벤트 계약 변경은 개선 로그만으로 정당화하지 않는다. 기준 문서와 필요하면 `$adr`을 먼저 갱신한다.
- 관련 기준 문서끼리 충돌하면 구현을 임의의 정답으로 삼지 않는다. 충돌과 영향을 보고하고 기준을 확정할 때까지 상태를 `비교 불가`로 둔다.
- 동일한 입력·데이터·환경·명령·반복 조건을 재현할 수 없으면 Before/After 개선을 입증했다고 결론 내리지 않는다.

다음 중 하나 이상을 실제 개선 목표로 명시한다.

| 유형 | 판단 대상 |
| --- | --- |
| 정합성 | 동시 요청 최종 상태, 트랜잭션 롤백, 멱등 처리, 중복 부수효과, 지역·소유 권한 |
| 안정성 | 반복 성공률, 실패 주입, 타임아웃·재시도·복구, 외부 의존성 장애 격리 |
| 성능 | 사전에 정한 응답 시간·처리량·오류율, 쿼리 수·실행 계획, 캐시 적중·미적중 |
| 유지보수성 | 책임·의존 방향, 중복 정책, 변경 지점 수, 테스트 격리, 계약 보존 |

## 1. 개선 계약 정의하기

코드 변경 전에 다음을 기록한다.

- 대상 기능, 관련 `FR-*`·`US-*`, 출시 단계와 기준 문서 링크
- 변경 전 정상 동작을 증명할 계약 테스트 또는 관찰값
- 줄이려는 위험·비용·병목과 개선 유형
- 보존할 API, DB 상태, 상태 전이, 이벤트, 정렬, 권한 등의 불변 조건
- 비교 지표, 수집 방법, 합격 기준, 반복 횟수와 요약 방식
- 픽스처·시드·데이터 크기·동시 요청 수·외부 시스템 상태
- 제외 범위와 도입하지 않을 후속 기능

합격 기준을 결과를 본 뒤 바꾸지 않는다. 정책 선택이나 장기 영향이 있는 기술 결정이 필요하면 추천안을 첫 번째에 둔 대안 비교 후 기준 문서 또는 ADR을 먼저 확정한다.

## 2. Before 기준선 수집하기

1. 기준 시각과 시간대, `git rev-parse HEAD`, 브랜치, `git status --short`를 기록한다.
2. Java·Spring Boot·DB·Redis·외부 연동 등 결과에 영향을 주는 버전과 설정을 기록한다.
3. 픽스처, 시드, 데이터 크기, 준비·워밍업, 동시성, 반복 횟수를 고정한다.
4. 정확한 명령·입력·종료 코드와 개별 측정값을 보존한다.
5. 관련 계약 테스트가 변경 전부터 통과하는지 확인한다.
6. 비밀키, 토큰, 개인정보, 결제 원문과 QR 원문은 증거에 포함하지 않는다.

변경이 이미 끝나 현재 작업 트리에서 Before를 실행할 수 없으면 안전한 별도 Git worktree에서 기준 revision을 검증한다. 사용자의 현재 작업을 되돌리지 않는다. 기준 revision이나 동일 환경을 복원하지 못하면 이유를 적고 `비교 불가`로 판정한다.

## 3. 변경하고 After 수집하기

1. 요청받은 목표에 필요한 최소 변경만 적용하고 관련 없는 리팩터링을 섞지 않는다.
2. Before와 같은 명령·입력·데이터·환경·반복 조건을 사용한다.
3. 목표 지표와 함께 불변 조건, 정상 경로, 경합·중복·재시도·롤백·권한 실패 경로를 검증한다.
4. 관련 테스트를 먼저 실행하고 구현 변경이면 가능한 범위에서 `./gradlew test` 또는 Windows의 `.\gradlew.bat test`로 회귀 검증한다.
5. 결과가 나빠지거나 측정 변동 범위 안이면 개선이라고 표현하지 않는다.

캐시, DB 인덱스, 동시성, 외부 연동처럼 조건에 민감한 변경은 [MVP PRD](../../../docs/local-stamp-platform-prd.md)의 관련 요구사항과 불변 조건을 따른다.

## 4. 비교하고 판정하기

- 개별 측정값과 요약값을 함께 제시하고 변화량 계산 방식을 적는다.
- 성능 비교는 콜드/웜 상태를 섞지 않고, 충분한 워밍업과 반복 없이 단정하지 않는다.
- 정합성은 성공 응답만 보지 말고 최종 DB 상태와 중복 부수효과까지 확인한다.
- 안정성은 단일 성공이 아니라 반복 결과와 실패 주입 후 복구 상태로 판정한다.
- 유지보수성은 코드 줄 수만으로 판단하지 않는다. 관찰 가능한 책임, 의존성, 중복, 변경 지점과 회귀 테스트로 설명한다.
- 목표 일부만 충족하면 부분 개선으로 한정하고 실패 항목과 잔여 위험을 남긴다.
- 실행하지 않은 검증, 재구성한 수치와 주관적 인상을 증거로 쓰지 않는다.

## 기록 위치와 파일 관리

- 사용자가 경로를 지정하면 그 경로를 사용한다.
- 지정하지 않으면 `docs/improvements/<YYYY-MM-DD>-<english-kebab-case>.md`를 사용하고, 디렉터리가 없으면 먼저 만든다.
- 같은 대상과 개선 계약을 이어 측정할 때만 기존 문서를 갱신한다. 별개의 위험·지표·기능이면 새 파일을 만든다.
- 이름이 충돌하면 덮어쓰지 말고 날짜, 이슈 번호 또는 세부 범위를 파일명에 추가한다.
- 문서의 코드·테스트·요구사항 링크는 저장소 상대 경로로 작성한다.

## 완료 검증하기

- Before와 After의 명령, 입력, 환경, 반복 조건이 같은지 확인한다.
- 기준 revision과 작업 트리 상태, 개별 값, 종료 코드, 실패 결과가 빠지지 않았는지 확인한다.
- 관련 `FR-*`·`US-*`, 불변 조건, 제외 범위와 출시 단계가 연결됐는지 확인한다.
- 새 기능·정책 변경·미확정 기술을 개선 명목으로 끼워 넣지 않았는지 확인한다.
- 모든 링크와 증거 파일이 존재하는지 확인하고 `git diff --check`를 실행한다.
- 최종 보고에 생성·갱신한 로그 경로, 판정, 핵심 수치, 실행한 검증, 한계와 잔여 위험을 포함한다.
