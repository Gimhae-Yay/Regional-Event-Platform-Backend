# 변경사항 커밋

## 기본 규칙

- 커밋 제목은 `<type>: <한국어 설명>` 형식을 사용한다.
- type은 feat, fix, refactor, test, docs, chore, perf 중 변경의 주목적 하나를 고른다.
- 제목은 실제 결과를 간결한 현재형 또는 명령형으로 설명하고 마침표를 붙이지 않는다.
- 이슈 번호는 제목에 강제로 넣지 않는다. 사용자 입력, 브랜치명 또는 연결된 PR에서 확인된 번호만 사용하며 추측하지 않는다.
- 한 커밋에는 독립적으로 설명·검증·되돌릴 수 있는 목적 하나만 담는다.
- 기능 코드와 그 동작을 보장하는 테스트·마이그레이션은 함께 커밋할 수 있다. 서로 독립적인 문서, 설정, 기능은 나눈다.
- 기존 staged 변경과 다른 사용자 변경을 보존한다. 의도하지 않은 파일을 stage, unstage, 수정 또는 삭제하지 않는다.
- `git add .`, `git add -A`, 경로 없는 `git commit -a`를 사용하지 않는다.
- `main`과 `dev`를 보호 브랜치로 취급한다. 사용자가 해당 브랜치에 직접 커밋하라고 명시하지 않았다면 커밋을 중단하고 작업 브랜치 사용을 안내한다.
- 이 스킬에서는 코드나 문서를 고치지 않는다. 검증 실패나 범위 문제가 발견되면 커밋하지 않고 원인과 필요한 조치를 보고한다.
- amend, rebase, reset, force push는 사용자가 명시적으로 요청하지 않는 한 수행하지 않는다.

## 논리 단위 커밋

- 변경사항을 논리 단위로 나눠 커밋한다. 한 커밋에는 독립적으로 설명·검증·되돌릴 수 있는 하나의 목적만 담는다.
- 파일 종류만 보지 말고 변경 목적과 서로 함께 있어야 동작하는지를 기준으로 나눈다.
- 전체 변경을 한 번에 스테이징하지 말고 아래 기준으로 커밋 계획을 먼저 세운다.

| 변경 조합 | 커밋 기준 |
| --- | --- |
| 기능 A + 기능 B | 기능별 논리 단위로 나눠 각각 커밋한다. |
| 기능 변경 + 그 기능과 무관한 설정 변경 | 기능은 `feat`, 설정은 `chore` 커밋으로 나눈다. |
| `docs/` 변경 + 코드 변경 | 문서를 `docs` 커밋으로 먼저 남기고 코드를 `feat` 또는 해당 목적의 커밋으로 나눈다. |

## 절차

1. 가장 가까운 `AGENTS.md`가 있으면 먼저 읽고, `.github/pull_request_template.md`, 최근 커밋 제목과 연결 이슈에서 커밋·검증 규칙만 확인한다.
2. `git status --short --branch`, `git diff`, `git diff --cached`, untracked 파일을 확인해 staged·unstaged·untracked 변경을 모두 파악한다.
3. detached HEAD, merge/rebase 진행 중, 충돌 파일 또는 보호 브랜치 직접 커밋 여부를 확인한다. 안전하지 않으면 중단한다.
4. 전체 변경을 논리 단위로 나누고 각 단위의 목적, 경로, 커밋 순서, `type`, 검증 명령을 먼저 정한다.
5. 이슈 번호가 확인되면 `gh issue view <번호>` 또는 사용 가능한 GitHub 도구로 범위와 TODO를 대조한다. 확인 수단이 없으면 번호를 추측하지 말고 검증하지 못한 항목으로 남긴다.
6. 민감정보, 로컬 접속값, 디버그 출력, 로그와 생성물을 점검한다. 특히 `.env*`, `application-local.*`, 토큰·비밀번호·개인키, `.gradle/`, `build/`, `.idea/`, `out/`을 커밋하지 않는다.
7. 변경 이후의 최신 검증 결과를 확보한다.
   - 소스 코드, 리소스, Gradle 설정 변경: Windows에서는 `.\gradlew.bat ciFastCheck`, Unix 계열에서는 `./gradlew ciFastCheck`를 기본으로 실행한다. `ciFastCheck`는 애플리케이션 패키징과 Testcontainers 기반이 아닌 `fastTest`를 검증한다.
   - 범위가 작고 `ciFastCheck`보다 관련 테스트가 적합하면 해당 테스트를 먼저 실행하되, PR 준비 수준에서는 `ciFastCheck`도 실행한다.
   - 문서 전용 변경: `git diff --check`를 실행하고 링크·경로·문서 정합성을 확인한다. `ciFastCheck`를 생략하면 보고한다.
8. 모든 변경에 `git diff --check`를 실행한다. 실패하면 커밋하지 않는다.
9. 한 논리 단위에 속한 경로만 `git add -- <경로...>`로 명시적으로 stage한다. 기존 staged 변경이 범위와 충돌하면 임의로 unstage하지 말고 중단한다.
10. `git diff --cached --check`, `git diff --cached --stat`, `git diff --cached`로 커밋 대상과 비밀값을 다시 확인한다.
11. `<type>: <한국어 설명>` 제목으로 커밋한다. 커밋할 변경이 없으면 빈 커밋을 만들지 않는다.
12. `git show --stat --oneline --decorate HEAD`와 `git status --short --branch`로 결과와 남은 사용자 변경을 확인한다.
13. 논리 단위가 더 있으면 7~12단계를 각 단위마다 반복한다.

## 완료 보고

- 각 커밋의 짧은 해시와 제목을 보고한다.
- 커밋별 포함 범위와 논리적으로 나눈 이유를 간단히 설명한다.
- 실행한 검증 명령과 성공·실패 결과를 보고한다.
- 제외해 보존한 사용자 변경, 생략한 검증, 확인하지 못한 이슈 연계를 명시한다.
- push는 사용자가 별도로 요청한 경우에만 수행한다.
