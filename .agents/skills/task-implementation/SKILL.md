# Task 구현

명시된 Task의 계약을 구현하고 검증한다. 불필요한 대기는 줄이되, 미합의 계약을 코드로 선점하지 않는다.

## 책임 경계

- Task의 제목·본문·라벨·이슈 유형·폼은 수정하거나 재정의하지 않는다. 이슈 생성과 보완은 `issue-create`를 따른다.
- Task Issue 종료, 커밋, push, 새 PR 생성은 수행하지 않는다. 검증된 변경의 커밋은 `commit`, 새 PR 생성은 `pr-create`를 따른다.
- 정책·공개 API·데이터 모델·장기 기술 결정이 필요하면 구현을 멈추고 `adr`로 전환한다.
- 원인이 불명확하거나 현재 Task 밖의 테스트·빌드 실패는 구현을 멈추고 `troubleshooting`을 권고한다.
- 구현이 시작된 뒤에는 문서를 수정하지 않는다. 기준 문서의 변경이 필요하면 문서·ADR 절차를 먼저 완료한다.

## 대상과 모드 판별

1. Task 구현 요청에는 정확한 Task Issue URL 또는 번호를, PR 피드백 요청에는 정확한 PR URL 또는 번호를 받는다. 현재 브랜치명으로 대상을 추론하지 않는다.
2. Task 구현은 GitHub 이슈 유형이 `Task`이고 작업 성격 라벨이 정확히 하나일 때만 시작한다. 다음 라벨로 브랜치 type을 정한다.

   | 라벨 | 브랜치 type |
   | --- | --- |
   | `New Feature` | `feature` |
   | `Fix` | `fix` |
   | `Refactor` | `refactor` |
   | `Test` | `test` |
   | `Docs` | `docs` |
   | `Chore` | `chore` |

   도메인·권한 등 분류 라벨은 이 판단에 사용하지 않는다. 이슈 유형·작업 성격 라벨이 없거나 작업 성격 라벨이 둘 이상이면 DoR 위반으로 보고하고 중단한다.
3. Task에 연결된 PR 상태를 확인한다.

   - 연결 PR이 없으면 **Task 구현 모드**로 진행한다.
   - Draft 또는 Open PR이 있으면 Task 구현 모드로 진행하지 않는다. 리뷰 피드백 수정을 요청받은 경우에만 **PR 피드백 구현 모드**로 전환한다.
   - Merged PR은 완료로 보고 구현하지 않는다.
   - Closed·미병합 PR은 기존 브랜치를 자동 재개하지 않는다. 재개·폐기·새 Task 여부를 사용자에게 확인한다.

## Task 구현 모드

### 1. 계약과 범위 확인

1. `docs/code-convention.md` 전체를 읽는다.
2. Task의 목표, TODO, 상위 Feature/Bug 맥락, 공식 `blocked by` 관계와 관련 기준 문서를 확인한다. Task가 직접 PRD를 참조하지 않아도 요구하지 않는다.
3. API 계약은 API 명세, 데이터 사실은 ERD, 기술 결정은 ADR, 구현 방식은 아키텍처와 코드 컨벤션에서 확인한다. Task는 범위와 완료 조건을 정한다.
4. 기준이 서로 충돌하거나 필요한 정책·계약이 없으면 코드를 변경하지 않고 차이와 영향, 보완할 Task 또는 문서를 보고한다.
5. Task 이외의 기능, 리팩터링, 문서 변경을 추가하지 않는다.

### 2. 선행 의존성과 병렬 구현

공식 `blocked by` 관계는 자동적인 구현 시작 차단이 아니라 계약과 통합 완료의 게이트로 취급한다.

- 선행 이슈가 미완료여도 필요한 동작 계약이 API·ERD·ADR·정책 중 하나에 확정돼 있고, 실제 Adapter 또는 구현의 담당 Task가 명확하면 병렬 구현한다.
- 현재 `dev`에 있는 협력자는 Mockito로 단위 테스트한다. 테스트 편의를 위해 내부 Service의 인터페이스, 임시 운영 구현체 또는 전달 전용 계층을 만들지 않는다.
- 새 Port는 역할이 명확한 외부 기술 경계일 때만 둔다. Port는 소비하는 UseCase가 필요로 하는 기술 독립 계약을 표현해야 하며, 미완성 내부 Service 의존이나 여러 도메인 흐름을 숨기는 우회 수단으로 만들지 않는다.
- 실제 Adapter 연동이 Task의 완료 조건이면, Adapter가 준비되기 전에는 해당 TODO를 완료로 표시하지 않는다. 현재 Task의 범위가 Port·소비 코드·단위 테스트라면 그 범위 안에서 완료할 수 있다.
- 계약이나 실제 구현 담당자가 불명확하면 Port를 새로 만들어 진행하지 않고 중단한다.

### 3. 작업 브랜치 준비

1. 작업 트리가 깨끗한지 확인한다. 변경이 있거나 `checkout`, `fetch`, `pull`이 실패하면 stash, reset, 강제 전환 없이 중단하고 사용자 변경을 보존한다.
2. 다음 순서를 지킨다.

   ```text
   git checkout dev
   git fetch origin
   git pull origin dev
   ```

3. 같은 Task의 기존 브랜치와 열린 PR을 확인한다. 열린 PR이 있으면 브랜치를 삭제하거나 새로 만들지 않는다.
4. 열린 PR이 없는 기존 동일 Task 브랜치는 로컬과 `origin`에서 삭제한다. 원격 삭제 실패 시 force push나 다른 이름의 브랜치를 만들지 않고 중단한다. 매일 수행하는 방치 브랜치 일괄 정리는 이 절차의 책임이 아니다.
5. 갱신된 `dev`에서 `<type>/<이슈번호>-<영문-kebab-case-설명>` 브랜치를 만든다. 설명은 Task 제목을 간결하게 옮기고, 기존 Git 규칙을 따른다.

### 4. 구현과 검증

1. 변경 범위와 검증 방법을 짧게 알린 뒤 사용자 승인을 기다리지 않고 구현한다.
2. Task와 기준 문서에 확정된 코드, 테스트, migration만 변경한다.
3. 방금 변경한 코드의 명백한 컴파일 오류나 신규 테스트 실패는 구현 안에서 바로 수정한다. 기존 테스트 회귀, 환경·마이그레이션·동시성 문제 또는 원인이 불명확한 실패는 `troubleshooting`으로 전환한다.
4. 도메인 규칙은 단위 테스트를 우선하고, API·JPA·보안·동시성 검증은 코드 컨벤션과 Task 계약에 맞는 테스트를 추가·수정한다.
5. 관련 테스트와 `./gradlew test`, `./gradlew build`를 모두 통과시킨다. 실패하거나 실행하지 못한 검증이 있으면 TODO를 갱신하지 않고 결과와 사유를 보고한다.
6. 각 TODO는 해당 변경과 관련 검증이 통과한 뒤에만 체크한다. 전체 테스트·빌드가 통과한 뒤 마지막 완료 항목을 체크한다. Issue 자체는 닫지 않는다.

## PR 피드백 구현 모드

1. `gh-address-comments`를 사용해 미해결 리뷰 스레드와 사용자가 선택한 피드백 범위를 확인한다.
2. 기존 Task·API·ERD·ADR 계약을 지키는 버그 수정, 누락 테스트, 오류 계약 준수, 가독성·구조 개선만 수정한다.
3. 새 API 필드·상태·정책·데이터 모델·기능 범위를 요구하는 피드백은 구현하지 않는다. Task 보완 또는 ADR이 필요한 이유를 보고한다.
4. PR 브랜치를 그대로 사용한다. `dev` 갱신, 브랜치 재생성, Task TODO 갱신을 수행하지 않는다.
5. 관련 테스트와 `./gradlew test`, `./gradlew build`를 통과시킨다. 커밋·push·리뷰 답글·스레드 해결은 사용자가 별도로 요청한 경우에만 해당 절차로 진행한다.

## 완료 보고

다음을 간결히 보고한다.

- 사용한 모드와 구현한 범위
- 확인한 계약·의존성·Port 또는 통합 보류 사항
- 갱신한 TODO와 남은 TODO
- 실행한 테스트·빌드와 결과
- 커밋·push·PR·Issue 종료를 수행하지 않았음을 포함한 다음 단계
