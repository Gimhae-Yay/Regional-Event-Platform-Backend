# Task 구현

명시된 Task의 계약을 문서·프로덕션 코드·테스트 작업 모드에 맞게 구현하고 검증한다. 불필요한 대기는 줄이되, 미합의 계약을 코드로 선점하지 않는다.

## 책임 경계

- Task의 제목·본문·라벨·이슈 유형·폼에 있는 목표·범위·완료 조건은 수정하거나 재정의하지 않는다. 단, 검증이 통과한 기존 TODO 체크박스의 완료 표시는 허용한다. 이슈 생성과 보완은 `issue-create`를 따른다.
- Task Issue 종료, push, 새 PR 생성은 수행하지 않는다. 일반 변경의 커밋은 `commit`, 새 PR 생성은 `pr-create`를 따른다. 단, PR 피드백 구현 모드에서 최신 `origin/dev`를 PR head에 병합해 자동으로 생성되는 병합 커밋만 이 규칙의 예외로 허용하며, 세부 조건은 해당 모드를 따른다.
- `Docs` Task만 이슈에 명시된 문서를 생성·수정한다. 프로덕션 코드 구현 Task와 테스트 전용 Task는 문서를 읽기 전용으로 사용하며, 기존 TODO 완료 표시 외에는 문서를 변경하지 않는다.
- 정책·데이터 모델·장기 기술 결정이 필요하면 코드·테스트 구현을 시작하지 않고 `adr`로 전환한다. ADR은 구현 전 선행 단계에서만 작성한다.
- 프로덕션 코드 구현 또는 테스트 전용 Task에서 공개 API·오류 계약·ERD의 추가·변경 필요가 드러나면 코드와 계약 문서를 변경하지 않고 근거와 영향을 보고한다. 재현 가능한 구현·계약 불일치는 `issue-create` 절차로 Bug Issue 초안을 만들고, 사용자 승인 뒤 현재 스프린트에 생성·배정한다. 정책이 미확정이면 `adr`로 전환하고, 동작에 영향을 주지 않는 문서 오류는 `Docs` Task로 분리한다.
- 원인이 불명확하거나 현재 Task 밖의 테스트·빌드 실패는 구현을 멈추고 `troubleshooting`을 권고한다.

## 대상과 모드 판별

1. Task 구현 요청에는 정확한 Task Issue URL 또는 번호를, PR 피드백 요청에는 정확한 PR URL 또는 번호를 받는다. 현재 브랜치명으로 대상을 추론하지 않는다.
2. Task 구현은 GitHub 이슈 유형이 `Task`이고 작업 성격 라벨이 정확히 하나일 때만 시작한다. 다음 라벨로 브랜치 type과 작업 모드를 정한다.

   | 라벨            | 브랜치 type   | 작업 모드      |
   |---------------|------------|------------|
   | `New Feature` | `feature`  | 프로덕션 코드 구현 |
   | `Fix`         | `fix`      | 프로덕션 코드 구현 |
   | `Refactor`    | `refactor` | 프로덕션 코드 구현 |
   | `Test`        | `test`     | 테스트 전용     |
   | `Docs`        | `docs`     | 문서 작업      |
   | `Chore`       | `chore`    | 프로덕션 코드 구현 |

   도메인·권한 등 분류 라벨은 이 판단에 사용하지 않는다. 이슈 유형·작업 성격 라벨이 없거나 작업 성격 라벨이 둘 이상이면 DoR 위반으로 보고하고 중단한다.
3. Task가 같은 저장소의 Feature 또는 Bug를 직속 부모로 가지며, Task의 결과가 부모의 범위와 완료 조건에 포함되는지 확인한다. API 엔드포인트나 재현 가능한 Bug와 무관한 문서·CI·개발 절차 Task의 부모 Feature는 독립적으로 검증 가능한 프로젝트·플랫폼 역량, 기준 문서와 완료 조건을 본문에 정의해야 한다. `new_non_api_feature.yaml` 도입 전에 생성된 부모 Feature는 기존 본문의 원격 커밋 permalink, 포함·제외 범위, 완료 후 상태와 TODO가 같은 근거를 제공하는지 확인한다. 부모가 없거나 유형·범위·근거가 이 조건을 충족하지 않으면 DoR 위반으로 보고하고 `issue-create` 절차에 따른 보완이 끝날 때까지 구현을 시작하지 않는다.
4. Task에 연결된 PR 상태를 확인한다.

   - 연결 PR이 없으면 **Task 구현 모드**로 진행한다.
   - Draft 또는 Open PR이 있으면 Task 구현 모드로 진행하지 않는다. 리뷰 피드백 수정을 요청받은 경우에만 **PR 피드백 구현 모드**로 전환한다.
   - Merged PR은 완료로 보고 구현하지 않는다.
   - Closed·미병합 PR은 기존 브랜치를 자동 재개하지 않는다. 재개·폐기·새 Task 여부를 사용자에게 확인한다.

## Task 구현 모드의 작업 브랜치 준비

이 절차는 **Task 구현 모드**에만 적용한다. PR 피드백 구현 모드는 아래의 별도 동기화 절차를 따른다.

1. `docs/git-convention.md` 전체를 읽고 브랜치 type과 이름이 현재 규칙에 맞는지 확인한다.
2. 작업 트리가 깨끗한지 확인한다. 변경이 있거나 `checkout`, `fetch`, `pull`이 실패하면 stash, reset, 강제 전환 없이 중단하고 사용자 변경을 보존한다.
3. 다음 순서를 지킨다.

   ```text
   git checkout dev
   git fetch origin
   git pull origin dev
   ```

4. 같은 Task의 기존 브랜치와 열린 PR을 확인한다. 열린 PR이 있으면 브랜치를 삭제하거나 새로 만들지 않는다.
5. 닫혔지만 미병합인 PR이 있으면 기존 브랜치와 미병합 커밋을 사용자에게 보여 주고, 기존 브랜치에서 재개할지 해당 브랜치를 로컬과 `origin`에서 삭제한 뒤 새로 시작할지 선택받는다. 열린 PR이 없는 기존 동일 Task 브랜치도 자동으로 삭제하지 않는다. 삭제는 사용자가 명시적으로 선택한 정확한 브랜치에만 수행하며, 원격 삭제 실패 시 force push나 다른 이름의 브랜치를 만들지 않고 중단한다.
6. 갱신된 `dev`에서 새 시작이 확정됐고 동일 Task 브랜치가 없을 때만 `<type>/<이슈번호>-<영문-kebab-case-설명>` 브랜치를 만든다. 설명은 Task 제목을 간결하게 옮기고, 확인한 Git 규칙을 따른다.

## 문서 작업 모드

1. `docs/code-convention.md` 전체와 문서 작업 범위와 직접 관련된 기준 문서를 읽고, Task가 명시한 문서 생성·수정 범위와 완료 조건을 확인한다.
2. Task가 요구하지 않는 정책·API·ERD·아키텍처 변경을 추가하지 않는다. 정책 선택이 필요하면 문서 변경 전에 `adr`로 전환한다.
3. 이슈에 명시된 문서만 생성·수정하고, `src/main`, DB migration, 런타임 설정과 테스트 소스는 변경하지 않는다.
4. 수정한 문서의 링크·참조·형식과 관련 문서 검증을 수행한다. 검증이 통과한 TODO만 완료 상태로 표시한다.

## 프로덕션 코드 구현 모드

### 1. 계약과 범위 확인

1. `docs/code-convention.md`, `docs/ARCHITECTURE.md` 전체를 읽는다.
2. Task의 목표, TODO, 상위 Feature/Bug 맥락, 공식 `blocked by` 관계와 관련 기준 문서를 확인한다. Task가 직접 PRD를 참조하지 않아도 요구하지 않는다.
3. API 계약은 API 명세, 데이터 사실은 ERD, 기술 결정은 ADR, 구현 방식은 아키텍처와 코드 컨벤션에서 확인한다. Task는 범위와 완료 조건을 정한다.
4. Entity, migration 또는 런타임 설정 변경에 ERD·API·PRD·아키텍처 문서의 변경이 필요하면, 해당 문서 Task가 선행 완료되기 전에는 프로덕션 코드 구현을 시작하지 않는다.
5. 기준이 서로 충돌하거나 필요한 정책·계약이 없으면 코드를 변경하지 않고 차이와 영향, 보완할 Task 또는 문서를 보고한다.
6. Task 이외의 기능, 리팩터링, 문서 변경을 추가하지 않는다.

### 2. 선행 의존성과 병렬 구현

공식 `blocked by` 관계는 현재 Task의 계약과 통합 완료 게이트로 취급한다. 병렬 구현은 제공·소비 Task가
같은 확정 계약을 사용하되 서로의 프로덕션 구현을 변경하지 않는다는 뜻이다.

- 선행 이슈, 실제 Adapter·통합 담당 Task 또는 다른 브랜치의 구현을 현재 Task 범위에서 변경하지 않는다. 필요한
  계약과 완료 여부만 확인하며, 독립된 제공·소비 Task는 확정된 계약을 기준으로 병렬 구현할 수 있다.
- 선행 이슈가 미완료여도 현재 Task에 필요한 API·ERD·ADR·정책 계약이 모두 확정돼 있고, 실제 Adapter 또는 통합
  구현의 담당 Task가 명확하면 현재 Task의 확정된 범위만 독립적으로 구현한다.
- 현재 `dev`에 없는 제공 Service가 복합 UseCase의 구현을 막고, 제공·소비 Task의 행위·오류·권한·트랜잭션
  계약이 문서와 ADR로 확정됐다면 제공 도메인은 별도 계약 Task에서 `domain.<도메인>.port.in`의 행위 인터페이스를
  먼저 `dev`에 반영할 수 있다. 소비 UseCase와 제공 Service Task는 그 계약을 기준으로 병렬 구현한다.
- 이미 `dev`에 있는 Service에는 `port.in`을 새로 만들지 않고 UseCase가 해당 Service를 직접 의존한다. `port.in`은
  제공 Service가 아직 없고 병렬 Task가 실제로 필요한 경우에만 허용하며, 소비 Task가 제공 도메인의 메서드를
  임의로 가정해 만들 수 없다.
- 확정된 `port.in` 계약과 이미 제공된 의존성이 필요한 UseCase 단위 테스트에서는 Mockito mock을 사용할 수 있다.
  이 조건을 충족하지 않는 현재 `dev` 부재 의존성을 대신할 임시 인터페이스나 임시 프로덕션 구현체는 추가하지 않는다.
- 테스트 편의만을 위해 내부 Service 인터페이스나 전달 전용 계층을 만들지 않는다. `port.in`은 제공 도메인이
  소유한 병렬 구현 계약이며, 제공 Service는 역할이 드러나는 이름으로 이를 구현하고 `Impl` 접미사를 붙이지 않는다.
- 외부 기술 기능이 필요하다는 이유만으로 UseCase를 추가하거나 Adapter 구현을 별도 Task로 분리하지 않는다. 단일
  Service 흐름은 해당 Service가 필요한 `port.out` 역할 인터페이스를 정의하거나 이미 확정된 Port를 사용하고,
  Task 범위에 포함되면 Adapter 구현과 검증까지 함께 변경할 수 있다. 여러 Service 또는 Repository의 실행 순서·
  권한·트랜잭션을 실제로 조정하는 복합 흐름에서만 UseCase가 `port.out` 역할 인터페이스를 사용하거나 정의한다.
- 실제 Adapter 연동이 Task의 완료 조건이면, 현재 Task가 Adapter 구현을 포함하는지 또는 공식 `blocked by` 관계로
  다른 담당 Task에 위임됐는지를 확인한다. 현재 Task 범위에 포함되면 연동 검증까지 완료한 뒤 TODO를 표시하고,
  다른 담당 Task에 위임됐으면 Adapter가 준비되기 전에는 해당 TODO를 완료로 표시하지 않는다. `port.out` 계약 또는
  Adapter 담당 범위가 불명확하면 새 Port나 임시 구현을 만들어 진행하지 않고 중단한다.

### 3. 구현과 검증

1. 변경 범위와 검증 방법을 짧게 알린 뒤 사용자 승인을 기다리지 않고 구현한다.
2. Task와 기준 문서에 확정된 프로덕션 코드, 테스트, migration과 설정만 변경한다. 문서는 기존 TODO 완료 표시 외에는 변경하지 않는다.
3. 방금 변경한 코드의 명백한 컴파일 오류나 신규 테스트 실패는 구현 안에서 바로 수정한다. 기존 테스트 회귀, 환경·마이그레이션·동시성 문제 또는 원인이 불명확한 실패는 `troubleshooting`으로 전환한다.
4. 도메인 규칙은 단위 테스트를 우선하고, API·JPA·보안·동시성 검증은 코드 컨벤션과 Task 계약에 맞는 테스트를 추가·수정한다.
5. 관련 테스트와 `./gradlew test`, `./gradlew build`를 모두 통과시킨다. 실패하거나 실행하지 못한 검증이 있으면 TODO를 갱신하지 않고 결과와 사유를 보고한다.
6. 각 TODO는 해당 변경과 관련 검증이 통과한 뒤에만 기존 체크박스의 완료 상태로 표시한다. 전체 테스트·빌드가 통과한 뒤 마지막 완료 항목을 표시한다. Issue 자체는 닫지 않는다.

## 테스트 전용 모드

1. `docs/code-convention.md` 전체와 Task에 연결된 API·ERD·ADR·정책을 읽고 테스트 대상 계약을 확인한다.
2. 테스트 소스, fixture와 테스트 실행에 필요한 범위만 변경한다. 프로덕션 코드, migration, 런타임 설정과 문서는 기존 TODO 완료 표시 외에는 변경하지 않는다.
3. 계약·정책이 미확정이면 `adr`로 전환하고, 재현 가능한 구현·계약 불일치는 Bug Issue 초안으로, 동작에 영향을 주지 않는 문서 오류는 `Docs` Task로 분리한다. 원인이 불명확하면 `troubleshooting`을 권고한다.
4. 관련 테스트와 `./gradlew test`, `./gradlew build`를 모두 통과시킨다. 검증이 통과한 TODO만 기존 체크박스의 완료 상태로 표시한다.

## PR 피드백 구현 모드

1. 연결된 Task의 작업 모드와 `gh-address-comments`의 미해결 리뷰 스레드, 사용자가 선택한 피드백 범위를 확인한다.
2. PR 메타데이터로 base와 head를 확인한다. base가 `dev`가 아니면 `dev`를 병합하지 않고 중단해 사용자에게 보고한다. 작업 트리가 깨끗하고 현재 브랜치가 PR head인지 확인한 뒤 `git fetch origin`을 실행한다. 갱신 후 `HEAD`가 `origin/<head>`와 다르면 로컬·원격 차이를 보고하고 중단한다.
3. `origin/dev`가 `HEAD`에 이미 포함돼 있으면 병합을 생략한다. 포함되지 않았으면 PR head에서 `git merge --no-ff origin/dev`를 실행한다. 성공 시 생성된 병합 커밋은 이 모드에서 허용하는 유일한 자동 커밋이며 push하지 않는다. 충돌하면 `git merge --abort`로 병합 전 상태를 복원하고, 충돌이나 피드백을 임의로 수정하지 않은 채 중단해 사용자에게 보고한다. 로컬 `dev`를 체크아웃·갱신하거나 PR 브랜치를 재생성하지 않는다.
4. 문서 작업 PR은 Task에 명시된 문서 범위와 직접 관련된 기준 문서를 읽는다. 프로덕션 코드 구현·테스트 전용 PR은 `docs/code-convention.md`, `docs/ARCHITECTURE.md` 전체와 기존 Task·API·ERD·ADR 계약을 읽는다. 계층·의존성·패키지 구조를 바꾸는 피드백에는 아키텍처의 유지보수 점검 기준을 적용한다.
5. 문서 작업 PR은 Task에 명시된 문서 범위 안에서만 피드백을 수정하고 링크·참조·형식을 검증한다. 프로덕션 코드 구현·테스트 전용 PR은 기존 Task·API·ERD·ADR 계약을 지키는 버그 수정, 누락 테스트, 오류 계약 준수, 가독성·구조 개선만 수정하며 문서를 변경하지 않는다.
6. 새 API 필드·상태·정책·데이터 모델·기능 범위를 요구하는 피드백은 구현하지 않는다. 재현 가능한 구현·계약 불일치는 Bug Issue 초안으로, 정책 미확정은 ADR로, 동작에 영향을 주지 않는 문서 오류는 Docs Task로 분리한다.
7. Task TODO 갱신을 수행하지 않는다.
8. 문서 작업 PR은 문서 검증을, 프로덕션 코드 구현·테스트 전용 PR은 관련 테스트와 `./gradlew test`, `./gradlew build`를 통과시킨다. 자동 병합 커밋 외 커밋·push·리뷰 답글·스레드 해결은 사용자가 별도로 요청한 경우에만 해당 절차로 진행한다.

## 완료 보고

다음을 간결히 보고한다.

- 사용한 모드와 구현한 범위
- 확인한 계약·의존성·Port 또는 통합 보류 사항
- 갱신한 TODO와 남은 TODO
- 실행한 테스트·빌드와 결과
- 커밋·push·PR·Issue 종료를 수행하지 않았음을 포함한 다음 단계
