# 로컬스탬프 문제 해결

관찰한 증상에서 검증 가능한 근본 원인까지 좁히고, 요청 범위 안에서 최소 수정과 회귀 검증을 수행한다. 다른 사람이 같은 조건으로 재현할 수 있도록 조사 과정을 남긴다.

## 시작하기

1. `git status --short --branch`와 가장 가까운 `AGENTS.md`를 확인하고 사용자 변경을 보존한다.
2. 기대 동작은 `docs/local-stamp-platform-prd.md`, 관련 제품 문서, 채택된 ADR과 테스트에서 확인한다.
3. 관련 코드, 설정, 테스트, 마이그레이션과 최근 diff를 읽어 현재 구현과 문제 범위를 확인한다.
4. 실제 재현·진단을 수행하면 첫 재현 전에 [조사 기록 양식](assets/troubleshooting-template.md)을 복사해 기록을 시작한다.
5. 진단만 요청받으면 원인과 최소 수정 방향까지만 제시한다. 수정이나 문제 해결까지 요청받은 경우에만 구현을 변경한다.

## 조사 원칙

- `관찰 사실`, `가설`, `추론`, `결론`을 명시적으로 구분한다.
- 재현하지 못했거나 반증 가능한 연결 고리를 확보하지 못한 문제를 근본 원인으로 확정하지 않는다.
- 한 번에 한 변수를 바꾸고 읽기 전용이며 비용이 낮은 검증부터 수행한다.
- 여러 변경을 한꺼번에 적용하거나 재시작 후 우연히 사라진 증상을 해결로 기록하지 않는다.
- 문서에 적힌 기술이 현재 구현돼 있다고 가정하지 않는다. 코드, 의존성, 설정과 실행 결과로 확인한다.
- 기준 문서가 충돌하거나 정책이 미확정이면 코드 결함과 계약 공백을 분리하고 임의로 정책을 정하지 않는다.
- 정책·공개 API·데이터 모델의 장기 결정을 바꿔야 하면 기준 문서와 채택된 ADR을 확인하고, 새 기술 결정은 `$adr`로 분리한다.
- 개인정보, 연락처 원문, JWT·QR 원문, 결제·HMAC 키, 비밀번호와 실제 인증 정보를 명령 출력이나 문서에 남기지 않는다.
- 운영 데이터 변경, 파괴적 명령, 외부 시스템 조작과 운영 재시작은 명시적 승인 없이 실행하지 않는다.

## 기록 위치와 상태

- 사용자가 경로를 지정하면 그 경로를 사용한다.
- 지정하지 않으면 `docs/troubleshooting/<YYYY-MM-DD>-<english-kebab-case>.md`에 기록한다.
- 같은 증상과 같은 원인을 이어서 조사하면 기존 기록에 타임라인을 추가한다.
- 증상은 같아도 원인이 다르거나 재발 방지가 별도 작업이면 새 기록으로 분리하고 서로 링크한다.

다음 상태 중 하나만 사용한다.

- `조사 중`: 재현 또는 원인 검증을 진행하고 있다.
- `미재현`: 필요한 조건이나 증거를 확보하지 못해 증상을 재현하지 못했다.
- `원인 확인`: 원인은 입증했지만 수정 적용 또는 해결 검증을 완료하지 않았다.
- `완화`: 영향은 줄였지만 근본 원인이나 회귀 위험이 남아 있다.
- `해결`: 원래 재현 절차와 필요한 회귀 검증이 모두 통과했다.
- `보류`: 외부 의존성, 권한 또는 사용자 결정이 필요하다.

## 조사 절차

### 1. 증상과 범위 고정하기

1. 커밋 ID, 브랜치, 작업 트리, 실행 환경, Java 버전과 활성 프로필을 기록한다.
2. 기대 결과를 관련 PRD 요구사항, 상태 규칙, 테스트 또는 사용자가 명시한 기대와 연결한다.
3. 실제 결과를 HTTP 상태와 응답, 예외 유형, 실패한 검증식, 종료 코드 또는 상태 전이로 구체화한다.
4. 최초 발생 시각과 시간대, 빈도, 영향 대상, 선행 요청, 데이터 상태와 외부 의존성 상태를 기록한다.
5. 가능하면 `requestId`와 예약·결제·방문 같은 비민감 식별자로 로그와 상태 전이를 연결한다.
6. 비밀값과 개인정보는 수집 단계에서부터 제거하거나 마스킹한다.

### 2. 최소 재현 만들기

1. 원본 실패를 가장 좁은 테스트, 단일 API 요청 또는 시작 명령으로 재현한다.
2. Windows에서는 `.\gradlew.bat test --tests "<fully.qualified.TestName>"`, POSIX에서는 `./gradlew test --tests '<fully.qualified.TestName>'`처럼 대상 테스트부터 실행한다.
3. 정확한 명령, 입력, 테스트 데이터, 프로필, 동시 요청 수, 시각·시간대, 외부 서비스 상태, 종료 코드와 핵심 출력을 기록한다.
4. 반복 횟수와 성공·실패 횟수를 남겨 간헐성, 순서 의존성, 경합 여부를 구분한다.
5. 시간, 난수, 순서와 데이터 상태를 제어할 수 있으면 고정한다.
6. 재현을 위해 운영 코드를 임시 우회하거나 공유 데이터를 파괴하지 않는다.

재현하지 못하면 환경 차이, 시도한 조건과 추가로 필요한 증거를 기록하고 `미재현`으로 남긴다. 추측한 수정은 적용하지 않는다.

### 3. 가설 검증하기

영향도와 검증 비용으로 가설의 순서를 정한다. 각 가설에 참일 때의 예측과 반증 조건을 먼저 적고, 한 번에 하나씩 검증한다.

| 시각 | 구분 | 가설 또는 작업 | 예측·반증 조건 | 결과 | 판정 |
| --- | --- | --- | --- | --- | --- |
| `<KST 또는 명시한 시간대>` | 가설 |  |  |  | 대기·채택·기각 |

반증된 가설도 삭제하지 않는다. 같은 조사를 반복하지 않도록 사용한 증거와 함께 남긴다.

### 4. 근본 원인 확정하기

다음 네 요소를 증거로 연결할 수 있을 때만 근본 원인으로 확정한다.

1. 문제를 촉발한 입력, 상태, 경합 또는 외부 실패
2. 잘못된 코드, 설정, 마이그레이션, 데이터 또는 계약 조건
3. 그 조건이 실제 증상으로 이어지는 실행 메커니즘
4. 기존 입력 검증, 제약, 테스트 또는 관측이 문제를 막거나 감지하지 못한 이유

단순 재시작, 재시도, 데이터 수동 보정과 예외 삼키기는 완화책으로 분류한다.

### 5. 해결하기

수정 권한이 있는 요청에서만 다음을 수행한다.

1. 문서 계약과 사용자 변경을 유지하는 가장 작은 수정안을 선택한다.
2. 가능하면 수정 전에 동일 원인으로 실패하는 회귀 테스트를 추가한다.
3. 스키마·상태·권한·멱등성 정책을 바꿔야 하면 계약 공백을 먼저 보고하고 필요한 결정을 받는다.
4. 임시 로깅이나 진단 플래그를 추가했다면 검증 후 제거한다.

### 6. 검증하기

1. 원래 재현 절차를 같은 조건으로 다시 실행한다.
2. 가장 좁은 회귀 테스트부터 관련 계층 테스트, 필요한 통합·동시성 테스트 순으로 넓힌다.
3. MySQL 잠금, 조건부 갱신, Flyway 또는 SQL 방언이 원인에 관련되면 H2 결과만으로 결론 내리지 않는다. 프로젝트에 MySQL 통합 테스트 환경이 구성돼 있으면 그 환경에서도 검증한다.
4. Redis, 결제사, S3 같은 외부 의존성이 관련되면 성공 경로뿐 아니라 타임아웃, 중복 전달, 재시도와 부분 실패를 검증한다.
5. 해당하는 경우 DB 엔터티 수와 상태 전이, 멱등 처리 이력, Outbox·캐시·로그 같은 부수효과를 확인한다.
6. 범위에 맞게 `.\gradlew.bat test` 또는 `.\gradlew.bat build`를 실행하고, 실행하지 못한 검증은 이유를 남긴다.
7. `git diff --check`와 실제 diff를 확인해 비밀값, 임시 진단 코드와 무관한 변경이 남지 않았는지 확인한다.

원래 증상만 사라지고 회귀 검증을 수행하지 못했으면 `해결`이 아니라 `완화` 또는 `원인 확인`으로 기록한다.

- 실행한 재현·회귀 테스트와 결과
