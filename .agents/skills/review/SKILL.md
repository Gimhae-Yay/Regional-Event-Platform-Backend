# 로컬스탬프 PR 리뷰

## 원칙

- 코드를 수정하지 않고 현재 변경이 만든 재현 가능한 결함과 검증 공백을 찾는다.
- 스타일 취향보다 기능 정확성, 데이터 정합성, 권한 경계, 보안, 장애 처리와 테스트를 우선한다.
- 연결 이슈와 현재 마일스톤의 범위만 요구한다. 후속 기능을 현재 PR의 필수 수정으로 제시하지 않는다.
- 문서와 코드가 다르면 코드가 옳다고 가정하지 않는다. 문서 자체가 미확정이거나 충돌하면 결함으로 단정하지 말고 `정책 확인 필요`로 분리한다.
- diff만 읽고 결론내리지 않는다. 변경 파일의 호출부, 엔터티, 쿼리, 설정, migration과 테스트를 필요한 범위까지 추적한다.
- 실행하지 않은 검증을 통과했다고 표현하지 않는다.
- 기존 코드의 문제와 이번 변경이 새로 만들거나 악화한 문제를 구분한다.
- 단순 리뷰 요청만으로 GitHub에 코멘트, 승인 또는 변경 요청을 게시하지 않는다. 사용자가 명시적으로 게시를 요청한 경우에만 외부에 반영한다.

## 워크플로

### 1. 리뷰 대상과 비교 기준 확정

1. PR 번호나 URL이 있으면 실제 PR의 base/head를 사용한다.
2. PR을 특정하지 않았으면 현재 브랜치에 연결된 열린 PR을 찾는다.
3. 열린 PR이 없으면 현재 브랜치와 추적 가능한 기본 브랜치의 merge-base를 비교한다. 작업 트리 변경 검토 요청이면 staged와 unstaged 변경도 포함한다.
4. base 브랜치를 이름만 보고 추측하지 않는다. PR 메타데이터, upstream 또는 remote HEAD로 확인한다.
5. 커밋 목록과 변경 파일을 먼저 확인한다. 병합 커밋, 이미 병합된 squash 커밋, 브랜치 목적과 무관한 큰 변경이 섞였으면 범위를 사용자와 확인한다.

범위를 안전하게 하나로 특정할 수 없을 때만 짧게 질문한다.

### 2. 요구사항과 프로젝트 기준 읽기

다음 순서로 원문을 읽는다.

1. 가장 가까운 `AGENTS.md`와 저장소 지침
2. PR 설명, 연결 이슈, 수용 기준, PR 템플릿과 기존 리뷰
3. 변경 API의 공통 계약은 `docs/api/common/README.md`와 연결된 공통 명세, 엔드포인트 계약은 `docs/api/<문서-분류>/<도메인>/*.md`에서 실제 대응 명세를 확인한다. 여기서 문서 분류는 `p0`, `future`처럼 `docs/api/` 하위 API 명세를 구분하는 최상위 디렉터리 이름이다.
4. 변경 도메인의 구현 계약은 `docs/` 하위의 실제 대응 명세를 확인한다. API 문서 분류와 구현 명세 경로가 1:1로 대응한다고 가정하지 않으며, 대응 명세가 불명확하거나 없으면 경로를 추정하지 않고 `구현 계약 확인 필요`로 분리한다.
5. 엔터티 관계, 컬럼, 제약·인덱스, migration 정합성은 `docs/erd.md`
6. 변경과 직접 관련된 승인된 ADR
7. 제품 범위·보안·동시성·정합성 정책 확인이 필요한 경우에만 `docs/local-stamp-platform-prd.md`
8. 의존성·설정 또는 기술 선택 검토가 필요한 경우에만 `docs/local-stamp-platform-tech-stack.md`

- 연결 이슈나 승인된 ADR이 기존 문서를 의도적으로 대체하면 적용 근거를 리뷰에 적는다.
- 문서 간 충돌이 아직 해결되지 않았으면 임의 정책을 강제하지 않고 `정책 확인 필요`로 분리한다.
- 제안서·과거 기획 문서는 배경 이해에만 사용한다. 구현 계약은 변경 API 명세서, 도메인 구현 명세서 및 ERD를 우선 기준으로 판별하며, 이들 문서 간 충돌은 AGENTS.md의 문서 충돌 우선순위를 따른다.

### 3. 전체 변경과 주변 맥락 수집

GitHub 연결 도구가 있으면 PR 메타데이터, diff, 커밋, CI, 기존 리뷰를 읽는 데 사용한다. 그렇지 않으면 `gh`와 로컬 Git을 사용한다.

예시:

```text
gh pr view <PR> --json title,body,baseRefName,headRefName,commits,files,statusCheckRollup,reviews,comments
gh pr diff <PR>
git diff --stat <merge-base>...HEAD
git diff <merge-base>...HEAD
git log --oneline <merge-base>..HEAD
```

- diff가 크면 파일별로 나누어 읽되 모든 변경 파일을 확인한다.
- 새 메서드의 호출자, 상태 전이의 이전·다음 단계, DB 제약, 외부 연동 실패 경로까지 추적한다.
- 생성 파일, lockfile, formatting-only 변경은 의미 있는 변경과 분리한다.

### 4. 위험 기반 분석

1. 잘못된 권한 또는 지역 경계 우회
2. 예약·정원·결제·체크인의 정합성 및 멱등성
3. QR 서명·만료·중복 처리와 개인정보 노출
4. 후기·쿠폰의 자격, 유일성, 원자성
5. 콘텐츠·예약·결제·방문 상태 전이와 MVP 범위 일치 여부
6. 트랜잭션, Outbox, 캐시, 외부 장애와 재시도
7. API·DB 계약, migration과 하위 호환성
8. 테스트의 재현력, 운영 관측성과 성능 회귀

근거 없는 가능성만으로 지적하지 않는다. 문제가 발생하는 입력, 상태, 동시 실행 순서 또는 장애 조건을 구체화한다.

### 5. 검증

- PR 리뷰에서는 먼저 CI 실행 결과와 각 job의 검증 범위를 확인한다.
- 정상·경계·실패 조건을 검증하는 테스트가 변경에 맞게 존재하는지 확인하고, PR CI 통과 결과를 검증 근거로 기록한다.
- PR CI가 통과했고 변경 범위가 CI 검증 범위에 포함되면, 리뷰어가 동일한 로컬 빌드·테스트를 다시 실행할 필요는 없다.
- CI가 실행되지 않았거나 실패했거나, 변경 범위가 CI 검증 범위 밖이면 가장 작은 관련 테스트부터 추가로 실행하고 필요하면 전체 테스트로 확장한다.
- 추가 실행의 기본 전체 검증은 Windows에서 `.\gradlew.bat test`, 다른 환경에서는 `./gradlew test`를 사용한다.
- 컴파일, 정적 검사, migration 또는 Testcontainers 검증이 변경 위험에 필요하면 추가로 실행한다.
- MySQL 잠금·조건부 갱신, Redis TTL·원자성, 외부 결제 웹훅과 같은 동작을 H2나 mock만으로 입증하지 않는다.
- 환경이나 자격 증명 부족으로 실행하지 못한 검증은 실패로 꾸미지 말고 `미검증`과 잔여 위험으로 기록한다.

### 6. 지적 선별

각 후보를 다음 조건으로 걸러낸다.

- 이번 변경 때문에 발생하거나 악화되는가?
- 현실적인 입력이나 운영 조건에서 재현 가능한가?
- 기능, 보안, 데이터, 운영 또는 유지보수에 구체적인 영향이 있는가?
- 작성자가 최소 범위로 수정할 수 있게 설명할 수 있는가?
- 기존 리뷰와 중복되지 않는가?

모두 충족하지 않는 스타일 선호나 막연한 추측은 제외한다. 문서 충돌 때문에 결론낼 수 없는 항목은 finding과 분리해 `정책 확인 필요`에 둔다.

## 심각도

- `[P0]`: 즉시 중단이 필요한 보안 침해, 결제·예약·방문 데이터 손실, 광범위한 서비스 장애
- `[P1]`: 머지 전에 수정해야 하는 재현 가능한 기능 버그, 권한 우회, 정합성·동시성·API 계약 위반
- `[P2]`: 특정 장애나 경계 조건에서 오동작하거나 중요한 회귀 방지·운영 대응이 빠진 문제
- `[P3]`: 영향이 제한적인 유지보수 문제 또는 저장소에 명시된 컨벤션 위반

심각도는 수정 난이도가 아니라 사용자·데이터·운영 영향으로 정한다.

## 결과 형식

findings를 가장 먼저 심각도순으로 작성한다. 각 finding에 다음을 포함한다.

```markdown
### [P1] 짧고 명령형인 제목
`src/.../File.java:42`

- 발생 조건: 문제가 드러나는 입력, 상태 또는 실행 순서
- 영향: 사용자·데이터·보안·운영에 생기는 결과
- 근거: 코드 흐름, 테스트 결과 또는 프로젝트 문서 계약
- 최소 수정 방향: 설계를 대신하지 않는 범위의 구체적인 해결 방향
```

이어서 아래 순서로 정리한다.

1. `검증 결과`: 실행한 명령과 결과, 실행하지 못한 검증
2. `정책 확인 필요`: 문서 충돌이나 미확정 정책 때문에 결론을 보류한 항목
3. `범위와 잔여 위험`: 리뷰한 diff, 제외한 범위, 환경 한계
4. `판정`: `수정 필요`, `논의 필요`, `승인 가능` 중 하나와 한 줄 근거

지적이 없으면 `발견된 문제 없음`이라고 쓰되 검증 범위와 잔여 위험은 생략하지 않는다. 칭찬은 리뷰 판단에 도움이 되는 구체적인 내용이 있을 때만 짧게 덧붙인다.

대화 환경이 코드 라인에 직접 피드백을 붙이는 기능을 제공하면 finding을 정확한 diff 줄에 연결한다.

## GitHub 게시

사용자가 명시적으로 게시를 요청한 경우에만 다음을 수행한다.

1. 기존 리뷰와 중복되지 않는지 다시 확인한다.
2. 먼저 대화에 게시할 본문과 판정을 보여 주거나, 사용자가 본문까지 위임했다면 작성한 내용을 그대로 사용한다.
3. 하나의 종합 리뷰로 게시하고 게시 결과를 확인한다.
4. 사용자가 리뷰 상태까지 지정하지 않았다면 `COMMENT`로 게시한다. 임의로 `APPROVE` 또는 `REQUEST_CHANGES`를 선택하지 않는다.

예시:

```text
gh pr review <PR> --comment --body-file <review-file>
```

로컬 변경 리뷰에는 외부 게시를 시도하지 않는다.
