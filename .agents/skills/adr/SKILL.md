# Architecture Decision Record

이 저장소의 기술 결정을 판별하고, 결정 당시의 근거와 수용한 손해를 보존하는 ADR을 작성한다.
ADR을 현재 제품·API·DB·운영 정책의 기준 문서 대신 사용하지 않는다.

## ADR 필요성 판정

다음 중 하나 이상에 해당하고 영향이 실질적일 때만 ADR 후보로 삼는다.

- 변경에 데이터 이관, 호환 계층, 중단 또는 이중 운영이 필요한 저장소·식별자·스키마·이벤트 계약
- 여러 요청이나 인스턴스의 정합성과 실패 의미를 정하는 락, 트랜잭션 경계, 전달 보장, 멱등성
- 외부 API, 결제사, 공개 계약, 프레임워크 또는 인프라처럼 장기간 종속을 만드는 선택
- 인증·지역 권한, QR 키, 개인정보, 시간, 소유권, 장애 복구 경계를 가로지르는 선택
- 정확성 대 처리량, 즉시 일관성 대 최종 일관성처럼 합리적 대안 간 품질 속성 교환이 큰 선택
- 익숙한 방식과 다른 제약을 의도적으로 받아들여 같은 논쟁이 반복될 가능성이 큰 선택

다음은 단독으로 ADR을 만들지 않는다.

- 지역 변수명, 단순 리팩터링, 쉽게 교체 가능한 내부 구현
- 아직 고르지 않은 아이디어, 짧은 실험, 폐기 가능한 spike
- PRD의 필드나 상태를 구현 문서에 그대로 옮기는 작업
- 장기 영향과 트레이드오프가 없는 patch 업데이트
- 취소·환불·노쇼, 후기 숨김, 개인정보 보관 기간 같은 순수 제품·운영 정책

ADR 대상이 아니면 만들지 않는 이유와 대신 수정하거나 참조할 기준 문서를 보고한다.

## 작성 절차

### 1. 기존 결정과 증거 확인

- 기준 문서에 이미 채택된 선택이면 문서, 이슈, 커밋과 테스트에서 당시 근거를 찾는다.
- 근거가 확인되는 범위에서만 소급 ADR을 작성하고 기록 유형: 소급을 표시한다.
- 원래 결정일을 확인할 수 없으면 결정일: 확인 불가로 적고 현재의 기록일과 섞지 않는다.
- 현재 구현만 보고 정책이나 과거 선택 이유를 역으로 만들어내지 않는다.
- 핵심 이유가 남아 있지 않으면 가능한 선택지를 다시 비교하고 사용자의 확인을 받은 뒤 기록한다.

## 2. 선택지 비교와 채택

선택이 확정되지 않았다면 파일을 만들기 전에 다음 순서로 사용자에게 제시한다.

1. 합격 조건과 반드시 지킬 불변 조건을 명시한다.
2. 추천안을 첫 번째에 둔다.
3. 정상 경로뿐 아니라 장애, 경합, 재시도, 운영, 이관, 롤백 영향을 비교한다.
4. 다음 표를 사용한다.

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 추천안 |  |  |  |  |
| 2 | 대안 |  |  |  |  |

- 추천과 사용자의 최종 선택이 다르면 표의 순서를 바꾸지 말고 최종 선택 이유를 별도로 기록한다.
- 사용자 선택 또는 명백한 기존 합의가 확인된 뒤에만 채택됨 ADR을 작성한다.

## ADR 생성

- 기본 위치를 `docs/adr/`로 사용하고 첫 ADR에서만 디렉터리를 만든다.
- 파일명은 NNNN-<영문-kebab-case>.md 형식으로 한다. 예: 0001-use-pessimistic-point-lock.md.
- 기존 파일 번호의 최댓값에 1을 더한 네 자리 번호를 사용한다. 삭제되거나 건너뛴 번호를 재사용하지 않는다.
- 제목은 # ADR-NNNN: <한국어 결정 제목> 형식으로 작성한다.
- [ADR 양식](assets/adr-template.md)을 복사해 모든 항목을 구체적으로 채운다.
- 관련 요구사항은 저장소 상대 링크와 `FR-xx`, `US-xx` 또는 안정적인 절 제목으로 연결한다.
- 현재 정책을 바꾸면 담당 기준 문서를 먼저 새 결정에 맞추고 같은 변경에서 ADR을 추가한다.
- 한 ADR에는 독립적으로 대체할 수 있는 결정 하나만 넣는다.
- ADR을 구현보다 먼저 확정한다. ADR 요청만으로 코드나 설정까지 변경하지 않는다.

`제안됨` ADR은 채택 전까지 수정할 수 있다. 사용자가 채택하면 필요한 내용을 모두 확정한 뒤 상태를 한 번 `채택됨`으로 바꾸고, 그 순간부터 파일 전체를 불변으로 취급한다.

## 채택된 ADR 대체

채택된 ADR의 상태, 본문, 링크, 파일명, 경로를 수정·삭제·이름 변경하지 않는다. 결정을 바꾸려면 다음을 수행한다.

1. 대체할 ADR과 그 ADR이 대체한 모든 선행 ADR을 읽는다.
2. 변경을 요구한 새 사실, 제약, 단계 변화 또는 실패 증거를 명시한다.
3. 새 번호의 ADR을 만들고 `대체 대상`에 이전 ADR 링크와 대체 범위를 적는다.
4. 데이터 이관, 호환성, 단계적 전환, 롤백, 운영 관측 방법을 결과에 포함한다.
5. 현재 정책의 담당 기준 문서를 새 결정에 맞춘다.
6. 여러 ADR의 일부를 대체하면 각 번호와 범위를 적고 대체 관계를 순환시키지 않는다.

여러 ADR의 일부만 대체하면 각각의 번호와 대체 범위를 새 ADR에 명시한다.
대체 관계를 순환시키지 않는다.
현재 결정은 특정 범위에 대해 가장 나중에 채택되어 이전 ADR을 명시적으로 대체한 ADR로 판단한다.

## 검증 및 보고

- 파일명과 제목 번호, 상태와 결정 근거, 기록일과 결정일을 확인한다.
- 링크가 실제 저장소 파일과 안정적인 제목·요구사항 ID를 가리키는지 확인한다.
- 결정 동인, 불변 조건, 대안, 실패 위험, 되돌림 비용, 수용한 단점, 검증 방법, 재검토 조건이 구체적인지 확인한다.
- 대체 ADR이면 대체 범위, 이관·호환성, 전환·롤백, 관측 방법을 확인한다.
- `git diff --check`를 실행하고 관련 문서 외 코드·설정이 바뀌지 않았는지 확인한다.
- 최종 보고에 ADR 필요성 판정, 생성하거나 대체한 파일, 상태, 근거의 한계, 기준 문서 변경 여부를 포함한다.
