# 이슈 생성

문서의 요구사항을 현재 구현 상태와 대조해, 근거와 완료 조건이 분명한 이슈를 만든다.
초안을 먼저 검토받고 승인된 내용만 원격 저장소에 생성한다.

## 지켜야 할 원칙

- 이슈 작업만 요청받았으면 코드와 제품 문서를 수정하지 않는다.
- 문서에 없는 API 경로, HTTP 상태, 에러 코드, 필드, 정책값, 스키마와 기술 선택을 추측하지 않는다.
- 기준 문서나 사용자 요청의 현재 범위 밖에 있는 기능을 백로그에 자동으로 추가하지 않는다.
- 문서 충돌이나 미결정 정책이 완료 조건을 바꾸면 구현 이슈를 만들지 말고 차단 사유를 먼저 보고한다.
- 사용자에게 제목, 본문, 유형, 라벨, 프로젝트와 의존 관계를 한 번에 보여주고 승인받기 전에는 원격 이슈를 생성하지 않는다.
- 사용자가 초안이나 분해만 요청하면 로컬 분석에서 끝내고 GitHub를 변경하지 않는다.
- 기존 이슈, PR과 현재 코드를 확인해 중복되거나 이미 끝난 작업을 만들지 않는다.
- 이슈 생성 전, 정책 결정이 필요한 경우 ADR 문서를 먼저 생성 후 이슈를 생성한다.
- Feature 이슈는 HTTP 메서드와 경로로 식별되는 API 엔드포인트 하나와 그 엔드포인트만 정의하는 확정 API 명세 하나를 단위로 만든다. 여러 엔드포인트, API 명세 없는 기능, 스케줄러·문서·공통 기반 작업은 Feature로 만들지 않는다.
- Task 이슈는 Feature 또는 Bug 이슈의 범위를 다른 Task의 구현을 포함하지 않는 하나의 PR 결과로 나눈 직속 하위 이슈다. 확정된 계약을 기준으로 독립적으로 검토·검증할 수 있어야 하며, 실제 선행 의존성이 있으면 통합 검증과 완료·병합은 해당 의존성이 해결된 뒤 수행한다. 부모가 없거나 부모 유형이 Feature·Bug가 아니면 Task 초안·생성을 진행하지 않는다.
- Task 이슈는 이슈 폼의 필수 단일 선택 `work-type` 값을 작업 성격 라벨 하나로 적용한다. 기본·도메인·권한 라벨은 이 조건과 별개다. 선택값이 없거나 둘 이상이면 DoR 위반으로 보고하고 초안·생성을 진행하지 않는다. 선택값과 일치하는 라벨이 없으면 승인된 이슈를 생성하기 직전에 같은 이름의 라벨을 생성하고 적용한다.

## 근거를 읽는 순서

저장소가 문서 우선순위나 기준 문서를 명시하면 그대로 따른다. 명시가 없으면 다음 순서로 근거를 확인한다.

1. `.github/ISSUE_TEMPLATE/new_feature.yaml`, `new_task.yaml`, `bug_report.yaml`에서 이슈 형식과 메타데이터를 읽는다.
2. `AGENTS.md`, 문서 허브와 코드 컨벤션에서 저장소 작업 규칙과 문서 체계를 확인한다.
3. PRD, 기능 명세, 유저 스토리, 수용 기준과 정책 문서에서 현재 범위와 요구사항을 확인한다.
4. API 명세, ERD, 상태 전이와 오류 계약 문서에서 구현 계약을 확인한다.
5. ADR, 기술 스택과 설계 문서에서 확정된 기술 결정과 대체 관계를 확인한다.
6. 빌드 설정, 소스, DB 마이그레이션, 테스트와 설정에서 현재 구현 사실을 확인한다. 이미 구현됐는지는 계획 문서보다 코드와 테스트를 우선한다.
7. 기준 문서가 아닌 제안, 검토와 아이디어 문서는 보조 근거로만 사용한다. 상위 근거와 다르면 임의로 한쪽을 선택하지 않는다.

요청에 필요한 명세나 설계 문서가 없거나 미완성이면 경로, DTO, 테이블, 상태와 정책값을 만들어내지 말고 필요한 결정이나 문서화 작업을 선행 이슈로 분리한다.

## 범위를 보호하기

- 사용자 요청과 기준 문서에서 현재 대상 범위, 제외 범위와 후속 범위를 구분한다.
- 현재 범위에 없는 기능과 미래 확장 아이디어는 사용자가 명시적으로 요청하지 않는 한 이슈로 만들지 않는다.
- 문서가 충돌하면 각 근거와 영향을 보고하고 임의로 우선순위를 정하지 않는다.
- 미결정 사항이 계약이나 완료 조건을 바꾸면 구현 이슈 본문에 숨기지 않는다. 결정·문서화 이슈를 먼저 만들거나 사용자에게 결정을 요청하고 구현 이슈를 차단한다.

## 사전 조사하기

1. `git status`, 현재 브랜치, `git remote -v`, 현재 커밋과 원격 포함 여부를 확인한다.
2. 관련 문서가 커밋되어 원격 GitHub에서 열리는지 확인한다. 커밋되지 않았거나 push되지 않은 문서를 근거로 초안은 만들 수 있지만 원격 이슈는 만들지 않는다.
3. 이슈 템플릿과 현재 문서·코드·테스트를 읽고 요청 범위를 정리한다.
4. `gh auth status`와 `gh repo view`로 대상 저장소를 확인하고, 저장소 이름을 하드코딩하지 말고 실제 `origin`을 기준으로 삼는다.
5. `gh issue list --state all`로 제목뿐 아니라 본문 속 요구사항 ID, API, 상태 전이와 완료 조건을 비교해 중복을 찾는다.
6. `gh label list --limit 200`으로 라벨의 정확한 철자와 대소문자를 확인한다.
7. 선택한 이슈 폼의 `projects` 값을 확인한다. 프로젝트 조회 권한이 없으면 인증 범위를 임의로 바꾸지 말고, 보드 추가 없이 생성할지 사용자에게 확인한다.

문서 근거 링크는 가능하면 원격에 존재하는 커밋 SHA의 영구 링크(permalink)를 사용한다. 작업 트리의 최신 내용과 링크의 내용이 다르면 생성 전에 그 차이를 보고한다.

## 이슈를 분해하기

먼저 이슈 유형과 작업의 성격을 구분한다.

- Feature: 확정 API 명세 하나에 정의된 API 엔드포인트 하나의 사용자 관찰 가능 결과를 관리한다.
- 정책·설계 결정: 구현 계약을 막는 오픈 이슈나 문서 충돌을 해소한다.
- Task: Feature 또는 Bug 범위에서 분리한 구현, 문서, 테스트, 공통 기반 중 하나의 PR로 검증할 수 있는 결과를 관리한다.
- 공통 기반: 여러 기능이 실제로 공유하는 설정, DB 마이그레이션, 오류 계약, CI나 관측 기반만 둔다.
- 버그: 하나의 재현 가능한 실패와 기대 동작 복구를 다룬다.
- 문서·리팩터링·운영: 제품 동작 변경 여부가 분명한 독립 결과로 둔다.

다음 기준으로 크기를 정한다.

1. Feature와 Bug는 검증 가능한 제품 결과나 실패 복구를 관리하고, 구현은 필요에 따라 직속 하위 Task로 나눈다. Task는 부모 범위의 일부만 가지며 다른 Feature의 엔드포인트나 다른 Bug의 실패를 섞지 않는다.
2. Task 하나는 다른 Task의 구현을 자기 범위에 포함하지 않고 작업 성격에 맞게 독립적으로 검토·검증할 수 있는 결과와 하나의 PR을 가진다. 여러 변경이 함께 있어야 빌드·계약·상태 전이 또는 검증이 성립하면 하나의 Task로 묶는다. 계층이나 파일 종류가 다르다는 이유만으로 나누지 않는다.
3. Task 간 `blocked by` 관계는 계약과 통합 완료 게이트가 되는 실제 blocker에만 둔다. 선행 Task가 미완료여도 필요한 API·ERD·ADR·정책 계약이 확정돼 있고 Adapter·통합 담당이 명확하면 현재 Task 범위는 병렬로 구현·검토·검증할 수 있다. 선행 결과가 필요한 통합 검증과 TODO 완료·병합은 의존성이 해결된 뒤 수행하며, 독립 Task에는 순서를 만들지 않는다. 여러 Feature·Bug가 공유하는 Task는 결과를 소유하는 부모 하나의 하위 이슈로 두고, 다른 소비 이슈에서는 실제 `blocked by` 관계로만 연결한다.
4. 기능 구현 Task의 작업 TODO는 다음 구조와 순서로 작성한다. 각 항목은 해당 Task 범위에서 실제 변경이 필요한 경우에만 작성한다.
   - Entity, Repository 생성 및 수정
   - Service, Controller, API 구현
   - 테스트 코드 구현

5. Feature 이슈 하나에는 HTTP 메서드·경로 조합 하나와 그 엔드포인트의 API 명세 permalink 하나만 둔다. 제목과 Summary에는 엔드포인트의 행위를 드러내고, `API Documentation`에는 대상 API 명세 permalink 하나만 적는다.
6. 한 API 명세가 여러 엔드포인트를 정의하면 Feature를 만들지 않고 엔드포인트별 API 명세 분리를 선행한다. 하나의 엔드포인트가 여러 문서에 중복 정의돼도 기준 API 명세 하나가 확정되기 전에는 만들지 않는다.
7. 여러 엔드포인트가 같은 불변식·트랜잭션·공통 기반을 공유해도 Feature는 엔드포인트별로 나눈다. 공유 구현은 별도 Task로 분리하고 실제 blocker 관계만 연결한다.
8. 공통 기반은 둘 이상의 Task가 선행 결과로 실제 공유할 때만 별도 Task로 만든다.
9. 문서 순서나 요구사항 ID가 연속된다는 이유로 의존성을 만들지 않는다. 결정, 스키마, 인증 계약이나 상태 전이처럼 실제 blocker만 연결한다.
10. 장기적인 기술 결정이 필요한 작업은 관련 ADR을 연결한다. 결정이 미확정이면 구현 Task보다 결정 Task를 먼저 둔다.

전체 작업 분해를 요청받으면 `정책·설계 선행 작업 → 공유 기반 → 수직 기능 → 교차 검증·배포` 순서로 검토한다.
모든 항목을 반드시 만들지는 말고, 현재 코드와 기존 이슈를 제외한 실제 잔여 작업만 제안한다.

## 이슈 폼에서 본문 만들기

Feature 이슈는 `.github/ISSUE_TEMPLATE/new_feature.yaml`, Task 이슈는 `new_task.yaml`, Bug 이슈는 `bug_report.yaml`을 실행 시점마다 직접 읽어 만든다. 이 스킬 안에 제목 접두사, 본문 필드, 필드 순서, 필수 여부나 기본 메타데이터를 별도 템플릿으로 복제하지 않는다.

1. 요청이 Feature, Task, Bug 중 어느 폼에 해당하는지 불명확하면 임의로 고르지 말고 사용자에게 확인한다.
2. 초안을 만들기 직전에 대상 브랜치의 YAML을 읽는다. 원격 `dev`에 생성할 때는 로컬 파일과 `origin/dev`를 비교하고, 다르면 차이를 보고한 뒤 실제 생성 대상 브랜치의 버전을 기준으로 삼는다.
3. 최상위 `title`, `type`, `labels`, `projects`, `assignees`를 이슈 메타데이터의 기준으로 사용한다. 값이 바뀌면 스킬 수정 없이 새 값을 따른다.
4. Feature 이슈는 API 명세 permalink의 커밋이 원격에 존재하고, 문서가 HTTP 메서드·경로 조합 하나만 정의하는지 확인한다. 같은 메서드·경로나 같은 API 명세를 연결한 기존 Feature를 제목뿐 아니라 열린 이슈와 닫힌 이슈 전체에서 검색한다. API 명세가 없거나 미확정·미반영 상태거나 여러 엔드포인트를 포함하거나 기존 Feature와 중복되면 초안·생성을 진행하지 않는다.
5. Feature 또는 Bug의 하위 Task를 자동으로 만들지 않는다. 사용자가 함께 분해해 달라고 요청한 경우에만 부모 범위 안의 잔여 작업을 Task로 제안한다.
6. Task를 만들기 전에 부모 이슈 번호·URL, Issue Type과 범위를 확인한다. 부모가 같은 저장소의 Feature 또는 Bug가 아니거나, Task 결과가 부모 범위에 포함되지 않거나, 다른 Task 아래로 중첩하려는 경우 초안·생성을 진행하지 않는다.
7. Task 이슈에는 필수 단일 선택 `dropdown`인 `work-type`이 있어야 한다. 작업 분해에서 확정한 성격에 맞는 폼 옵션 하나를 선택하고, 그 정확한 값을 작업 성격 라벨로 사용한다. 옵션 이름이나 목록을 이 스킬에 복제하지 않는다. 선택이 모호하거나 폼에 이 필드가 없으면 임의의 라벨을 추가하지 말고 DoR 위반과 필요한 폼 보완을 보고한다.
8. `gh label list`에서 선택값과 정확히 같은 라벨이 존재하는지 확인한다. 없으면 초안에 신규 생성할 라벨임을 표시하되 승인 전에는 생성하지 않는다. 초안의 라벨에는 폼의 기본 라벨과 선택한 작업 성격 라벨을 함께 표시하고, 작업 성격 라벨은 정확히 하나만 둔다. 도메인·권한 등 추가 분류 라벨은 이 판단에 사용하지 않는다.
9. `body` 배열을 선언된 순서대로 순회한다. 응답을 받는 항목의 `id`는 내부 식별자로만 사용하고, 본문에는 GitHub 이슈 폼의 제출 형식처럼 `### {attributes.label}` 제목과 해당 값을 적는다. `markdown` 항목은 안내 내용으로 처리하며 응답 필드를 임의로 만들지 않는다.
10. `attributes.description`을 작성 지침으로, `placeholder`를 값의 형식 예시로 따른다. 스킬이 별도의 고정 필드명이나 본문 골격을 추가하지 않는다.
11. `validations.required: true`인 필드는 근거 있는 값을 모두 채운다. 필수 정보를 확보하지 못하면 값을 추측하거나 `확인 필요`로 생성하지 말고 사용자에게 부족한 정보를 요청한다.
12. `textarea`, `input`, `dropdown`, `checkboxes`, `upload`, `markdown` 등 각 항목의 `type`에 맞춰 값을 표현한다. 지원하지 못하는 유형이면 임의의 대체 필드로 바꾸지 말고 생성 방법을 사용자와 확인한다.
13. 체크박스 형식을 요구하는 필드가 있을 때만 `- [ ]` 목록을 사용한다. 완료 조건은 명령, 상태, 응답, DB 결과, 로그나 자동화 테스트로 검증 가능하게 작성한다.
14. 첨부 필드에는 실제로 제공된 첨부나 공개 가능한 링크만 사용한다. 로컬 절대 경로, 비밀이 포함된 로그와 존재하지 않는 첨부를 넣지 않는다. CLI로 첨부할 수 없으면 웹 폼 사용이나 사용자 첨부가 필요하다고 보고한다.
15. 본문 파일에는 `body`에서 만든 내용만 넣는다. 제목, 유형, 라벨, 프로젝트와 담당자는 미리보기에서 별도 메타데이터로 보여주고 실제 본문에는 반복하지 않는다.
16. 폼에 없는 최상위 섹션을 추가하지 않는다. 목적, 범위, 근거, 의존성 같은 상세 정보는 현재 폼의 설명과 형식이 허용하는 가장 적절한 기존 필드 안에 배치한다.
17. YAML을 읽거나 해석할 수 없으면 과거에 기억한 구조로 대체하지 말고 중단해 오류를 보고한다.

## 메타데이터 적용하기

- 제목은 선택한 YAML의 `title` 값을 접두사로 사용하고, 그 뒤에 검증 가능한 결과 또는 재현되는 실패를 간결하게 적는다.
- 유형, 기본 라벨, 프로젝트와 담당자는 YAML에 선언된 값을 그대로 적용한다.
- Task 이슈의 선택한 `work-type` 값은 기본 라벨에 추가하는 유일한 작업 성격 라벨이다. 같은 범주의 다른 라벨을 추가하지 않는다. 선택값이 실제 라벨로 없으면 이슈 생성 승인 범위에 해당 라벨 생성을 포함해 미리 보여 준다.
- 추가 라벨은 사용자가 요청했거나 별도 저장소 규칙이 명시한 경우에만 검토한다. `work-type` 외의 추가 라벨은 `gh label list`에 존재하는 라벨만 사용하고 별도 승인 없이 새로 만들지 않는다.
- 프로젝트 권한 부족 등으로 YAML의 메타데이터를 완전히 적용하지 못하면 성공으로 숨기지 말고 생성 전에 선택지를 보고한다.

## 초안을 검토받기

생성 전 다음을 한 번에 제시한다.

1. 제외한 기존·중복·완료 작업과 근거
2. 차단하는 문서 충돌과 미결정 사항
3. 생성 순서, 제목, 유형, 라벨, 프로젝트, Task의 부모, 근거 ID와 선행 관계 표
4. 각 이슈의 전체 본문

`I-01` 같은 임시 식별자로 초안 의존성을 표시한다. 사용자가 승인하거나 수정한 뒤에만 생성한다. 승인 범위가 일부면 그 이슈만 생성한다.

## GitHub에 생성하기

1. 승인된 본문을 안전한 임시 파일에 각각 저장한다.
2. 승인 직전에 `gh label list`를 다시 조회한다. 선택한 `work-type` 라벨이 없으면 선택값 전체를 하나의 인수로 전달해 `gh label create "<work-type>"`으로 이름만 생성한다. 폼에 없는 색상과 설명은 추측하지 않는다. 생성 후 정확한 이름의 라벨이 존재하는지 검증하고, 생성이나 검증에 실패하면 이슈를 만들지 않는다.
3. 새 Feature·Bug와 하위 Task를 함께 승인받았으면 부모를 먼저 생성한다. 이어서 blocker와 기반 Task부터 `gh issue create --body-file`로 생성한다. 제목 접두사와 `--type`, 기본 `--label`, `--assignee`는 선택한 YAML에서 가져온다. Task 이슈에는 검증한 `work-type` 라벨 하나를 기본 라벨에 추가하고, 필요한 경우 `--blocked-by`를 사용한다. YAML 값이 비어 있으면 해당 옵션을 임의로 채우지 않는다.
4. Task를 생성한 직후 REST 이슈 ID를 조회하고 `gh api --method POST repos/{owner}/{repo}/issues/{parent_number}/sub_issues -F sub_issue_id={task_id}`로 검증한 Feature·Bug 부모의 직속 하위 이슈로 연결한다. `GET repos/{owner}/{repo}/issues/{task_number}/parent`로 부모 번호와 유형을 확인한다. 부모 연결에 실패하면 다음 Task를 만들지 않는다.
5. 생성된 URL을 사용해 `.github/ISSUE_TEMPLATE/*.yaml`의 `projects` 대상에 항목을 추가한다. 현재 GitHub CLI에서는 프로젝트 번호와 소유자를 확인한 뒤 `gh project item-add`를 사용할 수 있다.
6. 다음 이슈에는 방금 생성된 실제 번호를 GitHub의 blocked-by 관계에 반영한다. 부모 관계를 의존 관계로 대신하지 않으며, 실제 blocker만 기록한다. 의존성을 기록할 수 있는 필드가 현재 YAML에 있을 때만 해당 필드에도 번호를 적는다.
7. 생성 직후 `gh issue view`로 제목, 본문, 라벨, 유형과 의존 관계를 확인하고, Task는 부모 관계도 확인하며, 가능한 경우 프로젝트 항목도 검증한다.
8. 임시 본문 파일을 제거한다.

라벨·이슈·부모 연결의 일부 생성이 실패하면 같은 명령을 바로 반복하지 않는다. 라벨과 기존 이슈·부모 관계를 다시 조회해 실제 생성 여부를 확인하고, 생성된 라벨·이슈 번호·성공한 속성·누락된 부모·실패 원인을 보고한 뒤 재시도 승인을 받는다. 라벨 또는 Task 생성 후 다음 단계가 실패해도 승인 없이 라벨이나 이슈를 삭제하지 않는다.

## 완료 보고

- 새로 생성한 `work-type` 라벨이 있으면 이름을 보고한다.
- 생성한 이슈를 번호, 제목, URL, 유형, 라벨, Task의 부모와 의존 관계 순서로 보고한다.
- GitHub Project 추가 성공 여부를 따로 밝힌다.
- 중복·완료·범위 밖이라 생성하지 않은 항목과 보류된 정책 결정을 함께 적는다.
- 초안만 작성했다면 원격 변경이 없었다고 명시한다.
