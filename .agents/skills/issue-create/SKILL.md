# 이슈 생성

문서의 요구사항을 현재 구현 상태와 대조해, 근거와 완료 조건이 분명한 이슈를 만든다.
초안을 먼저 검토받고 승인된 내용만 원격 저장소에 생성한다.

## 지켜야 할 원칙

- 이슈 작업만 요청받았으면 코드와 제품 문서를 수정하지 않는다.
- 문서에 없는 API 경로, HTTP 상태, 에러 코드, 필드, 정책값, 스키마와 기술 선택을 추측하지 않는다.
- 기준 문서나 사용자 요청의 현재 범위 밖에 있는 기능을 백로그에 자동으로 추가하지 않는다.
- 문서 충돌이나 미결정 정책이 완료 조건을 바꾸면 구현 이슈를 만들지 말고 차단 사유를 먼저 보고한다.
- 사용자에게 제목, 본문, 유형, 라벨, 프로젝트와 의존 관계를 한 번에 보여주고 승인받기 전에는 원격 이슈를 생성하지 않는다.
- 사용자가 초안이나 분해만 요청하면 로컬 분석에서 끝내고 GitHub를 변경하지 않는다.
- 기존 이슈, PR과 현재 코드를 확인해 중복되거나 이미 끝난 작업을 만들지 않는다.

## 근거를 읽는 순서

저장소가 문서 우선순위나 기준 문서를 명시하면 그대로 따른다. 명시가 없으면 다음 순서로 근거를 확인한다.

1. `.github/ISSUE_TEMPLATE/new_task.yaml`과 `bug_report.yaml`에서 이슈 형식과 메타데이터를 읽는다.
2. `AGENTS.md`, `README`, `CONTRIBUTING`, 문서 허브와 코드 컨벤션에서 저장소 작업 규칙과 문서 체계를 확인한다.
3. PRD, 기능 명세, 유저 스토리, 수용 기준과 정책 문서에서 현재 범위와 요구사항을 확인한다.
4. API 명세, ERD, 상태 전이와 오류 계약 문서에서 구현 계약을 확인한다.
5. ADR, 기술 스택과 설계 문서에서 확정된 기술 결정과 대체 관계를 확인한다.
6. 빌드 설정, 소스, DB 마이그레이션, 테스트와 설정에서 현재 구현 사실을 확인한다. 이미 구현됐는지는 계획 문서보다 코드와 테스트를 우선한다.
7. 기준 문서가 아닌 제안, 검토와 아이디어 문서는 보조 근거로만 사용한다. 상위 근거와 다르면 임의로 한쪽을 선택하지 않는다.

요청에 필요한 명세나 설계 문서가 없거나 미완성이면 경로, DTO, 테이블, 상태와 정책값을 만들어내지 말고 필요한 결정이나 문서화 작업을 선행 이슈로 분리한다.

## 범위를 보호하기

- 사용자 요청과 기준 문서에서 현재 대상 범위, 제외 범위와 후속 범위를 구분한다.
- 현재 범위에 없는 기능과 미래 확장 아이디어는 사용자가 명시적으로 요청하지 않는 한 이슈로 만들지 않는다.
- 문서가 충돌하면 각 근거와 영향을 보고하고 임의로 우선순위를 정하지 않는다.
- 미결정 사항이 계약이나 완료 조건을 바꾸면 구현 이슈 본문에 숨기지 않는다. 결정·문서화 이슈를 먼저 만들거나 사용자에게 결정을 요청하고 구현 이슈를 차단한다.

## 사전 조사하기

1. `git status`, 현재 브랜치, `git remote -v`, 현재 커밋과 원격 포함 여부를 확인한다.
2. 관련 문서가 커밋되어 원격 GitHub에서 열리는지 확인한다. 커밋되지 않았거나 push되지 않은 문서를 근거로 초안은 만들 수 있지만 원격 이슈는 만들지 않는다.
3. 이슈 템플릿과 현재 문서·코드·테스트를 읽고 요청 범위를 정리한다.
4. `gh auth status`와 `gh repo view`로 대상 저장소를 확인하고, 저장소 이름을 하드코딩하지 말고 실제 `origin`을 기준으로 삼는다.
5. `gh issue list --state all`로 제목뿐 아니라 본문 속 요구사항 ID, API, 상태 전이와 완료 조건을 비교해 중복을 찾는다.
6. `gh label list --limit 200`으로 라벨의 정확한 철자와 대소문자를 확인한다.
7. 선택한 이슈 폼의 `projects` 값을 확인한다. 프로젝트 조회 권한이 없으면 인증 범위를 임의로 바꾸지 말고, 보드 추가 없이 생성할지 사용자에게 확인한다.

문서 근거 링크는 가능하면 원격에 존재하는 커밋 SHA의 영구 링크(permalink)를 사용한다. 작업 트리의 최신 내용과 링크의 내용이 다르면 생성 전에 그 차이를 보고한다.

## 이슈를 분해하기

먼저 작업의 성격을 구분한다.

- 정책·설계 결정: 구현 계약을 막는 오픈 이슈나 문서 충돌을 해소한다.
- 제품 기능: 사용자가 관찰할 수 있는 한 결과를 끝까지 구현한다.
- 공통 기반: 여러 기능이 실제로 공유하는 설정, DB 마이그레이션, 오류 계약, CI나 관측 기반만 둔다.
- 버그: 하나의 재현 가능한 실패와 기대 동작 복구를 다룬다.
- 문서·리팩터링·운영: 제품 동작 변경 여부가 분명한 독립 결과로 둔다.

다음 기준으로 크기를 정한다.

1. 한 이슈는 하나의 검증 가능한 결과와 하나의 PR로 검토 가능한 응집된 범위를 가진다.
2. 기능 이슈는 필요한 도메인 모델, DB 마이그레이션, 저장소, 서비스, API, 권한, 테스트와 문서 갱신을 포함하는 수직 슬라이스로 만든다.
3. Entity, Repository, Service, Controller처럼 계층별 이슈로 나누지 않는다.
4. 문서의 요구사항 ID는 추적 근거이지 이슈 개수나 제목을 강제하는 단위가 아니다. 여러 독립 결과가 섞인 요구사항은 나누고, 같은 불변식과 트랜잭션을 공유하는 작업은 묶는다.
5. 확정된 API 명세가 있으면 독립 API 또는 원자적인 거래·상태 전이 하나를 기본 단위로 삼는다. 같은 정합성을 한꺼번에 보장해야 하는 API를 억지로 분리하지 않는다.
6. 공통 기반은 둘 이상의 수직 슬라이스가 선행 작업으로 실제 공유할 때만 별도 이슈로 만든다.
7. 문서 순서나 요구사항 ID가 연속된다는 이유로 의존성을 만들지 않는다. 결정, 스키마, 인증 계약이나 상태 전이처럼 실제 blocker만 연결한다.
8. 장기적인 기술 결정이 필요한 작업은 관련 ADR을 연결한다. 결정이 미확정이면 구현 이슈보다 결정 이슈를 먼저 둔다.

전체 작업 분해를 요청받으면 `정책·설계 선행 작업 → 공유 기반 → 수직 기능 → 교차 검증·배포` 순서로 검토한다.
모든 항목을 반드시 만들지는 말고, 현재 코드와 기존 이슈를 제외한 실제 잔여 작업만 제안한다.

## 이슈 폼에서 본문 만들기

작업 이슈는 `.github/ISSUE_TEMPLATE/new_task.yaml`, 버그 이슈는 `.github/ISSUE_TEMPLATE/bug_report.yaml`을 실행 시점마다 직접 읽어 만든다. 이 스킬 안에 제목 접두사, 본문 필드, 필드 순서, 필수 여부나 기본 메타데이터를 별도 템플릿으로 복제하지 않는다.

1. 요청이 작업과 버그 중 어느 폼에 해당하는지 불명확하면 임의로 고르지 말고 사용자에게 확인한다.
2. 초안을 만들기 직전에 대상 브랜치의 YAML을 읽는다. 원격 `dev`에 생성할 때는 로컬 파일과 `origin/dev`를 비교하고, 다르면 차이를 보고한 뒤 실제 생성 대상 브랜치의 버전을 기준으로 삼는다.
3. 최상위 `title`, `type`, `labels`, `projects`, `assignees`를 이슈 메타데이터의 기준으로 사용한다. 값이 바뀌면 스킬 수정 없이 새 값을 따른다.
4. `body` 배열을 선언된 순서대로 순회한다. 응답을 받는 항목의 `id`는 내부 식별자로만 사용하고, 본문에는 GitHub 이슈 폼의 제출 형식처럼 `### {attributes.label}` 제목과 해당 값을 적는다. `markdown` 항목은 안내 내용으로 처리하며 응답 필드를 임의로 만들지 않는다.
5. `attributes.description`을 작성 지침으로, `placeholder`를 값의 형식 예시로 따른다. 스킬이 별도의 고정 필드명이나 본문 골격을 추가하지 않는다.
6. `validations.required: true`인 필드는 근거 있는 값을 모두 채운다. 필수 정보를 확보하지 못하면 값을 추측하거나 `확인 필요`로 생성하지 말고 사용자에게 부족한 정보를 요청한다.
7. `textarea`, `input`, `dropdown`, `checkboxes`, `upload`, `markdown` 등 각 항목의 `type`에 맞춰 값을 표현한다. 지원하지 못하는 유형이면 임의의 대체 필드로 바꾸지 말고 생성 방법을 사용자와 확인한다.
8. 체크박스 형식을 요구하는 필드가 있을 때만 `- [ ]` 목록을 사용한다. 완료 조건은 명령, 상태, 응답, DB 결과, 로그나 자동화 테스트로 검증 가능하게 작성한다.
9. 첨부 필드에는 실제로 제공된 첨부나 공개 가능한 링크만 사용한다. 로컬 절대 경로, 비밀이 포함된 로그와 존재하지 않는 첨부를 넣지 않는다. CLI로 첨부할 수 없으면 웹 폼 사용이나 사용자 첨부가 필요하다고 보고한다.
10. 본문 파일에는 `body`에서 만든 내용만 넣는다. 제목, 유형, 라벨, 프로젝트와 담당자는 미리보기에서 별도 메타데이터로 보여주고 실제 본문에는 반복하지 않는다.
11. 폼에 없는 최상위 섹션을 추가하지 않는다. 목적, 범위, 근거, 의존성 같은 상세 정보는 현재 폼의 설명과 형식이 허용하는 가장 적절한 기존 필드 안에 배치한다.
12. YAML을 읽거나 해석할 수 없으면 과거에 기억한 구조로 대체하지 말고 중단해 오류를 보고한다.

## 메타데이터 적용하기

- 제목은 선택한 YAML의 `title` 값을 접두사로 사용하고, 그 뒤에 검증 가능한 결과 또는 재현되는 실패를 간결하게 적는다.
- 유형, 기본 라벨, 프로젝트와 담당자는 YAML에 선언된 값을 그대로 적용한다.
- 추가 라벨은 사용자가 요청했거나 별도 저장소 규칙이 명시한 경우에만 검토한다. `gh label list`에 존재하는 라벨만 사용하고 새 라벨은 별도 승인 없이 만들지 않는다.
- 프로젝트 권한 부족 등으로 YAML의 메타데이터를 완전히 적용하지 못하면 성공으로 숨기지 말고 생성 전에 선택지를 보고한다.

## 초안을 검토받기

생성 전 다음을 한 번에 제시한다.

1. 제외한 기존·중복·완료 작업과 근거
2. 차단하는 문서 충돌과 미결정 사항
3. 생성 순서, 제목, 유형, 라벨, 프로젝트, 근거 ID와 선행 관계 표
4. 각 이슈의 전체 본문

`I-01` 같은 임시 식별자로 초안 의존성을 표시한다. 사용자가 승인하거나 수정한 뒤에만 생성한다. 승인 범위가 일부면 그 이슈만 생성한다.

## GitHub에 생성하기

1. 승인된 본문을 안전한 임시 파일에 각각 저장한다.
2. blocker와 기반 이슈부터 `gh issue create --body-file`로 생성한다. 제목 접두사와 `--type`, `--label`, `--assignee`는 선택한 YAML에서 가져오고, 필요한 경우 `--blocked-by`를 사용한다. YAML 값이 비어 있으면 해당 옵션을 임의로 채우지 않는다.
3. 생성된 URL을 사용해 `.github/ISSUE_TEMPLATE/*.yaml`의 `projects` 대상에 항목을 추가한다. 현재 GitHub CLI에서는 프로젝트 번호와 소유자를 확인한 뒤 `gh project item-add`를 사용할 수 있다.
4. 다음 이슈에는 방금 생성된 실제 번호를 GitHub의 blocked-by 관계에 반영한다. 의존성을 기록할 수 있는 필드가 현재 YAML에 있을 때만 해당 필드에도 번호를 적는다.
5. 생성 직후 `gh issue view`로 제목, 본문, 라벨, 유형과 의존 관계를 확인하고, 가능한 경우 프로젝트 항목도 검증한다.
6. 임시 본문 파일을 제거한다.

일부 생성이 실패하면 같은 명령을 바로 반복하지 않는다. 기존 이슈를 다시 조회해 실제 생성 여부를 확인하고, 생성된 번호·성공한 속성·누락된 속성·실패 원인을 보고한 뒤 재시도 승인을 받는다.

## 완료 보고하기

- 생성한 이슈를 번호, 제목, URL, 유형, 라벨과 의존 관계 순서로 보고한다.
- GitHub Project 추가 성공 여부를 따로 밝힌다.
- 중복·완료·범위 밖이라 생성하지 않은 항목과 보류된 정책 결정을 함께 적는다.
- 초안만 작성했다면 원격 변경이 없었다고 명시한다.
